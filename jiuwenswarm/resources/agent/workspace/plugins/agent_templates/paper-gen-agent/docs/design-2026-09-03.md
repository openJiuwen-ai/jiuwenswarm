# paper-gen-agent 设计说明（2026-09-03 v0.2，历史接口草图）

> **当前状态：历史设计记录，不是运行规范。** 当前四阶段 CLI、状态映射、REPLAN、token 账本和模块四发布规则以 [`skills/paper-gen/README.md`](../../../../skills/paper-gen/README.md)、[`skills/paper-gen/SKILL.md`](../../../../skills/paper-gen/SKILL.md)、Agent 根目录 `README.md` 与实际脚本为准。本文件保留用于解释早期 invoke-envelope 方案，不得据此假定旧写作子 Agent、旧状态值或旧输出文件仍是当前实现。

> 论文端到端生成 Agent 骨架。4 个子 Agent（调用 / 构思 / 实验 / 写作）+ 根 Agent 编排。
> **设计前提：构思/实验当前架构不完全一致，后续会统一；本骨架只约束接口契约，不耦合实现细节。**

---

## 1. 阶段划分（仅作参考）

CCF BDCI 2026 论文自动生成系统大致分 4 阶段，但**阶段边界会随子 Agent 演化而变**：

| 阶段 | 子 Agent | 当前后端 | 后续可能 |
|---|---|---|---|
| 1 | 构思 | `workspace/skills/conception` | 重构为 `conception-agent` 形态 |
| 2 | 规划 | `workspace/skills/planning`（via `plan-supervisor`） | 集成进 调用 子 Agent 内部 |
| 3 | 实验 | `workspace/plugins/agent_templates/experiment-agent` | 重构或合并 |
| 4 | 写作 | `workspace/skills/writing` | 替换为新 writing-agent |

> 骨架设计原则：**每个子 Agent 对外只暴露「输入契约 + 输出契约 + 一个 invoke 入口」**。
> 根 Agent 不感知子 Agent 内部结构；子 Agent 重构时只需保持 invoke 协议即可。

## 2. 子 Agent 接口契约（统一抽象）

所有 4 个子 Agent 共享同一个 JSON 协议（无论内部如何实现）：

```json
// 根 Agent → 子 Agent
{
  "run_id": "run_xxx",
  "stage_id": "conception | planning | experiment | writing",
  "run_dir": "/abs/path/run_dir",
  "input": {
    // 由 stage_id 决定 schema；见 §3
  },
  "previous_stage_outputs": {
    "conception": "/abs/path/stage1_conception/...",
    "planning": "..."
  },
  "iteration_context": {
    "rounds": 0,         // 本阶段已重试次数
    "max_rounds": 3,
    "last_feedback": null // 上次失败原因
  }
}

// 子 Agent → 根 Agent
{
  "status": "completed | replan | revise | aborted | failed",
  "output_dir": "/abs/path/run_dir/stage3_experiment",
  "summary": "一句话结论",
  "artifacts": {
    // 由 stage_id 决定 schema；见 §3
  },
  "next_action": {
    "type": "proceed | replan_to:<stage> | abort",
    "target_stage": "planning",     // replan_to 时填
    "reason": "experiment 报 compute 超限，回到 planning 调算力"
  }
}
```

**好处**：构思/实验后续重构时，只要 invoke 函数返回符合上述协议，根 Agent 一行不用改。

## 3. 各阶段输入/产物契约

### 3.1 conception（构思）

- **输入**：`ResearchRequest`（参见 `conception-schemas.md` §1.1）+ `Domain` + `ResourceConstraints` + `SearchConstraints` + `ResearchPreferences`
- **产物**：`stage1_conception/*.json`，至少含：
  - `research_question.json`
  - `hypotheses.json`
  - `gap_report.json`
  - `key_papers.json`
  - `research_frontier.json`
  - `status.json`（`complete` / `replan` / `failed`）

### 3.2 planning（规划，由 call-agent 内部调用 plan-supervisor 子进程）

- **输入**：conception 全部产物 + `ResourceConstraints`
- **产物**：参考 plan-supervisor 的 5 .json + 5 .md + `status.json`

### 3.3 experiment（实验）

- **输入**：`execution_config.json` + `experiment_plan.json` + `data_plan.json` + `method_design.json`
- **产物**：`experiment-module-output.json` + `artifact-manifest.json` + 原始/聚合数据 + 候选图表

### 3.4 writing（写作）

- **输入**：conception 产物 + planning 产物（method_design / experiment_plan）+ experiment 产物
- **产物**：`paper.pdf` + `latex_source.tex` + `writing_output.json`（含 `sections` / `review_history`）

## 5. 迭代逻辑（v0.2 简化）

```
                ┌────────────────────┐
                │  user_research_req │
                └─────────┬──────────┘
                          ▼
              ┌──────────────────────┐
              │ call-agent.dispatch  │  (根 Agent 持有)
              └─────────┬────────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   conception     experiment       writing
   (sub-agent)    (sub-agent)      (sub-agent)
        │               │               │
        └────┬──────────┘               │
             ▼                          │
        planning (via plan-supervisor)  │
             │                          │
             └──────────┬───────────────┘
                        ▼
                  paper.pdf
```

**核心变化**：去掉原设计中"阶段必须严格顺序"的硬约束。
- 根 Agent 接收 `next_action.type` 决定下一步
- `proceed` → 进入默认下一阶段
- `replan_to:<stage>` → 跳回指定阶段（任何阶段都可被 replan）
- `revise` → 当前阶段内重试（多用于 writing）
- `aborted` / `failed` → 终止

**好处**：构思/实验重构后，若某个阶段决定"自己要先跑一遍 mini-experiment 再交付"，只需让它返回 `replan_to: experiment` 即可，根 Agent 不变。

## 6. 子 Agent 职责（v0.2 极简）

| 子 Agent | 职责（v0.2 极简） | 实现状态 |
|---|---|---|
| `call-agent`（调用） | 调 invoke 协议、读 pipeline_state、决定 next_action、合并 REPLAN 反馈 | **骨架**：基本状态机 + invoke 入口，缺反思合并 |
| `conception-agent`（构思） | 透传到 conception skill（subprocess），把状态写回 run_dir | **stub**：1 个工具即可，协议对齐即可 |
| `experiment-agent`（实验） | 透传到 experiment-agent（subprocess），对接其 4 sub-agent 协议 | **stub**：1 个工具即可，协议对齐即可 |
| `writing-agent`（写作） | 调 invoke 协议、Reviewer/Reviser/Formatter 内循环、生成 PDF | **骨架**：含 reviewer/formatter 状态机，缺实际 LLM 逻辑 |

每个子 Agent = 1 个 persona + 1 个 invoke 工具（subprocess 或框架调用）。

**关键不耦合点**：
- 构思/实验若改成"agent_template 内嵌 4 个 sub-agent"，对外仍是 1 个 invoke 入口
- 根 Agent 不依赖任何 sub-agent 的内部 persona
- 后续统一时只需替换 invoke 工具的实现，persona/manifest 字段不变
