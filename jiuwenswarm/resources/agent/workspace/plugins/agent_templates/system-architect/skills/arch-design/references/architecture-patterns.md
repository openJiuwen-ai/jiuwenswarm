# 架构模式对比与选型指南

## 核心模式对比矩阵

| 维度 | 模块化单体 | 微服务 | 事件驱动 | CQRS |
|------|-----------|--------|---------|------|
| **团队规模** | 2-15 人 | 10+ 人，多团队 | 5+ 人，有事件流经验 | 任意，读写差异大时 |
| **部署复杂度** | 低（单进程） | 高（多服务+基础设施） | 中高（需消息中间件） | 中（读写分离） |
| **运维成本** | 低 | 高（监控/日志/链路追踪） | 中高 | 中 |
| **数据一致性** | 强（单库事务） | 最终一致（分布式事务难） | 最终一致 | 读写分离后需同步 |
| **独立扩展** | 不支持 | 支持（按服务扩展） | 部分支持（消费者独立扩展） | 支持（读/写独立扩展） |
| **技术异构** | 不支持 | 支持 | 支持 | 支持 |
| **故障隔离** | 弱（整体宕机） | 强（单服务故障隔离） | 强（消费者故障隔离） | 中 |
| **开发速度** | 快（无分布式开销） | 慢（服务间通信/契约） | 中 | 中 |
| **测试复杂度** | 低 | 高（契约测试+集成测试） | 中高 | 中高 |

## 何时使用

### 模块化单体

**适用场景：**
- 早期产品，领域边界尚未清晰
- 小团队，无法承担微服务运维成本
- 需要快速迭代验证业务模式
- 对部署简单性有强需求

**关键实践：**
- 按业务模块组织代码（feature-first），非按技术层
- 模块间通过内部接口通信，禁止跨模块直接访问数据库
- 保持模块边界清晰，为未来拆分预留可能
- 共享代码放 `shared/` 目录，明确公共边界

**避免场景：**
- 需要独立扩展特定模块
- 多团队并行开发同一代码库
- 技术栈异构需求

### 微服务

**适用场景：**
- 领域边界清晰（通过事件风暴确认）
- 多团队并行开发，需要自治
- 不同服务有不同的扩展/可用性要求
- 技术栈异构需求明确

**关键实践：**
- 每个服务拥有独立数据库（Database per service）
- 服务间通过 API 或事件通信，禁止共享数据库
- 实现 API 网关统一入口
- 分布式链路追踪（OpenTelemetry）
- 契约测试（Pact）保障服务间接口稳定性
- 实现熔断降级（Circuit Breaker）

**避免场景：**
- 小团队（< 10 人）
- 早期产品，领域边界不清晰
- 强一致性要求高且跨服务
- 运维能力不足

### 事件驱动

**适用场景：**
- 松耦合的异步工作流
- 事件溯源（Event Sourcing）需求
- 多系统需要响应同一业务事件
- 削峰填谷（消息队列缓冲）

**关键实践：**
- 明确事件命名规范（过去时：OrderCreated, PaymentCompleted）
- 事件版本化（schema registry）
- 幂等消费者（同一事件处理多次结果一致）
- 死信队列（DLQ）处理失败事件
- 事件存储（Event Store）用于回放和审计

**避免场景：**
- 强一致性要求高
- 事件流简单，引入消息中间件不划算
- 团队缺乏事件驱动经验
- 调试可观测性要求高（事件链路追踪复杂）

### CQRS

**适用场景：**
- 读写负载严重不对称
- 复杂查询需求（多维度聚合、全文搜索）
- 写入需要严格验证，读取需要高性能
- 事件溯源的天然伴生模式

**关键实践：**
- 写模型（Command）面向业务逻辑和事务一致性
- 读模型（Query）面向查询性能，可使用物化视图/搜索引擎
- 读写同步通过事件或变更数据捕获（CDC）
- 读模型最终一致，需告知用户延迟可能

**避免场景：**
- 简单 CRUD 领域
- 读写负载均衡
- 团队无法接受最终一致性

### 分层架构（Layered）

**适用场景：**
- 清晰分离表现层、应用层、领域层、基础设施层即可满足
- 团队规模小，领域行为简单
- 不需要复杂的依赖反转

**关键实践：**
- 依赖方向单向：上层依赖下层，不反向
- 每层有明确职责，不变成透传层
- 基础设施层（DB/消息/外部 API）在最底层

**避免场景：**
- 层变成无意义的透传仪式（每层只是调用下一层）
- 领域逻辑分散在多层中，无法集中管理

### 六边形架构（Hexagonal / Ports & Adapters）

**适用场景：**
- 核心用例必须与 UI、数据库、消息队列、外部 API 隔离
- 需要高可测试性（核心逻辑不依赖基础设施）
- 多种适配器（如同时支持 REST 和 gRPC 入口）

**关键实践：**
- 核心领域定义 Port（接口），基础设施实现 Adapter
- 依赖方向始终指向核心：Adapter → Port → Core
- 测试时用 Mock Adapter 替换真实基础设施

**避免场景：**
- 简单 CRUD 应用，适配器间接层无价值
- 团队不熟悉 Port/Adapter 抽象

### 洋葱架构（Onion）

**适用场景：**
- 需要强依赖规则，领域模型在中心
- 领域层不依赖任何外部框架/基础设施
- 与 DDD 配合使用

**关键实践：**
- 依赖方向始终向内：外层依赖内层
- 最内层是领域模型（实体、值对象、领域服务）
- 外层是应用服务、基础设施
- 内层不导入框架、ORM、消息、HTTP

**避免场景：**
- 领域模型贫血（只有 getter/setter）
- 团队不会强制执行内向依赖规则

## 迁移策略

### 单体 → 微服务

1. ** strangler fig 模式**：逐步用新服务替换单体中的模块，旧模块通过 API 网关代理
2. **数据库优先拆分**：先拆数据库 schema，再拆服务
3. **先提取独立能力**：从耦合度最低的模块开始拆分
4. **保持双向兼容**：拆分期间新旧系统并行运行

### 微服务 → 模块化单体

当微服务过度拆分时（"分布式单体"反模式）：
1. 合并高耦合的服务（频繁同步调用）
2. 共享数据库减少分布式事务
3. 保留独立部署能力但简化基础设施

## 常见反模式

| 反模式 | 症状 | 修复方向 |
|--------|------|---------|
| 分布式单体 | 微服务间强同步调用，改一处要改多处 | 合并高耦合服务或改异步通信 |
| 共享数据库微服务 | 多服务直连同一数据库 | 每服务独立数据库，通过 API 通信 |
| 事件驱动过度设计 | 简单 CRUD 也走事件流 | 评估同步调用是否更简单 |
| 过早微服务化 | 产品早期就拆微服务 | 回退到模块化单体 |
| 瀑布式 ADR | ADR 写完就束之高阁 | ADR 活文档，定期回顾和标记废弃 |

## 领域驱动设计指南

### 何时用 DDD，何时不用

**用 DDD 当：**
- 业务规则、领域语言、不变量和组织边界比技术管道更复杂
- 多个限界上下文，需要明确边界和上下文映射
- 领域专家能持续参与建模

**不用 DDD 当：**
- 系统主要是数据录入、报表或简单 CRUD，领域行为少
- 用更简单的分层设计更容易维护
- 团队没有领域专家参与

### DDD 核心概念职责

| 概念 | 架构职责 |
|------|---------|
| 限界上下文（Bounded Context） | 定义模型、语言和规则在内部一致的范围 |
| 聚合（Aggregate） | 保护不变量和事务一致性边界 |
| 实体/值对象 | 建模身份、生命周期和不可变领域概念 |
| 领域服务（Domain Service） | 表达不属于单一实体的领域行为 |
| 领域事件（Domain Event） | 捕获其他系统部分可能响应的业务事实 |
| 仓储（Repository） | 提供集合式访问聚合，不泄露持久化细节 |
| 防腐层（ACL） | 集成外部或遗留系统时翻译模型 |

### 依赖与边界规则

- 领域策略不导入框架、ORM、消息、HTTP 或数据库相关
- 应用/用例服务协调工作流、事务、授权决策和 Port 调用
- 适配器翻译外部机制和应用 Port 之间的数据
- 基础设施实现持久化、消息、文件、网络和供应商特定细节
- 跨上下文通信通过显式契约、事件、API 或防腐层
- Controller 直接调用 Repository 绕过用例是架构坏味道
