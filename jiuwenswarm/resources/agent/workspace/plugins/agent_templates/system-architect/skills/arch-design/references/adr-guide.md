# ADR 架构决策记录指南

## 什么是 ADR

架构决策记录（Architecture Decision Record）是捕获"为什么这么选"的轻量文档。ADR 记录上下文、决策和后果，不是设计文档——它回答 WHY，不是 WHAT。

## ADR 模板

```markdown
# ADR-{编号}: {决策标题}

## 状态
Proposed | Accepted | Deprecated | Superseded by ADR-{编号}

## 上下文
描述促使这个决策的问题、约束和背景。
- 业务需求是什么？
- 团队/技术约束有哪些？
- 当前架构的痛点是什么？

## 决策
描述我们选择做什么，以及为什么。
- 选择了什么方案？
- 考虑过哪些备选方案？
- 关键取舍理由是什么？

## 后果
描述这个决策带来的影响。
- 什么变得更容易了？
- 什么变得更难了？
- 需要后续跟进什么？
```

## 编号规范

- 顺序编号：ADR-001, ADR-002, ADR-003...
- 编号不回收，废弃的 ADR 保留编号
- 被取代时标记 `Superseded by ADR-{新编号}`，新 ADR 标注 `Supersedes ADR-{旧编号}`

## 状态流转

```
Proposed → Accepted → (Deprecated | Superseded)
```

- **Proposed**：已提出，待评审
- **Accepted**：已采纳，正在执行或已执行
- **Deprecated**：不再推荐，但历史参考
- **Superseded**：被新 ADR 取代

## 示例

### ADR-001: 采用模块化单体作为初始架构

**状态**：Accepted

**上下文**：
团队当前 6 人，产品处于 MVP 阶段，领域边界尚未通过事件风暴确认。运维能力有限，无法承担微服务的基础设施成本（服务发现、配置中心、链路追踪、API 网关）。需要快速迭代验证业务模式。

**决策**：
采用模块化单体架构，按业务模块组织代码（feature-first），模块间通过内部接口通信。预留模块边界，为未来拆分微服务做准备。

考虑过的备选方案：
1. 微服务 — 运维成本过高，领域边界不清晰
2. 纯单体（layer-first）— 模块边界模糊，未来拆分困难

**后果**：
- 更容易：开发部署简单，事务一致性天然保障，调试方便
- 更困难：无法独立扩展模块，技术栈锁定单一语言
- 后续跟进：当团队超过 15 人或某模块需要独立扩展时，启动拆分评估

### ADR-002: 订单服务引入 CQRS

**状态**：Accepted

**上下文**：
订单查询占整体请求量 95%，查询维度复杂（多状态筛选、时间范围、用户维度聚合）。写入需要严格的事务一致性。当前读写共用同一数据模型，查询性能瓶颈严重。

**决策**：
引入 CQRS，写模型保持关系型数据库（PostgreSQL），读模型使用 Elasticsearch 物化视图。通过 CDC（Debezium）同步数据。

**后果**：
- 更容易：查询性能大幅提升，读写独立扩展
- 更困难：读写最终一致（延迟约 200ms-1s），运维增加 Elasticsearch 和 Debezium
- 后续跟进：监控同步延迟，对延迟敏感场景提供降级直读写库方案

## 最佳实践

1. **一决策一 ADR**：不要在一个 ADR 里塞多个决策
2. **写上下文而非设计**：ADR 记录 WHY，设计文档记录 WHAT 和 HOW
3. **及时写**：决策做出时立即写，不要事后补
4. **保持简短**：一页纸原则，避免长篇大论
5. **链接关联 ADR**：决策有依赖关系时互相引用
6. **定期回顾**：季度回顾 Accepted 状态的 ADR，标记不再适用的为 Deprecated
