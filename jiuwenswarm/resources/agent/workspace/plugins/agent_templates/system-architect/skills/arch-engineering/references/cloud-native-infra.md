# 云原生基础设施架构

## 核心原则

基础设施是架构的底座。云原生不是"把服务放进容器"，而是围绕弹性、可观测、自动化重新设计架构。

## Kubernetes 架构决策

### 命名空间划分策略

| 策略 | 划分方式 | 适用场景 |
|------|---------|---------|
| 按环境 | dev / staging / prod | 小团队，环境隔离优先 |
| 按团队 | team-a / team-b / team-c | 多团队自治，Conway's Law 对齐 |
| 按领域 | orders / payments / users | 微服务按领域分组 |
| 混合 | env-domain（prod-orders） | 大规模，兼顾环境和领域 |

**关键约束：**
- 命名空间是软隔离，不是硬隔离（共享集群资源）
- 生产环境建议独立集群或独立命名空间 + ResourceQuota
- 跨命名空间通信通过 NetworkPolicy 控制

### 资源管理

```yaml
# 资源请求与限制的最佳实践
resources:
  requests:
    cpu: "500m"      # 调度依据，保证最小资源
    memory: "512Mi"
  limits:
    cpu: "1000m"     # 上限，防止资源抢占
    memory: "1Gi"    # 内存 limit = request（避免 OOM Kill）
```

**规则：**
- CPU request = 实际平均使用量的 1.5 倍
- Memory limit = request（避免内存超卖导致 OOM）
- 使用 HPA 基于 CPU/自定义指标自动扩展
- 设置 PDB（PodDisruptionBudget）保障最小可用副本

### 服务网格选型

| 方案 | 适用场景 | 复杂度 | 关键能力 |
|------|---------|--------|---------|
| 无服务网格 | < 10 服务，简单通信 | 低 | K8s Service + Ingress |
| Linkerd | 中小规模，渐进式引入 | 中 | mTLS、可观测性、轻量 |
| Istio | 大规模，需要精细流量控制 | 高 | 流量管理、策略执行、遥测 |
| Cilium(eBPF) | 性能优先，网络层安全 | 中 | eBPF 级网络策略、可观测 |

**决策规则：**
- 服务 < 10 且无 mTLS 需求 → 不引入服务网格
- 需要 mTLS 但无复杂流量控制 → Linkerd
- 需要金丝雀发布/流量镜像/精细策略 → Istio
- 对网络性能敏感 → Cilium

## 多区域/多可用区部署

### 部署模式

| 模式 | 架构 | 数据一致性 | 适用场景 |
|------|------|------------|---------|
| 单区域多 AZ | 同区域多可用区部署 | 强一致（同步复制） | 中小规模，低延迟 |
| 多区域主从 | 主区域写，从区域读 | 最终一致（异步复制） | 读多写少，容灾 |
| 多区域双活 | 双区域均可读写 | 最终一致 + 冲突解决 | 高可用，写分布均匀 |
| 全局边缘 | 边缘节点缓存+区域中心 | 边缘缓存最终一致 | 全球用户，低延迟 |

### 多活架构关键决策

```
1. 数据分区策略
   ├── 按用户 ID 分片（用户数据固定到某区域）
   ├── 按地理就近路由（延迟优先）
   └── 冲突解决策略（LWW / CRDT / 业务层合并）

2. 流量路由
   ├── DNS 层（GeoDNS / 延迟路由）
   ├── API 网关层（按 Header 路由）
   └── 客户端层（客户端选择最近节点）

3. 故障切换
   ├── 健康检查 + 自动切换
   ├── DNS TTL 短（60s）便于快速切换
   └── 切换演练（每季度一次）
```

## IaC（基础设施即代码）

### IaC 策略

| 工具 | 适用场景 | 关键特点 |
|------|---------|---------|
| Terraform | 多云/混合云 | Provider 生态丰富，状态管理 |
| Pulumi | 团队熟悉编程语言 | 用 TS/Python/Go 写基础设施 |
| Helm | K8s 应用部署 | Chart 模板化，版本管理 |
| Kustomize | K8s 环境差异化 | 无模板，Overlay 叠加 |

### 模块化原则

```
✅ 按环境分离状态文件（dev/staging/prod 独立）
✅ 按职责模块化（网络层/计算层/数据层分离）
✅ 变量化所有环境差异（不硬编码）
✅ IaC 代码与应用代码同等质量（Review/CI/版本控制）

❌ 手动修改基础设施（绕过 IaC）
❌ 状态文件不入版本控制或远程后端
❌ 一个模块管所有资源（巨型模块）
```

### 环境管理

```
基础设施代码仓库结构：
infra/
├── modules/           # 可复用模块
│   ├── vpc/
│   ├── eks-cluster/
│   ├── rds/
│   └── monitoring/
├── environments/      # 环境配置
│   ├── dev/           # 引用 modules + 环境变量
│   ├── staging/
│   └── prod/
└── pipelines/         # CI/CD 流水线
```

## 云成本优化架构

### 成本优化策略

| 层面 | 策略 | 预期节省 |
|------|------|---------|
| 计算 | Spot 实例（无状态服务）+ 按需（有状态） | 60-70% |
| 计算 | HPA + VPA 自动伸缩 | 30-50% |
| 存储 | 冷热分层（热 SSD / 冷对象存储） | 40-60% |
| 网络 | CDN 缓存 + 跨可用区流量优化 | 20-40% |
| 数据库 | 读写分离 + Serverless（低负载） | 30-50% |

### 成本架构评审清单

- [ ] 资源 request/limit 合理（不过度分配）
- [ ] 非生产环境自动缩容/关停
- [ ] Spot 实例用于可中断工作负载
- [ ] 存储生命周期策略就绪（冷数据自动迁移）
- [ ] 成本告警和预算监控就位
- [ ] 定期审查闲置资源（未挂载磁盘/未使用 IP）
