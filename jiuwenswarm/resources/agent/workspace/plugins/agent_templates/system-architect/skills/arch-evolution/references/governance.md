# 团队协作与架构治理

## 核心原则

架构不是一个人的决策，而是一套让团队持续做出好决策的治理体系。最好的架构是团队真正能理解和维护的架构。

## Conway's Law 与团队拓扑

### Conway's Law

"设计系统的组织，其架构会不可避免地映射组织的沟通结构。"

**实践含义：**
- 如果 4 个团队维护一个单体，模块边界会模糊
- 如果按微服务拆分但团队仍紧密耦合，会得到"分布式单体"
- 架构决策必须与团队结构对齐，或主动调整团队结构来驱动架构演进

### Team Topologies（团队拓扑模型）

| 团队类型 | 职责 | 交互模式 |
|---------|------|---------|
| **流式团队**（Stream-aligned） | 面向业务流，端到端交付 | 与其他团队 X-as-a-Service 交互 |
| **平台团队**（Platform） | 提供内部平台，减少认知负荷 | 以产品方式服务流式团队 |
| **使能团队**（Enabling） | 帮助流式团队获得新能力 | 短期深度协作后退出 |
| **复杂子团队**（Complicated-subsystem） | 深度技术领域 | 与流式团队 X-as-a-Service |

**交互模式：**
- **X-as-a-Service**：通过 API/自助平台交付，最低协作成本
- **协作**（Collaboration）：短期紧密协作，探索期使用
- **促进**（Facilitating）：引导式帮助，使能团队模式

### 团队边界与架构边界对齐

```
架构决策前先回答：
1. 有几个团队？各自职责是什么？
2. 团队间的依赖方向是什么？
3. 哪些团队需要自治（独立部署/发布）？
4. 认知负荷是否合理（一个团队能理解其负责的全部模块）？

如果团队边界与架构边界不对齐：
├── 调整团队边界（重组团队）→ 适合早期
└── 调整架构边界（重新拆分模块）→ 适合已有架构
```

## 架构治理流程

### ARB（Architecture Review Board）评审流程

```
1. 提案提交
   ├── 发起人填写架构提案文档（含 ADR 草稿）
   ├── 提交到 ARB 看板（提前 1 周以上）
   └── 附带：架构图、ADR、风险评估、替代方案

2. 预审（ARB 主席 + 1-2 名委员）
   ├── 检查文档完整性
   ├── 识别需要深入讨论的点
   └── 不完整则退回补充

3. 评审会议（30-60 分钟）
   ├── 发起人陈述（10 分钟）
   ├── 委员提问与讨论（20-40 分钟）
   └── 结论：通过 / 有条件通过 / 需修改 / 否决

4. 决议记录
   ├── 更新 ADR 状态
   ├── 记录评审意见和条件
   └── 通知相关团队

5. 执行跟踪
   ├── 关键里程碑检查点
   ├── 偏离方案时重新评审
   └── 完成后回顾（实际 vs 预期）
```

### ARB 委员构成

| 角色 | 人数 | 职责 |
|------|------|------|
| ARB 主席 | 1 | 议程管理、预审、决议 |
| 首席架构师 | 1 | 技术深度评审 |
| 资深后端工程师 | 1-2 | 可行性评估 |
| 平台/SRE 代表 | 1 | 运维和可观测性评估 |
| 安全代表（按需） | 0-1 | 安全合规评估 |

### 评审标准

提案必须回答：
1. **业务价值**：解决什么问题？不做的代价是什么？
2. **替代方案**：考虑过哪些方案？为什么选这个？
3. **质量属性**：对可扩展性/可用性/可维护性的影响？
4. **风险**：主要风险和缓解措施？
5. **依赖**：依赖哪些团队/系统/基础设施？
6. **回退方案**：如果失败，如何回退？
7. **演进路径**：后续如何演进？是否可逆？

## ADR 生命周期管理

```
Proposed → Accepted → ┌─ Deprecated（不再推荐）
                      └─ Superseded（被新 ADR 取代）

管理规则：
- ADR 编号不回收
- 废弃/取代时更新状态并链接新 ADR
- 季度回顾：检查 Accepted ADR 是否仍然适用
- ADR 存储在版本控制（与代码同仓库或独立文档仓库）
- 新成员 onboarding 时阅读 ADR 理解历史决策
```

## 技术雷达管理

### 技术雷达四象限

| 象限 | 含义 | 行动 |
|------|------|------|
| **Adopt**（采纳） | 已验证，推荐生产使用 | 新项目默认选择 |
| **Trial**（试验） | 有潜力，需验证 | 试点项目使用 |
| **Assess**（评估） | 值得探索 | 技术调研/Spike |
| **Hold**（暂缓） | 不推荐或已过时 | 新项目避免 |

### 技术雷达管理流程

```
1. 技术雷达每季度更新一次
2. 任何人可提交技术提案（附评估理由）
3. ARB 评审并决定象限归属
4. 发布技术雷达到团队 Wiki
5. 新项目技术选型参考雷达
6. 持续监控各技术实际使用效果
```

### 技术选型评估维度

| 维度 | 评估问题 |
|------|---------|
| 成熟度 | 版本稳定性？社区活跃度？生产案例？ |
| 团队匹配 | 团队是否有经验？学习成本？ |
| 生态 | 工具链/插件/文档是否完善？ |
| 运维 | 监控/告警/部署是否成熟？ |
| 许可证 | 开源协议是否合规？ |
| 退出成本 | 如果要替换，迁移成本多大？ |

## 架构原则制定与传播

### 架构原则示例

```
1. 领域优先 — 先理解业务问题再选技术
2. 可逆性优先 — 优先选择容易更改的决策
3. 最小复杂度 — 每个抽象层必须证明其合理性
4. 数据库独立 — 每服务拥有独立数据库
5. 契约先行 — API 变更先更新 OpenAPI Spec
6. 可观测内建 — 结构化日志 + 指标 + 链路追踪
7. 安全默认 — 最小权限 + 纵深防御
8. 自动化优先 — IaC + CI/CD + 自动化测试
```

### 传播策略

- 架构原则写入团队 Wiki 首页
- 新成员 onboarding 必读
- 代码审查时引用原则（"这违反了原则 3"）
- ADR 中标注遵循/偏离的原则
- 季度回顾原则适用性，按需更新
- 架构决策与原则冲突时，ADR 必须说明理由
