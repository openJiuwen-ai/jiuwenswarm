# 性能工程与容量规划

## 核心原则

性能不是事后优化，而是架构设计的一等公民。先建模预测，再压测验证，最后持续监控。

## 性能建模基础

### Little's Law（利特尔法则）

```
L = λ × W

L = 系统中平均并发请求数
λ = 请求到达率（请求/秒）
W = 平均响应时间（秒）
```

**用途**：估算系统所需并发容量。

示例：系统每秒接收 1000 请求，平均响应时间 50ms，则系统内平均有 1000 × 0.05 = 50 个并发请求在处理。数据库连接池至少需 50。

### 排队论基础

- **M/M/1**：单服务台，到达率 λ，服务率 μ，利用率 ρ = λ/μ
  - 当 ρ → 1 时，等待时间趋于无穷
  - 实际目标：ρ < 0.7（留 30% 余量）
- **M/M/c**：多服务台（c 个），适用于连接池/线程池容量评估

## 容量评估

### 容量评估公式

```
所需实例数 = (目标 QPS × 单请求平均耗时) / (单实例并发能力 × 目标利用率)

示例：
- 目标 QPS: 10,000
- 单请求平均耗时: 100ms
- 单实例并发能力: 500
- 目标利用率: 70%

所需实例数 = (10000 × 0.1) / (500 × 0.7) = 1000 / 350 ≈ 3 → 取 4（冗余）
```

### 容量评估清单

| 维度 | 评估项 | 公式/方法 |
|------|--------|----------|
| 计算 | CPU 核数需求 | QPS × 单请求 CPU 时间 / 单核频率 |
| 内存 | 堆内存 + 缓存 | 并发数 × 单请求内存 + 缓存大小 |
| 网络 | 带宽需求 | QPS × 平均响应体大小 × 8（bit） |
| 存储 | 磁盘 IOPS | 写 QPS × 写放大系数 |
| 数据库 | 连接池 | Little's Law: λ × W |

## 瓶颈定位方法论

### USE 方法（资源层面）

```
For each resource:
  U = Utilization（利用率）
  S = Saturation（饱和度）
  E = Errors（错误）

资源类型：CPU、内存、磁盘 I/O、网络、数据库连接
```

| 指标 | 健康范围 | 告警阈值 |
|------|---------|---------|
| CPU 利用率 | < 70% | > 85% 持续 5 分钟 |
| 内存利用率 | < 80% | > 90% |
| 磁盘 IOPS | < 峰值 70% | > 85% |
| 网络带宽 | < 70% | > 85% |
| DB 连接池 | < 70% | > 85% |

### RED 指标（服务层面）

```
R = Rate（请求速率，QPS）
E = Errors（错误率）
D = Duration（延迟分布：P50/P95/P99）
```

| 指标 | 监控方式 | 告警条件 |
|------|---------|---------|
| Rate | Counter（Prometheus） | 突增/突降 > 50% |
| Errors | Counter + 总请求比 | 错误率 > 1% |
| Duration P99 | Histogram | P99 > SLO 阈值 |

### 瓶颈定位决策树

```
响应时间升高？
├── CPU 利用率高？
│   ├── 是 → CPU 瓶颈：优化计算/加实例/异步化
│   └── 否 → 检查 GC 频率
│       ├── GC 频繁 → 内存瓶颈：调优 GC/减少对象创建
│       └── GC 正常 → 检查 I/O 等待
├── I/O 等待高？
│   ├── 磁盘 IOPS 饱和 → 存储瓶颈：SSD/缓存/读写分离
│   ├── 网络带宽饱和 → 网络瓶颈：压缩/CDN/加带宽
│   └── DB 连接池饱和 → 连接瓶颈：加池/优化慢查询
└── 资源都正常？
    └── 检查锁竞争/串行化瓶颈 → 架构层面优化
```

## SLO/SLA 定义

### SLO 分级模板

| 指标 | SLO 目标 | 错误预算 | 监控方式 |
|------|---------|---------|---------|
| 可用性 | 99.9% | 43.2 分钟/月 | 成功请求率 |
| 延迟 P99 | < 200ms | 超出次数 < 总量 0.1% | Histogram |
| 延迟 P95 | < 100ms | — | Histogram |
| 错误率 | < 0.1% | — | Counter |

### 错误预算管理

```
月度错误预算 = 总分钟数 × (1 - SLO)
99.9% 可用性 → 43.2 分钟/月

预算消耗策略：
- 预算 < 50% 消耗 → 正常发布
- 预算 50%-80% 消耗 → 仅紧急修复发布
- 预算 > 80% 消耗 → 冻结非紧急发布，优先稳定性
- 预算耗尽 → 冻结所有发布，专项稳定性改进
```

## 压测策略

### 压测类型

| 类型 | 目的 | 工具 | 负载模式 |
|------|------|------|---------|
| 基准测试 | 单接口性能基线 | wrk/vegeta | 固定 QPS |
| 负载测试 | 找到系统拐点 | k6/Locust | 阶梯递增 |
| 压力测试 | 找到崩溃点 | k6/Locust | 持续加压 |
| 浸泡测试 | 内存泄漏/资源耗尽 | k6 | 固定负载 24h+ |
| 混沌测试 | 故障恢复能力 | Chaos Mesh | 注入故障 |

### 压测流程

1. **定义场景**：基于真实流量分布（P50/P95/P99），不是均匀负载
2. **准备环境**：压测环境与生产同构（或按比例缩小）
3. **基线测量**：空载状态下的系统指标
4. **阶梯加压**：逐步增加负载，记录拐点
5. **瓶颈定位**：USE + RED 方法定位瓶颈资源
6. **容量结论**：输出最大 QPS、拐点 QPS、推荐工作 QPS（拐点的 70%）
