# 现状系统评估指南

## 代码阅读启发式

### 快速定位入口

```
1. 找入口文件：main/app/index/server 启动点
2. 找路由定义：REST 路由 / gRPC service / 事件处理器
3. 找配置加载：环境变量 / 配置文件 / secrets
4. 找数据库连接：ORM 初始化 / 连接池创建
5. 找中间件链：认证 / 日志 / 限流 / CORS
```

### 模块职责识别

| 信号 | 推断 |
|------|------|
| 文件名含 controller/handler | HTTP 入口层 |
| 文件名含 service/manager | 业务逻辑层 |
| 文件名含 repository/dao/model | 数据访问层 |
| 文件名含 dto/vo/entity | 数据传输对象 |
| 文件名含 config/settings | 配置管理 |
| 一个文件 > 500 行 | 可能是上帝类 |
| 一个类 > 20 个 public 方法 | 职责过多 |
| import 跨越多个层级 | 可能存在跨层引用 |

### 代码坏味道速查

| 坏味道 | 代码信号 | 架构影响 |
|--------|---------|---------|
| 上帝类 | 单文件 > 1000 行，> 30 个方法 | 高耦合，改一处影响全局 |
| 散弹手术 | 一个改动涉及 > 5 个文件 | 模块边界不清 |
| 平行继承 | 多个类有相同方法签名但无共享接口 | 缺少抽象 |
| 数据泥团 | 多处出现相同的字段组合 | 缺少值对象建模 |
| 基本类型偏执 | 用 String/Int 表示领域概念 | 领域建模缺失 |
| 依赖注入硬编码 | new ConcreteClass() 而非注入 | 测试困难，耦合高 |

## 依赖映射技术

### 静态依赖分析

```bash
# TypeScript/JavaScript
npx madge --circular --extensions ts src/          # 检测循环依赖
npx dependency-cruiser src/                         # 依赖规则检查

# Python
pip install pydeps && pydeps --max-bacon=2 src/     # 生成依赖图
pip install pyflakes && pyflakes src/               # 未使用 import

# Java
mvn dependency:analyze                              # 依赖分析
# 用 JD-Core + jdepend 分析包依赖

# Go
go mod graph                                         # 模块依赖图
```

### 依赖图分析维度

| 维度 | 分析方法 | 健康信号 | 风险信号 |
|------|---------|---------|---------|
| 依赖方向 | 检查是否单向 | 外层→内层 | 循环依赖 |
| 依赖扇入 | 被多少模块依赖 | 核心领域扇入高 | 工具类扇入过高（上帝模块） |
| 依赖扇出 | 依赖多少模块 | < 5 | > 10（过度耦合） |
| 跨层引用 | 是否违反分层规则 | 无 | Controller→Repository 直连 |
| 共享依赖 | 多个模块依赖同一模块 | 共享内核明确 | 共享数据库 |

### 依赖热点定位

```
1. 计算每个模块的扇入（被依赖次数）
2. 扇入 Top 5 的模块 = 耦合热点
3. 检查热点模块的变更频率 → 变更频率高 + 扇入高 = 最高风险
4. 检查热点模块的测试覆盖率 → 覆盖率低 + 扇入高 = 急需补测试
```

## As-Is C4 画法

### 从代码反推 Context 图

```
1. 搜索外部调用：HTTP client / gRPC client / SDK 调用
2. 识别外部系统：数据库连接串、消息队列地址、第三方 API URL
3. 识别用户类型：从认证中间件提取角色
4. 画出系统边界和外部依赖
```

### 从代码反推 Container 图

```
1. 搜索部署入口：Dockerfile / docker-compose / k8s manifest
2. 识别可独立部署的单元：每个 Dockerfile = 一个 Container
3. 识别数据存储：数据库连接 / Redis / Elasticsearch
4. 标注通信协议：REST / gRPC / 消息队列
5. 标注技术栈：从 package.json / requirements.txt / go.mod
```

### 从代码反推 Component 图

```
1. 对每个 Container，分析其内部模块结构
2. 按 feature-first 或 layer-first 识别组件
3. 标注组件间依赖方向
4. 标注共享代码位置（shared/ common/）
5. 标注已知坏味道（红色标注）
```

## 架构坏味道目录

### 结构型坏味道

| 坏味道 | 症状 | 影响 | 修复方向 |
|--------|------|------|---------|
| 分布式单体 | 微服务间强同步调用 | 改一处要改多处 | 合并或改异步 |
| 共享数据库 | 多服务直连同一 DB | 数据耦合，无法独立变更 | 拆库或 API 隔离 |
| 上帝服务 | 一个服务承担过多职责 | 无法独立扩展 | 按领域拆分 |
| 循环依赖 | A→B→A | 无法独立部署 | 引入事件或接口反转 |
| 跨层引用 | Controller 直连 DB | 分层失效 | 强制走 Service 层 |

### 数据型坏味道

| 坏味道 | 症状 | 影响 | 修复方向 |
|--------|------|------|---------|
| 共享可变状态 | 多服务读写同一表 | 数据竞争 | 单写者 + 事件通知 |
| 缺少事务边界 | 跨服务操作无补偿 | 数据不一致 | Saga 模式 |
| N+1 查询 | 循环内查 DB | 性能瓶颈 | JOIN 或批量加载 |
| 无分页 | 全量查询 | 内存溢出 | 强制分页 |

### 部署型坏味道

| 坏味道 | 症状 | 影响 | 修复方向 |
|--------|------|------|---------|
| 单实例部署 | 无水平扩展 | 单点故障 | 多实例 + 负载均衡 |
| 手动部署 | 无 CI/CD | 环境不一致 | IaC + 自动化 |
| 配置硬编码 | 密钥/URL 在代码中 | 安全风险 | 环境变量 + Secrets |
| 无健康检查 | 无 /health 端点 | 故障不可见 | liveness + readiness |

## 系统健康度评估

### 评分标准

| 属性 | 1 分（严重） | 3 分（及格） | 5 分（优秀） |
|------|------------|------------|------------|
| 可扩展性 | 单实例，无法扩展 | 可垂直扩展 | 无状态，水平扩展 |
| 高可用性 | 单点，无备份 | 有备份，无演练 | 多活，自动故障切换 |
| 可维护性 | 循环依赖，无测试 | 模块边界基本清晰 | 清晰边界，覆盖率 > 80% |
| 可观测性 | 无日志/监控 | 有日志，无链路 | 结构化日志+指标+链路+告警 |
| 安全性 | 无认证，明文存储 | 有认证，无威胁建模 | 零信任+威胁建模+审计 |
| 成本 | 资源闲置 > 50% | 有基本成本监控 | FinOps+成本优化 |
