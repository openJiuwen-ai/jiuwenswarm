# 技术选型评估框架

## 评估维度

每个技术选型决策须从以下 6 个维度评估，输出加权评分矩阵。

| 维度 | 权重 | 评估问题 | 评分标准(1-5) |
|------|------|---------|-------------|
| 成熟度 | 20% | 版本稳定性？社区活跃度？生产案例？ | 5=主流稳定，1=实验性 |
| 团队匹配 | 20% | 团队有经验？学习成本？招聘难度？ | 5=已有专家，1=全新领域 |
| 生态 | 15% | 工具链/插件/文档完善？社区支持？ | 5=生态丰富，1=孤岛 |
| 运维 | 15% | 监控/告警/部署成熟？运维复杂度？ | 5=开箱即用，1=需大量定制 |
| 性能 | 15% | 满足性能要求？资源效率？ | 5=超出需求，1=勉强达标 |
| 退出成本 | 15% | 替换迁移成本？数据锁定？ | 5=易替换，1=深度锁定 |

### 评分计算

```
总分 = Σ(维度评分 × 权重)

决策规则：
- 总分 ≥ 4.0 → Adopt（采纳）
- 总分 3.0-3.9 → Trial（试验，需试点验证）
- 总分 < 3.0 → Hold（暂缓，寻找替代）
```

## 语言选型

| 语言 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| TypeScript | 全栈 Web、API 服务 | 类型安全、生态丰富、前后端同构 | CPU 密集型弱 |
| Python | 数据/AI、快速原型 | 生态丰富、开发快、AI 框架 | 性能弱、GIL |
| Go | 高并发后端、微服务 | 性能好、并发模型简单、部署简单 | 生态不如 TS/Java |
| Java | 企业级、大型系统 | 生态成熟、性能好、人才多 | 启动慢、内存大 |
| Rust | 系统级、极致性能 | 性能极致、内存安全 | 学习曲线陡、生态小 |

### 决策规则

```
团队已有主力语言？
├── 是 → 优先用主力语言，除非有明确痛点
└── 否 → 按场景选：
    ├── Web API + 全栈 → TypeScript
    ├── 高并发微服务 → Go
    ├── 数据/AI 密集 → Python
    ├── 企业级大型系统 → Java
    └── 系统级极致性能 → Rust
```

## 框架选型

### 后端框架

| 框架 | 语言 | 适用场景 | 选型理由 |
|------|------|---------|---------|
| Express/Fastify | TS | 简单 API、快速原型 | 轻量、灵活、生态大 |
| NestJS | TS | 企业级、结构化 API | 装饰器、DI、模块化 |
| Django/DRF | Python | 内容管理、快速开发 | Admin、ORM、开箱即用 |

| Gin/Echo | Go | 高性能微服务 | 轻量、快、中间件生态 |
| Spring Boot | Java | 企业级大型系统 | 生态成熟、DI、事务管理 |

### 前端框架

| 框架 | 适用场景 | 选型理由 |
|------|---------|---------|
| React | 组件复用、大团队 | 生态最大、灵活 |
| Vue | 快速开发、中小团队 | 上手快、文档好 |
| Next.js | SSR/SSG、SEO | React 全栈、文件路由 |
| Svelte | 性能优先、小包体 | 编译时优化、无虚拟 DOM |
| HTMX | 服务端渲染增强 | 无构建步骤、简单 |

## 数据库选型

### SQL vs NoSQL

| 维度 | SQL | NoSQL |
|------|-----|-------|
| 数据结构 | 结构化、关系型 | 灵活、文档/键值/图 |
| 一致性 | 强一致（ACID） | 最终一致（BASE） |
| 查询 | 复杂 JOIN、事务 | 简单查询、高吞吐 |
| Schema | 固定 Schema | 灵活 Schema |
| 扩展 | 垂直为主 | 水平扩展友好 |

### 具体产品

| 产品 | 类型 | 适用场景 | 关键特性 |
|------|------|---------|---------|
| PostgreSQL | SQL | 通用、复杂查询 | JSON 支持、扩展丰富 |
| MySQL | SQL | 简单 Web 应用 | 成熟、运维资源多 |
| SQLite | SQL | 嵌入式、开发测试 | 零配置、单文件 |
| MongoDB | 文档 | 灵活 Schema、文档存储 | 水平扩展、聚合管道 |
| Redis | 键值 | 缓存、会话、排行榜 | 内存级速度、数据结构丰富 |
| Elasticsearch | 搜索 | 全文搜索、日志分析 | 倒排索引、聚合分析 |
| Cassandra | 列族 | 高写入、时间序列 | 多区域复制、线性扩展 |

### 决策树

```
数据有复杂关系？需要强一致性？
├── 是 → PostgreSQL（默认选择）
│   ├── 需要全文搜索 → PostgreSQL + Elasticsearch
│   └── 需要高写入时间序列 → PostgreSQL + Cassandra
└── 否 → 数据结构灵活？
    ├── 是 → MongoDB
    └── 否 → 需要缓存/会话？
        ├── 是 → Redis
        └── 否 → 需要全文搜索？
            ├── 是 → Elasticsearch
            └── 否 → 重新评估需求
```

## 基础设施选型

| 组件 | 选项 | 决策因素 |
|------|------|---------|
| 容器编排 | K8s / Docker Swarm / Nomad | 规模、团队运维能力 |
| 服务网格 | 无 / Linkerd / Istio / Cilium | 服务数、mTLS 需求、性能 |
| 消息队列 | RabbitMQ / Kafka / Redis Streams | 吞吐量、有序性、持久化 |
| API 网关 | Nginx / Kong / APISIX / 自研 | 插件需求、动态配置 |
| 监控 | Prometheus+Grafana / Datadog | 自建 vs SaaS、预算 |
| 日志 | ELK / Loki / CloudWatch | 规模、预算、已有基础设施 |
| CI/CD | GitHub Actions / GitLab CI / Jenkins | 代码托管平台、团队偏好 |

## Build vs Buy 决策

```
这个能力是核心竞争力吗？
├── 是 → 自建（Build）
└── 否 → 自建成本 vs 购买成本？
    ├── 自建 < 购买 → 自建
    ├── 自建 ≈ 购买 → 看维护成本和灵活性
    └── 自建 > 购买 → 购买（Buy）
        └── 退出成本可接受？
            ├── 是 → 购买
            └── 否 → 重新评估或自建
```

## 选型记录

每个技术选型决策应记录为 ADR，包含：
- 候选方案列表
- 评估矩阵（6 维度评分）
- 最终选择及理由
- 已知风险和缓解措施
- 退出策略
