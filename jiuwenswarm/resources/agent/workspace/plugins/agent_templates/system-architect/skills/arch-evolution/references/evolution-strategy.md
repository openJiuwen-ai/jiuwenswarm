# 架构演进与技术债务管理

## 核心原则

架构演进不是"推倒重来"，而是"从现状安全过渡到目标"。每一步迁移都必须可验证、可回退、可并行运行。

## Strangler Fig（绞杀者）模式

### 工作原理

新系统逐步替换旧系统的功能模块，旧模块通过 Facade/API 网关代理到新系统。当所有功能迁移完毕，旧系统下线。

```
客户端 → API 网关/Facade →├→ 新服务（已迁移功能）
                         └→ 旧系统（未迁移功能）
```

### 落地步骤

1. **识别迁移边界**：选择耦合度最低、价值最高的模块作为首个迁移目标
2. **搭建 Facade**：在旧系统前部署 API 网关，所有请求先经过网关
3. **逐功能迁移**：每次迁移一个功能，网关将对应路由指向新服务
4. **并行运行**：新旧系统同时处理请求，比对结果一致性
5. **流量切换**：灰度切流（1% → 10% → 50% → 100%），每阶段监控
6. **旧模块下线**：确认无流量后下线旧模块

### 关键约束

- 每次只迁移一个功能，降低风险
- 迁移期间保持 API 向后兼容
- 必须有回退方案（网关一键切回旧系统）
- 监控迁移功能的错误率、延迟、数据一致性

## 技术债务量化评级

### 债务评级矩阵

| 级别 | 影响范围 | 紧急度 | 示例 | 处理策略 |
|------|---------|--------|------|---------|
| D1-致命 | 核心链路，阻碍扩展/可用 | 立即 | 单点故障、数据丢失风险 | 本迭代内修复 |
| D2-高 | 核心模块可维护性差 | 本季度 | 循环依赖、无测试覆盖 | 纳入近期迭代 |
| D3-中 | 非核心功能技术落后 | 半年内 | 过时框架、手动部署 | 纳入技术债务看板 |
| D4-低 | 代码风格/小优化 | 按需 | 命名不规范、缺少注释 | 随业务迭代顺手改 |

### 债务偿还优先级

```
优先级 = 影响范围 × 紧急度 × 修复成本（倒数）

决策规则：
- D1 债务阻塞业务 → 立即偿还，优先级最高
- D2 债务影响团队效率 → 排入近 2 个迭代
- D3 债务有替代方案 → 排入季度规划
- D4 债务 → 随业务迭代顺手偿还（Boy Scout Rule）
```

### 债务看板管理

- 维护技术债务清单（与产品 Backlog 同级可见）
- 每个迭代预留 15-20% 容量偿还技术债务
- 债务项必须标注：描述、级别、影响范围、预估工时、偿还方案

## 演进路线图方法论

### 四阶段框架

```
1. 现状评估（As-Is）
   ├── 架构现状图（C4 Container 级别）
   ├── 技术债务清单
   ├── 痛点访谈（开发/运维/业务）
   └── 质量属性基线（性能/可用性指标）

2. 目标架构（To-Be）
   ├── 目标架构图（C4 Container + Component 级别）
   ├── 质量属性目标（SLO）
   ├── 关键架构决策（ADR）
   └── 与现状的 Gap 分析

3. 迁移规划
   ├── 分阶段拆解（每阶段 1-3 个月）
   ├── 每阶段：迁移范围、依赖、风险、回退方案
   ├── 并行运行策略
   └── 关键里程碑和验收标准

4. 执行与反馈
   ├── 每阶段完成后架构评审
   ├── 监控指标对比基线
   ├── 路线图动态调整（新信息出现时）
   └── ADR 更新（决策变化时记录）
```

### 路线图模板

| 阶段 | 时间 | 目标 | 关键任务 | 依赖 | 风险 | 回退方案 |
|------|------|------|---------|------|------|---------|
| P0 基线 | 2 周 | 现状评估 | 架构图+债务清单+痛点访谈 | — | 评估不全面 | 补充访谈 |
| P1 解耦 | 1 月 | 模块边界清晰 | 提取接口+消除循环依赖 | P0 | 接口设计不当 | 保留旧调用路径 |
| P2 提取 | 2 月 | 首个服务独立部署 | Strangler Fig+并行运行 | P1 | 数据不一致 | 网关切回旧系统 |
| P3 扩展 | 持续 | 按需拆分剩余模块 | 逐功能迁移+监控 | P2 | 迁移速度慢 | 调整迁移粒度 |

## 并行运行与灰度切换

### 并行运行策略

- **双写模式**：新旧系统同时写入，比对数据一致性后切读
- **影子流量**：新系统接收只读流量副本，不影响生产
- **金丝雀发布**：小比例真实流量导向新系统，逐步扩大

### 灰度切换检查清单

- [ ] 新系统通过功能测试和集成测试
- [ ] 监控仪表盘就绪（错误率、延迟、吞吐量）
- [ ] 回退方案验证通过（一键切回）
- [ ] 数据一致性校验脚本就绪
- [ ] on-call 团队知晓切换计划
- [ ] 切换窗口选择低峰期
- [ ] 每个灰度比例有明确的通过/回退判断标准
