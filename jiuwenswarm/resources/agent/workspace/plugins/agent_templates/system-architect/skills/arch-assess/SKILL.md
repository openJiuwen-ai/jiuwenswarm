# 现状系统评估

## 目标

对现有系统进行逆向架构分析：从代码出发，画出 as-is 架构图，识别耦合热点和架构坏味道，输出系统健康度评估报告。这是"从零设计"的正交工作流——不假设绿地，从棕地出发。

## 工作流

### 1. 代码阅读与依赖映射

- 静态分析：解析 import/require 语句，构建模块依赖图
- 动态分析：运行时调用链追踪，识别实际执行路径
- 依赖方向检查：标注循环依赖、跨层引用、反向依赖
- 代码阅读启发式和依赖映射技术见：
`references/assessment-guide.md`

### 2. As-Is C4 架构图

从现有代码反推架构图：
- **Context**：识别系统边界和外部依赖（数据库、消息队列、第三方 API）
- **Container**：识别可独立部署的组件（服务、前端应用、批处理）
- **Component**：识别每个容器内的主要模块和职责
- 标注技术栈、数据流方向、通信协议

C4 画法规范（Mermaid/PlantUML 模板、命名规范、每层粒度、坏味道标红方法）见：
`arch-design` 技能的 `c4-conventions.md` 参考

### 3. 耦合热点与坏味道定位

识别架构层面的坏味道：
- **耦合热点**：被最多模块依赖的"上帝类/上帝服务"
- **循环依赖**：A→B→A 或更长的环
- **跨层引用**：Controller 直连数据库、Service 导入 HTTP 类型
- **共享数据库**：多服务直连同一数据库
- **分布式单体**：微服务间强同步调用
- 坏味道目录和定位方法见：
`references/assessment-guide.md`

### 4. 系统健康度评估

按质量属性逐项打分（1-5），输出健康度雷达图和改进建议：
- 可扩展性 / 高可用性 / 可维护性 / 可观测性 / 安全性 / 成本
- 评估方法和报告模板见：
`references/assessment-guide.md`

## 决策规则

- 先读代码再画图——as-is 图必须反映真实代码结构，不是"应该是的样子"
- 依赖图比架构图更有诊断价值——耦合热点藏在依赖关系中
- 坏味道按影响范围排序——先修影响最大的
- 评估结果直接输入 `arch-evolution` 技能制定演进路线图
- 不在评估阶段提改造方案——先诊断后开方，诊断和方案分离
