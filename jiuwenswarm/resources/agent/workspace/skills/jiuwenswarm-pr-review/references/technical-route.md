# JiuwenSwarm Technical Direction and Applicable PR Standards

These standards reflect repository source and maintained documents around commit `ceb4b200d`. They describe the mechanisms and direction a PR should respect; they do not claim that all legacy code already meets the intended boundaries. Recheck claims against the target branch, applicable project instruction files, and approved design decisions when reviewing a later revision.

## Languages, frameworks, and deliverables

| Area | Current mechanism | Review standard |
| --- | --- | --- |
| Python application | Root `pyproject.toml` requires Python `>=3.11,<3.14`, uses `uv.lock`, and pins openJiuwen to a Git commit. Console entry points include AgentServer, Gateway, Web, CLI, ACP, and jiuwenbox. | New dependencies, versions, and entry points need a clear requirement and compatibility evidence. Keep locks, packaging, and affected platform checks aligned. Avoid a parallel execution framework for an existing responsibility. |
| Services and protocols | `jiuwenswarm/gateway/` accepts and routes channel requests; `jiuwenswarm/server/` hosts AgentServer; `jiuwenswarm/common/schema/` and `common/e2a/` define shared messages and E2A contracts. Transport uses WebSocket, with FastAPI for some HTTP endpoints. | For protocol, identity, status, error, or stream-terminal changes, check producers, consumers, older clients, and tests. Keep transport encoding at the boundary and give runtime state an explicit owner. |
| Agent execution | `jiuwenswarm/runtime/` provides the `AgentRuntime` lifecycle and events; `server/runtime/agent_manager.py` and agent adapters connect to openJiuwen; `agents/harness/` contains Work/Code/Team Rails, permissions, tools, and extensions. | Prefer existing public entry points, adapters, Rails, or tool extension points. Do not bypass permission or sandbox controls or introduce a second Runtime with the same responsibility. Shared abstractions need real consumers. |
| Web, TUI, desktop, SDKs | Web uses React, TypeScript, Vite, and existing Zustand state; TUI uses TypeScript/Node and can build with Bun; desktop includes Electron; Python and TypeScript SDKs have separate packages. See their `package.json` files. | Shared contract changes must account for affected frontends, channels, SDKs, and packaging. A local representation in one client should not replace a shared model. |

## Architecture boundaries and evolution

- **One Agent Runtime.** The public surface in `jiuwenswarm/runtime/__init__.py` and `runtime/service.py` shows Process CLI and AgentServer using the same `AgentRuntime`. AgentServer owns WebSocket and control entry points; Gateway owns channel ingress and routing. For new process-style CLI work, `docs/zh/JiuwenSwarm_CLI架构原则.md` requires a direct Runtime client, without starting AgentServer or building another Runtime. Apply that document only within its stated scope.
- **Process-local session state versus durable state.** The Coordinator, Registry, and Scheduler in `runtime/session/` own process-local executions, queuing, cancellation, and closing. Metadata, history, and checkpoint persistence still have separate implementations. `runtime/session_provisioner.py` owns product transactions for create, switch, fork, and delete. Changes here must respect a single source of truth, prepare/commit/abort, generation, idempotency, failure rollback, and cleanup. `docs/session-runtime-current-architecture.md` is a useful guide after checking its source baseline against the target branch.
- **Assess transitional boundaries as they exist.** `runtime/service.py` still imports `server.runtime.agent_manager`; some persistence implementations remain in `server/runtime/session/`. Determine whether a new dependency is a deliberate migration step or widens existing coupling. Do not claim full Runtime/Server separation, and do not treat old bridges as blanket exemptions.
- **Shared channel semantics.** Web, TUI, ACP, IM, and other entry points depend on shared request, event, and session contracts. If identity, mode, readiness, cancellation, interaction reply, push, or error semantics change, check the affected channels and both Gateway and AgentServer. Unaffected channels do not require automatic retesting.
- **Permissions and extension points.** `agents/harness/common/rails/permissions/`, AgentManager, Skill/Tool/MCP/Extension facilities, and the jiuwenbox sandbox are existing execution controls. New paths must preserve authorization, trusted-directory checks, sensitive-data protection, and tool lifecycle. Look for an existing Rail, adapter, or registration point before adding a new one.

## openJiuwen Harness and Swarm Rail standards

openJiuwen is a pinned framework dependency (`pyproject.toml` and `uv.lock`); JiuwenSwarm supplies product behavior around it. For each affected PR, verify the API against the **pinned revision used by the target branch**, not an arbitrary local openJiuwen checkout. If the PR changes the pin, compare the target branch revision with the proposed revision and verify Swarm's integration against the proposed one. The concrete assembly points below are from this repository and must be rechecked if the target branch changes them.

- **Framework boundary.** openJiuwen `DeepAgent` and its `AgentRail`/`DeepAgentRail` callback model own the agent execution loop. JiuwenSwarm's `server/runtime/agent_adapter/interface_deep.py` builds single-agent Rails and connects them to the product Runtime. Generic framework behavior belongs in the upstream contract or a justified framework contribution; product prompts, permissions, events, modes, and tools belong in Swarm's adapter, Harness, or providers. Review any direct use of framework private state for version fragility and a public extension alternative. A change to the pinned framework revision needs a compatibility audit of imports, lifecycle hooks, registration, and affected modes.
- **Rail lifecycle and ordering.** The framework exposes invoke, task-iteration, model, and tool hooks; registration and unregistration also affect rail tools and state. At the pinned revision, Rails initialize in descending `rail.priority` order with stable ties; callbacks run in descending `rail.callback_priority(event)` order, which can differ by event. Model/tool hooks, `after_react_iteration`, `on_user_message`, and `before_steering_drain` register on the inner ReAct agent; invoke and task-iteration hooks stay on the outer DeepAgent. Inspect the hook actually used, its execution layer and ordering against adjacent Rails, shared `ctx.extra`/session state, initialization, cleanup, and behavior on exception, retry, cancellation, or force-finish. Multiple Rails may use the same callback event; the defect is duplicated responsibility, side effects, prompt content, tool ownership, or registration, not a shared hook name.
- **Single-agent assembly and mode state.** `interface_deep.py` declares separate agent/code Rail sets and conditionally attaches Rails. `server/runtime/agent_manager.py` treats single-agent Plan as session runtime state on the same cached agent so conversation context survives mode switches. Review the actual assembled chain for every affected Work/Code/Plan profile and channel; confirm model-visible tools, prompt state, permission behavior, and context continuity. A Rail required for a mode must be present when that mode becomes active, including after configuration reload.
- **Reload and dynamic extensions.** Rails can be rebuilt, registered live, or toggled by mode. `interface_deep.py` contains explicit post-`configure(rails=...)` registration handling because pending Rails can otherwise miss the live execution chain. `agents/harness/common/plugins/rail_manager.py` manages user Rail extensions. Check idempotent register/unregister, duplicate tool registration, repeated registration of the same callback or duplicate callback effects, retained dynamic Skill state, cache isolation, and cleanup across reload and reused agents. A Rail object being stored on the adapter is not proof that it is active on the running agent.
- **Permissions and tool execution.** Preserve the composed permission, approval, security, `SysOperation`, and sandbox path across tool calls and subagents. In particular, review the permission Rail group and its live registration on reload, trusted workspace roots, interaction/interrupt routing, and any mode-specific exceptions. Do not let a new tool, background path, or Team member invoke an equivalent action outside those controls.
- **Team assembly.** `agents/swarm/assembly.py`, `config_specs.py`, and `registry.py` build Team members from role/profile configuration, `RailSpec`/tool/subagent provider names, and a per-team `SwarmBuildContext`; they do not copy a prebuilt single agent. Check provider registration, manifest names, role-specific and code-profile composition, member workspace/config isolation, and tool/Rail ownership. Avoid a parallel imperative Team assembly path or double-registration of a capability already supplied by a Rail.
- **Evidence for a Rail change.** Tests should prove the behavior through the applicable assembled agent or member, including hook execution, mode transition or reload when affected, and failure/cancellation/permission behavior where relevant. Isolated Rail unit tests alone do not establish that the Rail is mounted or ordered correctly. Use existing assembly and permission contract tests as a guide; require only cases implicated by the PR.

### Cross-layer contracts to protect

| Contract | Ownership and review questions |
| --- | --- |
| Agent construction | openJiuwen `DeepAgentConfig`/factory and Swarm's `JiuWenSwarmDeepAdapter` construct a single agent; Team members use openJiuwen `TeamAgentSpec` and Swarm's declarative provider specs. Does the change preserve these two assembly paths and their shared behavior without copying a live agent or building a competing execution loop? |
| Execution and control | openJiuwen `DeepAgent` runs the inner ReAct agent and optional outer task loop; Team `NativeHarness` drives rounds and `TeamHarness` adapts them for members. Does a change to invoke, stream, steer, follow-up, interrupt, pause, abort, or resume preserve the corresponding state transition and the owner of that transition? |
| Context and persistence | The inner ContextEngine owns model conversation context; openJiuwen sessions/checkpointers persist agent state; Swarm owns product session lifecycle and a process-wide persistent checkpointer. Which state is live, checkpointed, or derived? Will it survive reload, mode change, recovery, and session deletion without duplication or leakage? |
| Capabilities and security | `AgentRail`/`DeepAgentRail` hooks, `AbilityManager`, `Runner.resource_mgr`, `SysOperation`, and the permission/security Rails jointly determine available and executable actions. Is a capability exposed once, guarded at execution time, and retained or released according to its actual ownership and lifecycle? |
| Team composition and runtime | Swarm `SwarmBuildContext`, provider manifest, `RailSpec`/tool/subagent specs, and openJiuwen `AgentConfigurator` build members; openJiuwen `TeamRuntimeManager` owns team pool, dispatch, and interaction gate. Are build data, live handles, leader/member identity, and runtime control kept in their respective layers? |

- **Identity and resource scope.** In the pinned framework, `DeepAgentConfig.card.id` is a stable checkpoint identity, while `tool_owner_id` separates live tool registrations that share that card. Swarm fixes its single-agent card ID and scopes tool ownership separately (`interface_deep.py`). Review card/session IDs, cached agent keys, `Runner.resource_mgr` registrations, and `SysOperation` ownership together. A PR must not fix tool collisions by changing persistence identity, overwrite another live agent's resource, or remove a shared resource while another user still holds it.
- **Task-loop, ReAct, and tool-result integrity.** Check whether a hook runs on the outer task iteration or inner model/tool loop. Every model tool call needs a matching result in the conversation protocol; a background completion should enter through its intended later-message path rather than inventing a delayed result for an old call. Review bounded iteration, no-progress and retry behavior, especially for actions with side effects. A graceful stop or resume must not replay a completed tool call or leave the model context with an unmatched tool call.
- **Interrupt and cancellation semantics.** openJiuwen `NativeHarness` distinguishes queued follow-up, immediate steering, abort of a round, and pause/resume over retained context. A running tool can already have irreversible effects. Review acknowledgements, state transitions, snapshot/rollback points, and cleanup for model calls versus tools. For Team changes, also inspect Swarm's control translation and any background task; do not infer that ending one DeepAgent round ends a persistent Team stream or releases its pool entry.
- **Prompt and context authority.** openJiuwen's prompt builder and ContextEngine are the live model-facing sources; Swarm layers runtime, response, Skill retrieval, memory, and context-processing Rails on them. Check prompt-section ownership, priority, language, deduplication, token budget, and reset/rebuild behavior. Model switching must update the selected model's context-window and tokenizer metadata as well as the model client (`interface_deep.py` builds the ContextEngine config). Do not treat a logged prompt string or adapter field as proof of the messages actually sent to the model.
- **Workspace and access boundaries.** openJiuwen distinguishes the agent's artifact `workspace`, shell `cwd`, and access-boundary `project_root`. Team members can run in a project or worktree while retaining a private artifact workspace. Check which root each filesystem, shell, Skill, prompt, permission, subagent, and cleanup path uses. Passing a workspace path in place of a project root can broaden access or put durable artifacts in an ephemeral checkout.
- **Tool, Skill, MCP, and subagent ownership.** Inspect the whole route from declaration to registration, model visibility, invocation, hot reload, and disposal. The process-global resource manager and Rail-owned tools require stable IDs and explicit ownership. Team Skill use has a shared physical library plus team/member visibility declarations (`config_specs.py`, `providers/skills.py`); avoid a second library or double-registering Skill management tools. Verify child agents inherit the intended model, tools, permissions, workspace, iteration limits, and stop behavior without inheriting mutable parent state accidentally.
- **Serializable specs versus live handles.** openJiuwen Team specs and `build_context_seed` cross process boundaries; `SwarmBuildContext` carries live handles only in the process where providers build. Check `to_seed`/`from_seed`, `derive()` for member fields, provider registration and manifest names, defaults, and spawn payload readers/writers together. A new non-serializable object or implicit local closure in a spec can work in process and fail for a spawned member or cold recovery.
- **Team state and message boundaries.** openJiuwen's Team runtime pool, interaction gate, member startup, checkpoint namespace, message transport, and stream tagging have separate owners. Review leader versus teammate paths, one active team per name/session policy, lazy-start concurrency, persisted team state, and cross-process message delivery. A member-visible change must work when leader and teammate do not share Python objects. A stream/event change must preserve member identity and terminal semantics at the Swarm channel boundary.
- **Upstream integration changes.** When a PR changes the openJiuwen pin or starts using a new API, compare public exports and actual behavior in the target-branch and proposed openJiuwen revisions, then check Swarm adapter/provider assumptions against the proposed version. Check config and spec fields, Rail hook routing and priority, hot-reconfigure behavior, session/checkpoint keys, resource registration, Team member construction, and stream/interrupt contracts. Update the lockfile and affected documentation; require integration evidence for the paths that depend on the changed contract.

Treat a demonstrated permission bypass, broken checkpoint identity, lost or duplicated tool execution, cross-session state leak, missing required live Rail, or Team member build failure as a merge-significant architectural finding. For other risks, identify the affected path and observable consequence; a theoretical layering preference by itself is not a defect.

## Code, UI, verification, and documentation standards

- **Python.** `pytest.ini` configures pytest, asyncio, coverage, and strict markers. The root `Makefile` provides test and Ruff commands. In `make lint`, Ruff fails the target; Pylint, Mypy, and Codespell currently run with `|| true`, so they are not equivalent mandatory gates. `docs/zh/developer_guide.md` recommends `uv run pytest`. Judge test sufficiency by affected contracts and failure paths; public boundary changes need relevant integration or system evidence.
- **Web.** Applicable Web project instruction files specify Chrome/Chromium 107 compatibility, Prettier, semantic color tokens, `currentColor` for themeable SVGs, `data-testid` for touched elements, Chinese and English UI text, and shared Settings components. Web `package.json` builds with `tsc && vite build` and lints with ESLint. Many frontend tests are separate `test:*` scripts; select relevant suites rather than assuming a unified `npm test`.
- **TUI and specialized areas.** TUI `package.json` provides TypeScript type checking, oxlint, oxfmt, and test scripts. More specific project instruction files, such as the Web trajectory rules, add data-flow, generated-file, and testing constraints for their own paths only.
- **PR description and docs.** `.gitcode/PULL_REQUEST_TEMPLATE.zh-CN.md` asks for kind, motivation, linked issue, test plan and results, and checks on design review, unit/system tests, goal verification, interface review, and documentation. Code behavior, documentation, and PR claims should agree. Public interface, configuration, and user-visible behavior changes require relevant docs, examples, and migration notes. A future design document is not evidence of current implementation.
- **Packaging and multiple clients.** `pyproject.toml` package-data and exclusions, `MANIFEST.in`, Web/TUI builds, and SDK packages have separate delivery boundaries. For resource, dependency, or generated-file changes, check source installs and built distributions, and avoid depending on local caches or build artifacts as if they were source files.
