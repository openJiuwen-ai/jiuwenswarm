# 系统插件文档写法

沿用系统插件目录已有文档的写法。新系统插件先说明有什么效果、怎样安装和验证，再说明实现。
并列要求分点，步骤按先后编号，字段或职责对照用表格，避免把多项要求挤在一段里。
编写系统插件说明时，按当前需要读取对应章节；核对平台契约时先搜索相关条目和符号，只展开必要段落。

## 1. 说明能力与运行条件

先用简短段落说明系统插件在什么业务操作时运行、读取或修改什么、用户会看到什么，再分点说明：

- **适用环境：** 宿主、已验证版本和必要依赖。
- **已有能力：** 使用哪些事件、Ops 或槽位，实际触发条件是什么。
- **使用范围：** 哪些会话、页面或对象会受影响。
- **当前状态：** 已完成开发、已安装激活还是已验证业务效果，分别说明。

示例问候系统插件复用 `ui.ready` 和 `ops.ui.render`，在会话输入区上方槽位挂载后显示后端问候语，不发起模型调用。
这是示例本身的效果，其他系统插件按实际需求选择能力。

## 2. 写清安装和验证步骤

使用者应能照着完成：

1. 找到最终 ZIP，知道 package_id 和版本。
2. 通过宿主 CLI 或已有 Web 命令安装；有配置时，知道参数、默认值和生效时机。
3. 查询并确认激活状态和实际安装目录。
4. 执行一项真实业务操作，看到约定结果，并知道结果确实来自本系统插件。
5. 有页面效果时，系统插件激活和必要的业务触发完成后，立即使用当前环境提供的提问能力让用户确认是否符合预期；不要求智能体启动或查找浏览器。用户提出意见后，说明怎样更新安装副本、reload 和再次确认。
6. 按需要修改、重载或卸载；失败时知道查询哪些状态。

说明安装时注意：

- **调用方式：** skill 执行者可以参考 [CLI 安装说明](package-installation.md)。系统插件 README 保留目标宿主可直接使用的管理方式，不要求普通使用者另外安装本开发 skill。
- **Swarm 命令：** 人工安装可用 `/extension install <ZIP 绝对路径>`，查询、重载和卸载使用同一 package_id；路径必须对运行服务可读。
- **源码与副本：** 重载读取安装副本；修改来源目录后重新测试、打包，并按宿主规则更新安装内容。
- **已有版本：** 同 ID 已存在时说明更新方法。首次安装后收到修改意见时，更新安装副本并 reload，不卸载后重装，也不写成重新执行 install 就一定覆盖。
- **用户表达：** 普通说明使用“安装目录”等产品概念，接口开发说明再解释进程和协议。

## 3. 说明开发者需要的契约

使用真实类型和字段表，按涉及范围说明：

- **输入字段：** 名称、类型、默认值和空值含义。
- **匹配与修改：** 支持的匹配模式、允许修改的数据，以及只读的会话和系统插件身份。
- **输出规则：** 默认结果、next 后加工结果和短路结果，分别由谁产生、交给谁使用。
- **Ops 调用：** 完整方法名、参数、上下文、返回值或副作用，以及失败方式。
- **登记示例：** 导入和类型完整，注释解释关键意图。

公共机制引用目标环境的原文，系统插件文档重点维护自己的行为，不复制整套 Core 或 Swarm 设计。
复杂系统插件的方案、设计取舍和状态管理放在系统插件自己的设计文档中。

## 4. 如实记录测试与安装结果

用“输入与前置条件、操作、预期结果、实际验证”组织场景，区分以下记录：

| 记录 | 应说明 |
| --- | --- |
| 隔离测试 | 正常、未命中、失败、取消和相关隔离行为，命令及结果 |
| 最终 ZIP | 正式打包文件是否经过加载测试，文件或 SHA-256 如何对应 |
| 运行安装 | 目标环境、Report 结果、查询状态和实际安装目录 |
| 业务效果 | 执行哪项真实操作，取得什么结果，界面是否实际检查 |
| 未完成项 | 缺失能力、认证、未运行的服务，或仍在等待用户确认的界面效果 |

记录时注意：

- **状态区别：** “已激活”表示后续事件可以使用已发布 Handler，不等于已经执行目标业务或页面已经显示。
- **结果未知：** 没有明确报告时保留未知状态；当前查到系统插件已激活，也不能补造原操作成功的报告。
- **验证范围：** 模拟传输成功不代替真实页面验收，未执行的检查不写成通过。
- **用户确认：** 已安装且需要用户查看的界面效果，单独记录用户是否确认；没有回复、通知未送达或只看到了渲染回执，都不能写成“用户满意”。不能把智能体未启动浏览器写成验证失败，应进入用户确认。
- **章节范围：** 只有涉及外部产品兼容时才补充对照，不强制加入无关内容。
