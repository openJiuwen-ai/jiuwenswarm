# 系统插件开发与安装

围绕用户要实现的效果，先搜索相关目录、事件名和 Ops 关键词，读取命中片段，再按需要核对接口和实现，开发系统插件。
默认完成开发、测试和打包；是否安装按用户的明确意愿执行。
用户未说明时，完成开发后通过提问工具确认；用户只要求分析时，按其指定范围执行。

## 职责边界

- **对外称呼：** 介绍开发产物时，统一称为“系统插件”；代码、类型和命令保留实际名称。
- **系统插件开发：** 复用宿主已有事件和 Ops，交付包含源码、说明和测试的系统插件 ZIP。
- **运行安装：** 使用已有 `bash` 工具，调用宿主提供的 `extension` 命令完成安装和查询。
- **修改范围：** 宿主源码和依赖代码只读。系统插件自己的源码和本轮安装返回的安装副本可以按本 Skill 的流程修改；重载按当前宿主的实际规则执行。
- **平台缺口：** 缺少事件、触发入口、Ops、槽位或 CLI 支持时，向用户说明具体缺口，不通过修改平台或绕过校验补齐。
- **完成依据：** 不安装时，交付已验证的最终 ZIP 即可；需要安装时，还要分别核对系统插件已激活和业务效果，不能用打包完成代替安装或验证。

## 1. 确认目标环境和目录

命令示例中的 `SKILL_ROOT` 指本 Skill 所在目录，使用时替换为实际路径。

先确认目标 Swarm、它依赖的 Core、实际运行环境及系统插件输出目录。按下文选择源码；只有需要补充细节时，再查看 [开发流程](references/package-workflow.md#1-确认源码和阅读位置) 的相关小节。

- **已有系统插件：** 如果用户指定修改已有系统插件，则优先修改其源码，但要保留该系统插件已有能力。
- **新系统插件：** 在用户指定位置或工作区的独立目录创建，不放进平台内置事件目录；未指定内部名称时，按用途选择清晰的英文名称与 ID。
- **必要信息：** 只询问影响可行性的缺失信息，例如目标宿主不明确、缺少运行依赖，或需求有两种明显不同的业务含义。

### 1.1 固定阅读入口

源码来源按以下顺序确定，具体读取方式和仓库地址见 [开发流程](references/package-workflow.md#1-确认源码和阅读位置)：

- **已指定目录：** Swarm 和 Core 分别使用用户指定的目录；只指定一个时，仅为另一个获取源码。
- **固定远端分支：** 未指定源码的仓库，Swarm 使用 `releases/0.2.9.beta3`，Core 使用 `release/v0.1.20.post3`；优先 GitCode，无法获取时再尝试 GitHub。需要 clone 时，按 [稀疏检出说明](references/source-reading.md#1-按需稀疏检出) 只获取当前所需目录，不先按运行版本查找其他提交或 Tag。
- **Wheel 回退：** 两个平台都获取不到指定分支时，可以读取当前环境中已安装的代码。
- **EXE、DMG 回退：** 两个平台都获取不到指定分支时，调用提问工具请用户提供源码目录或可访问的源码下载地址，等待答复后继续；不搜索安装目录、`_internal` 或二进制内容。

源码位置确认后，先读取适用的仓库根、模块内 `AGENTS.md` 和本地规则，再从以下入口搜索相关文档、公开接口和测试，按命中片段展开。不要预先通读整个 `docs/` 或模块实现：

| 模块 | 相对于仓库根的确定目录 |
| --- | --- |
| Core 事件与 Ops | `<CORE_ROOT>/openjiuwen/core/events/` |
| Core 系统插件加载与生命周期 | `<CORE_ROOT>/openjiuwen/core/extension/` |
| Swarm 系统插件与 WebUI | `<SWARM_ROOT>/jiuwenswarm/extensions_v2/` |

查阅时注意：

- **Swarm 层级：** `SWARM_ROOT` 是仓库根，其内部还有同名 Python 包 `jiuwenswarm/`。若仓库目录也叫 `jiuwenswarm`，从其父目录看模块路径为 `jiuwenswarm/jiuwenswarm/extensions_v2/`。
- **依赖位置：** Wheel 回退时，使用实际 Swarm 解释器定位已安装的代码。模块目录 `CORE_DIR` 指向 `openjiuwen/core/`，不是源码仓根；EXE、DMG 不走此回退。
- **源码位置：** 用户指定或从固定分支获取的仓库根记作 `CORE_ROOT` 或 `SWARM_ROOT`；Wheel 回退时按实际模块目录阅读，不把安装目录当作源码仓根。
- **接口依据：** 版本、类型、已登记事件和 Ops 以实际目标环境为准，不把示例当作现成功能，也不把设计文档中未实现的能力当做已有能力，一切以源码实现为准。
- **目录范围：** 上表固定模块入口，模块内部的文件布局和能力清单仍需核对当前实现。

### 1.2 确认安装目标

用户已明确要求安装时，开发前按 [安装与状态核对](references/package-installation.md) 确认运行中的宿主、命令入口，以及 ZIP 在宿主侧的可读路径。
尚未确定是否安装时，先核对开发环境；运行安装所需的信息在用户同意后确认。

- **用户输入：** 用户描述需求即可，按照用户需求完成系统插件功能，注意涉及前端页面时，设计要保持美观。
- **运行上下文：** 当前实例的本机管理连接由 Swarm 自动提供。不要扫描端口、查找浏览器凭据或自行拼接认证参数。
- **命令选择：** 源码和 Wheel 使用 `jiuwenswarm extension`；EXE、DMG 使用 `JIUWENSWARM_EXECUTABLE` 指向的现有后端程序执行 `extension`。
- **安装意愿：** 按第 5.1 节区分明确安装、明确不安装和未说明三种情况，不默认安装，也不重复询问已有明确答复。
- **入口缺失：** 可以先完成独立的开发、测试和打包；宿主版本缺少 CLI 或本机连接不可用时，向用户说明具体缺口，不修改平台或另写安装客户端来绕过。
- **界面验收：** 用户同意安装，且系统插件声明了 UI contribution 或改动会让用户在页面上看到变化时，安装和技术验证完成后必须进入第 6 节的用户确认循环。没有得到用户的明确确认前，不得以安装成功、收到渲染回执、没有浏览器能力或无法自行观察页面为由结束会话。

### 1.3 确认执行环境

开发调试、测试和打包使用当前 Swarm 已有的执行环境，选择方式见 [复用宿主的执行环境](references/package-workflow.md#15-复用宿主的执行环境)。

- **源码、Wheel：** 使用启动当前 Swarm 的现有 Python，沿用其中的 Swarm、Core 和依赖。
- **EXE、DMG：** 使用 `JIUWENSWARM_EXECUTABLE` 指向的后端程序执行脚本，复用 APP 内置的 Python 和依赖，不另找系统 Python。
- **源码与环境：** 用户指定或下载的仓库用于阅读。不会因为获取了源码，就为它新建虚拟环境、安装依赖或替换 APP 内的模块。
- **环境缺失：** 说明缺少的入口或模块，向用户确认可用环境，不自动准备另一套完整环境。

## 2. 判断已有能力能否完成

根据需求搜索事件名、Ops 方法、输入字段或槽位名称，先读取命中片段。
只为确认本次所需的定义、登记、业务触发位置和调用条件继续查阅相关符号；实现前用真实名称说明本次选择：

| 判断 | 需要说明 |
| --- | --- |
| 采用的事件 | 为什么符合诉求，何时触发，一次处理什么，输入输出和匹配字段是什么 |
| Handler 行为 | 前置处理、继续、加工结果还是短路；对默认业务有什么影响 |
| 复用的 Ops | 完整方法名、参数、上下文、返回值和副作用；不需要则说明 |
| 可见效果 | 用户从哪里看到变化，哪项已有业务操作能够触发 |
| 安装后的验证 | 怎样确认系统插件已激活，怎样验证实际业务效果，是否需要刷新已有页面或重新进入会话 |

已有能力足够时继续开发。缺少必要能力时，向用户说明位置、缺口和影响，先与用户讨论可行范围，不把不存在的事件写进系统插件。

## 3. 编写系统插件说明和实现

需要参考系统插件结构、Handler 或 UI 写法时，先查 [示例索引](references/example.md)，只读相关文件和片段；编写系统插件说明时，再查看 [文档写法](references/package-writing.md) 的对应章节。
先说明能力、运行条件、实现方案和验收方法，再开发代码；复杂的系统插件可在自己的目录增加设计文件，无需向只读宿主仓补 feature、plan 或 spec。

按需要提供：

- 根目录 `manifest.json`，声明 `schemaVersion`、`package_type`、系统插件 ID、版本、运行域、代码入口和实际依赖。
- `create_extension()` 工厂，以及入口对象的 `register(registrar)`。
- 类型和导入完整的异步 Handler，必要的状态隔离与资源清理。
- 系统插件自己的测试和使用说明；需要界面时，声明目标宿主支持的 UI contribution。

实现时注意：

- **Handler 登记：** 使用 `ExtensionRegistrar.register_event_handler(...)`。外部系统插件默认使用 USER 层，传匹配模式；可信系统插件身份由平台注入，不自行传入 PackageMetadata。
- **能力范围：** 不登记新事件类型、不能定义 CORE Handler、不修改 `ops.build`，也不新建业务 Bus 或 Registry。需要 BUILTIN 时按实际需求说明理由。
- **返回结果：** 按契约决定是否调用 `next_handler(event)`；继续和短路都返回合法输出，除非场景需要，不要直接短路返回，影响其它Handler执行。
- **上下文与状态：** 从现有 Ops 读取会话和系统插件身份，状态按会话或业务实例隔离；不保存本次调用的 ops 或 next 供以后使用。
- **Ops 调用：** 可以执行现有 Ops 提供的操作，但不能新增平台能力或真实业务触发点。
- **UI 开发：** 复用已有槽位、组件和样式 token，保留目标、会话和活跃实例校验；按实际协议恢复界面，并检查窄窗口和较长文案。涉及UI开发时，要保持界面美观。
- **代码风格：** 使用真实导入、完整类型和公开接口，代码行不超过 120 字符；注释和命名遵循系统插件目录已有风格。

## 4. 测试并生成最终 ZIP

不能仅测试系统插件内函数的执行，应在隔离的临时安装目录中验证真实加载、Handler 发布和事件结果。
按本次范围覆盖：

- **事件处理：** 命中、未命中、继续和短路的结果，以及默认动作执行次数。
- **失败与隔离：** 主要失败、取消、会话隔离和重复调用。
- **UI 行为：** contribution、渲染结果和返回状态；涉及界面时补相应测试，浏览器未验证则按事实记录。
- **生命周期：** 从临时安装副本重载，核对新结果、失败保留和卸载清理。

使用第 1.3 节确认的执行入口运行 [测试脚本](scripts/run_tests.py) 和 [打包脚本](scripts/build_package.py)。
下文的 `<PYTHON_ENTRY>` 指现有 Python 或桌面后端的绝对路径；PowerShell 调用时在命令前加 `&`。

```text
"<PYTHON_ENTRY>" "<SKILL_ROOT>/scripts/run_tests.py" "<系统插件测试目录或文件>"
"<PYTHON_ENTRY>" "<SKILL_ROOT>/scripts/build_package.py" "<系统插件源码目录>" "<输出 ZIP 路径>"
```

打包后注意：

- **ZIP 布局：** ZIP 根目录直接包含唯一的 `manifest.json`，不多包一层目录。
- **打包范围：** 脚本校验 Core manifest 与入口路径，排除缓存和开发环境；不执行系统插件代码，不能代替行为测试。
- **最终产物：** 使用这个最终 ZIP 补一次隔离加载和效果验证；用户同意安装时，安装同一份文件。不要只验证源码目录或另行生成的测试 ZIP。
- **覆盖输出：** 输出已存在时不默认覆盖；确认替换后再使用 `--force`。最终 ZIP 验证后如有修改，重新打包和验证。

## 5. 确认是否安装并核对运行状态

### 5.1 确认是否安装

完成开发、测试和最终 ZIP 验证后，根据用户当前的明确意愿决定下一步：

- **明确要求安装：** 用户已说“开发后安装”“安装并生效”等，直接进入第 5.2 节，不再弹出安装确认卡片。
- **明确不安装：** 用户已说“不安装”“只生成 ZIP”等，交付源码、README、测试结果和最终 ZIP，说明本轮未安装后结束对话。不弹出安装确认或界面效果确认卡片。
- **未说明是否安装：** 调用当前环境提供的提问工具，显示安装确认卡片，询问：“当前开发已完成，是否需要安装？”不能只在普通回复中提问后结束对话。

安装确认卡片提供两个选项：

- A 为“需要，立即安装”。
- B 为“不需要，结束对话”。

发出卡片后必须等待用户回答。用户选择 A 或明确同意安装后，进入第 5.2 节；选择 B 或明确表示不安装时，交付开发结果并结束对话。
用户尚未回答或答复含糊时，继续等待或追问，不将默认选项、沉默或含糊答复当作同意，也不提前结束会话。

### 5.2 执行安装并核对状态

按 [安装与状态核对](references/package-installation.md) 选择当前发行方式的入口，通过 `bash` 工具执行。
源码、Wheel 的命令如下；桌面包使用运行环境提供的后端程序路径，参数保持一致：

```text
jiuwenswarm extension install "<最终 ZIP 路径>" --json
```

命令连接当前实例中已经装配的系统插件管理器。执行后核对：

- **安装报告：** 不只看命令是否执行，还要检查退出码、总体 `status` 与原始 Report。
- **当前状态：** 确认系统插件 ID、版本、本次激活记录编号（generation）和实际安装目录；CLI 成功后已再次查询核对。
- **宿主归属：** 安装时按最终 ZIP 的 `domain` 选择宿主；后续查询、重载和卸载 Gateway 系统插件时使用 `--domain gateway`。
- **已有版本：** 首次安装遇到同 ID 的系统插件或安装副本时，先确定更新方式；不自动卸载或覆盖。当前轮已安装的系统插件收到用户修改意见后，从收到意见到用户最终确认期间，禁止执行 uninstall，也禁止再次 install 同 ID ZIP。修改本轮安装报告返回的安装目录副本，再执行 reload；reload 读取安装副本，不读取来源 ZIP。只有用户明确要求删除系统插件时，才可以执行 uninstall。
- **结果未知：** 超时、断连或报告不明确时不重复安装。CLI 会查询一次当前状态，但不会据此补写原请求成功。
- **界面更新：** 安装成功后宿主会通知已经就绪的页面重新上报 `ui.ready`。结果中的 `ui_notified: true` 表示通知已送达，页面通常不需要刷新；它不代表用户已经看到了正确效果。`ui_notified: false` 只记录为通知未送达，不启动或查找浏览器补做页面操作；仍按第 6 节由用户确认实际效果。
- **安装边界：** 命令不上传 ZIP、不启动服务、不修改认证配置；沙箱与宿主的文件或网络不互通时，说明具体缺口。

## 6. 验证业务效果并交付

本节仅适用于用户同意安装且系统插件已激活的情况。用户不安装时，按第 5.1 节交付并结束，不进入本节的界面效果确认。

系统插件已激活后，使用原有业务入口验证用户要求的效果。页面需要重新挂载或业务需要下一次操作才能触发时，按实际生命周期完成验证，不新增演示按钮或平台触发代码。

### 6.1 涉及界面的用户确认循环

只要本系统插件有 UI contribution，或本次改动会改变页面上的位置、大小、文案、颜色、状态或交互，就必须完成本循环。页面上的实际效果由用户判断；你的职责是先让改动真实生效，再请用户确认，不能省略或替代用户确认。

#### 何时提问

完成最终 ZIP 的首次 install，或用户提出意见后的 reload，并查询到系统插件已激活后立刻提问。由用户在确认卡片中判断实际页面效果，不再启动、查找、操作、刷新、等待浏览器或截图来证明页面效果。只有安装、reload 或必要的页面触发返回失败时，才说明该技术阻塞，先解决系统插件未生效的问题，再向用户提问。

#### 怎样提问

使用当前环境提供的提问能力显示一张确认卡片。问题应说明本轮已经生效的可见效果，并询问：“你现在看到的实际效果是否符合预期？”

- A 为“是，符合效果”。
- B 为“不符合，填写修改意见”。B 是自定义输入项，不是点选后立即提交的普通选项；用户选择 B 后，应在同一张卡片展开输入框，让用户自己填写修改意见。

不要只问“是否安装成功”。发出确认卡片后必须等待用户回答，根据用户回答决定是否完成本次对话。

#### 结束与修改

用户选择 A 后，才结束界面验收并交付。确认卡片仍在等待、用户尚未回答，或用户回答的内容不能判断是否满意时，保持等待或继续追问；不得输出最终答复、交付总结或结束会话。

用户选择 B 并填写修改意见后，先复述要改的可见效果，修改系统插件源码并补相应测试，重新验证效果。再把已验证的改动同步到本轮安装结果返回的安装目录，只修改该系统插件自己的文件，并执行 reload 操作。此阶段只能 reload，不能 uninstall 后重新 install，也不能用重新安装来源 ZIP 代替 reload。完成必要的页面触发后，重新显示同样的确认卡片。重复这一过程，直到用户选择 A。

安装副本是本轮已安装系统插件的运行副本。每次同步前保留可恢复的旧文件，不修改宿主源码、其他系统插件或安装目录以外的文件；系统插件 ID、domain 和版本保持不变。reload 失败时恢复旧文件并再次 reload，不得用卸载再安装作为恢复手段，也不能把失败副本写成已生效。

最终给用户的说明应包含：

- 交付系统插件的 ZIP 文件，说明其 package_id、版本和 README。
- 测试命令、结果，以及最终 ZIP 的加载验证范围。
- 运行安装是否完成、实际安装目录和查询核对结果。
- 做了哪项真实业务操作、取得什么结果，界面是否已经实际验证。
- 涉及界面时，记录用户最后一次确认的结果；仍在等待确认或用户提出的新意见也要如实写明。
- 重载和卸载方式，以及尚未执行的检查、联调或其他必要提醒。
