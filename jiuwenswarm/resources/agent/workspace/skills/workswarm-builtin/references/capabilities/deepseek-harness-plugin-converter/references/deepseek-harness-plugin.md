# DeepSeek Harness 源码定位与结构检查

本文只记录转换时长期需要的查找顺序、源码获取规则和结构检查项，不保存 DSH API 手册。插件机制、字段和界面可能变化，每次转换都以目标版本的最新官方材料和实际源码为准。

## 1. 先读目标版本的官方材料

按下面顺序确认当前入口：

1. [DeepSeek Harness 官网](https://deepseek.com/harness)：确认官方仓库、开发文档和插件入口有没有调整。
2. [官方开发文档](https://deepseek-harness.github.io/deepseek-harness/en/develop/basic/)：从目录进入目标版本的插件入门、生命周期、依赖、事件、打包和界面说明，只读本次插件涉及的章节。
3. [官方插件索引文档](https://deepseek-harness.github.io/deepseek-harness/en/guide/plugin-market)：了解当前插件页面和索引元数据怎样给出 npm 或 Git 源。
4. [官方仓库](https://github.com/deepseek-ai/deepseek-harness)：只有目标插件属于内置插件，或官方文档不足以确认某个接口时，才读取目标 Tag 或 commit 下的对应源码。

用户指定 DSH 版本时，官方材料和源码都要切到匹配的 Tag 或 commit。用户没有指定时，记录分析当天采用的文档版本、插件版本和源码 commit，不把 `master` 的行为说成所有历史版本都支持。

官网链接的 GitHub `dsh-plugin` topic 是社区插件发现入口，不代表其中每个仓库都由 DeepSeek 官方维护。第三方市场、awesome 列表和搜索结果也只能提供候选。

## 2. 定位目标插件

### 用户已经给出源码

直接使用用户提供的目录、压缩包、仓库或精确发布地址：

- 不再搜索同名插件，不下载完整 DSH 仓库。
- 核对包名、显示名称、版本、作者、仓库和许可证，确认没有拿错插件。
- 对用户本地目录只读分析，不切换分支、不覆盖修改；需要固定证据时记录当前 commit 和工作区状态。

### 用户没有给出源码

1. 先查当前 DSH 插件页面、官方仓库内置插件和用户提供或当前环境已配置的插件索引。
2. 从插件条目或包元数据提取精确 npm 包名与版本，或 Git 仓库、commit 和插件子目录。
3. 没有命中时，使用网络搜索工具搜索插件名、别名、作者、npm 包名、`dsh-plugin` 和仓库地址。
4. 多个候选无法唯一确定时，让用户确认；没有源码或可核对发布包时停止转换。

索引标题、介绍和截图不能替代源码。最终身份必须落到以下一种形式：

```text
Git:  repository_url + commit + plugin_subdirectory
npm:  package_name + exact_version + registry/integrity（可获得时）
local: absolute_path + current_commit/worktree_state（可获得时）
```

## 3. 缓存并按需获取

缓存键使用上面的精确身份。缓存目录放在任务缓存区，不放进最终系统插件源码；同一仓库和 commit 已缓存时直接复用。

普通第三方插件不 clone 完整 DSH 仓库，也不先下载插件所在的整个 monorepo：

- Git 源先取得目标 commit 的目录树和插件子目录；需要 checkout 时使用部分克隆和 sparse-checkout，只展开目标插件目录。
- npm 源先读取 registry 元数据，再下载该精确版本的发布包；不执行 install、postinstall、构建脚本或插件代码。
- DSH 内置插件只稀疏获取它自己的目录。为了确认某个宿主接口需要源码时，再补取该接口的声明或直接实现目录。

第一次读取源码时一次性收集以下内容，形成完整轮廓后再深入，避免连续用许多命令逐个试读：

- manifest 或包元数据、README、许可证和目标目录树；
- manifest 指向的 Host、Client、组合或配置入口；
- 入口直接引用的插件内模块；
- 配置/schema、locale、资源和测试的文件名及与入口的关系。

然后沿真实入口分析 import、注册和数据流。只补取会影响核心行为的直接依赖：

- 插件仓库内的相对模块直接读取；
- monorepo 内被入口真实引用的同仓包，追加到同一 sparse-checkout；
- 普通外部包先根据版本和公开契约判断，只有其行为决定转换结果时才获取源码；
- DSH 或 Cordis API 回到目标版本官方文档，文档不足时只读取对应声明或实现，不扩展成完整仓库下载。

## 4. 转换前必须拿到的结构

文件名可能随版本变化，按用途确认，不根据旧模板猜路径。

| 结构 | 需要确认的内容 |
| --- | --- |
| 来源身份 | 包名、版本、仓库、commit、子目录、许可证、兼容的 DSH 版本 |
| 安装声明 | DSH 如何识别和装配该插件，入口、配置和依赖从哪里声明 |
| Host 入口 | 核心能力从哪里注册，什么业务动作触发，输入、输出、错误和清理怎样处理 |
| Client 入口 | 是否有页面或槽位，怎样调用 Host，怎样接收和渲染数据；无界面则记为不适用 |
| 状态与权限 | 状态作用域、持久化、文件、进程、网络、凭据、审批和沙箱要求 |
| 直接依赖 | 入口真实引用且影响核心行为的本地模块、同仓包、外部服务或 MCP |
| 行为证据 | README、配置说明、测试和源码分别证明了什么；冲突时以固定版本源码和测试为准 |

按调用链输出简短行为表，不复述整个目录：

| 原插件能力 | 真实入口 | 触发与输入 | 输出或界面效果 | 状态与权限 | 是否核心 |
| --- | --- | --- | --- | --- | --- |

“是否核心”用于判断平台缺口。缺少后插件主要用途无法成立的能力标为核心；只影响装饰、动画、性能或次要便利性的能力标为非核心。

## 5. 安全和许可证

- 静态阅读前不运行安装脚本、构建脚本、插件代码或未知二进制。
- 不输出源码中的密钥、令牌、私有地址和用户数据。
- 许可证允许转换时，保留要求的版权和许可声明；不兼容或无许可证时，不复制实现和素材。
- 索引宣传、README 与固定版本源码不一致时，记录差异并以源码和可执行测试为准。
