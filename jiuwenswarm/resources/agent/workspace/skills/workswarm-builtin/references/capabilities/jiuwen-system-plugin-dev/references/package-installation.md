# 系统插件安装与状态核对

单域系统插件通过已有 `bash` 工具调用 Swarm 的 `extension` 命令。
组合包先按 [组合包安装说明](bundle-development.md#3-安装与验收) 核对入口，当前终端 CLI 不支持时，不照搬本页的单域命令或伪造根 domain。
运行中的 Swarm 自动提供当前实例的本机管理连接，用户无需在提问中提供端口、会话 ID 或认证信息。

开发前可以查询安装状态，用来定位已有系统插件和确定版本；安装、重载等写操作按用户意愿执行。
是否需要提问按 [主流程第 5.1 节](../SKILL.md#51-确认是否安装) 判断；用户不安装时，交付开发结果即可，不进入安装或界面效果确认。
本文命令供智能体调用终端工具使用；README 和最终答复中的用户维护步骤使用 `/extension`，写法见 [用户维护命令](package-writing.md#2-写清安装和验证步骤)。

## 1. 选择命令入口

| 当前运行方式 | 使用的入口 |
| --- | --- |
| 源码、Wheel | 虚拟环境已有的 `jiuwenswarm extension` |
| EXE、DMG | `JIUWENSWARM_EXECUTABLE` 指向的现有后端程序，后接 `extension` |

工具名 `bash` 表示终端执行能力，不要求每台机器都使用 POSIX Bash。
Windows 可选择 PowerShell；工具支持时显式设置 `shell_type: "powershell"`，直接传 PowerShell 语句，不再套一层 `powershell -Command`。按当前终端语法引用程序路径，保留路径中的空格。

源码、Wheel 示例：

```text
jiuwenswarm extension install "<最终 ZIP 路径>" --json
jiuwenswarm extension query "<package_id>" --json
```

桌面包使用 PowerShell 时：

```powershell
& $env:JIUWENSWARM_EXECUTABLE extension install "<最终 ZIP 路径>" --json
```

桌面包使用 Bash 时：

```bash
"$JIUWENSWARM_EXECUTABLE" extension install "<最终 ZIP 路径>" --json
```

选择入口时注意：

- **桌面程序：** 使用运行环境给出的后端路径，不猜 APP 名称，不另找系统 Python，也不新增通用 CLI 启动器。
- **可用性：** 已知入口时直接 query；只有命令或参数不识别时再查看 `extension --help`，不把查帮助作为每次必做步骤。
- **环境边界：** 内部 agent 的终端继承当前宿主环境；外部独立终端和远程沙箱不一定有相同的运行上下文。

## 2. 确认当前实例和文件

| 检查项 | 要求 |
| --- | --- |
| 安装目标 | 使用当前任务所在的 Swarm 实例，不扫描端口或改连其它实例 |
| 管理授权 | 由宿主生成并校验本机管理访问密钥；不读取或展示内部连接变量与密钥 |
| 系统插件的归属 | install 从 `manifest.json` 的 `package.domain` 确定；只能为 `agentserver` 或 `gateway` |
| ZIP 文件 | 运行服务可以读取同一份最终 ZIP；本机路径不能直接当作远程沙箱路径 |

- **影响范围：** 安装影响目标宿主进程的扩展能力，不只影响当前对话。
- **自动连接：** CLI 读取宿主提供的连接上下文或当前实例确定的运行记录，不要求用户填写连接参数。
- **连接缺失：** 返回 `HOST_UNAVAILABLE` 时说明宿主未启动、版本不支持或终端未获得运行上下文；保留已完成的源码和 ZIP，不另写客户端或搜索凭据。
- **沙箱场景：** 本机通道不负责沙箱网络和文件映射。需要已有、已授权的传输能力；缺少时如实记录，不能把打包完成写成安装完成。

### 2.1 定位安装目录和已有版本

按目标 ID 查询；已知 domain 时一并指定，避免查询无关宿主。使用第 1 节确认的入口：

```text
jiuwenswarm extension query "<package_id>" --domain agentserver --json
```

- **修改起点：** 从 `state.active` 中取该 ID 的 `version` 和 `root`；没有活动版本时，查看 `state.installed_packages` 中该 ID 的 `version`、`domain` 和 `install_path`，根据用户要求确定目标。安装副本包含源码时直接复制使用，不再寻找原开发目录。
- **版本范围：** 只核对当前宿主返回的该 ID 的安装记录；需要读取 manifest 时，只读这些记录给出的目录。不扫描历史会话、工作区、下载目录，也不从记忆补出一个“旧版本”。用户明确提供的源码或版本另行核对。
- **没有记录：** 查询成功且没有该 ID 时，新开发按首次版本处理；用户要求修改已有插件时，说明未安装，请用户提供源码、ZIP 或准确 ID。查询失败不当作空记录；已有完整源码和执行环境时，仍可独立开发打包，并说明尚未核对安装冲突。
- **目录来源：** 安装根由宿主配置决定，CLI 已返回实际路径；不拼接用户家目录，也不把 `extension_pkgs` 的默认位置写死。运行副本不在当前环境可读范围时，说明具体缺口，不改查其他人的目录。

## 3. 安装最终 ZIP

先完成最终 ZIP 的隔离加载与效果测试，再安装同一份文件。
CLI 按以下步骤执行：

1. 读取根目录 manifest，取得 ID、版本和 domain，计算本地 SHA-256，不导入系统插件代码。
2. 连接对应宿主，先查询该系统插件。同 ID、不同版本交给宿主多版本机制安装；同版本已有副本时拒绝，不自动卸载或覆盖。
3. 发送一次安装请求，保留宿主原始 Report。
4. 取得成功报告后再次查询，核对 ID、版本、generation 和安装目录。
5. 输出 JSON 和退出码。安装成功后由宿主通知现有页面，实际业务效果另行验证。

这些步骤由 CLI 内部完成。成功结果已包含 `state`、目标版本和目录核对，直接检查即可，不再为同一结果额外执行一遍 query；只有结果缺失、失败或用户要求重新查询时才补查。

若最终 ZIP 已通过已有方式放到宿主另一位置，可使用 `--server-path "<宿主 ZIP 绝对路径>"`。
命令不上传文件；输出的 `zip_sha256` 只代表本地最终 ZIP，不能据此声称服务端核对了同一摘要。

## 4. 查询、重载和卸载

以下示例使用源码、Wheel 入口；桌面包替换命令前缀，参数不变：

```text
jiuwenswarm extension query "<package_id>" --json
jiuwenswarm extension reload "<package_id>" --json
jiuwenswarm extension uninstall "<package_id>" --json
```

Gateway 系统插件的后续操作增加 `--domain gateway`，例如：

```text
jiuwenswarm extension query "<package_id>" --domain gateway --json
```

- **查询：** 按 ID 查询实际安装与活动记录；未指定 domain 时由当前 CLI 自动判断归属，不带 ID 时查询可用宿主。需要限定范围时使用 `--domain`，不把查询失败展示成空列表。
- **重载：** 读取已安装副本。修改源目录或 ZIP 后，不会自动更新安装副本。
- **正式升级：** 上一轮已经确认或交付结束后再修改，在源码副本中递增版本、测试并生成新 ZIP，然后 install。新版本成功安装后由宿主切换启用状态，旧版目录保留；同 ID 不同时运行多个版本。启动恢复还会遵循启用状态，不能只按目录里的最大版本号推断。核对目标版本的 active 记录及实际目录，不能只看 installed。
- **验收内调整：** 只在尚未结束的用户效果确认循环中，保持版本不变，将已测试的修改同步到当前活动安装副本并 reload。不要重新 install 同版本，也不卸载重装。
- **失败核对：** 新版本安装失败时，核对旧活动版本是否保留及失败副本是否清理；不擅自改写启用状态。操作报告或版本、目录核验失败时，先解决差异，不能将 query 成功视为安装成功。
- **版本目录：** 例如 `1.0.0` 升级到 `1.0.1`，安装区应保留各自的版本目录和 manifest。禁止将 `1.0.1` 写入 `1.0.0` 目录，也不能把临时备份当作宿主已安装的旧版本。路径以实际安装报告为准，不写死用户数据目录。
- **旧入口：** 若运行中的旧 CLI 仍拒绝同 ID 的新版本，说明具体版本限制，保留新 ZIP，并提供已有 Web `/extension install` 入口；不得借 reload 改旧版本号来绕过限制，不把人工安装说明写成自动安装完成。
- **未知结果：** 超时、断连或报告不明确时只核对状态，不重复发送写请求。

## 5. 读取结果并验证效果

| 字段 | 含义 |
| --- | --- |
| `status` / `ok` | 本次命令的总体结果 |
| `domain` | 实际选择的宿主 |
| `operation_status` | 原始管理操作的结果 |
| `verification_status` | 操作后的状态核对结果 |
| `reports` | 宿主原始报告 |
| `state` / `before_state` | 操作后的查询状态与操作前状态，不能混用 |
| `install_path` | 当前生效副本的实际安装目录；须与目标版本及 manifest 一致 |
| `ui_notified` | 宿主是否已发出页面更新通知，不是浏览器显示回执。reload 的通知也可能由生命周期回调发出，不能因返回值没带此字段就断定没有通知 |
| `business_verification` | CLI 固定为 `not_run`，业务效果由后续验证确认 |

| 退出码 | 含义 | 后续处理 |
| --- | --- | --- |
| 0 | 查询成功，或写操作和状态核对均成功 | 按系统插件的要求验证业务效果 |
| 1 | 已确认失败，或成功报告与当前状态不符 | 阅读报告，处理具体原因 |
| 2 | 输入、连接上下文或写入前检查失败 | 处理缺口，不宣称已安装 |
| 3 | 写操作结果或后续状态尚未确认 | 保留原结果，仅查询，不重复写入 |

安装后使用原有业务入口验证需求。带界面的系统插件检查现有槽位与页面，依赖业务事件的 Handler 等下一次正常操作触发。
安装、目标版本核对和页面更新链路无已知失败后，通过提问工具让用户确认效果；不启动或查找浏览器代替用户确认。已打开的页面应自动更新，无变化时先查通知、`ui.ready` 和渲染结果，不能把手动刷新作为默认步骤。确认循环中提出的修改保持版本不变，同步活动安装副本并 reload，再次提问直到用户确认。
