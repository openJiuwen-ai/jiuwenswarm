# MCP 工具调用内部取消被误传为业务请求取消

## 元信息

| 项 | 值 |
|---|---|
| 日期 | 2026-10-28 |
| 严重程度 | 高：工具传输故障可能中断业务请求 |
| 范围 | mcp_call_timeout_patch.py，SSE / Streamable HTTP |
| 测试基线 | Python 3.11 / 3.12 各 380 项相关回归通过 |
| 关联 spec | S_09_mcp-integration.md，N7 |

## 现象与根因

PR #9175 整体复核发现，生命周期修复后 `_invoke_with_cleanup` 无条件传播
CancelledError。底层单次 I/O 自行抛出取消时，没有收到 cancel 请求的业务调用者
也会被取消，绕过 MCPTool.invoke 的普通异常处理。发现阶段和 worker 初始化的
取消隔离没有覆盖这个调用阶段入口。

## 决策

- 单次 I/O 取消时检查当前等待任务的取消计数。真实外部取消仍在所属任务清理后传播。
- 内部取消清理成功后映射为专用 RuntimeError 子类，复用既有一次重连重试分支。
  第二次内部取消返回普通工具错误，不无限重试；行为仍是 at-least-once。
- 清理失败返回普通清理错误并保留不可复用状态，不重连。清理期间新增的真实取消
  优先传播，不被内部错误分类覆盖。
- ToolMgr 两种传输、池化 worker 和发现都沿用同一 call_tool/list_tools 类方法补丁；
  唯一安装入口仍为 interface_deep。未改变 owner 分配、连接及工具调用超时。

## 拒绝的方案

不将所有 CancelledError 都转换为普通异常，否则用户取消和超时会失效；不在清理
失败后强制重连，也不把清理移动到后台任务。使用异常类型区分可重试的内部取消，
避免通过伪造死会话错误文本触发重试。

## 验证

修复前新增及调整的 11 项核心断言失败。修复后新增 14 项测试，覆盖双传输的
call_tool/list_tools 一次及持续内部取消、worker 后续调用恢复、清理失败阻止重连、
内部取消清理期间发生外部取消。既有重复取消、超时、任务归属、后台任务及取消回调
收敛检查继续通过。模拟内存传输使用真实 AnyIO TaskGroup，不依赖外网或凭据。
