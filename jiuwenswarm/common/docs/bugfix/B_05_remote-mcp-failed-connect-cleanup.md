# HTTP 建连失败后的等待者取消打断 owner 清理并阻止重连

## 元信息

| 项 | 值 |
|---|---|
| 日期 | 2026-10-29 |
| 严重程度 | 中：清理被打断后客户端无法再次连接 |
| 范围 | mcp_call_timeout_patch.py，ToolMgr Streamable HTTP |
| 测试基线 | Python 3.11 / 3.12 各 386 项相关回归通过 |
| 关联 spec | S_09_mcp-integration.md，N7 |

## 现象与根因

建连超时后，owner 先向调用者的 future 发布异常，再在 finally 中关闭连接。
`_StreamableHttpOwner.submit` 的异常分支直接 await owner；此时调用者被取消，
取消会传入正在执行上下文退出的 owner。owner 结束后残留 session/client 引用，
后续连接被 previous owner cleanup incomplete 检查拒绝。

原有取消处理保护的是等待操作结果的分支，没有保护已经收到操作失败、正在等待
清理结束的分支。单次取消、重复取消以及 AnyIO 外层取消均可复现。

## 决策

- 建连/断开失败后使用 shield 等待既有 owner，不迁移上下文或重新执行关闭。
- 等待者真实取消时，复用有界清理等待，使用进入该异常分支时记录的截止时间；
  不再次取消正在清理的 owner，清理结束后继续传播调用者取消。
- 预算耗尽后才取消 owner，并有界收尾；失败标记为不可复用并记录日志。
- owner 自身取消不能伪装为调用者取消，保留原操作异常并报告清理失败。
- 同构检查：此分支同时覆盖 connect/disconnect 失败；原有操作中取消分支、SSE
  owner 包装及 pooled worker 不变，共用清理 helper 的预算语义不变。

## 拒绝的方案

不再次 cancel 正在清理的 owner，不跨任务补做 aclose，不清空失败资源句柄以绕过
重连检查；不无限 shield，也不吞掉真实外部取消。

## 验证

新增 6 项回归：无外部取消时保留建连超时；单次、重复、AnyIO 外层取消后原 owner
完成清理，并验证同一客户端重连及工具调用成功；清理预算耗尽后有界返回并拒绝复用；
owner 自身取消保留原操作错误。前三种外部取消场景在修复前失败，修复后通过。

真实 SDK 客户端配合模拟内存传输与真实 AnyIO TaskGroup，检查进入/退出任务一致、
session 及后台任务结束、清理后取消回调不再增长。全部测试离线运行。

## 已知遗留

底层协程拒绝响应取消时，仍只能有界结束等待并报告清理失败，不能强制保证资源释放。
本次不涉及尚未证明与该问题直接相关的模型断流或专家团长耗时。
