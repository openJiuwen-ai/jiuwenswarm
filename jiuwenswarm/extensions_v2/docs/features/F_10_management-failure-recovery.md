## 1. 问题与范围

失败报告和没有报告的异常必须分开。Core 已处理候选失败，Swarm 不再手动拼 Plan 触发回滚；
但管理事件可能在实际操作完成后由外层抛错，此时不能向调用方声称“什么都没发生”。

本项补充后端响应及集成验证，不实现恢复上一发布版本、继续未完成 Plan 或 Core 资源管理。
Web `/extension` 复用这些结果，不增加新的恢复操作；命令接入见 [F_09](F_09_backend-management-requests.md)。

## 2. 处理顺序

1. 取得 Report：原样返回成功或失败，不补查，不重复安装、重载或回滚。
2. 写请求抛出普通异常：保留错误码和诊断，调用门面 `query` 一次读取当前事实。
3. 查询成功：响应仍为失败且 `outcome=unknown`，附 `state`；查询不能补发原 Report，也不能证明本次操作成功。
4. 查询失败：保留原错误，附 `query_error`，不返回伪造的空状态。
5. 取消继续传播，不在被取消的请求里自动恢复或重放。后续获准请求可以独立查询。

批量安装异常无法保证已识别全部来源包，因此查询全部事实；单包卸载、重载只查询目标包。
查询请求本身失败不再递归查询。

Web 对失败 Report 显示包 ID、错误码与原因；对 `outcome=unknown` 或网络超时显示“结果未确认”，
提示 `/extension query` 核对。后端附带的查询事实仅作为当前状态展示，不改成操作成功，不自动重放命令。
Gateway 完整传递失败 payload；核对查询失败时展示 `query_error`，不展示为空状态。

## 3. 关键决策与排除方案

- 失败候选交给 Core，宿主不调用 Runtime 私有方法，不自行撤销新旧 Handler。
- 只有没有报告时查询；拒绝“每次失败都查询”，与 V5 保持一致。
- 不将查询到的 generation 转成成功报告，避免把当前事实误当作本次回执。

## 4. 实施与验证

独立的 `query_after_error` 只依赖门面，可在没有网络适配器时调用；适配器仅负责将查询结果编码到响应。
门面返回类型保持不变。已取得 Report 但响应编码失败时，不将其当作没有 Report，也不补查。
测试通过真实 Core 模拟发布失败，检查回滚执行、旧 Handler 保留及安装副本边界；
另用受控异常模拟操作后丢失 Report、查询失败和取消，检查没有重复操作。
入口：`tests/unit_tests/extensions_v2/management/test_management_recovery.py`。

## 5. 结论与遗留

2026-10-23 执行 `test_management_recovery.py`，11 项通过，覆盖 Core 回滚、结果未知、取消、查询及编码失败。
Core 当前查询不提供可续做 Plan 和完整回滚残留记录，本项不承诺自动续清理。
