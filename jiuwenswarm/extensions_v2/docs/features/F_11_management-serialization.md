## 1. 为什么改

门面原来要求调用方串行执行写操作，但多个后端请求可以同时到达，安装与卸载可能在 Core 子事件的等待点交错。
将同一门面的写入顺序放在门面内部维护，调用方不再需要自行协调同一实例。

## 2. 设计与边界

`ExtensionManager` 持有一把 `asyncio.Lock`。初始化、安装、启动加载、卸载、重载和停机在锁内完成包状态修改，
任何异常或取消都通过上下文管理器释放锁。查询和普通业务事件不取这把锁，查询只代表当前可确认事实。
锁不跨进程，不向 Core 子事件传递；同一调用只进入一次根方法，避免父子事件重新争用根锁。

包退出通知在锁外执行，卸载通知可以查询或发起另一项管理请求；停机全部成功后门面已回到未初始化状态。
通知抛错仍沿用原有记录日志的行为。初始化被取消时，解除本次 Core 绑定，后续使用新 Bus 重新初始化。
排队期间取消的请求不会进入 Core；已经执行的操作被取消后，不据此认定副作用已撤销。

## 3. 关键决策与排除方案

- 不在 Gateway 加锁，避免不同来源绕开协调，也不把用户状态放到传输层。
- 不修改 Core 事件调度或添加业务 Handler；只保证经同一门面的根写操作互斥。
- 不锁住整个 Handler 执行链，普通业务仍可按 Core 契约与重载并行。

## 4. 实施与验证

只调整门面及其规约。用可控制的异步操作验证安装与重载不重叠、排队取消、异常后继续执行，
并由卸载回调发起下一次安装，证明不会发生锁重入等待。
入口：`tests/unit_tests/extensions_v2/management/test_management_serialization.py`。

## 5. 结论与遗留

2026-10-23 执行 `test_management_serialization.py`，7 项通过，覆盖根操作互斥、排队及初始化取消、异常释放和通知重入。
经 `manager.registry` 直接调用 Core 会绕过门面锁；产品请求必须走门面公开方法。
