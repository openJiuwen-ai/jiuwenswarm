## 1. 现有问题

门面原来按依赖包在前的顺序撤销，Core 会拒绝移除仍被依赖的包；随后门面仍清空 Registry，
并通知宿主清理未成功撤销的包。装配层也提前丢掉单例，失败后无法再查询原运行实例。

## 2. 正确的关闭顺序

1. 调用方停止新业务入口，并等待自身业务退出；门面不提供业务 drain。
2. 门面逐层选择没有剩余依赖方的包，先用 `Runtime.uninstall_decision` 检查，再调用公开 `unpublish`。
3. 忙、被依赖或撤销抛错的包保留当前 Core 记录；继续尝试独立包。只为确认撤销成功的包发送退出通知。
4. 仍有失败时保留门面与装配实例，通知完成后抛出 `ExtensionFailure`，由调用方核对后重试关闭。
5. 全部撤销成功才 `unbind_context(bus)` 并重置门面；不删除安装副本。随后清理剩余 WebUI 视图并释放装配单例。

同一 Bus 的 Ops 不重复 Build。重新装配产品运行时创建新的 Bus，
不能把已构建 Bus 再交给 `Registry.init` 重复初始化。

## 3. 关键决策与排除方案

- 不通过正常卸载事件停机，因为正常卸载会删除安装副本。
- 不在 Core 外调用私有发布或清理方法，也不在撤销失败后猜测如何恢复 Handler。
- 不把单个失败吞掉并报告整体成功；保留原运行实例比建立一套空 Registry 更便于核对。
- 不补做在途自动计数或旧模块回收。本项只遵守 Core 当前公开判断结果。

## 4. 验证

验证依赖链的逆序、独立包继续撤销、BUSY 保留 Handler 和通知边界、撤销异常后的查询与重试、
成功时上下文解绑和安装副本保留，以及装配层失败时不提前清空单例。
入口：`tests/unit_tests/extensions_v2/management/test_management_shutdown.py`。

## 5. 结论与遗留

2026-10-23 执行 `test_management_shutdown.py`，6 项通过，包括装配失败保留与视图清理重试。
Core 的判断只覆盖已登记的在途计数，不据此认定产品调用跟踪已经完成。
