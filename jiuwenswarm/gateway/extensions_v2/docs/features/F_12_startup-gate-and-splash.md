## 2. 背景、目标与范围

### 2.1 背景与问题

V1 壁纸引擎在页面加载后注入开场动画，主页会先露出一帧；开场时长、跳过与卡死处理全由插件自行实现。
V2 由宿主等待开场插件就绪，主页不先于开场出现（概览中的目标 A），宿主负责时机、时限、跳过与结束通知。

另外，请求策略插件（如登录示例）在登录前拒绝其他包的 `webui.dispatch`，背景与开场在登录前无法取得 `ui.ready`。

### 2.2 目标与关键场景

| 场景 | 预期行为 |
| --- | --- |
| 未安装开场插件 | 中性层一闪即逝，直接进入界面 |
| 安装壁纸插件且本次启动首次打开 | 中性层后播放开场，结束后进入登录入口或工作界面 |
| 多个开场插件 | 依次播放；外观提供者在前 |
| 用户长按空格 | 可跳过的开场立即结束，进入下一个 |
| 插件卡死或不响应 | 按时限结束，不阻塞进入界面 |
| 刷新页面、断线重连 | 不再播放 |
| 安装了登录插件 | 背景与开场在登录前正常工作 |

### 2.3 本次范围与非目标

范围：声明、提供者查询、`application.splash`、平台帧、`ui.closed`、候选提示、启动标识、前端门控与队列、跳过。

非目标：首帧即显示主题（目标 B，已推迟）；开场顺序与停用的设置（GW-12）；全局音频。

## 3. 设计约束、假设与待决问题

- Electron 在静态服务就绪后即加载前端，此时 Gateway 可能尚未启动；首帧不能依赖 Gateway。
- agent-core 的 `ActivationReport` 没有警告字段；超过 60 秒的声明只能记录日志并截断，安装报告中的提示待 agent-core 支持。
- 无待决问题。

## 4. 总体方案与设计取舍

### 4.1 方案概览

`index.html` 自带中性层，首帧即显示。前端启动后读取 `app_web` 的候选提示与启动标识决定是否等待；
需要时经 WebSocket 查询提供者，按顺序发送定向 `ui.ready`，提供者以 `ops.ui.render` 渲染 `application.splash`
表示播放。宿主控制就绪、心跳、上限与跳过，结束后先本地关闭再通知 `ui.closed`。队列结束后移除中性层，开放界面与登录入口。

### 4.2 关键决策

#### D-01 显示型槽位的生命周期帧作为平台帧

背景与开场的 `ui.ready` / `ui.closed` 以及提供者查询不进入 `gateway.request`。它们不携带用户输入，由包自己的 Handler
决定显示内容，与素材路由同样属于平台通道。若仍经请求策略，登录插件会在登录前拒绝它们，背景与开场无法工作。
其他 `webui.dispatch`（入口、侧栏底部及其交互）的策略语义不变。

#### D-02 回执说明是否进入播放

Handler 返回后由 Gateway 检查该包在此连接上是否有开场实例，回执为 `playing` 或 `skipped`。前端无需区分清除帧与未渲染，
也不等待迟到的异步渲染；准备时限只覆盖回执本身。

#### D-03 候选提示由 `app_web` 本地提供

2026-11-07 修订（PR #10763 检视）：提示原先由 `app_web` 自行读取 `config.yaml`、按字符串扫描 manifest，前端收到“无候选”后直接结束门控，一个非权威的判断实际上能挡住应播放的开场。现在提示由 Gateway 的 `installed_splash_providers()` 按同一套配置、manifest 规则与开场偏好计算，`app_web` 只调用它；提示仍在本地应答，因为冷启动时页面可能早于 Gateway 就绪。前端在“无候选”时先开放门控，连接后仍向 Gateway 复核，列表非空则播放。曾考虑把提示改由 Gateway HTTP 应答、`app_web` 转发，但冷启动时 Gateway 尚未就绪，提示会失败，桌面端冷启动的开场会被跳过，因此未采用。

首帧时 Gateway 可能尚未就绪，而 `app_web` 已在服务页面。提示接口只做 manifest 文本扫描，不导入扩展运行时，
避免拖慢静态服务；开发模式没有该接口时按“未知”处理，短时查询。

#### D-04 启动标识与完成记录

Electron 主进程生成的标识覆盖一次启动内的所有窗口；完成记录放在本地存储，刷新与新窗口不重播。浏览器模式降级为会话级标识。

2026-11-07 修订（PR #10763 第二轮检视）：浏览器的标识在每个标签页的会话存储里各不相同，完成记录却是本地存储中的单一值，
后完成开场的标签页会覆盖前一个的记录，前一个标签页刷新时重新播放开场。现在完成记录与标识放在同一作用域：浏览器写入标签页的会话存储，
桌面端仍写本地存储（同一次启动的各窗口共享同一标识，写入的值相同；下次启动的新标识使旧记录失效），`launch.ts` 与 `index.html`
的首帧脚本按同一规则读取。曾考虑在本地存储中按标识保存多条记录，但需要另定条数上限与淘汰规则，而标签页关闭后它的标识也随会话存储消失，
记录没有保留的意义，因此未采用。回归用例 `each browser tab keeps its own splash completion through reloads` 在修复前失败、修复后通过；
`desktop windows of one start share the completion and a new start plays again` 修复前后都通过，确认桌面端语义不变。

2026-11-07 第三轮修订（检视收敛，用户批准）：提示为“无候选”时，门控开放后不再补播开场。原先连接后向 Gateway 复核，
列表非空就依次播放，会在用户已经开始操作时盖上开场。现在复核结果只更新首帧提示，下次启动据此显示中性层并等待；
提示已按 Gateway 的规则计算，两者只会在提示与连接之间恰好安装了开场插件时不一致。

#### D-05 门控期间的输入与登录入口

门控期间 `#root` 设为 `inert`，开场层挂在 `#root` 之外；登录入口的模态对话框推迟到门控开放后再显示，
因为模态对话框位于浏览器顶层，任何层级都无法遮挡。

#### D-06 时限全部有界、不设总上限

准备 5 秒、媒体就绪 10 秒、心跳 5 秒、单个开场不超过 60 秒；等待连接 30 秒（有提示）或 3 秒（未知）。
正常播放不会被截断，异常情况都能进入界面。

### 4.3 替代方案与排除理由

| 方案 | 排除理由 |
| --- | --- |
| R-01 请求策略插件自行放行背景与开场 | 每个登录类插件都要知道其他插件的槽位，组合关系脆弱 |
| R-02 在 `index.html` 中注入提示 | 需要改写静态文件响应；提示接口更独立，开发模式也能降级 |
| R-03 由 Gateway 推送开场 | 首帧时 Gateway 可能不可用，且推送无法与门控的时机对齐 |
| R-04 队列总上限 | 会截断正常的多段开场，与已确认的“不截断”原则冲突 |

## 9. 风险与已知遗留

### 9.2 已知遗留

- 安装报告中缺少超时声明的提示（agent-core `ActivationReport` 无警告字段），目前只记录日志。
- 开场顺序与停用设置待 GW-12；`disabled`、`removed` 原因届时启用。（2026-11-05 已由 GW-12 实现，见 [F_13](F_13_application-settings-page.md)。）
- 开场期间断线后重连，运行时会向当前提供者重发 `ui.ready`；服务端已随断线丢弃开场实例，随后的 `ui.closed` 会被拒绝。
- 桌面打包版（Electron）联调待真实插件完成后进行。（2026-11-06：Electron 开发模式已验证，见 V-10；打包版与 Windows 交由打包团队。）
