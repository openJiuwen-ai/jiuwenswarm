# jiuwenmate/docs

本目录记录 `jiuwenswarm.server.jiuwenmate` 的服务端设计、接口契约与特性变更。
本文规定文档组织、内容分工、开发中的设计确认与同步，以及特性计划和进度维护；
具体设计写入对应文档，不写入本 `AGENTS.md`。
当前行为以源码、测试和实际运行证据核实；目标设计与已实现行为须明确区分，未执行的验证不能写成已通过。

## 目录用途

| 目录 | 用途 | 何时创建或更新 |
| --- | --- | --- |
| `designs/` | 设计概览、详细架构、开发计划，以及备选方案和待确认问题；各文档按内容分工维护 | 总体目标、架构、范围或开发安排变化时 |
| `specs/` | 按主题维护接口、状态、边界与不变量；拟议契约必须标明状态，定稿后维护当前已确认契约 | 新主题形成时按需创建，关联契约变化时同步修订 |
| `features/` | 一次完整特性或重构的具体方案、实施影响、决策与验证记录 | 开发前建档，开发中补充，落地后归档并保留历史决策 |
| `templates/` | 本目录各类文档的编写与维护模板 | 编写或修改相关文档前阅读，模板规范变化时维护 |

不为未来主题预建空白 spec 或 feature 文件。已有拟议规约按其状态和实际范围维护，
不因文档已建立就视为契约已确认、接口已实现或功能已验收。

## 范围与跨仓边界

- 本目录维护 JiuwenMate 服务端的业务身份、配置发布、渠道接入、会话排队与执行权、
  业务事实提交、结果投递、授权、查询及长期作业等职责；涉及页面时记录其与服务端契约的交互边界。
- Persistent Agent 的通用执行能力在 `agent-core` 仓维护，包括宿主指定 Session 内的执行、
  调用状态隔离、上下文组装、活动窗口与归档、历史检索、资产访问及恢复现场重建。
  相关设计引用对端[文档约定](../../../../../agent-core/openjiuwen/harness/persistent_agent/docs/AGENTS.md)
  及对应设计或规约，不在本目录复制其内部实现方案。
- PersonalContext 的采集与发布实现归属 `agent-core/openjiuwen/harness/personal_context/`；
  本目录维护服务端知识来源、授权、学习作业和发布交接等责任，不代替对端定义通用能力。
- 跨仓接口写清双方输入、输出、确认依据和约束，标明对端仓库及文档或代码路径。
  不复制 Harness 的 DeepAgent、Rail、工具和工作空间通用规约；公共契约变化时同步其归属文档。

## 内容分工

| 文档 | 主要维护内容 | Overview 中的处理方式 |
| --- | --- | --- |
| Overview | 目标、范围、职责、核心模型、事实权威、关键流程和设计原则 | 完整说明概览层面的结论 |
| 详细架构设计 | 系统边界、模块职责、依赖关系、逻辑状态、数据归属及跨模块约束 | 概述关键结论并链接对应章节 |
| `specs/` | 可核验的接口、状态、边界和不变量；拟议与已确认契约分别标明 | 使用一致术语并引用契约来源，不复制完整定义 |
| `features/` | 具体特性方案、接口 Schema、数据结构、算法与提交步骤、源码修改点、交互及验证记录 | 保留关联入口，不在概览展开实施细节 |
| 开发计划 | 特性拆分、验收场景、依赖、开发顺序、负责人、状态和交付证据 | 引用权威计划，不维护第二份进度或验收清单 |

新增或迁移内容时，按上述分工确定归属。概览可以说明“能力开放须满足哪些保证”以及阶段目标，
但完整验收矩阵、测试步骤和阶段进度应在对应计划、feature 或验证记录中维护。
没有独立计划时也须指定唯一维护位置，不在多份文档重复维护同一张台账。

`specs/` 维护契约，`features/` 解释具体方案和契约变化原因；
`designs/` 中的概览、架构与计划分别维护总体认识、跨模块约束和交付安排。
方案成熟度、开发状态与验证结论分别表达，不能用“设计定稿”代替“实现完成”。

## 命名与归档

```text
specs/S_NN_<slug>.md
features/F_NN_<slug>.md
designs/<slug>.md
```

- `S_NN` 使用两位递增序号，按目录现有最大编号加一，不复用已有编号。
- `F_NN` 与所属开发计划条目 `JM-xx` 的编号相同，例如 JM-10 的特性设计文档为 `F_10_<slug>.md`；尚未建档的条目编号保留给对应条目，不由其他特性占用。
- `<slug>` 使用简短英文小写单词，以短横线连接；文件名不带日期，日期写在文档元信息中。
  保留现有概览、架构和开发计划的文件名，备选方案使用描述性文件名，不占用 spec 或 feature 编号。
- 同一开发计划条目需要多份特性设计文档时，在编号后追加子序号，例如 `F_10_02_<slug>.md`；首份文档不加子序号。
  feature 元信息列出关联计划条目，计划条目链接对应 feature；一份方案覆盖多个条目时写清各自范围。
- 一项连贯的特性或重构维护一份 feature，不按提交次数拆分。
  延续原特性的修复或补充在原文档按日期记录；独立变更新增 feature 并与原文档互相链接。
- 归档时补齐实际范围、设计决策、验证结论及遗留，记录归档日期并保留建档日期。
  历史决策和旧验证证据保留其适用范围，不作为当前状态或新增行为已通过验证的证明。

## 开发流程与契约同步

### 特性设计先于实现

- 开发特性前，先在 `features/` 新增或修改对应的特性设计文档，写清本次实现的范围和设计，
  再按该设计开展代码开发。
- 尚未实现的内容明确标为待实现；开发过程中补充实际决策、方案调整和验证结果。
  计划中的验证、模拟验证、真实联调及实际验收分别记录，不把预期结果写成已通过。

### 架构设计变更与 spec 同步

- 代码实现过程中若需要调整[JiuwenMate 服务端架构设计](designs/jiuwenmate-architecture.md)，
  先向开发者说明拟修改的设计内容、原因和对当前特性的影响，取得确认后再修改架构设计文档，
  并按确认后的方案实现。未经确认，不擅自改写架构设计文档。
- 定稿的接口契约同步到对应 spec。开发过程中若改变了 spec 所描述的接口、状态、
  不变量或其他契约，及时更新对应规约，并用 feature 记录变化原因、实施影响和验证证据；
  新主题按需建档，关联索引和开发计划中的范围、依赖及验收关系同步核对。
- 拟议契约、已确认契约与已实现行为分别说明状态和适用范围；局部实现或验证通过不能代表整份规约已生效。
- 阅读文档时发现描述与源码、测试或运行证据不一致，先核对事实并记录差异。
  过时的实现描述及时修正；涉及架构设计调整时遵循上述确认流程，不能把意外实现自动认定为新的架构。

## 特性计划与进度维护

本模块的特性计划、开发顺序与进度跟踪统一维护在
[JiuwenMate 开发计划](designs/jiuwenmate-development-plan.md)。
该文档尚未建立时，在首次登记或认领特性时建立。

- 新增特性时，及时补充特性条目、开工硬前置、所属并行工作线与交付节点，
  并同步特性总数和进度信息。
- 认领特性时，在对应条目的“负责人”列登记；开始开发时更新“状态”。
  开发、阻塞、验证和完成的进度变化，及时更新“状态”“证据”、相关交付节点及变更记录。
  “状态”“负责人”“证据”分别使用独立列。
- feature 可保留负责人、状态等便于阅读的管理字段，必须链接对应计划条目，
  与计划中的字段含义、当前值和适用范围一致；进度变化时在同一次更新中核对两处。
- feature 承载技术验证记录和设计演进，计划引用其证据；不另建独立的排期、完成率或验收台账。
  文档写完、PR 合并或本仓组件通过测试本身不等于整项交付完成，跨仓交付按实际责任和联合验证判断。

## 引用与一致性检查

- 文档间优先使用相对路径链接；引用跨仓内容时标明仓库和路径，避免仅凭同名模块定位。
- 维护后核对链接、文件编号、关联计划条目、章节引用和术语，确保正文、图表及相关契约的语义一致。
- 核对目标设计与实现状态、验证摘要与实际证据、feature 管理字段与开发计划是否一致。
  新增或变化的契约同步规约，必要的范围与依赖变化同步索引和计划。
- 本文件补充 JiuwenMate 文档规则；代码、测试和文档提交遵循适用的上级及仓库约定，
  不在此另行定义提交顺序或 scope。
