## 2. 背景、目标与范围

团队版员工目前没有权限模式字段，运行时也没有把个人版的权限策略绑定到员工发布版本。目标是在员工详情中提供“默认、智能审批、完全访问”三种模式，保存后通过发布生效，并由服务端按该员工固定的 Spec 执行。

本特性包含员工设置读写与发布快照、智能审批与人工确认回退、Web 和飞书确认、审批持久化与重启恢复、完全访问工作区授权和中英文界面。本特性不修改个人版全局权限、不扩大服务进程 OS 用户本身的权限，也不引入容器或新的 OS 沙箱。

| 场景 | 当前行为 | 目标行为 |
| --- | --- | --- |
| 配置员工权限 | 仅有默认执行能力 | 每名员工独立选择模式；仅发布后影响新 Request |
| 工具需要人工批准 | 现有暂停和恢复原语未接入团队审批路由 | 默认模式将工具调用暂停，原 Request 可经可信渠道批准或拒绝 |
| 智能审批不确定 | 没有员工级审核 | 复用当前审核策略；不确定、超时或失败转人工确认 |
| 完全访问 | 读写限制在员工办公目录 | 明确确认并发布后，可访问服务 OS 用户有权访问的主机文件并运行联网命令 |

## 3. 设计约束、假设与待决问题

- 每名员工独立保存权限模式；旧设置缺失字段时按 `default` 读取，未知值拒绝。
- 请求接受时固定 Spec 和路由身份。设置发布后仅新 Request 使用新版本。
- 自动审核复用个人版当前有效的权限配置和审核模型，发布时冻结策略；缺省审核超时 60 秒、最低置信度 0.7，未配置模型时沿用当前解析缺省 `gpt-4`。
- 人工审批超时 15 分钟，超时按拒绝处理。审批期间同一 Session 不派发后续 Request。
- core 持久化工具中断现场；JiuwenMate 持久化审批状态、截止时间和可信 Request 路由。重启后两侧状态必须匹配才能恢复。
- `full_access` 是服务进程 OS 权限边界内的宿主级访问；同一账户可读的其他员工数据、配置和凭据可能暴露，页面必须明确提示并要求确认。

## 4. 总体方案与设计取舍

### 4.1 方案概览

员工详情保存 `permission_profile` 草稿；发布服务把模式及有效权限策略写入不可变 Persistent Agent Spec 并参与指纹。core 使用该快照构造本次 Execution 的权限 Rail 和文件访问范围。需要人工决定时，core 发出带工具调用 ID 的暂停事件并保存 Session 现场；JiuwenMate 保存审批路由并通过原始 Web 或飞书渠道请求确认，验证后用相同 Spec 恢复同一 Request。

### 4.2 关键决策

#### D-01 员工级快照

- 选择与依据：设置挂在 `ColleagueSettings`，随发布版本固定在 Spec；个人版的进程级 `config.set` 不作为团队运行时状态。
- 代价与成立条件：修改审核配置后需要重新发布员工，旧 Request 不切换策略。

#### D-02 智能审核是单次调用授权

- 选择与依据：只对策略判为 `ask` 的精确调用执行审核；通过仅允许对应工具调用一次。
- 代价与成立条件：审核缺证据、低置信、异常或超时转人工确认；审核结果不记为员工长期白名单。

#### D-03 完全访问受宿主 OS 身份限制

- 选择与依据：由已发布 `full_access` Spec 扩展 workspace 读写根范围，并保留执行身份绑定；Bash 使用服务宿主现有能力。
- 代价与成立条件：该 OS 身份能访问的其他员工目录和凭据也可被读写；界面风险确认不能替代部署隔离。

#### D-04 人工审批由 core 与宿主分层持久化

- 选择与依据：core Session 状态保存原生中断现场；JiuwenMate 保存 `Request`、`Execution`、员工、渠道、发起人和审批截止时间。
- 代价与成立条件：任意一侧状态缺失、过期或不匹配均失败关闭，不重放工具。

### 4.3 替代方案与排除理由

| 候选 | 拒绝原因 |
| --- | --- |
| 只增加员工页面按钮并沿用全局 config | 显示值和实际执行值会互相覆盖，不能满足员工隔离 |
| 仅支持工作区内“完全访问” | 不符合用户确认的个人版宿主文件访问范围 |
| 只实现自动批准，不接人工回退和重启恢复 | 低置信或审核失败时无法安全继续，无法形成可用闭环 |

## 5. 详细设计

### 5.1 模式与执行语义

| 模式 | 文件范围 | 工具决策 |
| --- | --- | --- |
| `default` | 员工办公目录与既有已授权目录 | 按发布时的默认策略执行；`ask` 调用等待人工确认 |
| `automatic` | 与 `default` 相同 | 仅在安全且高置信时批准当前调用一次；其余进入人工确认 |
| `full_access` | 服务 OS 用户可访问的主机路径 | 停用工具确认约束并允许联网命令；OS 权限拒绝仍生效 |

### 5.2 设置、发布和身份

`ColleagueSettings` 和管理 API 增加 `permission_profile`。读取旧记录时缺省 `default`。保存只写草稿；发布时校验模式，冻结有效策略并计入 Spec fingerprint。`RequestRecord` 已固定版本，后续编辑不会改变旧 Request。客户端不能提交员工、Session、渠道或主机路径来变更审批绑定。

### 5.3 审批生命周期

core 对 `ask` 工具调用保存原生中断状态，暂停事件只暴露工具名与脱敏且有界的参数摘要。JiuwenMate 创建 15 分钟审批记录，并通知 Request 原始发起人。批准、拒绝均通过已认证来源提交，服务端绑定工具调用 ID 并校验尚未过期和尚未处理；拒绝、超时、重复或错配回复不执行工具。重启后只有审批记录与 core 中断现场一致时，才恢复原 Request 和原 Spec。

### 5.4 完全访问

只有发布后的 `full_access` Spec 可以请求主机级 workspace scope。core 继续校验 Agent、Session、principal、policy revision 与 Execution 绑定。员工页面始终显示该模式和风险说明；切换到其他模式并发布后，新 Request 收窄访问。

### 5.5 前端

员工详情增加权限设置区，提供三种模式说明、保存状态和完全访问风险确认；继续使用现有员工设置保存/发布链路。中英文案一致，并提供稳定 `data-testid`。

### 5.6 飞书与钉钉的审批回复（2026-10-26 修订）

本次修订已获用户确认，实施与自动化验证结果见第 7 节；真实渠道验收待完成。钉钉原实现仅发送审批通知，没有消费审批回复，导致批准消息作为新 Request 排队并被旧审批阻塞。

两渠道统一在普通请求入队前解析控制消息，继续使用原有持久化审批与 core 确认恢复。查询和决定同时绑定 namespace、Agent、发起人、渠道、接收应用及目标会话。只有一条待审批且仅含一次工具调用时，允许回复“批准”；“拒绝”在唯一审批下拒绝该批全部调用。多个调用时给出每条完整命令，沿用当前契约：批准选中的一次调用，其余调用拒绝，文案明确说明。

审批消息按平台消息 ID 持久绑定首次选中的审批；无待审批或多条记录无法选定时也持久记录未受理结果，重推不能批准之后的新中断。格式错误、占位符、过期、重复和身份错配都有明确反馈，不能进入普通请求队列。普通业务消息在等待审批时保留排队，并提醒先处理原任务；其他群成员仅收到不含审批详情的等待提示。“同意”“同意这个方案……”属于普通业务输入，审批别名“同意”须带明确审批 ID。发布完全访问配置不隐式批准旧操作。

本次不新增交互卡片或第三方 OAuth 授权流程，不自动重放旧命令。与单独为钉钉复制解析器相比，公共处理器保持身份校验和错误反馈一致；与直接放行等待中的操作相比，显式确认保留原 Request 固定的权限边界。

## 8. 风险与已知遗留

- 完全访问会扩大到同一服务账户下可达的其他员工目录与配置；不能替代每名员工独立 OS 身份隔离。
- 真实飞书卡片动作和重启后恢复需在可用 Feishu 应用环境验收；单元测试通过不代表真实渠道验收。

## 9. Agent 接力的审批主体与反馈（2026-10-30）

用户已批准本方案并要求在当前仓实施；代码与验证状态在本节更新。

任务的执行主体不变，另在 Request 的宿主记录冻结 permission_origin：原始人类发起人、原 Agent、原 Request 与原渠道路由。接力来源仅从同一命名空间内已送达的群消息、宿主保存的输出和请求关联核实；来源消息 ID、群、平台及明确目标 Agent 均须匹配。消息正文宣称的发起人不作为依据。多次接力保留最初来源；来源缺失、歧义或外部 Bot 发起时，不创建可由群成员或 Bot 批准的审批路由，并将本次待确认工具调用按拒绝处理。

审批记录区分执行 agent_id 和接收审批的 approver_agent_id。有可信人类来源时，通过原应用、原群发审批，原提问者从该应用回复；通过宿主将决定交给实际执行请求。不得用目标应用下的 open_id 比较原应用身份，不合并不同应用的用户。当前有效绑定和入站身份校验继续执行，不更改 access、能力范围及业务回复目的地。

找不到可信来源时暂不提供所有者 Web 私聊回退；待确认工具调用按拒绝处理。Web 只记录其原有渠道请求决定，不运行 IM 任务。跨群业务审批继续走原有专用路径，普通工具审批不能放行来源数据。

审批查询、决定和消息去重按审批接收 Agent、渠道、应用、会话和人类身份绑定；被批准的仍是原执行 Request 的精确工具调用。通知说明实际执行员工，拒绝、过期及错误均有反馈。反馈幂等键使用稳定 UUID，不把过长内部键直接传给飞书。

兼容：旧 Request 缺省新增字段；原有直接人类任务行为不变。既有已决审批不改写、不自动批准或重放。没有可验证来源的 Bot 接力请求按拒绝处理；不猜测审批人，也不提供回退审批。

验证：可信单次及多次接力、跨应用原身份、错误人／应用／群／Agent、伪造正文、缺失来源拒绝、重启与去重、跨群审批隔离及真实 SDK 请求中的 UUID。6 个审批相关测试文件共 63 项通过；真实平台待用户联调。
