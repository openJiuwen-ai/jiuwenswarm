# skill_turbo/docs

`jiuwenswarm.server.runtime.skill_turbo` 模块的设计归档目录。代码看 `git log` / 模块
`AGENTS.md`，本目录只承载**长期设计规约文档**——specs。结构规约、命名与提交约定见本文。

## 目录用途

| 目录 | 用途 | 关联触发 |
|---|---|---|
| `specs/` | 模块设计规约：不变量、接口契约、执行路径全景、异常边界 case 清单、修改检查单。**长期有效**，描述"系统现在是什么样、改代码前必须知道什么"。 | 任何**模块设计规约变动**（契约 / 不变量 / 执行路径 / 事件协议 / 持久化结构变化）都必须同步修订对应 spec；新规约主题 = 新 spec 文件 |
| `features/` | 特性变更归档：一次完整设计/重构/新特性的来龙去脉（决策 + 拒绝的方案）。**只增不删**，描述"为什么这么改"。当前暂无；首次特性变更时建立。 | 每次特性更新提交代码前归档 `F_NN_<slug>.md`；归档日期写进文档元信息 |

`specs/` 是状态快照（描述当前），`features/` 是变更日志（描述过程）。spec 改动通常对应一份
feature 文档解释"为什么改成这样"。

## 命名规约

```
specs/    S_NN_<slug>.md    例：S_06_hitl-interrupt-resume.md
features/ F_NN_<slug>.md    例：F_01_xxx.md
```

- 前缀 `S_` / `F_` 表明文档类型，grep / IDE 列表可视识别
- `NN` 是两位**递增序号**，目录内已有 N 份文档时新文档编号 `N+1`；不复用、不回填空缺
- `<slug>` 短横线分隔的英文小写 slug，描述主题
- 文件名末尾不带日期——日期写在文档元信息表里

不允许：序号跳号（features 不允许删除）、大写字母、下划线（`_` 仅用于前缀分隔）、空格、
未带 `S_` / `F_` 前缀的散落 markdown。

## specs 内容约定（本模块特有骨架）

本模块的 specs 承担"修改前必读的全面说明书"职责，除标准骨架外强制包含三个特色章节
（缺任何一个等于没归档）：

```markdown
# <Spec 名称>

## 元信息
| 项 | 值 |
|---|---|
| 类型 | spec |
| 编号 / slug | S_NN / <slug> |
| 关联模块 | jiuwenswarm/server/runtime/skill_turbo/<path> |
| 最近一次修订日期 | <YYYY-MM-DD> |
| 关联 feature | F_NN_<slug>.md（暂无时写"暂无"） |

## 范围 / 边界
（本规约管什么、不管什么→指向其它 spec）

## 不变量
（N1、N2… 编号，每条可判定；点名数量的句子是契约的一部分）

## 接口契约
（关键签名 / 参数语义 / 错误语义）

## 数据结构
（状态字段 / 谁写谁读 / 何时清理——含持久化键与生命周期）

## 执行路径全景
（P1、P2… 编号路径，逐步标注 文件+方法名；这是"改哪些路径才算改全"的依据）

## 异常分支与退出路径
（退出路径编号表 / 异常分型矩阵 / 违反后果）

## 边界 case 清单
（表格式：场景 / 现行为 / 风险 / 测试覆盖）

## 修改检查单
（"改 X → 必须连带检查 Y" 格式；HITL / 事件流类改动附全场景矩阵要求）

## 与其它 spec 的关系
```

### specs 间的引用与分工

- 跨 spec 引用一律写 `[[S_NN]]`（上下文明确时），不复制对方内容——单一真相源。
- spec 内不变量用 `N1`/`N2` 编号（各 spec 独立编号），供 code review 单条引用；
  模块 `AGENTS.md` 的"架构铁律"从各 spec 不变量中提炼，铁律条目回链 `[[S_NN]]`。
- 退出路径统一使用 `E1`~`E13` 编号（定义在 [[S_01]]），事件类型 / 缓冲约束统一以
  [[S_08]] 为准，HITL 路径统一以 [[S_06]] 为准——其它 spec 引用这些编号，不另立编号体系。

## 提交约定

涉及本目录文档（`S_*` / `F_*`）更新的特性改动，**特性代码、测试代码、文档拆成三个连续提交**：

1. **提交 1 — 特性代码**：`feat(skill_turbo): <实现>`（或 `fix` / `refactor` 等对应 type）。
2. **提交 2 — 测试代码**：本次新增 / 改动的单测，`test(skill_turbo): ...`。
3. **提交 3 — 文档**：本次涉及的 `specs/S_NN_*.md` 修订与 `features/F_NN_*.md` 新增，
   `docs(skill_turbo): ...`。

三个提交必须**连续紧邻**，在同一工作单元 / PR 内落地。bugfix 若触及 spec 描述的执行路径 /
不变量，同样遵守三连续提交（`fix` / `test` / `docs`）。

## 与其它 AGENTS.md 的关系

- `jiuwenswarm/server/runtime/skill_turbo/AGENTS.md`：模块入口索引 + 公开 API + 架构铁律 +
  **本目录的归档强制约束**
- 本 `docs/AGENTS.md`：只讲归档结构与命名规约，**不重复模块设计内容**——内容写在对应
  `S_*` / `F_*` 文档里
- 技能侧仓 `<skill>/turbo/TURBO_CODE_SPEC.md`：**技能侧** turbo code
  的规范（目录 / import / 修改规则），与本文档体系正交互补；jiuwenswarm 侧 spec 不复制其
  内容，需要时引用

## 反模式

- **把 commit message 复制粘贴当 feature 归档**：feature 要写 commit 写不下的东西（拒绝的
  方案、设计思路、follow-up）
- **靠 docs 维护代码行为**：实现行为是代码 + 单测的事；specs 描述契约 / 路径 / 检查项，
  不是 source of truth
- **契约改了 spec 不改**：执行路径 / 不变量 / 事件协议 / 持久化结构变了但对应 spec 没改，
  下次读 spec 的人（或 agent）会被误导——提交前自查
- **在元信息里写 commit hash**：只写日期（`YYYY-MM-DD`）
- **spec 里堆砌问题故事**：specs 写"系统现在是什么样 + 改动必须检查什么"；变更缘由归
  feature 文档
- **一次连贯设计拆成 N 份小文档**：一次设计变动归档一份
