# 最简全双工接入

本次按用户要求收缩为：快模型路由 + 原 SDK steer / 暂停恢复。

## 当前行为

- APPEND：直接调用原 Jiuwen steer，在下一次原有慢模型调用前注入，不取消当前计算，不额外增加执行轮次。
- INTERRUPT：通过 SDK supervisor 校验当前执行位置，调用原暂停，再作废旧计划并结合新消息重新规划。模型阶段取消生成、保留当前 ctx；工具阶段沿用 SDK 等待工具完成。
- 快模型调用失败、超时、返回非法内容或状态已过期：退回原 steer，不重判。
- 未开启、空闲、非 Native、非普通消息：原 Jiuwen 路径。

## 已移除

独立持久化收件箱、工具执行账本、进程崩溃恢复、浏览器动作收据、`update_working_intent` 工具、状态发布 rail、消息合批重判、额外 steering 队列，以及 APPEND 后自行补 continuation 的逻辑。

对应实现文件 `duplex_inbox.py`、`duplex_ledger.py`、`duplex_state.py`、`duplex_controller.py` 和 `duplex_browser_checkpoint.py` 已删除，评测入口也不再引用这些机制。旧机制专用测试随功能移除；保留并更新原消息投递和执行行为的回归。

进一步删除 `ShadowObserver` 客户端外壳、无来源的摘要字段、独立投递版本计数器，以及要求快模型回传状态编号的协议。快模型现在只返回 `{"action":"APPEND"}` 或 `{"action":"INTERRUPT"}`；过期校验留在本地，复用 SDK `seq_counter`。

## 最小适配边界

- 消息接收、排队和已读确认继续由 SDK 管理。路由随原投递调用执行，投递完成后才返回；没有额外后台收件任务或“先持久接受再投递”。快模型等待因此仍在这条消息的投递路径上，慢模型计算继续。
- SDK 没有内部打断并注入的组合接口，保留 supervisor 内的最小连接代码。显式用户暂停 / 停止优先，防止被内部恢复覆盖。
- 不再每次模型调用前额外复制 ctx。内部 INTERRUPT 跳过暂停回滚，直接保留已接纳的原任务、补充消息和完整工具结果；未完成的模型回复尚未写入 ctx。
- 仅内部 INTERRUPT 不提交 `[Request cancelled by user]`；显式用户暂停、取消仍用 SDK 原处理。SDK 自带的轮次 / 迭代边界快照保留。
- 保留一次应用前校验和同实例消息 ID 去重，以免旧判断打断新状态或已读确认重试重复投递。没有跨进程恢复保证。
- APPEND 的最终调用时序完全沿用 SDK，不再自行增加最后一轮。

## 2026-09-15：安全点开销与复用核查（移除前）

以下是新增快照仍存在时的测量记录；当前实现已移除这份模型调用前快照。

本机 Python 3.12，调用真实 SDK `capture_snapshot`、上下文和任务状态，使用模拟消息及已缓存的运行状态，不包含模型请求或环境启动。20 个计划项时，100 / 1,000 / 10,000 条消息的单次保存中位耗时约为 0.03 / 0.04 / 0.20 毫秒，一份安全点新增内存约为 7 / 15 / 85 KiB。正文共享引用，不是完整深复制；更大的任务计划仍会增加状态序列化开销。

连续覆盖 1,000 次后只保留一份最新快照；清除引用并 GC 后该快照被回收。SDK 还单独持有轮次开始和外层边界快照，因此不能将“一个最新快照”说成整个 Agent 始终只有一个快照。共享消息若仍被快照引用，也会继续存活。

评估了“消息与序列化状态相同就复用上一份”的保守方案。在 1,000 条消息、20 个计划项下，直接保存约 0.039 毫秒，复用核对约 0.042 毫秒；10,000 条消息时分别约 0.202 / 0.212 毫秒。本次未测出收益，未采用该方案，也未修改运行代码。不能只凭消息数量或有无新输入跳过保存，因为任务状态、上下文替换和模型异常恢复也可能改变恢复位置。
