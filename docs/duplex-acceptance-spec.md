## 4. 必须实现的契约

### R0：先核对 SDK，再决定新增机制

新增队列、轮询、存储、超时、重试或全局包装前，必须记录：现有 SDK 对应能力及调用位置、实际缺口、复用方案、新增部分的唯一职责、如何验证原目标没有退化。找不到扩展接口时明确提出最小接口改造，不把全局 monkey patch 包装成现成扩展接口。

具体参数必须能追溯到协议约束、模型预算、用户要求或负载验证。仅改为可配置不算取得依据。删除参数也不能把有界处理改成无界积压、无限等待或无限重试。

测试先于实现冻结目标：不能通过删除“新消息打断旧判断”“生命周期不被模型阻塞”等断言，使缩水实现重新变绿。功能目标变更必须单独说明，不能混在删除重复代码中。

### R1：一条输入主链

A2A 必须经过：原消息 DB → EventBus/Poll 唤醒 → 未读读取 → 接收侧控制器 → Native supervisor → 原投递确认。

U2A 经过原用户输入入口并进入同一个控制器；必须保留稳定 message_id 和可恢复的接受记录。两种输入不得各自维护另一套慢 Agent 历史或恢复逻辑。

任务生命周期内每个 Native 只有一个输入控制器、一个权威会话；正常模型调用之间不得重建 Native。supervisor 负责串行应用状态变更，控制器只组织输入和分类。

### R2：持续接收、有界分类

- 慢模型生成、工具执行、旧快模型分类期间都能登记新消息；接收入口不得持锁等待模型返回。
- 新消息到达时取消尚未应用的旧分类，按权威顺序合并未处理消息，使用新快照重判。取消后的迟到结果必须失效。
- 分类期限优先沿用现有模型客户端/任务的期限并计算剩余预算；需要独立路由时限时，给出需求依据及测量。重算不能无限延长最早消息的等待时间；不规定拍脑袋的默认秒数，也不接受直接取消总期限。
- 背压和积压优先由现有 DB / 队列机制承担；控制器仅持有处理所需批次。不规定额外“默认 32 条”。若确需独立容量，说明资源模型、容量作用域及满载行为并验证；未接收消息保持可重试，不得静默丢失。模型输入按实际 token 预算构造，保留完整持久化原文；不得按任意字符数静默截掉关键约束。
- 已进入 supervisor 的应用事务不能被普通新消息拆散；新消息进入下一批。stop / abort 等生命周期命令可以取代该事务。
- 原 HTML 明确要求分类失败/超时退回现有 steer：分别记录“分类未决”和“实际采用原 steer”，不把降级标成模型判断 APPEND 成功，也不声称 steer 能确保安全。确定性的取消和审批控制走原规则通道，不等待快模型。若要改成失败留未读，必须单独评审重试期限、队头阻塞和可用性变化，不能当作删除数字顺带修改。

分别记录接收等待、分类、请求取消、工具安全等待和恢复耗时；配置期限不等于远端计算必然停止。

### R3：摘要有来源，未知就写未知

Control Snapshot 至少包含会话标识、context_version、round_id、checkpoint_id、执行阶段、goal、constraints、current_hypothesis、next_action，以及当前工具状态。

- 模型调用前、工具结果提交后、消息/目标采纳后、恢复后，由运行时发布对应版本的快照。
- 每个语义字段保留来源事件或计划版本、更新时间。最近已提交假设可保留，但必须标识其版本；没有新证据不能把时间戳刷新当作内容刷新。
- goal / constraints 来自已采纳任务状态；假设与下一动作来自已提交计划或显式 Working Intent。缺失字段标记 unknown，不读取隐藏思维、半截生成或猜测模型意图。
- 模型工具可以补充语义摘要，不能成为发布机制的唯一触发器。快模型每次调用无长期对话状态，不共享慢模型 KV。

### R4：追加与恢复语义

- APPEND 不取消正在运行的模型/工具；按顺序在下一次模型调用前纳入消息。最后一次生成期间到达的消息也必须安排后续处理。
- INTERRUPT 应用前，在 supervisor 中再次校验会话、轮次、版本和检查点；过期结果重算，预算耗尽则追加。旧结果不能打断新的任务。
- 模型阶段：取消当前请求，丢弃未提交输出及不完整 tool call，从调用前最近一致检查点继续。
- 工具阶段：未开始的调用可撤销；已开始的工具默认等待结果并提交。只有工具声明可取消且能确认无副作用，才允许取消后重试。
- 恢复必须保留原任务、已采纳约束、已完成工具结果及全部未消费消息；只有新消息明确修改的目标/约束才能替换冲突项。
- stop / abort 优先。被停止任务不得因迟到分类或工具回调自动复活。

### R5：消息确认和工具账本

区分三件事：接收入队、提交到权威上下文、首次按新要求行动。日志分别记录，不能都叫 ACK。

- 消息只有在可恢复地接受后才允许原 DB 标记已读。重复事件、DB ACK 失败重投、广播重读必须去重；广播水位不能越过尚未成功交付的消息。
- 持久化工具调用记录至少含 logical_call_id、任务/会话、参数摘要、幂等键、执行状态、结果或外部回执、关联检查点。状态至少为 prepared / running / committed / failed / unknown。
- 已提交结果恢复后直接复用；参数摘要不能单独当幂等键，因为相同参数可能是两次合法操作。重试同一逻辑调用必须复用原幂等键。
- 外部操作成功但本地落账前进程崩溃：有外部查询/幂等支持则核对并恢复；否则标记 unknown 并暂停该操作的自动重试。禁止宣称任意工具都能 exactly-once。
- 账本优先扩展现有存储，不新造第二份任务真相。要证明检查点、消息接受和工具提交的恢复顺序；仅增加 JSON 文件或内存字典不算通过。

### R6：评测使用同一执行链

- AgentRadio 保留原任务、角色、协作流程、消息正文与评分。Jiuwen 被测组的消息必须实际写入 Jiuwen DB 并从生产入口消费；Coral 如作桥接，需保留双向 ID 映射且禁止直接旁路调用 receive。
- InterruptBench 每个任务保持同一 Native 会话跨动作运行；官方轨迹、网页状态、动作结果必须与 Native 提交边界对齐。浏览器执行可在独立进程，但必须通过同一工具提交/恢复契约。
- 官方 step 边界模式与“生成中注入”扩展分别标记。不得把官方 step 边界实验描述成验证了任意生成阶段抢占。
- 固定任务/数据/评分器版本、模型、采样参数、工具和环境快照。无答案、rubric 或预期路由标签进入模型输入。
- A2A 自然消息会随策略变化；完整实验如实保留。若另做固定消息回放，单列结果，不能声称自然运行的每条消息完全相同。

### R7：对照和结论

| 名称 | 实际语义 |
| --- | --- |
| serial | 当前轮结束后处理消息 |
| steer | 当前 Jiuwen 增量处理 |
| always_interrupt | 每条消息均触发安全打断；与 model 共享恢复实现和账本 |
| model | 快模型选择 APPEND / INTERRUPT，安全点恢复 |
| abort_restart | 额外基线：丢弃执行上下文后从头处理，保留不可撤销外部状态，明确报告重复工作 |

上游 official / L2 / L3 可作参考；当模型和运行时不同，不能据此单独归因于快路由。

报告必须含任务成功率、变更采纳、首个符合变更的动作延迟、总工期、快慢模型与恢复总成本、重复副作用和失败明细。首次正确动作须由任务验收规则或预先冻结的标注判定；没有判定器则记未测。取消请求的未返回 usage 记缺失，不当零，不用字符数冒充 token。

净收益是实验结果，不是开发承诺。先冻结任务清单、重复次数（至少 3）、策略、超时及统计方法，再跑分。失败和超时保留在分母；任务配对统计报告区间。质量下降则不达发布门槛；差异证据不足写“尚不能证明收益”，不能用“预计更快”补齐。

| ID | 条件与触发 | 必须观察到 |

## 6. 开发顺序和完成定义

1. 固定当前稳定提交、锁文件和验证基线；保存当前未提交工作。先补能暴露上述偏差的验收用例，再修改对应链路。
2. 完成 R1–R5 和 T01–T12。SDK 私有接口适配集中管理，固定依赖版本；未满足入口契约不得静默报告 active 已启用。新增 EventBus 包装、预取循环必须覆盖并发及关闭行为。
3. 用一个真实 A2A 场景、一个真实 U2A 多动作场景证明主链闭环，再接正式公开任务。环境缺失记录具体失败命令和缺项；不通过换通信/生命周期语义来掩盖接入失败。
4. 冻结评测清单，先做每条轨道原题小样本接线验收，再完成冻结清单。小样本成功只能称接线通过。
5. 图、代码、规范按相同术语更新；图上每条关键边都对应调用位置和 trace。PlantUML 能渲染仅证明图的语法。

每个验收项必须记录：需求 ID、提交 SHA（及脏工作区差异）、SDK SHA、测试命令、退出码、产物路径、实际结果和剩余限制。建议产物为 `manifest.json`、逐事件 `trace.jsonl`、测试报告、官方逐题结果及汇总；均不得包含密钥。

状态只使用：未做 / 已实现未验证 / 验证通过 / 验证失败 / 外部条件阻塞。整体验收由必需项逐项通过决定，禁止用“测试共 N 项通过”“代码已接上”“已部署”“图已完成”代替。

只有主链和故障契约通过，才能称“Native POC 完成”；只有冻结评测清单全部给出可追踪结果，才能称“评测完成”；只有质量与成本、时延结果支持，才能称“有净收益”。这三个结论必须分开报告。
