## 具体问题

1. **执行 Agent 解析表格的逻辑出错。** 它先将 C 列所有非空文本视作标题，数据行中的批次号也进入该分支，后面的数字行判断永远执行不到。重放原始只读命令：退出码为 0，但数据统计为空。它随后继续查表，而没有尽早写方案。
2. **看护过滤过粗。** 当前规则把“没有修改 final/ 且命令返回 0”全部跳过，所以漏掉了上述逻辑错误。该命令不是有用的正常检查，但看护未收到它。
3. **错误真实，不代表这次必须打断。** TypeError 已经作为工具结果交给执行 Agent。路由的 next_action 却只有刚结束的失败命令，没有证据说明它仍在坚持错误方案。此次将重复提醒升级为全计划失效，必要性未得到验证。
4. **无效沟通占了一轮。** `office-model.log:191` 记录了 SendMessage 的“Thanks for catching…”；接线把该消息直接拦截返回，看护不会因此开展新工作。生成这条消息耗时 10.11 秒。通用提示仍鼓励交流，而 live-review 提示要求不发确认消息，工具也仍然可调用。

打断后的文本仍正确列出了“日期排序、按 DATE/REF 汇总、TOTAL、保存文件”等原要求，没有任务丢失的迹象。暂停到下一轮模型启动约 **6 毫秒**；主要损耗是取消生成、再次生成和无效确认，不是安全点保存很慢。两组累计模型请求时间分别 **176.89 / 175.26 秒**，Bash 执行仅 **2.63 / 4.38 秒**，时间用在了不同的模型输出上。

普通组 174 秒收到的“应按金额排序”也是看护误报，但它发生在普通组，**不是全双工组本次无产物的原因**。普通组当时已有正确文件，截止时尚未按错误意见改写；不能据此认为它在更长时间下仍会保持正确。

## 对比边界与修正方向

两组输入 SHA256 相同，任务、角色、提示和预算相同，但模型生成路径不同，每组仅跑一次。此前 617.5 秒成功的三 Agent 版本使用 720 秒上限；本次改为执行 + 快速看护、180 秒上限，不能将前后差异全部归因于 A2A 路由。

优先修正：已返回给执行 Agent 的普通工具错误，缺乏“当前仍在沿用错误方案”的证据时应追加提醒；区分正在执行和已完成动作；让空解析、反复无进展进入有限复核；live-review 模式移除向被动看护发送确认消息的工具入口。比较打断收益需要从相同执行状态分支重放，单独改变 APPEND / INTERRUPT。
