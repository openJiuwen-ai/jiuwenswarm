# Team Organization 专家团与汇总配置

本文说明 JiuwenSwarm 如何把 AgentGroup 模板接入 Team Organization，以及共享 Summary Team 如何读取配置和交付结果。

首次测试建议先运行[使用指南](TeamOrganization使用指南.md)中的用例一：安装商业策划、技术洞察和代码架构设计三个已有专家团，从商业策划专家团进入 Owner Team，无需手动制作模板。本文 1.1、1.2 提供缺少合适模板时的手动配置材料，1.3 说明两种 Owner 入口和能力匹配规则；完整启动步骤、测试提示词与验收标准统一见使用指南。

---

## 一、AgentGroup 发现

JiuwenSwarm 通过现有专家团安装登记和包解析入口发现可用模板。资源包先通过广场安装为 built-in 包；只有满足以下条件的目录才会进入组织专家目录：

- 目录名是安全的单个名称，不包含路径分隔符。
- 存在可解析的 `manifest.json`。
- `package_type` 为 `agent_group`。
- manifest 的 `name` 与目录名完全一致。
- 安装登记为已安装，且 local 与 built-in 或 resources 中不存在同名冲突。
- AgentGroup 包可以被完整加载并通过模板校验。

目录扫描只返回模板描述，不创建 Team。`org_create_and_invite_expert_team` 被调用后，Launcher 才会装配并激活实例。

### 1.1 在 Web 中手动创建专家

先按[使用指南](TeamOrganization使用指南.md)初始化工作区、配置模型并启动 Web。已有合适且已安装的专家团时，直接使用即可。缺少模板时，进入专家管理界面，选择「手动创建 → 创建专家」。下一节提供投资初筛场景的负责人和成员材料；普通 Owner Team 用例只需准备法律、技术和市场三个受邀专家团，财务专家团为可选模板。

每个专家按以下方式填写：

- 「专家名称」填写表中的名称。
- 「能力介绍」填写表中的职责。
- 「专家人设」复制下面的通用人设，并将其中的名称和职责替换为表中对应内容。

```text
你是【专家名称】。你的职责是：【职责】。
遵守当前用户任务限定的公开资料范围、篇幅和交付要求。
仅依据实际访问到的资料形成判断，区分已确认事实、推断和待核验事项。
不要虚构营收、估值、客户数量、融资条款、用户访谈或安全结论。
作为成员时，接受本团负责人的任务并提交有来源依据的成果；没有新任务时等待通知。
作为负责人时，协调本团成员、检查证据并提交本团可验收的正式成果。
```

技能和连接器按实际需要选择，不要求为本用例添加不存在的技能或连接器；公开网页与代码文件访问能力须在运行环境中可用。完成后点击确认，并在「我的」中确认专家已安装，才能在组团时选为负责人或成员。不要直接拿包含独立 `AGENT.md` 的外部专家模板作为普通成员；手动创建的专家由系统生成所需文件。

### 1.2 通过界面手动配置专家团

首次使用先按[使用指南](TeamOrganization使用指南.md)同步依赖、初始化工作区、配置模型并启动 Web。专家团广场支持安装和使用已有模板；需要复现投资初筛用例且缺少对应模板时，可以按下面材料手动创建法律合规、技术尽调与 Coding、市场与商业三个专家团，不需要运行生成脚本或手写包目录。该用例由前端创建的普通 Owner Team 承担投资与财务职责，不要求安装财务专家团；财务模板材料保留供需要模板化主团队时参考。

先在「手动创建 → 创建专家」中建立各团的负责人和成员。填写「专家名称」「能力介绍」「专家人设」，确认创建成功并已安装。再切到「创建专家团」，填写「专家团名称」「能力介绍」「专家团介绍」，选择负责人、至少一名成员及领域标签，点击确认。创建成功后系统自动生成 AgentGroup 文件并完成安装登记；负责人不能同时被选为普通成员。

各领域专家团的负责人和成员建议如下：

| 专家团 | 负责人 | 成员 |
|--------|--------|------|
| 投资与财务专家团（可选） | 科技投资负责人 | 财务建模分析师、交易结构分析师 |
| 法律合规专家团 | 科技交易律师 | 开源与知识产权律师、数据隐私与 AI 合规律师 |
| 技术尽调与 Coding 专家团 | CTO 技术尽调负责人 | Rust Coding 审计工程师、AI 编辑器架构工程师、软件供应链与安全工程师 |
| 市场与商业专家团 | 开发者工具市场负责人 | 开发者客户研究员、竞争与 GTM 分析师 |

创建每个专家时，「能力介绍」可填写下面的职责；「专家人设」使用“你是〈专家名称〉。〈职责〉。仅使用实际访问的资料；缺失资料标为待核验，不虚构结论。收到工作后提交可验收的成果，遵守用户资料范围与篇幅要求。”，并替换名称和职责：

| 专家名称 | 职责 |
|----------|------|
| 科技投资负责人 | 协调领域分工、验收成果并向用户交付投资建议；负责整体事项，不提前结束，全部必需成果验收通过后再交独立团队汇总 |
| 财务建模分析师 | 识别投资前提及需要索取的财务材料，不编造财务数据 |
| 交易结构分析师 | 识别交易条件和下一轮尽调事项，不虚构融资条款 |
| 科技交易律师 | 协调法律合规分析并提交带公开来源的短意见，不作正式法律意见 |
| 开源与知识产权律师 | 核验官方许可证文本与知识产权风险 |
| 数据隐私与 AI 合规律师 | 分析公开隐私和 AI 合规信息，缺失合同与政策标为待核验 |
| CTO 技术尽调负责人 | 协调技术分析，区分已确认工程事实和待核验风险 |
| Rust Coding 审计工程师 | 实际查看 README、许可证与 Cargo.toml，给出文件路径依据 |
| AI 编辑器架构工程师 | 根据公开文件识别架构与 AI 功能的事实和不确定性 |
| 软件供应链与安全工程师 | 根据依赖和许可证信息识别风险，不声称完成安全审计 |
| 开发者工具市场负责人 | 协调市场分析并提交产品机会与商业不确定性 |
| 开发者客户研究员 | 从产品介绍识别目标用户及需求，不虚构用户访谈 |
| 竞争与 GTM 分析师 | 识别商业化前提和待核验事项，不扩展竞品调查 |

创建专家团时，「能力介绍」填写下面的团级职责；「专家团介绍」复制该职责，并追加：“遵守用户资料范围和篇幅；仅认领符合本团能力的任务；将交付物写入工作空间并提交结果；整体事项负责人收到完成通知后验收，全部必需成果通过后再汇总并展示最终正文；不反复轮询或催促，也不只回复正在等待。”

| 专家团 | 团级职责 | 建议添加的自定义领域标签 |
|--------|----------|------------------------|
| 投资与财务（可选） | 依据公司公开介绍形成投资前提、财务材料需求与交易风险判断，不虚构估值或营收 | finance、valuation、transaction |
| 法律合规 | 核验开源许可证、知识产权与隐私风险，区分许可证事实和待核验事项 | legal、compliance、privacy、ip、open_source_license |
| 技术尽调与 Coding | 实际查看公开代码仓关键文件，形成有路径依据的工程事实，不进行完整审计或构建 | coding、rust、technical_due_diligence、security、ai_platform |
| 市场与商业 | 仅依据公开产品介绍分析用户需求与商业机会，不虚构客户数量、收入或竞品融资 | market、customer_research、go_to_market、developer_tools |

每个自定义标签单独添加，不要把逗号分隔的整串内容作为一个标签。技能和推荐问题为可选项，本用例不要求额外安装技能或连接器；模型及基础网页访问能力仍按运行配置准备。Summary Team 由框架按需创建，不需要手动制作。

### 1.3 广场安装、标签与组织能力

在专家团广场安装职责合适的已有专家团即可准备模板，安装本身不会启动 Team。Owner 有两种入口：

- 从专家团广场进入：在选作主团队的专家团卡片上点击「使用」，进入新的 Team 会话并选中该模板；首次发送消息后装配运行实例，其 Leader 创建 Organization 后成为 Owner。
- 从前端创建普通 Team：在任务页面新建会话，选择「集群模式」（Team），不选择专家团模板；首次发送消息后按默认 Team 配置构建主团队，其 Leader 根据提示词创建 Organization 并担任 Owner。

两种入口使用相同的组织协作流程。其他专家团仅需安装，不必逐个点击「使用」，由 Owner 在当前 Organization 和 session 下按需创建独立运行实例并邀请入组；不会直接接管其他会话中已经运行的 Team。组织 Owner 和根任务负责人是不同概念，根任务需要明确认领；使用指南的两个用例均要求 Owner 创建并认领整体事项。

组织目录只返回已安装且可加载的模板，显示专家团名称、职责和可用于任务匹配的能力标识。未安装、已卸载或文件不可加载的模板不能被 Owner 创建。

标签到组织能力的规则如下：

- 模板存在显式 capabilities 时使用该字段，保持旧模板行为；显式空列表也不会被标签覆盖。
- 模板没有 capabilities 时，使用 tags：有 id 的取 id；旧本地化标签固定优先取中文文本，其次英文文本；字符串标签直接使用其文本。
- 前端新建专家团会保存预设标签的稳定 id，自定义标签以填写的文本作为 id，不随中英文界面切换变化。
- core 内部仍使用 capabilities 和 required_capabilities，不改数据库或任务工具参数。广场卡片中的 canUse 等操作权限不属于领域能力。

不要把“市场营销”和“market”假定为同一个标识，系统不做翻译或同义词匹配。Owner 应使用专家目录实际返回的能力创建任务；没有任何能力标签的模板可以作为普通 Team 使用，但不能承担本用例要求能力匹配的组织任务。广场模板若无标签，应选择有合适标签的模板，或按上一节手动创建。

手动创建的专家团默认位于用户工作区下 `.agent_teams/agent_groups/local/<实际包ID>/`；包 ID 由创建流程生成，不必与显示名称一致。随仓库提供的广场资源包安装到 `.agent_teams/agent_groups/built_in/<包ID>/`，不能把所有已安装模板都视为 local 包；具体目录由安装来源和包解析入口决定。设置了 `JIUWENSWARM_DATA_DIR` 时使用对应工作区。已创建的 Team 使用装配时的模板快照，改动模板或原始专家后不要假定已有运行实例自动更新，测试应新建会话。

## 二、专家 Team 配置继承

专家 Team 使用 AgentGroup 中的 Leader、预置成员、技能、提示词和 capabilities，同时从当前 JiuwenSwarm Team 配置继承运行底座，包括：

- 默认模型与模型路由。
- storage 和共享 `TeamDatabase`。
- transport 与 spawn mode。
- workspace 和系统操作能力。
- 当前 session 与 Organization 上下文。

同一个 AgentGroup 可以创建多个实例。运行时 `team_id` 由 Launcher 唯一生成，不能在提示词中把 AgentGroup 包名当作目标 `team_id`；创建后应通过 `org_view_organization` 读取真实 ID。

## 三、Summary Team

JiuwenSwarm 的 Summary Team 是一个固定的持久 Team：

| 成员 | 职责 |
|------|------|
| `summary-leader` | 校验来源、协调汇总并提交最终结果 |
| `source-integrator` | 把只读来源整理为带来源归属的结构化提纲 |
| `delivery-drafter` | 根据来源和提纲生成面向用户的最终稿 |

它使用默认 Team 模型，但不会复制用户 Team 的成员、工具或模板提示词。内部 transport 固定为 `inprocess`，成员使用 `build_mode`；中间稿写入自身 Team workspace，最终交付写入 Organization workspace 的 `summary/`。

每个 Organization 最多有一个共享 Summary Team。第一次创建 `SUMMARY_TEAM` execution 时懒加载，后续根任务复用；完成一次汇总不会立即停止它。

使用 `SUMMARY_TEAM` 时，汇总与最终交付按以下流程推进：

1. 根任务负责人先认领根任务，再设置 `SUMMARY_TEAM` 汇总模式，并创建绑定来源子任务的 Summary Execution；不是仅在用户提示词中声明模式就会自动创建汇总。
2. 作为汇总来源的子任务需要完成并通过验收。`COMPLETED` 但验收仍为 `PENDING` 时不能开始汇总；提前创建的汇总任务会等待来源就绪，根任务负责人仍需处理验收。
3. Summary Team 只读取绑定的来源快照，整理提纲和最终稿，不新增领域研究。两个成员交付提纲或稿件后结束各自内部任务，`summary-leader` 核验最终稿、摘要和交付路径后，通过 `org_summary_complete` 正式提交汇总结果。仅写出文件或口头回复“已完成”不算汇总完成。
4. 汇总完成后，根任务负责人继续处理最终交付；使用指南的两个用例均由 Owner 在当前会话展示报告正文并完成整体事项。

Summary Team 各角色继承默认 Team 对应角色的有限 `max_iterations` 预算；预算无效时使用 200，不会无限重试。达到预算上限或成员报错不等于汇总完成，应检查执行状态、已有稿件及失败日志，不能仅靠增加轮数代替正式提交结果。

## 四、配置建议

以下片段应合并到现有用户配置中，保留其他实验项、模型及 Team 设置：

```yaml
experimental:
  team_organization_ui_enabled: true

modes:
  team:
    jiuwen_team:
      lifecycle: persistent
      spawn_mode: inprocess
      teammate_mode: build_mode
      agents:
        leader: $agent_leader
      workspace:
        enabled: true
      transport:
        type: inprocess
      storage:
        type: sqlite
```

实验开关默认关闭，同时控制前端组织入口和新构建 Team 的后端组织能力。关闭或缺省时，新 Team 不挂载 `org_*` 工具，也不恢复组织绑定，普通 Team 协作不受影响。切换开关不会立即卸载已运行的组织；更改后需完整重启后端（包括常驻 Runtime Worker）并使用新 Team 会话，已有组织任务应先停止。具体操作见[使用指南的运行前配置](TeamOrganization使用指南.md#二运行前配置)。

运行建议：

- 当前 Organization 仅支持同进程协作，各 Team 共享同一 `TeamDatabase` 实例；更换 PostgreSQL 不会开启跨进程组织协作。
- 启用 Organization Workspace，并确保当前进程可以读写其本机目录。
- 确保默认 leader 和 teammate 模型均可解析。
- AgentGroup capabilities 使用稳定、小写、面向领域的标签，提示词中使用完全相同的值。
- 不要在配置中预启动每一个专家 Team；由 Owner Leader 按任务需要创建。

## 五、生命周期与故障处理

任务完成状态与 Web 执行状态分别收尾：后台组织 turn 结束后，前端关闭对应 Team 本轮的思考与流式输出，不影响其他 Team 正在执行的工作。仅接收消息的 `attach_only` 订阅不会使会话持续显示忙碌；真实任务执行及等待用户输入仍保留忙碌状态。判断汇总是否完成，应查看 Summary Execution 和任务状态，不能只依据某一段回复的 `chat.final`。

专家 Team 创建成功后会进入暂停待命状态，由 Organization 事件唤醒。若启动后入组失败，Launcher 会停止临时 Team。Summary Team 的创建状态与当前 Summary Execution 分开持久化；在开关开启、使用同一 session 和持久化 storage 并重新激活 Team 的前提下，进程重启后会恢复共享实例并重新检查来源是否就绪。

解散 Organization 后，组织临时创建的专家 Team 和共享 Summary Team 停止；Owner Team 保留，可继续聊天或重新组建组织。原本独立存在、后来受邀加入的普通 Team 只解除组织绑定。Web 团队选择器回到 Owner，不再提供已停止的临时专家 Team。解散不会卸载专家团模板，也不会删除历史消息和已写入的交付物，但会删除该组织的任务、验收及汇总执行等组织数据。

排障时重点查看：AgentGroup 扫描日志、专家/汇总 Launcher 日志、Organization 进度事件、Team runtime 状态，以及各 Team 是否持有同一个数据库实例。

## 导入包

导入在保存和安装前校验技能。`skills` 字符串项必须是技能名称，例如 `"docx-pro"`；目录映射使用包内相对路径，例如 `{"dir": "skills/docx-pro", "mode": "all"}`。拒绝 POSIX 和 Windows 绝对路径，包括上传至非 Windows 服务端的 Windows 路径。技能目录必须位于包内并包含 `SKILL.md`。
