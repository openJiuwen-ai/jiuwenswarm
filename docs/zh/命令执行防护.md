# 命令执行防护

这些边界为什么存在，以及一次线上事故暴露了什么缺失。

## 1. 事故经过

2026-08-02，用户连续三轮向 Agent 提问：最新提交的哈希、标题、日期。前两轮都正常回答。
第三轮模型生成了：

```
git log -1 --format=%ad --date=format:'%m月%d日'
```

在 Git for Windows 上这条命令会无限制分配内存：自定义 `format:` 路径进入
`strbuf_addftime`，C 运行时的 `strftime` 返回 0，Git 将 0 理解为「缓冲区太小」，
于是翻倍重试，直到 `xrealloc` 失败。单次调用达到约 8.5 GB 工作集、49 GB 私有内存。
该命令在 glibc 上是正确的（`git 2.43.0` 返回 `08月04日`），所以这是 Git for Windows
的缺陷，不是 JiuwenSwarm 的。

以下是属于 JiuwenSwarm 的部分。

工具返回了明确的失败——`success=False`、退出码 128、
`fatal: Out of memory, realloc failed`——而 Agent 又发出了同一条命令。
**2 分 34 秒内九次完全相同的调用**，其中八次以完全相同的字节完成，第九次由人工取消。
九轮之中模型没有输出任何文本。

运行时没有任何一层拦住它，也没有任何一层能来得及拦住。

## 2. 缺失了什么

**墙钟是唯一的边界，而且它是错误的维度。** `timeout_seconds` 默认 300 秒，但九次调用
每一次都**正常结束**了——它在大约 18 秒时以 OOM 失败返回。超时永远不会在一条已经结束的
命令上触发。即使是同类工具中最紧的默认值（Claude Code 在两分钟处终止 bash）也拦不住本次
事故，而整起事故总共只跑了 2 分 34 秒。

能拦住它的是限制**资源**而不是时钟。第 4 节说明为什么本次改动没有包含它。

**工具自己报告的失败对防护不可见。** 有几条路径返回的是裸字符串：

```python
return f"[ERROR]: command timed out after {timeout_seconds}s."
```

`ToolResultErrorDetector` 会把这种字符串判为「既不是成功也不是失败」，因此超时或被安全
检查拦截的命令不计入断路器的任何连续计数。只有真正执行并以非零码退出的命令才会被计入。

**没有任何检测器匹配这个特征。** 断路器的检测阶梯是：

| 规则 | 阈值 | 级别 |
| --- | --- | --- |
| `global_breaker`——无进展 | 30 | critical |
| `unknown_tool_repeat`——连续报错 | 10 | critical |
| `ping_pong`——两个工具交替 | 20 | critical |
| `generic_repeat`——**同工具、同入参** | 10 | **仅 warning** |

唯一匹配「相同调用、相同失败、反复出现」的规则在任何计数下都没有 critical 级别。
而 warning 只是 `logger.warning`——服务端日志里的一行，模型永远看不到，
因此无法改变下一轮的行为。

**断路器默认关闭**，这让上面所有阈值都失去意义：没有一条规则运行过，因为开关是 false。
这不是次要细节——一整套调好的检测器在一次为它而生的事故里完全缺席，原因就是它。

**唯一真正触发的子系统触发得太晚，而且被无视了。** `ws-dev.log` 中整场运行只有一条
`context.compression_state` 事件：`ReasoningToolLoopCompactProcessor`，
`reasoning_tool_loop_compacted:tool_args`，耗时 15 ms，发生在第七次失败到达时，
把 23 条消息折叠为 14 条。

**折叠不是删除。** `_compact_messages` 返回 `messages[:fold_start] + [summary]`，
其中 `summary` 是一条携带 `_TOOL_ARGS_LOOP_WARNING_TEMPLATE_CN` 的 `AssistantMessage`
——包含失败的命令、完整的 OOM 错误，以及「**请跳出多轮重复工具调用，推进尚未完成的实质
工作。**」所以在第 8 次调用时，模型手里有两次明确的失败，外加一条明确的停止指令。
它仍然发出了字节完全相同的第 8 次和第 9 次调用。

折叠确实有两处代价。摘要只复现**最后一轮**，且从不说明折叠了多少轮，因此
**重复次数**——唯一能让情况变得毫无歧义的数据——正是被折叠销毁的东西。
而且该警告是 `AssistantMessage`，也就是说「跳出循环」这条指令被归属于模型自己，
而不是系统。

这就是为什么下面的防护是**对损害设边界**，而不是试图说服模型。
已经有东西用模型自己的语言、附上完整证据说服过它了——而第 5 节表明，
正是这次说服本身让它无法恢复。

## 3. 防护措施

### 3.1 终止命令意味着终止它的整棵进程树

`terminate_shell_process` 在 POSIX 上通过 `os.killpg` 覆盖整个进程组，但在 Windows 上
退化为 `proc.terminate()`，只触及直接子进程。那个子进程是 shell 包装器；真正在干活的
是它的后代。

agent-core 的 `AsyncProcessHandler._kill_process_tree`——也就是 `bash` 工具背后的
拆除逻辑——形态完全相同。于是在 Windows 上，超时或取消会上报「命令已被终止」，而真正占着
内存的进程还在跑，恰恰是在失控分配正在发生的那个平台上。

`reap_process_descendants` 用 psutil 清扫整棵树，并且接入了**两条** shell 路径：
`mcp_exec_command` 的循环直接调用，`bash` 则通过已有的 `bash_tool_safety` 补丁接入。
**事故用的正是 `bash`**，只覆盖另一条路径等于完全没有覆盖到。

**顺序很重要，而且是先父后子。** 一个 shell 的当前子进程消失后，它只会接着执行脚本里的
下一条命令；因此在请求父进程退出**之前**清扫后代，反而会留出一个窗口让新派生的进程活过
这次清扫。正确顺序是先终止父进程；随后清扫的，是在终止之前刚取到的那份后代 pid 快照。

**已被回收的 pid 绝不再遍历。** 终止动作通常会顺带回收子进程，而一个已被回收的 pid 可能
被内核分配给无关进程，那个进程的子进程并不该由我们杀掉——这是本清理逻辑唯一可能造成实际
损害的地方。因此两条 shell 路径在每次遍历前都会检查进程是否尚未被回收，孤儿进程则交由终止
前的那份快照覆盖。全程尽力而为：回收某一个成员失败，不应阻止回收其余成员。

### 3.2 防护能读懂的失败

现在每条失败路径都返回工具本就在文档中承诺的 JSON 结构：非零 `exit_code`、
`success: false`，消息放在 `stderr` 中——仍保留 `[ERROR]:` 前缀，因此依赖日志的工具
仍能识别。

正是这一点让断路器能够计入超时或被拦截的命令。
`tests/unit_tests/agents/test_command_tool_guards.py` 双向锁定了这个行为：
新的载荷能被检测到，而裸 `[ERROR]:` 字符串仍然不能——这样该缺陷无法悄悄回归。

用户取消也走同一个 helper。取消是用户行为而非工具故障，但它同样不是成功；把它留成检测器
唯一读法不同的那条路径，正是「每条失败路径都可读」这句话悄悄失真的方式——一个不断重发被
用户不断取消的命令的 Agent，同样是卡住了。

### 3.3 断路器已默认开启

`execution_guard.circuit_breaker.enabled` 现在为 **true**。

默认关闭的防护保护不了任何人。调节灵敏度的是阈值；这个开关只决定这一切是否运行，
而在事故中它决定了「不运行」。

**只改模板默认值是送不到任何人手上的**，这一点值得写出来，因为它完全不可见。
`migrate_config_from_template` 会把模板深合并进用户配置，并且对模板中**已存在**的每个键
都保留用户的值——而这个键自 2026-06 起就在模板里。于是每个已有安装都带着一个显式的
`false` 并会继续保留它；与此同时两个新阈值因为是新键**会**被写入：最终得到一份看起来
配置齐全、而防护是关着的配置。`_migrate_circuit_breaker_default_enabled` 只迁移这一种情况。

单看一个 `false` 无法区分它是旧默认值还是用户的决定，因此用两个新阈值作为判据：它们与默认值
翻转来自同一次模板变更，所以配置里已经带上它们，就说明它至少与事故后的模板合并过一次，而
其中的 `enabled` 是在那次合并后仍然保留下来的值。这样的配置一律不动——文档里承诺的关闭开关
也才真正成立：写下 `enabled: false`，它在后续升级中会一直保持关闭。

### 3.4 完全相同的重复分两级切断

`identical_repeat_threshold`，默认 **3**，下限 2 —— 记录一条 warning 日志。
`identical_repeat_abort_threshold`，默认 **5**，始终高于前者 —— 终止本次执行。

该规则比 `generic_repeat` 更严：同工具、同入参，**并且结果相同**。
每次返回新内容的工具即使入参重复也仍在推进；返回完全相同字节的则没有。

**中断这一级还额外要求整段连续调用都是失败的。** 完全相同的**成功**结果正是正当轮询的
特征——在干净的工作区上连查五次 `git status`，或对一个尚未就绪的服务做健康检查——它们在
工具、入参、结果三个维度上都与事故无法区分，唯一的区别就是它们成功了。所以提示这一级
两种都计数，只有中断坚持要求失败。把任一阈值设为 `0` 即可关闭对应的那一级；在此之前，
把某个阈值清零反而会落进 clamp，让规则比默认**更严格**。

分两级，是因为低阈值单独使用过于粗暴。连续三次查询同一个未完成的构建，同样是
「工具+入参+结果」全同，但这不是故障——在最初几轮里，确定性失败与正当等待的特征
是一样的。两个阈值之间的间隔，正是一个正当的轮询者得以幸存的空间。

放到事故的时间线上：**执行在第 5 次调用处结束**——早于循环压缩器在第 7 次的触发，
也比人工在第 9 次的干预早了四次调用。

关于「什么算一次重复」，有两个细节。`description` 字段本就被排除在 `bash` 的入参哈希
之外，因此即使模型在第 1、2、3 次调用之间改写了自己的说明文字，该规则依然能匹配上事故中
的这些调用。另外，两次尝试之间对**其他**工具的调用会被跳过，而不是打断连续计数——在两次
完全相同的尝试之间写个 todo、读个文件，做的仍然是同一件事，而要求严格连续意味着一次插入
调用就足以让整个模式彻底隐身。对**同一个**工具的不同调用则是真正的变化，仍然会打断计数。
跳过有上限，且这个上限**按每段间隔**计算，以免把会话早期的一次重复拼接到最近的一次上。之所以
按间隔而不是按整条链计算：若整条链只共享一份额度，连续计数最终会被额度本身卡住——每次尝试之间
插入两次调用，该规则就只会一直告警，永远到不了中断。

### 3.5 打开断路器会唤醒什么

有三个检测器在第 3.3 节之前是不运行的，现在它们活了；而且它们的阈值当初选定时，并没有
考虑第 3.2 节的载荷改动——那个改动让更多路径被判定为错误。

其中值得注意的是 `unknown_tool_repeat`：这个名字是历史遗留，它统计的是对**同一个工具**
的连续报错调用，与该工具是否存在无关。一个 Agent 在排查问题时连续跑十次失败的 `pytest`
是很正常的事，而在默认阈值 10 下，这现在会终止执行。连续段中任何一次成功都会重置计数。
它的文案也不再把一个已注册的工具称作「未知工具」——此前是这么写的。

`ping_pong` 和 `global_breaker` 分别需要 20 轮和 30 轮，触及的可能性要小得多。
这三个检测器现在都有测试了；此前一个都没有。

两项相关改动：

- **critical 级检测现在以 `result_type="error"` 结束，而不是 `"answer"`。**
  切断卡死的执行是一次失败。把它报告为答案，正是「从未成功的执行看起来像成功」的由来。
- **warning 有意只写日志。** 本次工作最初确实在 warning 级推送了 steering 消息，
  理由是「只有日志能看到的警告改变不了下一轮」。复现实验的结论正好相反，数据见第 5 节：
  `push_steering` 会把消息追加到失败的工具结果**之后**，而在发生本次事故的那个模型上，
  这一点足以让它无法自行恢复。真正终止执行的是 abort；warning 是给看日志的人的。

## 4. 这些改动没有解决什么

**Git 的缺陷在上游。** 这些防护只是把它围住，并没有修复它。它在没有 Agent 的情况下也能
复现，值得向 git-for-windows 上报。

**模型仍然选择了重复。** 失败是明确的、结构化的，且连续八次完全相同；满足同一诉求的
替代方案存在（`--date=short` 加格式化）却从未被尝试；`ask_user` 已注册却从未被调用；
并且从第 8 次调用起，它已经被用中文告知要跳出循环。这里的任何改动都不为此开脱——
它们只是限制损害。

**也没有解释清楚。** 用 1、2、3、5、8 次相同失败预置上下文重放该事故——逐字节还原的请求、
`bash` 真实的双字段 schema、产品实际存储的工具结果渲染格式——模型 **52 次中有 52 次**
改变了做法。该行为在生产环境之外不可复现，而这恰恰是「防护不应依赖预测模型行为」的论据。

**没有任何东西限制单条命令可以消耗多少资源。** 这是留下的最大缺口，而且是刻意留下的，
不是遗漏。本次改动的早期版本确实加过一个按命令生效的内存上限——用 psutil 轮询进程树，
超限即终止——后来移除了。

理由是同类工具都不这么做。云端沙箱（E2B、Daytona、Modal、Vercel）在容器或 microVM
层面限制整个环境，从不关心单条命令；本地 Agent（Claude Code、Cursor、Aider）只限制墙钟。
按命令做 RSS 上限，会是这一类工具没有先例的机制，仅凭一次事故调参，而且在 Agent 被要求
运行的每一次重型构建上都存在误杀面。

它真正该待的地方是 `jiuwenbox`，那里已经按沙箱建模了 `cgroup.memory_max` / `cpu_max` /
`pids_max`——而这三项默认全是 `null`，即不设限。那正是让断路器缺席本次事故的同一个
「防护默认关闭」模式，只是下沉了一层，值得单独开一个 issue。

在那之前，失控命令的**第一次**调用是不受限的。重复规则把九次尝试减少到五次；对第一次
无能为力。

**Windows 上的进程树回收仍弱于 POSIX。** 第 3.1 节解决了幸存者可被枚举的情形，但 psutil
只能杀掉它在那一刻看得见的进程，所以一棵正在抢着派生的树仍可能留下漏网之鱼，而且没有
job object 让整个拆除保持原子性。`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` 是正确的原语，
并且能在该平台上顺带提供按命令的内存上限；那需要原生代码，也需要一台 Windows 机器来验证。

**进程树回收仍可能让人意外，但在「拆除」路径上这是刻意的。** 第 3.1 节只在运行时
已经决定终止某次调用时运行——超时、用户取消、`communicate()` 挂起（例如 ``cmd &`` 后
仍有孙进程占着 stdout）、或 harness 对 `bash` 会话的 kill——**不会**在正常 exit 0 时运行。
在这些路径上，它会杀掉 psutil 能枚举到的每一个后代，包括同一条命令里用 ``&`` 拉起的
后台任务、并行构建/worker（`make -j`、pytest worker），或尚未从该树脱钩的 `nohup` 子进程。
这与 POSIX 上 `killpg` 已有的语义一致：取消就是取消整棵树，而不是在 Windows 上留下
仍占内存的失控子进程。它**不能**覆盖事故形态——每次调用都在约 18 秒内带着 OOM **正常结束**，
没有 cancel。一条命令在成功路径上 fork 出长期 daemon 并立即退出，只要后续没有 teardown
命中其会话，就不受影响。

**阈值仍然对代价一无所知。** 三次相同调用，对一条廉价命令是合适的，对一条每次吃掉 49 GB
的命令则仍然宽松。一个会参考上一次尝试代价的防护会更好；它目前还不存在。

**检测发生在事后。** 计数在 `after_tool_call` 中进行，因此触发阈值的那次调用已经执行过、
代价已经付出。同一个 rail 上存在 `before_tool_call`，可以在调用发生前直接拒绝而不是事后计数；
那是比本次更大的改动。

## 5. 为什么这里没有任何东西对模型说话

最显而易见的一条防护，就是告诉模型它在打转。本次工作一开始确实做了，后来又移除了——
因为复现实验测出它有害。

复现实验重建了生产环境在第 8 次调用时持有的上下文（压缩之后的状态，并用压缩事件自身的
消息统计做过校验），只改变最后一条消息。在事故实际运行的模型 `Gemma4-26B` 上：

| 最后一条消息 | 结果 |
| --- | --- |
| 无：失败的工具结果就是最后一条 | **10/10 恢复** |
| 其后追加一条 steering 消息（即 `push_steering` 的形态） | 8/20 重复 |
| 其后追加任意 `assistant` 消息 | **10/10 重复** |

内容无关紧要。一条「仓库是干净的」的中性说明，与一条明确要求跳出循环的指令，产生同样的
10/10 重复。只要失败还是上下文里的最后一条，模型就会回应那个失败；一旦其后追加了任何东西，
失败就不再处于模型所回应的位置上。

`ctx.push_steering` 最终走到 `_admit_user_message(..., prefix="[STEERING] ")`，
正是这种形态。所以一条「能传达给模型」的警告，反而让事故在受害的那个模型上更容易发生，
因此该 rail 不再发送它。

两点局限。这只是一个模型——`deepseek-v4-flash` 在包括生产形态在内的所有分支上都 10/10
恢复——而且每个单元只有 10 次试验。这足以让我们不去发布一个唯一的测量结果说它适得其反的
机制；但不足以对 steering 这件事本身下任何一般性结论。

上游的另一半不在本仓库范围内：agent-core 中的 `ReasoningToolLoopCompactProcessor`
追加的正是这样一条消息，也正是上面复现实验所重建的对象。那应当作为 agent-core 的 issue
提出。
