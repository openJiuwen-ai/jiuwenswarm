# 模型路由：任务驱动的自动模型选择

---

## 概念科普

### 模型路由是什么

模型路由（Model Routing）是 JiuwenSwarm 在多模型环境下提供的任务适配系统。它解决核心问题：**选谁干** —— 根据任务类型和难度自动选择最合适的模型。

- **分数路由**解决"选谁干"：根据任务类型和难度算出目标分数，在能力表里选 model_score 最接近的模型——重活选强模型，轻活选弱模型，避免大马拉小车或小马拉大车。

可以把模型路由理解为"三段式智能派单"：**健康检查 → 单模型跳过 → 分数路由**。如果模型端点不健康，先过滤掉；如果只有一个模型可选，路由自动跳过；正常情况下按分数最近匹配派给最合适的模型。

#### 分数路由怎么派单

分数路由的核心是 **目标分数 → 最近匹配**：

1. 分类器根据用户 prompt 判断任务类型（category）和难度（difficulty），给出原始分数（raw_score）。
2. 从分数表（score_table）查 `(category, difficulty)` 的精确分数；查不到则按难度取默认分数（easy=10, medium=30, hard=50）；如果分类器给出的难度不在(easy, medium, hard)的范围内，则取默认分数为 50。
3. **Hard 难度特长约束**：如果难度为 hard，优先把候选范围缩小到 `model_expertise_category` 含该任务 category 的模型。例如 coding/hard 只选标了 coding 专长的模型。无专长匹配时兜底回全表（与 vision 约束同样的 fallback 策略）。
4. **model_type 约束**：如果显式注入了 `required_model_type`（如 `"vision"`、`"coding"`），候选限到 `model_type` 匹配的模型；未注入时排除专用模型。
5. 在候选里选 `model_score` 最接近目标分数的模型；等距时偏高分（质量优先）。

#### 为什么 hard 任务要走特长约束

medium/easy 任务对模型专长的要求不高——通用模型也能做格式化、简单总结。但 hard 任务往往需要深度理解：coding/hard 要写出复杂算法，reasoning/hard 要严密推理链。如果只按分数匹配，一个 score=90 的通用聊天模型可能被选中，但它未必擅长写代码。

特长约束确保 hard 任务优先交给**声称擅长该领域的模型**。如果一个模型标了 `model_expertise_category=["coding", "reasoning"]`，说明它在编程和推理上有专门优化；coding/hard 的请求就会优先路由到它，而不是一个分数相近但只会聊天的通用模型。

无模型标了对应专长时，兜底回全表——不做空约束，让分数路由在所有候选里选最近的。

#### model_type 约束怎么工作

模型路由通过 `model_type` 字段支持通用类型约束，替代旧版 `_has_image` 硬编码分支。`_detect_model_type(ctx)` 从上下文检测当前请求需要的 model_type，当前仅支持**显式注入**方式：

```python
# 在 before_invoke 阶段写入 ctx.extra
ctx.extra["_required_model_type"] = "vision"   # 路由到视觉模型
ctx.extra["_required_model_type"] = "coding"   # 路由到编程模型
ctx.extra["_required_model_type"] = "audio"    # 路由到音频模型
```

约束逻辑：

| `required_model_type` | 行为 |
|----------------------|------|
| 非空（如 `"vision"` / `"coding"`） | 候选限到 `model_type == required_model_type` 的模型；无匹配则保持原表兜底 |
| 空（默认） | 排除 `model_type` 非空的专用模型；全为专用模型则保持原表兜底 |

#### 健康检查怎么保护

模型端点健康检查以**后台异步循环**运行，在首次 `before_invoke` 时懒启动，按可配置间隔定期刷新缓存。路由决策直接读取缓存状态——**永远不阻塞**路由路径。

- **后台循环**：每隔 `interval_seconds`（默认 600s）调用 `update_health` 刷新状态缓存。首次 invoke 懒启动循环；后续 invoke 直接读缓存。
- **缓存 TTL**：默认 600s（10 分钟），用 `time.monotonic()` 不受系统时钟调整影响
- **能力验证**：通用模型用纯文本 ping；vision 模型发送红色方块图片验证视觉能力；audio 模型发送语音 WAV 验证音频能力
- **全不健康回退**：所有模型都不健康时回退原表，不阻断路由
- **连续判定**：连续失败 ≥ `max_consecutive_failures`（默认 2）才标记不健康；连续成功 ≥ `recovery_consecutive_successes`（默认 1）才恢复健康
- **非阻塞**：路由直接读取缓存的 `_status_map`；健康检查循环在后台更新缓存供下次 invoke 使用

#### 路由生命周期

路由在每个 invoke 的 `before_invoke` 钩子（优先级 95）中执行一次，早于所有模型调用。每个新用户 turn 触发一次全新的路由周期。`before_invoke` 每个 invoke 天然只触发一次，无需去重机制。

#### 它解决什么问题

| 问题 | 传统做法 | 模型路由的做法 |
|------|---------|--------------|
| 重活轻活都给同一个模型 | 手动切换或固定最强模型 | 按分数自动选——重活选强，轻活选弱 |
| Hard 任务给了不擅长的模型 | 不区分专长，按分数/品牌随便选 | hard → expertise 约束 → 选声称擅长该领域的模型 |
| 多 API 同模型怎么区分 | 不区分，token 统计串账 | client_id 按(api_base+api_key)派生哈希，独立记账 |
| 特定类型请求选错模型 | 不区分，含图/编程/音频可能选错 | model_type 显式注入 → 约束到对应类型模型 |
| 模型端点宕机仍路由 | 不感知，路由到宕机模型 | 异步健康检查 → 过滤不健康端点 |
| 健康检查阻塞路由 | 同步检查，每次调用前等待 | 后台循环 + 缓存，路由永不等待 |
| 模型能力参数分散在各处 | config 硬编码 | 外置 JSON（capability_map/mapper），用户可自定义覆盖 |

### 基本工作流

```text
启动 → 加载能力表 + 分类器 + 分数表 + 健康检查器
  ↓
首个用户请求 → 懒启动健康检查后台循环
  ↓
每次用户请求（before_invoke）：
  ↓
[健康检查] 读取缓存状态（非阻塞）
  ├─ 过滤不健康模型（全不健康回退原表）
  └─ ↓
[检查] 单模型跳过？
  ├─ 是 → 直接输出唯一模型，不走后续
  └─ 否 ↓
[正常路由] 分类器 → (raw_score, category, difficulty)
  ↓
task_score(category, difficulty, mapper) → 目标分数
  ↓
[约束 1] hard 难度特长约束（difficulty=="hard" 时优先选 expertise 匹配的模型；无匹配→全表兜底）
  ↓
[约束 2] model_type 约束（显式注入 → 匹配对应类型；未注入 → 排除专用模型）
  ↓
model_score 最近匹配 → 推荐模型
  ↓
apply_routing=True？set_llm 切换模型 / 否：只推荐不切
```

### 运行时行为

模型路由作为 DeepAgentRail 运行，优先级 95，在每次用户 turn 的 `before_invoke` 中自动执行。用户不需要手动触发——只要配置了 `model_routing.enabled`，所有请求都会经过路由。

健康检查以后台异步循环运行，首次 `before_invoke` 时启动，定期刷新缓存状态。路由决策始终读缓存——不会因 HTTP 健康检查而阻塞。

路由完成后，决策结果写入 `ctx.extra["model_routing_decision"]`，包含：

| 字段 | 说明 |
|------|------|
| `recommended_model_id` | 推荐模型的 client_id |
| `analysis` | TaskAnalysis：category、difficulty、target_score、predicted_input_tokens |
| `reasoning` | 路由推理过程（"classifier score=90; score match: target=90 → big-model(score=90)"） |
| `prior_calls_otel` | 本次 invoke 内前置调用的 OTel span 列表 |
| `model_usage_stats` | 当前 token 统计快照 |

## 操作指导

### 1. 准备模型配置

模型路由依赖两个前提：

- **config.yaml 里配置了多个模型**：`models.defaults` 至少包含 2 个模型条目（含 `model_client_config`）。只有 1 个模型时路由会自动跳过。
- **模型能力表文件就绪**：`routing_state/model_capability_map.json` 已存在（首次启动会从包内模板自动拷贝）。

模型配置方式见 [配置信息](配置信息.md)。

### 2. 开启模型路由

操作路径：

```text
左侧导航栏 → 配置信息 → 模型路由
```

打开 **启用模型路由** 后保存配置。

相关配置项：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `model_routing.enabled` | `false` | 是否启用模型路由 |
| `model_routing.apply` | `false` | 路由结果是否真切换模型（`set_llm`）；`false` 时只推荐不切 |
| `model_routing.stats_path` | 空字符串 | 统计文件路径；为空时使用默认位置 |
| `model_routing.health_check.enabled` | `true` | 是否启用健康检查 |
| `model_routing.health_check.interval_seconds` | `600` | 健康检查缓存 TTL（秒） |

开启后，每次用户 turn 的 `before_invoke` 会自动执行路由。关闭后回到原有行为——所有请求使用默认模型。

> **提示**：`apply=false` 是安全的起步方式——路由只给出推荐结果，不实际切换模型，适合观察路由效果后再决定是否开启真切换。

### 3. 配置视觉模型

含图请求需要至少一个 `model_type: vision` 的模型。在模型条目中设置：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: GLM-5.1
        ...
      # 普通文本模型（默认 model_type=""）
  vision:
    model_client_config:
      model_name: qwen-vl-max
      client_provider: DashScope
      api_key: "你的密钥"
      api_base: "https://..."
      # vision 专用模型，含图请求时参与路由
```

也可以在 `models.defaults` 条目上直接标 `model_type: vision`：

```yaml
models:
  defaults:
    - model_client_config: {...}
      model_type: vision       # ← 标记为视觉模型
```

视觉模型在非含图请求时会被排除；含图请求时只选视觉模型（无视觉模型则用全表兜底）。

### 4. 配置模型专长

Hard 难度的任务会优先路由到声称擅长对应领域的模型。在模型条目中通过 `model_expertise_category` 标记专长：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: deepseek-coder-v2
        client_provider: DeepSeek
        api_key: "你的密钥"
        api_base: "https://..."
      model_expertise_category: ["coding"]    # ← 标记编程专长
    - model_client_config:
        model_name: GLM-5.1
        client_provider: DashScope
        api_key: "你的密钥"
        api_base: "https://..."
      model_expertise_category: ["reasoning", "coding"]  # ← 标记推理+编程专长
    - model_client_config:
        model_name: qwen3-max
        ...
      # 不标记 expertise → hard 任务时不在特长候选里
```

专长标记的效果：

| 场景 | 无专长标记 | 有专长标记 |
|------|-----------|-----------|
| coding/hard | 全表按分数选（通用模型可能被选中） | 先限到标了 coding 的模型 → 再按分数选 |
| reasoning/hard | 同上 | 先限到标了 reasoning 的模型 → 再按分数选 |
| chat/easy / format/medium | **不受约束**——全表按分数选 | **不受约束**——easy/medium 不触发特长筛选 |
| 无模型标了对应专长 | — | 兜底回全表，不做空约束 |

> **调整建议**：如果你的模型确实在某个领域有优势（如 DeepSeek-Coder 在编程、Claude 在推理），建议标记对应专长。Hard 任务会优先路由到它，避免通用聊天模型抢了需要深度理解的请求。

也可以在 `model_capability_map.json` 的 `models` 字段中覆盖：

```json
{
  "models": {
    "deepseek-coder-v2": {"model_score": 80, "model_expertise_category": ["coding"]},
    "GLM-5.1": {"model_score": 57, "model_expertise_category": ["reasoning", "coding"]}
  }
}
```

### 5. model_type 显式注入

模型路由支持通过 `ctx.extra["_required_model_type"]` 显式注入 model_type 约束，控制路由到特定类型的模型。这是目前唯一的 model_type 检测来源。

#### 注入方式

在 `before_invoke` 阶段，由 adapter 层、前端或其他 rail 写入 `ctx.extra`：

```python
# 方式一：在 Rail 的 before_invoke 中注入
class MyRail(DeepAgentRail):
    async def before_invoke(self, ctx: AgentCallbackContext) -> None:
        # 检测到图片输入 → 注入 vision
        if self._has_image_input(ctx):
            ctx.extra["_required_model_type"] = "vision"
        # 检测到音频输入 → 注入 audio
        elif self._has_audio_input(ctx):
            ctx.extra["_required_model_type"] = "audio"

# 方式二：在 adapter 层注入
class JiuWenClawDeepAdapter:
    async def _invoke(self, ctx):
        # code 模式 → 注入 coding
        if self._mode == "code":
            ctx.extra["_required_model_type"] = "coding"
```

#### 注入值与路由行为

| 注入值 | 路由行为 | 典型场景 |
|--------|---------|---------|
| `"vision"` | 候选限到 `model_type=="vision"` 的模型 | 含图请求、文件附件含图片 |
| `"coding"` | 候选限到 `model_type=="coding"` 的模型 | 编程模式、代码生成任务 |
| `"audio"` | 候选限到 `model_type=="audio"` 的模型 | 语音输入、音频处理 |
| `""` 或不注入 | 排除专用模型（model_type 非空）；全为专用模型则保持原表兜底 | 默认行为 |

#### 模型端 model_type 配置

在 `config.yaml` 的模型条目中标记 `model_type`：

```yaml
models:
  defaults:
    - model_client_config: {...}
      # 普通文本模型（默认 model_type=""）
    - model_client_config: {...}
      model_type: coding          # ← 标记为编程模型
    - model_client_config: {...}
      model_type: vision          # ← 标记为视觉模型
    - model_client_config: {...}
      model_type: audio           # ← 标记为音频模型
```

也可以在 `model_capability_map.json` 的 `models` 字段中覆盖：

```json
{
  "models": {
    "deepseek-coder-v2": {"model_score": 80, "model_type": "coding"},
    "qwen-vl-max": {"model_score": 45, "model_type": "vision"}
  }
}
```

#### 如何新增 model_type

1. 在 `config.yaml` 或 `model_capability_map.json` 中给目标模型配置新 `model_type`（如 `"audio"`）
2. 在注入方（adapter / rail / 前端）写入 `ctx.extra["_required_model_type"] = "audio"`
3. 路由自动生效 — `_decide_and_select` 会按 `required_model_type` 过滤候选

### 6. 自定义分类器和分数表

分类器和分数表由 `classifier_mapper.json` 控制。首次启动时从包内模板拷贝到用户目录：

```text
~/.jiuwenswarm/config/routing_state/classifier_mapper.json
```

#### 分数表

`score` 字段定义 `(category, difficulty)` 到目标分数的映射：

```json
{
  "score": {
    "chat.easy": 5,
    "chat.medium": 20,
    "chat.hard": 45,
    "coding.easy": 15,
    "coding.medium": 40,
    "coding.hard": 65,
    "reasoning.hard": 55,
    "summarization.medium": 30,
    "format.easy": 5
  }
}
```

- 格式：`"category.difficulty"` → 整数分数。
- 分数越高 → 选越强的模型；分数越低 → 选越弱的模型。
- 未覆盖的组合按难度默认分：easy=10, medium=30, hard=50。

> **调整建议**：如果轻任务总是选到大模型，适当降低对应分数（如 `"format.easy": 5→3`）；如果重任务选到弱模型，适当提高分数（如 `"coding.hard": 65→85`）。

#### 分类器

`classifier` 字段定义分类器的行为。使用 **文本注入** 方式——`source` 是 `async def classify(prompt_text)` 的函数体文本，被 exec 编译为异步函数：

```json
{
  "classifier": {
    "imports": ["re", "json"],
    "source": "import logging\nfrom jiuwenclaw.agentserver.deep_agent.rails.model_routing.classifier import (\n    _build_llm_model, _parse_classifier_response, _lookup_score\n)\n\n_log = logging.getLogger(\"ModelRouting\")\n\nif not _EXTRAS.get(\"api_base\"):\n    _log.debug(\"no api_base → fallback\")\n    return 50, \"unknown\", \"hard\"\n\nmodel = _build_llm_model(_EXTRAS)\nif model is None:\n    _log.debug(\"build model failed → fallback\")\n    return 50, \"unknown\", \"hard\"\n\n_log.debug(\"LLM call start, prompt=%r\", prompt_text[:80])\nmessages = [\n    {\"role\": \"system\", \"content\": _EXTRAS.get(\"system_prompt\")},\n    {\"role\": \"user\", \"content\": prompt_text[:4000]},\n]\ntry:\n    resp = await model.invoke(messages)\n    content = getattr(resp, \"content\", \"\") or \"\"\n    category, difficulty = _parse_classifier_response(content, _CATEGORIES, _DIFFICULTIES)\n    score = _lookup_score(category, difficulty)\n    _log.debug(\"result: %s/%s score=%d\", category, difficulty, score)\n    return score, category, difficulty\nexcept Exception as exc:\n    _log.warning(\"LLM call failed: %s → fallback\", exc)\n    return 50, \"unknown\", \"hard\"",
    "extras": {
      "api_base": "https://your-llm-endpoint/v1",
      "api_key": "your-api-key",
      "model_name": "your-classifier-model",
      "client_provider": "OpenAI",
      "temperature": 0,
      "system_prompt": "You are a task classifier. Classify the user input into a category and difficulty. Output ONLY a JSON object. No explanation, no markdown.\n\nCategories:\n- chat: greeting, small talk, casual conversation\n- reasoning: logic, analysis, planning, research, investigation, math\n- coding: write code, debug, programming\n- summarization: summarize, condense, compress, extract key points\n- format: convert between formats (JSON, CSV, table, list)\n\nDifficulty:\n- easy: simple, short task\n- medium: moderate complexity\n- hard: complex, long task\n\nExamples:\n\"hello\" -> {\"category\":\"chat\",\"difficulty\":\"easy\"}\n\"write a Python sort function\" -> {\"category\":\"coding\",\"difficulty\":\"medium\"}\n\"summarize this article\" -> {\"category\":\"summarization\",\"difficulty\":\"medium\"}\n\"convert this CSV to JSON\" -> {\"category\":\"format\",\"difficulty\":\"easy\"}\n\"prove that sqrt(2) is irrational\" -> {\"category\":\"reasoning\",\"difficulty\":\"hard\"}\n\nOutput ONLY: {\"category\":\"<category>\",\"difficulty\":\"<difficulty>\"}"
    }
  }
}
```

分类器 source 内可引用的注入数据：

| 变量 | 类型 | 说明 |
|------|------|------|
| `_EXTRAS` | `dict` | classifier.extras 字段 |
| `_CATEGORIES` | `tuple` | categories 列表 |
| `_DIFFICULTIES` | `tuple` | difficulties 列表 |
| `_SCORE_TABLE` | `dict` | `{(cat, diff)→int}` 分数表 |
| `_DEFAULT_SCORE` | `dict` | `{diff→int}` 默认分 |

工具函数不自动注入——source 需要时自行 import：

```python
from jiuwenclaw.agentserver.deep_agent.rails.model_routing.classifier import (
    _build_llm_model, _parse_classifier_response, _lookup_score
)
```

#### 无分类器时的行为

如果 `classifier_mapper.json` 缺少 `classifier` 字段，或分类器加载失败，路由会 fallback 到 `(raw_score=50, category="unknown", difficulty="hard")`。此时目标分数固定为 50，选 model_score 最接近 50 的模型。这保证了即使分类器不可用，路由仍能产出决策——只是不区分任务轻重。

### 7. 自定义模型能力映射

模型能力映射由 `model_capability_map.json` 控制，包含两部分：

- **vendor_map**：model_name 子串 → (model_group, model_provider) 的前缀映射（22 条默认）。
- **models**：model_name 精确匹配 → 能力字段覆盖（约 70 条默认），主要覆盖 `model_score`。

```text
~/.jiuwenswarm/config/routing_state/model_capability_map.json
```

```json
{
  "vendor_map": [
    {"prefix": "glm", "group": "GLM", "provider": "zhipu"},
    {"prefix": "qwen", "group": "Qwen", "provider": "alibaba"}
  ],
  "models": {
    "GLM-5.1": {"model_score": 57},
    "deepseek-chat": {"model_score": 35}
  }
}
```

如果配置了模型能力表未覆盖的模型或者有自主训练的特制模型，`model_score` 也可以在 `config.yaml` 的模型条目中设置：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: GLM-5.1
        client_provider: DashScope
        api_key: "你的密钥"
        api_base: "https://..."
      model_score: 55          # ← 手动设置 model_score
    - model_client_config:
        model_name: deepseek-chat
        client_provider: DeepSeek
        api_key: "你的密钥"
        api_base: "https://..."
      # 不设置 model_score → 会按照 model_capability_map.json 映射
```

`model_score` 是路由的核心分数。调整模型 score 会直接影响路由选择：

- score 越高 → 越容易被重任务选中。
- score 越低 → 越容易被轻任务选中。
- 等距时偏高分（质量优先）。

> **调整建议**：如果某个模型总是不被选中，检查它的 `model_score` 是否与任务分数差距过大。可以在 `models` 字段中精确覆盖该模型的 score。

### 8. 查看路由日志

路由过程通过日志输出，可在服务端日志中观察：

```text
[ModelRouting] classifier: [coding,hard] score=90 in_tok=4 model_type=coding -> recommend=f345159ce878
[ModelRouting] classifier: [format,easy] score=10 in_tok=2 model_type=(none) -> recommend=abc123
[ModelRouting] skipped (single model); in_tok=4
[ModelRouting] applied set_llm -> GLM-5.1
[ModelRouting] filtered 1 unhealthy models: ['def456']
[ModelRouting] all models unhealthy, falling back to full table
[ModelRouting] health check background loop started
```

| 日志关键字 | 含义 |
|-----------|------|
| `classifier: [...]` | 正常路由：分类结果、目标分数、model_type、推荐模型 |
| `skipped (single model)` | 单模型跳过 |
| `applied set_llm ->` | 真切换模型 |
| `filtered N unhealthy models` | 健康检查过滤了不健康模型 |
| `all models unhealthy, falling back` | 全不健康，回退原表 |
| `health check background loop started` | 异步健康检查循环已启动 |

## 配置说明

### 配置项总览

```yaml
model_routing:
  enabled: true             # 启用模型路由
  apply: false              # 路由结果是否真切换模型
  stats_path: ""            # 统计文件路径（为空用默认位置）
  health_check:
    enabled: true           # 健康检查开关
    interval_seconds: 600   # 缓存 TTL（秒）
    timeout_seconds: 10     # 单次请求超时
    max_rounds: 1           # 重试轮次
    max_consecutive_failures: 2          # 连续失败阈值
    recovery_consecutive_successes: 1    # 恢复健康所需连续成功
    health_check_prompt: "hi"            # 最小 prompt
    max_tokens: 1                        # 最小输出
```

### `model_routing.enabled`

是否启用模型路由。默认 `false`。

开启后，每次用户 turn 的 `before_invoke` 中会执行路由逻辑。关闭后回到原有行为——所有请求使用默认模型，不做分类或模型选择。

### `model_routing.apply`

路由结果是否真切换模型（`set_llm`）。默认 `false`。

- `false`：路由只产出推荐结果和决策信息，不切换模型。适合观察路由效果。
- `true`：路由后会实际切换 agent 当前模型到推荐模型，并同步 config 里的 `model_name`、`model_client_config`、`model_config_obj`。后续模型调用会使用路由后的模型。

> **注意**：开启 `apply=true` 后，所有请求都会被路由到推荐模型。建议先在 `apply=false` 模式下观察路由日志，确认路由选择合理后再开启真切换。

### `model_routing.stats_path`

模型统计文件的存储路径。为空时使用默认位置：

```text
~/.jiuwenswarm/config/routing_state/model_routing_list.json
```

统计文件记录每个模型的 token 使用量（input/output/call_count/last_used），跨会话累积。路由启动时合并已有统计到能力表，热重载时回写整表。

### `model_routing.health_check.*`

健康检查配置。详见上方"健康检查怎么保护"部分。

要点：

- 健康检查以**后台异步循环**运行，首次 `before_invoke` 时懒启动。
- `interval_seconds` 同时控制缓存 TTL 和循环间隔。
- 路由读取缓存状态，不会因 HTTP 健康检查请求而阻塞。

### 附：完整配置项示例

```yaml
model_routing:
  enabled: true
  apply: true                # 真切换模型
  stats_path: ""             # 使用默认路径
  health_check:
    enabled: true
    interval_seconds: 600    # 缓存 TTL 10 分钟
    timeout_seconds: 10      # 单次请求超时
    max_rounds: 1            # 重试轮次
    max_consecutive_failures: 2
    recovery_consecutive_successes: 1
    health_check_prompt: "hi"
    max_tokens: 1
```

### 外置 JSON 配置文件

两个 JSON 文件存放在 `routing_state` 目录，首次启动从包内模板自动拷贝，用户可修改覆盖：

```text
~/.jiuwenswarm/config/routing_state/
├── classifier_mapper.json      分类/难度/分数表 + 分类器配置
├── model_capability_map.json   厂商前缀映射 + 模型 score 覆盖
├── model_routing_list.json     token 统计（自动生成，不要手动改）
```

#### `classifier_mapper.json`

| 字段 | 类型 | 说明 |
|------|------|------|
| `categories` | `list[str]` | 任务分类列表（chat/reasoning/coding/summarization/format） |
| `difficulties` | `list[str]` | 难度列表（easy/medium/hard） |
| `score` | `dict` | `"category.difficulty"` → 目标分数 |
| `classifier.imports` | `list[str]` | 注入到 exec namespace 的模块名 |
| `classifier.source` | `str` | classify 函数体文本 |
| `classifier.extras` | `dict` | 分类器专用配置（rules/category_utterances/length_signal 等） |

#### `model_capability_map.json`

| 字段 | 类型 | 说明 |
|------|------|------|
| `vendor_map` | `list[{prefix, group, provider}]` | model_name 子串 → 品牌组/厂商映射 |
| `models` | `dict{name → {model_score, model_type, ...}}` | model_name 精确匹配 → 能力字段覆盖 |

## 常见问题

### 为什么开启后路由没有生效？

可能原因：

- 只配置了 1 个模型 → 路由自动跳过（"skipped (single model)"）。
- `model_routing.enabled` 没有开启。
- `model_routing.apply=false` → 路由只推荐不切，模型仍用默认。

检查日志中是否有 `[ModelRouting]` 相关输出。

### 为什么重任务总是选弱模型？

可能原因：

- `model_score` 配置不合理——弱模型 score 过高或强模型 score 过低。
- 分数表中重任务的目标分数偏低（如 `coding.hard` 只有 30）。
- 分类器误判——重任务被分类为轻任务。

检查日志中 `classifier: [...]` 行的 category、difficulty 和 score，对照 `classifier_mapper.json` 的分数表和 `model_capability_map.json` 的模型 score。

### 为什么含图请求选了非视觉模型？

可能原因：

- 没有配置 `model_type: vision` 的模型 → 全表兜底，选分数最近的。
- 没有注入 `_required_model_type` → 路由不知道需要视觉模型。

确保 config 中有 vision 模型条目，且在 `before_invoke` 阶段注入 `ctx.extra["_required_model_type"] = "vision"`。

### 为什么分类器加载失败？

日志中会出现 `[ModelRouting] classifier load skipped: ...`。可能原因：

- `classifier_mapper.json` 缺少 `classifier` 字段 → fallback 到无分类器模式。
- `classifier.source` 文本有语法错误 → exec 编译失败。
- `imports` 中引用了不可用的模块。

分类器失败不影响路由——会 fallback 到 `(50, unknown, hard)`，目标分数固定 50。

### 同模型多 API 怎么独立统计？

同一个 model_name 配了多个 api_key（如 DeepSeek 3 key 预算分配），每个条目的 `model_id` 会按 `(model_name|api_base|api_key)` 派生 12 位哈希，独立统计 token 用量。也可以在 config 中显式指定 `client_id`：

```yaml
model_client_config:
  model_name: deepseek-chat
  api_base: "https://api.deepseek.com"
  api_key: "sk-aaa"
  client_id: "my-deepseek-aaa"    # ← 显式指定，不派生哈希
```

### 路由决策信息在哪里看？

路由决策写入 `ctx.extra["model_routing_decision"]`，包含推荐模型、任务分析、推理过程、OTel span 和统计快照。这个信息主要供内部 rail 链使用，不直接展示给用户。用户可通过服务端日志观察路由过程。

### `apply=false` 和 `apply=true` 的区别？

| 模式 | 行为 | 适用场景 |
|------|------|---------|
| `apply=false` | 路由只推荐模型，不切换。后续调用仍用默认模型 | 观察路由效果，调试分数/分类 |
| `apply=true` | 路由后实际切换模型（`set_llm`），后续调用用推荐模型 | 生产使用，自动按任务选模型 |

### 为什么模型端点健康但被标记为不健康？

- vision 模型健康检查会发送红色方块图片，回答必须包含"红"/"red"等关键词才通过。纯文本模型无法识别图片，会验证失败。
- audio 模型健康检查会发送语音 WAV，回答必须包含"你好"/"hello"等关键词才通过。
- 如果模型端点响应慢，可能超时。可调大 `timeout_seconds`。

### 健康检查会拖慢路由吗？

不会。健康检查以后台异步循环运行——路由读取缓存状态，永远不会等待 HTTP 健康检查完成。首次 invoke 时循环懒启动，缓存异步填充；在首次健康检查完成前，所有模型默认视为健康（保守策略）。

### 怎么注入 model_type 让路由选编程模型？

在 adapter 层或 rail 的 `before_invoke` 阶段写入：

```python
ctx.extra["_required_model_type"] = "coding"
```

确保 config 中有 `model_type: coding` 的模型条目，路由会自动约束到该模型。
