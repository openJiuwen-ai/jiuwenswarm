# 敏感信息读写开发指南

本文面向 **需要在代码中读取或写入 API Key、Token、密码等敏感字符串** 的开发者，说明统一入口 `SecretStore` 的用法、约定与禁止事项。

> 个人版与企业版共用同一套接口；企业版 managed 模式下配置可能来自 Manager 下发，业务代码用法不变。  
> 相关：[配置说明](配置信息.md)、[工具权限与安全防护](工具权限与安全防护.md)

---

## 1. 核心约定（必读）


| 约定               | 说明                                                          |
| ---------------- | ----------------------------------------------------------- |
| **读写接口**         | `get`、`set`（业务代码只用这两个）                                      |
| **初始化接口**        | 启动时为各 algorithm **分别**调用对应的 configure / register 方法（见 §2.2） |
| **统一入口**         | 敏感字符串只通过 `SecretStore` 读写，禁止在新代码中直接 `os.getenv` 读密钥         |
| **明文 IO**        | `get` 返回明文，`set` 传入明文                                       |
| **默认存储**         | 非敏感 key → 明文；敏感 key 且已注册自定义加解密 → 自动加密（与现网一致）                |
| **key 自定**       | key 任意字符串，读写一致、不跟别人冲突即可                                     |
| **内置 algorithm** | 仅 `aes256gcm`、`dek` 等内置算法需在 `set` 时显式传 `algorithm=`         |
| **职责分离**         | 存哪里：代码用 logical key；非默认路径时在 `secret_registry.yaml` 声明（见 §6） |

## 2. 接口概览

### 2.1 导入

```python
from jiuwenswarm.common.secrets import SecretStore

store = SecretStore.get_instance()
```

### 2.2 启动时初始化 algorithm（进程入口调用）

每种 algorithm **单独一个方法**，入参固定，**不使用**统一入口承载多种算法的异构参数。

```python
# 内置：本地磁盘 AES-GCM，依赖 Master Key
store.configure_aes256gcm(
    master_key_env="JIUWEN_SECRET_MASTER_KEY",
    master_key_file="~/.jiuwenswarm/config/.master_key",
)

# 内置：dek（示例：依赖 Gateway 加密私钥）
store.configure_dek(private_key_b64=gateway_enc_private_key)

# 自定义加解密：见 §2.5
store.register_custom_crypto(my_provider)
```


| 方法                                 | 用途             | 何时调用                                     |
| ---------------------------------- | -------------- | ---------------------------------------- |
| `configure_aes256gcm(...)`         | 内置 `aes256gcm` | 业务显式 `set(..., algorithm="aes256gcm")` 时 |
| `configure_dek(...)`               | 内置 `dek`       | 业务显式 `set(..., algorithm="dek")` 时       |
| `register_custom_crypto(provider)` | 客户自定义加解密       | 部署时注册；**敏感 key 自动走此 Provider**           |


- 在 `app_gateway.py` / `app_agentserver.py` 启动阶段调用，**业务功能不调用**  
- 根密钥持久化、可重启；Provider 在构造时传入密钥即可  
- 未初始化的内置 algorithm 不能用于 `set(..., algorithm=...)`

### 2.3 get

```python
api_key = store.get("my_feature.api_key")
```

不存在 → `""`。`get` 自动解密，**不用传 algorithm**，业务始终拿到明文。

### 2.4 set

```python
store.set("my_feature.api_key", "sk-abc123")                          # 敏感 key：有自定义加解密则自动加密，否则明文
store.set("my_feature.api_key", "sk-abc123", algorithm="aes256gcm") # 显式指定内置算法
store.set("my_feature.display_name", "Acme")                          # 非敏感 key：始终明文
```

- **敏感 key** + 已 `register_custom_crypto` → 自动加密（与现网 `encrypt(name, text)` 行为一致）  
- **非敏感 key** → 明文  
- 传 `algorithm=` → 使用对应**内置**算法（`aes256gcm`、`dek` 等），与是否注册自定义加解密无关

### 2.5 自定义加解密（部署 / 插件）

> 业务功能开发通常**只需 §2.3–2.4**。本节供实现 `CryptoProvider` 或在进程入口注册加解密的场景阅读。

客户可替换加解密实现（国密、硬件加密模块、企业 KMS 等），**具体算法由 Provider 内部决定，框架不预设名称，业务也不感知算法名。**

做法是：**实现 `CryptoProvider`，启动时 `register_custom_crypto(provider)`，之后敏感 key 的 `get` / `set` 自动走该 Provider**——与升级前行为一致，业务代码无需改动。

#### 实现 Provider

`CryptoProvider` 是 **Protocol（结构类型）**：实现 `encrypt` / `decrypt` 两个方法即可。**建议**类声明写 `(CryptoProvider)` 便于类型检查。

```python
from jiuwenswarm.common.security.base_crypto import CryptoProvider

class MyCryptoProvider(CryptoProvider):
    def __init__(self, **config):
        # 密钥、连接等由客户自行配置，构造时传入，重启不变
        ...

    def encrypt(self, plaintext: str, **kwargs) -> str:
        ...

    def decrypt(self, ciphertext: str, **kwargs) -> str:
        ...
```

#### 启动时注册

```python
store = SecretStore.get_instance()
store.register_custom_crypto(MyCryptoProvider(...))
```

全局**仅一个**自定义加解密槽位；注册后，凡命中「敏感 key」规则的读写均自动加解密。

#### 哪些 key 会走自定义加解密？

由框架 **legacy 兼容层** 判定（内部封装现网 `is_sensitive_env_name`，业务不调用、secret_registry.yaml 不参与）。规则与现网一致，**按 key 名**（不区分大小写）：


| key 名特征     | 示例                                  |
| ----------- | ----------------------------------- |
| 含 `api_key` | `llm.api_key`、`API_KEY`             |
| 含 `token`   | `verification_token`、`access_token` |
| 含 `secret`  | `app_secret`、`client_secret`        |
| 含 `header`  | `default_headers`                   |


注册了自定义加解密后，命中上述规则的 key 在 `set` 时自动加密、`get` 时自动解密；未命中则明文。新功能若需内置算法加密，在 `set` 时显式传 `algorithm=`。

#### 业务侧用法（无缝）

```python
# 与现网相同：只传明文，不传 algorithm
store.set("llm.api_key", user_input)
api_key = store.get("llm.api_key")
```

配置页、CLI、模型 Key 保存等场景 **不要** 手写 `algorithm=`；框架按 key 名自动决定是否加密。

#### 与内置 algorithm 的关系


| 方式                                      | 何时用                                                          |
| --------------------------------------- | ------------------------------------------------------------ |
| `register_custom_crypto`                | 客户部署自己的加解密；**敏感 key 自动生效**                                   |
| `configure_aes256gcm` / `configure_dek` | 选用框架内置算法；须在 `set` 时 **显式** `algorithm="aes256gcm"` 或 `"dek"` |
| 都不注册                                    | 全部明文落盘（与现网未装 crypto 插件相同）                                    |


自定义加解密与内置 algorithm **不冲突**：同一 key 若 `set` 时写了 `algorithm="aes256gcm"`，走内置；否则敏感 key 走自定义 Provider。

**要点：**


| 项        | 说明                                              |
| -------- | ----------------------------------------------- |
| 注册位置     | 进程启动入口                                          |
| Provider | 客户自定实现；框架只约定 `encrypt` / `decrypt` 接口           |
| 业务代码     | 只 `get` / `set`；不直接调 Provider，不传 algorithm      |
| 生效范围     | 由 legacy 兼容层按 key 名判定；与 secret_registry.yaml 无关 |
| 升级       | 已有密文 `get` 仍可读；读写代码不用改                          |


### 2.6 delete

```python
store.delete("acme_webhook_token")
```

## 3. key 怎么取？

**自行约定。** `SecretStore` 提供 logical key 维度的持久化读写：`get(key)` / `set(key, value)`。key 为任意字符串，无中央注册；命名须模块内读写一致，并避免与其他模块冲突。

唯一建议：**别跟别人撞 key**。可选习惯（非强制）：

- 用模块名作前缀，如 `feishu_connector.app_secret`、`my_tool.api_key`
- 多实例加后缀，如 `feishu.{app_id}.app_secret`

```python
store.set("billing.stripe.secret_key", sk)
store.get("billing.stripe.secret_key")
```

### 3.1 新增一个 key（步骤）

1. **定 logical key**（§3 命名习惯），读写用同名字符串。
2. **写代码**：`store.set(key, 明文)` / `store.get(key)`。
3. **定存储路径**：
  - 走持久化层**默认存储** → 完成，**不用**改 `secret_registry.yaml`。  
  - 须写入**已有**物理位置（如 `.env` 里已有变量名、yaml 固定字段）→ 在 `secret_registry.yaml` 增加条目（§6 条目格式）。

## 4. 怎么保存？（明文 vs 加密）

### 4.1 默认行为（与现网一致）

```python
store.set("llm.api_key", "sk-abc123")       # 敏感 key + 已注册自定义加解密 → 自动加密
store.set("my_app.title", "Daily Report")   # 非敏感 key → 明文
```

未注册自定义加解密时，**全部明文**，与现网未装 crypto 插件相同。

### 4.2 内置 algorithm（显式指定）

```python
# 启动时（进程入口）
store.configure_aes256gcm(master_key_file="~/.jiuwenswarm/config/.master_key")

# 业务代码：须显式传 algorithm
store.set("my_feature.api_key", "sk-abc123", algorithm="aes256gcm")
store.get("my_feature.api_key")
```

```
启动 → register_custom_crypto（敏感 key 自动加解密）
     或 configure_aes256gcm / configure_dek（set 时显式 algorithm=）
     → get(key) → 明文
重启 → 再次注册 / configure（同一套根密钥）
     → get 仍可解密旧数据
```


| 方式           | 启动时                                | 业务 set                            |
| ------------ | ---------------------------------- | --------------------------------- |
| 自定义加解密       | `register_custom_crypto(provider)` | 敏感 key 照常 `set`，**不传 algorithm**  |
| 内置 aes256gcm | `configure_aes256gcm(...)`         | `set(..., algorithm="aes256gcm")` |
| 内置 dek       | `configure_dek(...)`               | `set(..., algorithm="dek")`       |


### 4.3 根密钥

在 Provider 构造或 configure 里传入，**重启不变**；不是每次 `set` 随机生成。

### 4.4 怎么选


| 场景                    | 写法                                                        |
| --------------------- | --------------------------------------------------------- |
| 日常配置（无加密要求）           | 不注册 Provider，`set(key, value)`                            |
| 客户指定加解密（现网 crypto 插件） | `register_custom_crypto`；敏感 key 自动加密                      |
| 磁盘加密、用框架内置            | `configure_aes256gcm` + `set(..., algorithm="aes256gcm")` |

## 5. 常见场景

### 5.1 调用 LLM / 外部 API

```python
store = SecretStore.get_instance()
api_key = store.get("llm.api_key")   # key 名你自己定，读写一致即可

client = OpenAI(api_key=api_key, base_url=base_url)
```

`get` 返回的已是明文，直接传给 SDK 即可。

### 5.2 配置页 / CLI 保存用户填写的 Key

```python
# Web、TUI、RPC handler 收到用户提交的新 Key
store.set("llm.api_key", user_input)
```

**不要**在保存用户 Key 时手写 `algorithm=`；若部署注册了自定义加解密，敏感 key 会自动加密。

### 5.3 判断「是否已配置」（不回显明文）

```python
configured = bool(store.get("llm.api_key"))
# 返回给前端：{"configured": true} 或占位 "***"，不要返回完整 key
```

### 5.4 IM 频道启动时读平台密钥

```python
app_secret = store.get(f"feishu.{app_id}.app_secret")
```

### 5.5 进程内临时 secret（重启失效）

适用于临时 SSH 私钥、短时 token 等 **不应写盘** 的数据：

```python
store.set("ssh.session.private_key", private_key_pem)
key = store.get("ssh.session.private_key")
```

## 6. secret_registry.yaml

**文件位置**：`~/.jiuwenswarm/config/secret_registry.yaml`（与 `config.yaml` 同目录；目录可由 `JIUWENSWARM_CONFIG_DIR` 指定）。

**用途**：代码用 **logical key** 调用 `store.get` / `store.set`；本文件仅在 logical key **不能走持久化层默认存储** 时，声明其绑定的**物理位置**。无条目 → 走默认存储；有条目 → 覆盖默认。

**本文件不管**：是否敏感、加解密、`algorithm`、key 重命名（见 §2.5、§4）。

#### 个人版 vs 企业版

| 问题 | 结论 |
| --- | --- |
| **logical key** | **同一套**（代码共用） |
| **文件格式** | **同一套**：`medium` / `path` / `field` / `format` |
| **运行时文件名** | **始终** `{config_dir}/secret_registry.yaml`（包内 + 用户覆盖） |
| **仓库里两个模板** | `secret_registry.yaml`（个人）、`secret_registry.enterprise.yaml`（企业） |
| **谁选版本** | **部署 / 安装**：企业环境把 enterprise 模板安装为 `secret_registry.yaml`；个人版用 personal 模板 |

代码**不**判断个人版/企业版；介质差异体现在**安装到 config_dir 的那份 yaml 内容**里。

---

### 条目格式（速查）

顶层为 YAML 映射：**键 = logical key**（与代码字符串完全一致，大小写敏感），**值 = 条目对象**。

```yaml
<logical_key>:
  medium: <env | file | db>     # 必填：存储介质（通道）
  path: <string>                # 必填：该介质内的定位（见下表）
  field: <dotted.path>          # 可选：从结构化内容中取子字段
  format: <yaml | json | text>  # 可选：path 所指内容的序列化格式；与 medium 独立
```

#### 字段说明


| 字段           | 必填  | 可选值                      | 说明                                                                        |
| ------------ | --- | ------------------------ | ------------------------------------------------------------------------- |
| `**medium**` | 是   | `env` | `file` | `db`    | **存储介质**：值存在哪类通道。不是格式名，禁止写 `json`/`yaml`/`default`                        |
| `**path**`   | 是   | 见下表                      | 介质内的**定位符**（变量名 / 文件路径 / DB 物理 key）                                       |
| `**field**`  | 否   | dotted 路径                | 当 `path` 指向的是**结构化文档**时，取其中的子字段；整段就是 secret 时可省略                          |
| `**format**` | 否   | `yaml` | `json` | `text` | `**path` 处内容的序列化格式**；与 `medium` 无关。需要配合 `field` 解析时必填；存 plain string 时可省略 |


#### `format` 何时写


| 场景                                         | 是否写 `format`                              |
| ------------------------------------------ | ----------------------------------------- |
| `env` + 单个变量值（plain string）                | **不写**                                    |
| `file` + 整文件即 secret（如 `.pem`）             | `text`，或省略（按扩展名推断为 text）                  |
| `file` + 读写字段 `field`                      | **写** `yaml` / `json`（或省略后按 `path` 扩展名推断） |
| `db` + 持久化层按 KV 返回 plain string            | **不写**（格式由 DB 层处理，registry 不感知）           |
| `db` + `path` 指向 JSON/YAML 文档且需 `field` 取值 | **写** `json` / `yaml`                     |


#### 各 `medium` 下 `path` / `field` 怎么写


| medium     | `path`                 | `field`                      | 典型 `format`               |
| ---------- | ---------------------- | ---------------------------- | ------------------------- |
| `**env**`  | `.env` 变量名，如 `API_KEY` | 不写                           | 不写                        |
| `**file**` | 文件路径（见下）               | 文件内 nested 字段；整文件 secret 可省略 | 有 `field` 时写；整文件 text 可省略 |
| `**db**`   | 持久化层约定的 DB 物理 key      | 仅当 DB 存的是结构化文档且要取子字段         | 有 `field` 时写；plain KV 不写  |


`file` 的 `path` 解析：


| `path` 形式                                  | 解析为                                               |
| ------------------------------------------ | ------------------------------------------------- |
| `config.yaml` 等相对路径                        | `{config_dir}/<path>`                             |
| `workspace/agent/skills/skills_state.json` | `{workspace_root}/agent/skills/skills_state.json` |
| `/...`、`~...`、盘符路径                         | 绝对路径                                              |


#### 完整示例

```yaml
# env：plain string，无 format
llm.api_key:
  medium: env
  path: API_KEY

# file：结构化文件 + 子字段
channel.feishu.app_secret:
  medium: file
  path: config.yaml
  field: channels.feishu.app_secret
  format: yaml

skills.clawhub.token:
  medium: file
  path: workspace/agent/skills/skills_state.json
  field: clawhub.token
  format: json

# db：plain string KV，registry 不写 format
enterprise.shared.api_key:
  medium: db
  path: secrets.enterprise_shared_api_key

# db：存 JSON 文档且取子字段（示例）
legacy.config.api_key:
  medium: db
  path: tenant_config_blob
  field: models.default.api_key
  format: json
```

### 6.1 多处存储与优先级（现网 vs 本文件）

**现网确实存在「同一 secret 多处可读」**，但模式不统一，散落在各模块：

| 模式 | 示例 | 现网行为 |
| --- | --- | --- |
| **两处都能存值** | `API_KEY`（`.env`）与 `models.defaults[].api_key`（`config.yaml` 明文） | `get_default_models`：**config 列表优先**，无列表才回退 env |
| **yaml 引用 env** | `config.yaml` 里 `api_key: ${API_KEY}` | 值只在 `.env`；yaml 是占位引用，经 `resolve_env_vars` 解析 |
| **代码内 fallback 链** | 多模态 `embed_api_key` → 再 fallback `API_KEY` | 各模块自行定义顺序（如 `multimodal_config.py`） |
| **文档声明 env 优先** | `embed_api_key` ↔ `EMBED_API_KEY` | 环境变量覆盖 config 字段 |

Web 配置保存也分流：`_CONFIG_SET_ENV_MAP` 里的项（含 `embed_api_key`、`jina_api_key` 等）**写 `.env`**；模型列表等**写 `config.yaml` 的 `models.defaults`**。

**本文件的设计选择：一条 logical key 只绑定一处物理位置，不在 yaml 里表达优先级链。**

| 操作 | 规则 |
| --- | --- |
| **`set`** | 只写 registry 声明的那一处（或无条目时写默认存储） |
| **`get`** | 只读 registry 声明的那一处（或无条目时读默认存储） |
| **迁移期** | 若现网仍有 fallback 链，由 SecretStore **代码层**做 legacy 读兼容（顺序在实现里固定，**不写进 yaml**）；兼容窗口结束后删除 |

因此：`llm.api_key` 若 registry 绑 `medium: env` + `path: API_KEY`，则 `store.get/set` 只碰 `.env`，**不会**同时读写 `config.yaml` 里的 `models.defaults[].api_key`。存量两处都有值时，迁移条目即选定** canonical 落点**；另一处逐步废弃。

---

### 6.2 解析规则


| 情况       | 本文件               | 结果                                                   |
| -------- | ----------------- | ---------------------------------------------------- |
| **默认**   | 无该 logical key 条目 | 持久化层按**默认存储**读写                                      |
| **显式映射** | 有条目               | 按 `medium` + `path`（及 `field`/`format`）读写，**覆盖**默认存储 |


业务代码只调 `store.get(key)` / `store.set(key, value)`，不引用 `medium`。

### 6.3 何时增加条目


| 存储需求      | 代码                        | 本文件     |
| --------- | ------------------------- | ------- |
| 走默认存储     | `store.get` / `store.set` | **不写**  |
| 须绑定已有物理位置 | 同上                        | **写**条目 |


新功能走默认存储 → 只写代码。存量迁移且暂不能改物理位置 → 加条目；完成后可删。

本文件**不是**全量 key 注册表：无条目 = 走默认存储。

### 6.4 排障


| 步骤  | 操作                                                                                  |
| --- | ----------------------------------------------------------------------------------- |
| 1   | 确认代码里 logical key                                                                   |
| 2   | 查本文件是否有该 key                                                                        |
| 3   | **有条目**：看 `medium` + `path` + `field` + `format`；`env`→`.env`；`file`→文件；`db`→持久化层文档 |
| 4   | **无条目** → 默认存储                                                                      |
| 5   | 仍有 `os.getenv` / 直读 yaml → 可能尚未迁到 SecretStore                                       |
