# Symphony：技能编排与智能分发
---

## 概念科普

### Symphony 是什么

Symphony（技能交响乐）是 JiuwenSwarm 面向海量已安装技能提供的技能编排与智能分发系统。它要解决的是两个问题：**怎么选**，以及**怎么用**。

- **技能检索**解决“怎么选”：把原本平铺的技能列表组织成可逐层浏览的技能树，让智能体按任务需求动态探索分支，找到候选技能。
- **技能编排**解决“怎么用”：基于候选技能、输入输出结构和技能依赖关系，生成一条可确认、可执行的技能链。

可以把 Symphony 理解为“双核心架构”：**检索用树，编排用图**。如果只需要调用一个明确的技能，按普通技能流程即可；Symphony 更适合“先找技能、再判断能否串起来、最后形成执行路线”的多步骤任务。在团队/集群模式中，这条路线也可以作为 Leader 分发后续任务的依据。

#### 用技能检索找到候选技能

技能检索是 JiuwenSwarm 面向**较大规模已安装技能**场景提供的技能目录检索能力。

当已安装技能数量较少时，智能体可以直接查看技能列表并选择合适技能；当技能数量达到几十、上百甚至更多时，直接把所有技能注入上下文会带来两个问题：

| 问题 | 影响 |
|------|------|
| 上下文占用过高 | 用户任务、文件内容和历史对话更容易被挤出上下文 |
| 注意力分散 | 模型容易被大量无关技能干扰，漏掉真正需要的技能 |

技能检索通过离线构建一棵**已安装技能树**，并在运行时提供目录浏览工具，让智能体像查目录一样逐层披露相关分支，再决定读取哪些 `SKILL.md`。

#### 用技能编排生成执行路线

如果说技能检索回答的是“选谁上场”，那么技能编排回答的就是“怎么让它们配合起来”。例如“先识别图片文字，再翻译，再写文案，最后发送邮件”这类任务，通常不是单个技能能完整完成的，需要把候选技能按输入输出依赖组织成一条稳定路线。

技能编排会围绕任务目标、已有输入和候选技能，参考技能图谱里的可衔接关系生成一条可执行路线。遇到缺失输入时，系统可以沿关系图反向查找能够补上该输入的上游技能；确认路线后，再继续执行具体技能。

技能编排的重点不是把技能简单排成列表，而是判断上游结果是否真的能喂给下游技能。可衔接关系、输入输出结构、任务语义都会影响最终编排。这样生成的不是“看起来相关”的技能组合，而是能够解释依赖关系、可确认、可执行的技能链。

技能图谱是编排使用的关系图。图中的每个节点代表一个技能，边代表一个技能的输出可以作为另一个技能的输入，也就是可衔接关系。它既可以帮助用户理解技能之间如何组合，也会为技能编排提供可参考的候选关系。

#### 根据实际使用效果持续优化编排

开启 **动态图谱** 后，Core 的 Symphony Observation 会收集执行证据并生成运行时图快照，Flow 会将满足阈值的成功技能组合沉淀为候选技能包。用户确认候选包后，JiuwenSwarm 完成审核与安装。关闭开关后，编排使用静态图谱，已积累的数据不会删除。

#### 它解决什么问题

- **技能太多时怎么选**：避免把所有技能说明一次性塞进上下文，让智能体按任务需要逐步找到候选技能。
- **技能选对后怎么用**：不只判断技能是否相关，还判断上游输出能否真正接到下游输入。
- **多技能流程怎么稳定串起来**：基于技能图谱里的可衔接关系生成可确认、可执行的技能链，减少临场拼接导致的中断。
- **复杂任务怎么解释和分发**：让用户或 Leader 能看清每个技能为什么被选中、结果如何传递，以及后续任务如何分发执行。

### 基本工作流

```text
安装技能
  ↓
需要时在后台构建本地技能树索引
  ↓
构建或读取技能图谱
  ↓
用户发起任务
  ↓
智能体读取会话技能清单
  ↓
通过 capability_search 的 type=["skill"] 列出分类或搜索技能
  ↓
发现候选技能
  ↓
技能编排基于任务目标、候选技能和技能图谱生成技能链
  ↓
用户确认
  ↓
继续执行具体技能
  ↓
动态图谱根据实际使用效果优化后续编排（仅开启时）
```

技能检索主要负责“找技能”；技能编排负责把候选技能组织成一条面向任务的执行路线；技能图谱负责展示和沉淀“技能之间能否衔接”，为编排提供关系图依据。技能检索和技能编排构成 Symphony（技能交响乐）的两类核心能力。

### 运行时工具

Discovery 提供 `capability_search`。技能检索开关控制分类树的构建与使用。启用技能交响乐后，智能体也能使用技能编排工具。系统根据任务选择工具。

#### 能力检索工具

| 工具 | 作用 | 使用时机 |
|------|------|----------|
| `capability_search` | 省略 `type` 会同时查询 Skill、专家和 MCP 服务。传 `"type": ["expert", "mcp"]` 可只查后两类。所选类型共享最多八条查询、分类范围、整页 `top_k` 和一个续页游标，也可用 `operation=list` 浏览。连接器归入 MCP，按服务汇总当前可用的工具和随包 Skill。 | 按任务找能力或所属服务。如果只需要已安装专家，例如安排独立审查，可传 `"type": ["expert"]`。 |

在自动权限模式下，显式指定 `"type": ["skill"]` 的检索可以走只读快速通道。省略 `type` 或选择专家、MCP 时，检索会调用宿主提供的目录，需要人工确认。

当技能检索找到相关技能后，智能体会根据技能名称和描述缩小候选范围；如果后续需要编排，这些候选技能会作为生成技能链的参考。

#### 技能编排工具

| 工具 | 作用 | 使用时机 |
|------|------|----------|
| `symphony_read_graph` | 查看技能关系图是否可用、是否需要更新 | 需要确认技能图状态时使用 |
| `symphony_refresh_graph` | 刷新技能关系图 | 图谱缺失、过期，或已安装技能变更时使用 |
| `symphony_compose_graph` | 根据可用能力规划任务，默认 `type=auto` 自动选择执行策略，`candidate_ids` 提供已筛选的候选 ID | 用户要求编排，或复杂任务需要规划时使用 |

开启渐进式工具加载时，智能体可以直接调用 `symphony_compose_graph`。

主智能体需要编排时调用 `symphony_compose_graph`，通常省略 `type`，由本次调用自动选择合适的执行策略。仅当用户明确要求技能工作流或专家任务分工时，显式指定 `skill` 或 `expert`。普通对话不会为每条新任务提前规划，也不缓存自动计划。

| strategy | 执行方式 | 是否生成图 |
| --- | --- | --- |
| `direct_answer` | 利用已知上下文直接回答 | 否 |
| `single_capability` | 使用一个 Skill 或现有工具 | 否 |
| `capability_workflow` | 主智能体协调多个 Skill 或工具 | 纯 Skill 生成技能图；工具或混合流程由主智能体执行 |
| `single_expert` | 一名已安装专家或临时角色 | 单节点专家任务图 |
| `multi_expert` | 多名专家互补、交接、隔离或并行 | 专家任务 DAG |

自动规划选择足以完成任务的简单策略。多个步骤或多个事项本身不要求多专家，单个 Skill 可以在内部使用多个工具。工具返回 `planned_graph` 时，主智能体按图中的节点和依赖处理任务。编排成功且无图时，主智能体直接使用可用能力继续处理。

自动规划传入 `candidate_ids` 时，只使用这些候选中当前可见、可用的能力；省略时才从可见能力中选择。空列表或无效 ID 不会回退到整个目录，候选不等于必选。候选可包含 Skill、专家或现有工具的准确 ID，专家策略仍可使用临时角色。

规划使用当前会话模型、原始任务和通过 `inputs` 提供的资料。调用时提供能力范围和必要约束，不复制会话历史或完整系统提示词。是否允许专家由程序控制；禁止时专家和临时角色均不可选。技能工作流使用技能图，专家任务计划无需技能图或已安装专家。结果通过工具消息和流程图展示。Plan 模式只展示专家计划，原有工具权限继续生效。

技能和专家编排都会在形成有效 DAG 时返回 `ready`，无法形成计划时返回 `no_plan`。主智能体可查看节点声明的输入、输出、依赖和 `missing_inputs`，结合会话中已有的材料选择可执行分支。确实需要用户提供资料时，由主智能体发起追问。

使用支持具名资料的 Core 版本时，两种编排均可通过可选的 `inputs` 传入已有资料。每项包含唯一的 `name`、`kind`（`text` 或 `file`）和字符串 `value`，也可用 `description` 说明用途。事实表等文件可传工作区内的可读路径，执行节点再通过工作区工具读取。

技能编排会根据原始任务、检索得到的候选技能及其可衔接关系生成技能链。若编排结果提示缺少合适技能，需要先通过 **技能** 页面搜索并安装新技能，再刷新技能图谱并重新编排。

任务有明确的专业工作规则、上下文隔离、互补分工或独立验证收益时，Core 可以选择专家层级。`type=expert` 在同一份任务图中安排已安装专家和临时内联角色，并沿用会话的规划模式。专家从已发布的专家层与实时安装清单的交集中选择。事先检索和匹配到已安装专家都不是专家编排的前提，整份计划也可以全部使用内联角色。任务节点标明分工，工具结果记录交接产物和接收方输入。Web 流程图为每个有向依赖绘制一条箭头，同一对节点可以通过该依赖交接多项产物。

可以在实例的 `.env` 中设置 `SYMPHONY_EXPERT_DOMAIN_HINTS`，用逗号或顿号列举适合专家分工的领域。宿主提示词按顺序保留完整领域名，渲染后的列表最多 160 个字符，含空格和分隔符。留空时省略示例，宿主也可以主动编排其他领域的任务。

用户明确要求检索时，主智能体调用检索工具；明确要求编排或任务需要规划时，按需调用编排工具并默认省略 type。若用户指定必须使用某位已安装专家，而该专家不可用，智能体应说明限制，不能静默用内联角色替代。

专家编排可在返回有效 DAG 的同时列出资料缺项。`ready` 表示任务图已通过结构校验。在单智能体工作会话中，用户要求完成任务时，主智能体须按计划 ID 和节点 ID 调用 `task_tool` 派发符合条件的节点，待前置任务完成后继续派发下游，不能只把计划当作参考再自行包办。仅需规划、看图或处于 Plan 模式时只展示计划。资料缺项属于提示：主智能体补齐真正的前置条件，继续执行不受影响的分支，并说明具体阻塞；派发能力不可用时说明限制。

主智能体默认信赖已完成的专家与内联角色结果，直接将其产物用于下游任务和最终交付，承担协调、验收和整合职责。独立验证由计划中的质检节点完成。只有具体错误、缺失交付物、证据矛盾或验收不通过才触发定向检查或修正，并保留有效结果；不能因主观担忧质量、一致性或耗时而重新完成专家的工作。

内联角色使用临时通用子智能体，已安装的原生专家加载模板中的人设、技能和工具。独立节点最多并行执行五个。Swarm 将前置节点的产物交给下游，并把失败或受阻的节点反馈给主智能体。

子智能体卡片显示各节点的 `task`。执行时，子智能体收到原始需求、节点任务、该节点引用的已有资料和上游产物。

已安装专家的卡片使用专家包的展示名和头像，名称随界面语言切换。缺少展示名时显示包名，头像不可用时显示默认头像。回看新执行的记录时，卡片使用派发当时的名称和头像。

## 操作指导

### 1. 准备已安装技能

Symphony 只会使用已安装技能。请先在左侧导航栏 **技能** 页面安装需要的技能。

技能安装方式见 [技能系统](技能.md)。

### 2. 开启技能检索

操作路径：

```text
左侧导航栏 → 配置信息 → 技能检索
```

打开 **启用技能检索** 后保存配置。

关闭该开关后，JiuwenSwarm 不会注册技能检索工具，也不会注入技能树提示，系统会回到原有技能使用流程。

### 3. 构建技能索引

操作路径：

```text
左侧导航栏 → 技能 → 技能索引 → 构建索引
```

构建过程会扫描已安装技能，读取技能名称、描述和 `SKILL.md`，并生成本地技能树索引。构建完成后会复用同一套索引，不需要每次启动都重新构建。

当以下情况发生时，建议重新构建：

- 安装、卸载或大量修改了技能。
- 页面提示索引缺失、过期或构建失败。
- 调整了树根分层配置、最大树深等构建参数。

### 4. 构建技能图谱

操作路径：

```text
左侧导航栏 → 技能 → 技能图谱
```

#### 如何解读技能图谱

| 元素 | 说明 |
|------|------|
| **节点** | 一个已安装技能，节点名称通常对应技能名称或技能 ID |
| **边** | 两个技能之间的可衔接关系，表示上游技能的输出可以供下游技能使用 |
| **方向** | `A → B` 表示技能 A 的输出可以接到技能 B 的输入 |
| **关联强度** | 系统判断两个技能可衔接程度的百分比；关联强度越高，越适合作为编排候选 |
| **入度** | 当前筛选条件下，有多少上游技能可以接入该技能 |
| **出度** | 当前筛选条件下，该技能可以接到多少下游技能 |

#### 页面区域说明

| 区域 | 用途 |
|------|------|
| **左侧面板** | 展示当前可见的技能数、关联数；支持构建图谱、调整最小关联强度、搜索技能和查看技能列表；构建时还会显示进度与日志 |
| **中间画布** | 展示技能关系图；可拖拽平移、滚轮缩放，也可用右上角的缩小、缩放百分比和放大控件调整视图；点击节点查看详情 |
| **右侧详情** | 展示选中技能的 ID、入度、出度、描述、任务和关联技能；页面较窄时会以右侧覆盖式详情抽屉打开，不压缩画布 |

右侧的 **关联技能** 中：

- `→` 表示当前技能可以向目标技能提供输出。
- `←` 表示当前技能可以接收上游技能的输出。
- `关联强度 85%` 表示当前技能与关联技能之间的可衔接程度。

#### 常用操作

| 操作 | 说明 |
|------|------|
| **搜索技能** | 在左侧搜索框输入关键词，同时筛选列表和图谱，并保留匹配技能的关联节点 |
| **调整最小关联强度** | 过滤关联强度低于当前阈值的边；数值越高，显示的关联越少 |
| **增量构建** | 在新增、删除或修改技能后，优先使用增量构建更新图谱 |
| **取消构建** | 图谱构建耗时较长时可取消；已经完成的部分会保留，之后可以继续构建 |
| **全量构建** | 当图谱异常、关系明显过旧或需要彻底重算时使用 |
| **调整视图** | 将当前可见图谱重新居中并缩放到合适大小 |

#### 最小关联强度说明

“最小关联强度”滑块只影响当前显示的关联，不会重新计算技能关系。如果希望重新生成候选关系，需要执行增量构建或全量构建。

### 5. 使用技能检索

通常不需要用户手动调用工具。正常输入任务即可，例如：

```text
请优先利用当前已安装技能完成该任务；如果发现相关技能，请结合技能内容给出结果。

我有一份 PDF 合同和一份 Excel 表格，请提取关键条款，核对金额字段，并生成一份中文审阅报告。
```

启用技能检索后，模型会先浏览技能树，找到可能相关的 PDF、Excel、文档审阅、报告生成等技能，再决定读取哪些 `SKILL.md`。

### 6. 查看检索过程

在聊天消息中展开技能检索树，可以看到：

- 模型探索了哪些第一层分类。
- 哪些分支被 `peek` 查看过。
- 哪些分支被 `explore` 展开。
- 最终出现了哪些候选技能。

如果某个技能被认为相关，模型后续可能会读取该技能的 `SKILL.md`，再按技能说明执行任务。

### 7. 使用技能编排

#### 使用前准备

1. 打开左侧导航栏 → **技能** → **技能图谱**。
2. 在页面顶部开启 **启用技能编排**；开关点击后会自动保存并立即生效。
3. 确认任务需要的技能已经安装；如果刚新增、删除或修改过技能，建议先到 **技能** → **技能图谱** 中执行一次 **增量构建**。进入页面时会自动读取当前图谱。

这里的 **启用技能编排** 是 Symphony 编排总开关；技能检索仍由配置页中的 **技能检索** 开关单独控制。

#### 推荐的提问方式

在对话里直接说明要使用技能，并把任务目标、输入材料、期望输出和后续动作一次说清楚。

**推荐模板：**

```text
使用 Skill，帮我完成 <最终目标>。
输入是 <文件、链接、文本或账号信息>。
需要输出 <结果格式或交付物>，然后 <是否继续执行下一步动作>。
```

**示例：**

```text
使用 Skill，将一张英文技术博客图片翻译成中文，
并写一段公众号介绍文案后发送到我的邮箱。
图片位置：<本地位置或图片连接>
```

更容易触发技能编排的写法：

- 明确写出“使用 Skill”或“使用技能”。
- 描述完整目标，而不是只写单个步骤。
- 如果希望系统继续执行，明确说“按照编排结果执行”或“确认后继续执行”。

#### 看懂编排结果

开启后，系统会先返回一张技能编排图和简短说明。图中的每个方块是一个技能，箭头表示执行顺序和结果传递关系。下面示例中，系统先规划出 `image-translate → yescan-ocr-universal → general-writing → imap-smtp-email` 的路线，再说明每个技能分别负责翻译图片、提取文字、撰写文案和发送邮件。



看到编排结果后，可以继续这样回复：

- **路线正确**：回复“按照编排结果执行”。
- **缺少信息**：补充系统提示中缺少的文件、链接、邮箱、账号或参数。
- **只想看方案**：不确认执行即可，编排结果本身可以作为技能组合建议。

> **提示**：技能编排只会基于当前已安装技能和可用配置进行规划。如果结果提示没有合适技能，需要先安装对应技能，再刷新或重建技能图谱后重试。

#### 查看专家任务

使用专家编排时，可以在子智能体详情中查看本节点的任务、要求、产物和验收标准。产物名称和格式对应任务图中该节点声明的输出，子智能体按验收标准检查产物后提交。

## 配置说明

用户配置文件为 `~/.jiuwenswarm/config/config.yaml`。`symphony` 节点直接校验为 Core `SymphonyConfig`；Swarm 只解析宿主目录、环境变量、产品缺省值和会话模型上下文。显式配置优先，未知字段按完整路径报错。

### 开关、模型和会话

- `retrieval.enabled` 控制分类树检索。开启「发现技能包」后，Swarm 在运行时启用所需的编排能力，接收新观测并沉淀技能包。Swarm 默认关闭这些开关，`null` 继承缺省值。
- 面板的「发现技能包」保存 `orchestration.experience.enabled`。规划是否采用已有动态观测由 `orchestration.plan.dynamic_graph_enabled` 独立配置。
- 分类树和关系图使用宿主默认模型构建；在线编排使用当前会话模型。没有独立检索 `llm` 配置。指纹 `max_output_tokens: null` 沿用宿主模型输出预算。
- Discovery 的 `retrieval.prompt.context_window_tokens` 缺省由实际会话模型解析，显式值优先。配置保存影响新会话；已建立会话的预算与索引版本保持冻结。工具和提示 Rail 共用绑定在智能体 Runtime 上的能力目录。
- `capability.sources` 按 `type` 和 `root` 声明目录。Skill 与独立专家包共用一棵分类树。会话 Skill 检索按宿主可见范围和禁用规则过滤。单智能体和团队会话均从宿主已安装目录检索专家。显式配置专家来源时，检索和专家规划均按已安装独立专家的实际 manifest 路径取交集。省略专家来源时，检索目录也包含已安装专家组的非队长成员。关系图以一个 Skill 来源为基础，可同时纳入配置的专家来源。

### 目录与重建

省略 `capability.sources` 时，Swarm 使用工作区 `skills` 目录。显式列表整体替换默认值。`storage.artifact_root` 为空时使用工作区 `symphony/runtime`。模板允许通过 `SYMPHONY_ARTIFACT_ROOT` 设置产物根目录。多目录或含专家的集合在 `taxonomy_collections/<scope_id>` 下构建分类树。添加专家来源后刷新分类树和编排图，混合图从原图谱入口发布。

旧的 `paths`、`fingerprint`、`build`、`skill_retrieval`、`evolution` 顶层配置以及旧模型后端节点不再接受。旧缓存签名和目录布局不能复用，需要按新配置重新构建；系统不会自动迁移或删除旧目录。刷新失败保留上一可用版本，取消后不发布。

部署本次 Retrieval 配置时重新获取 YAML 模板。现行 Runtime 布局中的分类树和 v2 Discovery 会话快照可以继续使用。

### 构建与发现参数

以下路径相对于 `symphony`。并发和批量的“模板值”是主模板显式设置，不等同于程序缺省值。

| 配置 | 缺省/模板 | 作用 |
|---|---|---|
| `capability.fingerprint.extraction.max_concurrency` / `batch_size` | 缺省 `1/1`，模板 `4/2` | 指纹提取；实际并发还受构图并发上限限制 |
| `orchestration.build.max_concurrency` / `matching.batch_size` | 缺省 `1/12`，模板 `4/16` | 关系匹配并发和批量 |
| `orchestration.min_edge_confidence` | `0.5` | 构图和规划共用的关系阈值 |
| `orchestration.build.matching.require_consensus` | `false` | 是否要求关系判断共识 |
| `orchestration.plan.mode` | `fast` | 支持 `fast` 和 `beam`；`top_k` 仅束搜索使用 |
| `retrieval.index_build.structure.branching_factor` / `max_depth` | `128/6` | 树拆分阈值基数和深度；元戎模板分支为 `12` |
| `retrieval.index_build.structure.max_capabilities_per_node_multiplier` | `1.5` | 递归构树叶节点容量倍率；一次性构树不依此拆分 |
| `retrieval.index_build.structure.root_categories` | `null` | 根分类列表或文件；可通过 `children` 预设下级分类 |
| `retrieval.index_build.request.max_concurrency` / `timeout_seconds` | `2/420` | 构树请求并发和秒级超时 |
| `retrieval.index_build.request.classification_batch_limit` | `32` | 递归分类调用批量 |
| `retrieval.index_build.task.total_timeout_seconds` | `0` | 整体构建超时，`0` 表示不限 |
| `retrieval.output.max_chars` | `12000` | 目录操作输出字符上限 |
| `orchestration.experience.acceptance.min_successes` | `3` | Flow 接纳成功证据次数 |

根分类用于稳定目录骨架，包含 `id`、`name`、`description`，可选 `select_when`、`dont_select_when` 和 `children`。下例显式开启功能；默认模板保持关闭。修改构建策略后重新构建，规划、Flow 阈值和展示设置不会无故使分类树缓存失效。

```yaml
symphony:
  capability:
    sources:
      - type: skill
        root: /path/to/skills
      - type: expert
        root: /path/to/agent_templates/local
    fingerprint:
      extraction:
        max_concurrency: 4
        batch_size: 2
        max_output_tokens: null
  storage:
    artifact_root: ""
  retrieval:
    enabled: true
    index_build:
      structure:
        branching_factor: 128
        max_depth: 6
        max_capabilities_per_node_multiplier: 1.5
        root_categories:
          - id: office-docs
            name: Office documents
            description: Read, edit and generate office files.
      request:
        max_concurrency: 2
        max_retries: 2
        timeout_seconds: 420.0
        classification_batch_limit: 32
      task:
        total_timeout_seconds: 0.0
        preserve_previous_index_on_failure: true
    use_existing_index: true
    output:
      max_chars: 12000
  orchestration:
    enabled: true
    min_edge_confidence: 0.5
    build:
      max_concurrency: 4
      matching:
        batch_size: 16
        require_consensus: false
    plan:
      mode: fast
      max_depth: 4
      dynamic_graph_enabled: true
    experience:
      enabled: true
      acceptance:
        min_successes: 3
        min_pack_success_rate: 0.8
```

## 常见问题

### 为什么开启后模型没有调用技能检索工具？

可能原因：

- 当前任务已经明确指定了技能。
- 当前任务不需要已安装技能。
- 索引未构建，且模型尚未触发检索工具。
- 技能检索开关未开启。

可以在任务中明确说明“请优先利用当前已安装技能完成该任务”。

### 为什么工具提示索引未构建？

请进入：

```text
技能 → 技能索引 → 构建索引
```

构建完成后再次发起任务。

### 为什么构建时间较长？

构建会读取所有已安装技能，并调用模型生成分支和分类。技能越多、树越深，耗时越长。构建完成后索引会复用，不需要每轮对话重建。

### 为什么技能图谱构建时间较长？

技能图谱构建需要读取已安装技能，并分析技能之间的输入输出和语义衔接关系。技能越多、关系越复杂，耗时越长。构建完成后可以直接读取图谱，不需要每轮对话都重建。

### 技能检索和技能图谱有什么区别？

技能检索负责从大量已安装技能中找到候选技能；技能图谱负责描述候选技能之间是否能够衔接。前者像查目录，后者像看技能之间的连接图。

### 技能检索和技能编排是什么关系？

技能检索和技能编排都是 Symphony 的组成部分。技能检索负责缩小候选技能范围；技能编排负责根据任务目标、候选技能和技能图谱生成执行路线。

### 它会自动安装新技能吗？

不会。Symphony 只使用已安装技能。安装新技能仍需通过 **技能** 页面完成。

### 它会替代集群模式的 Leader 派发吗？

不会。Symphony 可以帮助 Leader 或普通智能体找到相关技能并形成技能链。具体如何拆解任务、读取技能、执行工具、组织团队，仍由 JiuwenSwarm 原有运行模式完成。

### 构建技能图谱和生成执行图是一回事吗?

这里有一个容易混淆的点：构建技能图谱不是生成执行图。构建技能图谱通常发生在任务到来之前，关注的是整个技能库里，哪些技能之间可能存在稳定的可衔接关系。生成执行图发生在任务到来之后，关注的是面对这次具体需求，应该从技能图谱中选出哪些技能、按什么顺序执行，以及哪里需要补充输入材料。

## SkillPack：Hub 兼容发布

使用包含 SkillPack 特性的新版 WorkSwarm，在“设置 → 实验功能”开启“发现技能包”，即可从已有薄 SkillPack 的详情页发起发布。成员必须是独立普通 Skill，不支持 SwarmSkill 或嵌套 Pack。

新发布固定复用普通 Skill 通道，无需配置 `SKILLPACK_HUB_TRANSPORT_PROFILE` 或 `SKILLPACK_HUB_DEPLOYMENT_SCOPE`；这两个环境变量不再控制新发布。历史发布记录仍按原协议恢复。开启功能不等于自动公开发布，仍需用户确认并经过 Hub 审核。

一次预检列出成员的“复用／先发布／阻断”，用户确认后先上传缺失成员并等待审核，再发布 Pack。Pack 失败不删除已经成功发布的独立成员；重新打开面板可继续查询原操作，内容变化必须重新准备并确认。

薄 ZIP 包含外层 `plugin.yaml`、根说明和 `skillpack.lock.json`，不复制成员源码。锁按顺序记录精确 Hub asset ID、版本及原始 ZIP SHA-256。消费端必须支持成员锁，并从同一 Hub 独立下载成员，普通单 Skill 安装器不能替代这一步。发布／安装契约测试使用共享安装器检查实际生成的包，但不会单独开启技能广场的安装入口。

Hub 连续三次网络检查失败后停止自动轮询，网络恢复后由用户明确重试原操作，沿用已有上传标识。正常审核等待不算网络失败；轮询逐步放缓至 30 秒，已审核成员不反复查询，Pack 上传前及完成前仍完整检查成员闭包。授权失效或上传结果不明时停止自动推进，用户处理原因后可重试原操作。

本地模拟测试不代替真实 Hub 审核、模型或桌面平台验收，结果应分别记录。关闭“发现技能包”会停止新 Pack 发布，不会下架既有资产，也不会中断已确认开始的发布。

### 开发与维护边界

检索、指纹提取、图谱编排和演化算法由 `openjiuwen.symphony` 提供。JiuwenSwarm 的应用适配负责模型配置与用量、构建状态、Web/RPC、运行时工具以及技能包安装；配置解析位于 `jiuwenswarm/common/symphony_config.py`。部署升级需要包含对应公开接口的 openjiuwen 版本。删除无调用的 SDK 遗留不改变持久化图谱目录和用户配置路径。

## SkillPack：沉淀、复用与安装

SkillPack 是单 Agent 使用的复合 Skill。根 `SKILL.md` 说明成员的执行顺序；成员仍是可以单独使用的普通 Skill，不包含 SwarmSkill 或嵌套 SkillPack。

### 开启

在“设置 → 实验功能”开启“发现技能包”，统一启用沉淀、确认复用、安装与发布；对应持久化配置为 `symphony.orchestration.experience.enabled`，无需额外开启 Symphony。旧 `SKILLPACK_PRODUCTIZATION_ENABLED`、`SKILLPACK_DIRECT_ROUTE_MODE` 和 `skillpack.direct_route_mode` 不再覆盖页面设置。

关闭后停止新的自动发现、自动复用、沉淀、安装和发布；保留已安装包的查看、卸载、成员引用保护，以及显式选包后的安全执行。已确认开始的执行、安装或发布不因关闭设置而中断；单个技能包的启停及原有权限校验仍生效。

### 使用

- 对话中请求沉淀已完成的多 Skill 流程，Agent 调用 `skillpack_distill`。候选来自持久化的真实执行记录；查看成员和说明并确认后才安装。
- 自动发现会检查当前已安装的技能包：已有完整成员及相同有向执行链的包时，不再重复提示创建，跨会话和重启后也生效。禁用已有包不会触发重建；不同执行顺序仍按不同组合处理。显式请求沉淀、安装确认和执行校验保持不变。
- 创建时若本地已有同名 Skill 或 SkillPack，会提示创建失败并保留确认卡片，已有内容不会被覆盖。可以选择“暂不创建”，或处理同名冲突后重试；重试仍会检查成员和执行证据。 WebSocket 与 HTTP 确认均等待最终结果，接收 ACK 不代表创建完成；HTTP 使用 Gateway 显式启用的最终答复回执。超时或断连时保留确认卡，并提示先检查“我的技能”再重试。
- 安装后在“我的技能”与任务“+ → 技能”中使用，卡片显示 SkillPack 类型。成员状态变化会影响整个 Pack 的可用性。
- 新 query 完整匹配本地 Pack 时，先确认使用该 Pack；多个匹配由用户选择。确认后直接加载根说明与成员，跳过 Symphony 编排。部分匹配和不确定情况仍走原有流程。执行成员后失败不会自动再编排，以免重复副作用。
- 显式选择一个 Pack 视为已确认；与普通 Skill 混选时再次选择使用方式。外部写入等权限仍按原有机制确认。
- 选择“继续智能编排”、跳过或取消本次复用问答，均表示本请求不使用整包，继续普通任务处理，不反复询问。同会话的下一条新消息重新判断，不继承上一任务的确认或阻断状态。
- 自动匹配判断最多等待 60 秒；超时表示没有得到判定，不等于判定不匹配。超时或未匹配时继续普通流程，不能借普通 `skill_tool` 直接执行未确认的 Pack；该入口仅返回只读摘要。超时原因记录在后台日志，当前页面不单独显示该原因。
- 未确认读取按 `skill_tool` 当前会话中的实际目录识别目标，包括外置技能和恢复会话；只新读目标根文件，不因无关库存扫描或锁失败阻断普通 Skill，也不靠旧类型缓存放行。目标自身不可读或类型无法可靠识别时保守拒绝；确认后的 Pack 执行仍使用实时库存及成员校验。
- 已确认的 Pack 执行中若状态变化或校验失败，直接返回停止说明，不再让模型在清空工具后继续生成，也不会自动改为重新编排。

### 安装和管理

Pack ZIP 只包含外层 `plugin.yaml`、根说明和 `skillpack.lock.json`，不复制成员源码。锁定清单按顺序记录每个成员的 Hub asset ID、精确版本和原始 ZIP SHA-256。成员从同一 Hub 单独下载。

技能广场安装 Pack 时，会先展示安装计划。来源、版本、ZIP 摘要和本地内容都一致的成员可复用；缺失成员下载；同名冲突或本地修改会阻断。全部内容校验通过后统一安装，并保存 `.archive` 副本。失败会恢复目录和登记状态；进程中断后在加载技能前恢复未完成事务。

确认时若计划过期或本地库存变化，会重新展示一次最新计划，仍需用户再次确认；完整性校验失败不会自动重试。技能目录被其他操作占用时会提示稍后重试，不显示内部锁文件路径。

卸载 Pack 只删除 Pack，不删除成员。普通 Skill 仍被已安装 Pack 引用时，卸载会被拒绝并列出引用方。

### 运维边界

若事务日志损坏、安装目录归属改变或备份缺失，启动会明确报告待修复的事务路径并停止加载该库存；不会删除事务后强行启动。运维应先保留现场，核对目录标记与状态备份后恢复，避免把半安装结果暴露给 Agent。

安装计划和事务位于当前技能目录的 `.skillpack/`，Hub 来源记录位于各技能 `.archive/hub-provenance.json`。这些文件不随 Pack 发布。关闭产品开关会停止新的沉淀和 Pack 安装；已有普通 Skill 入口及显式选包后的安全执行保留。

部署必须同时使用本特性的 agent-core 和 JiuwenSwarm 改动。Core 版本以当前 `pyproject.toml` 与 `uv.lock` 中一致固定的提交为准，必须包含新的 Runtime 接口。真实 Hub 审核、实际模型和各桌面平台的验收结果应单独记录，不能由本地模拟测试替代。
