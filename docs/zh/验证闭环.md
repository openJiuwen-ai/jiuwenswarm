# 验证闭环（`run_tests`）

Code 模式可以通过专用工具 `run_tests` 运行项目测试，而不是由模型在 bash 中拼 `pytest …` / `npm test` 命令并把原始输出读回上下文。工具会为模型修改过的文件挑选相关测试、返回精简结果，其结论由「实现完成度门控」直接记为验证证据。

English: [Verification Loop](../en/VerificationLoop.md)

## 1. 为什么需要

第 1 波 A/B 评测（SWE-bench Pro 10 题、deepseek-flash、门控开）的实测：

| 观察项 | 数值 |
| --- | --- |
| 运行测试或 Python 的 bash 调用（repo 臂） | 约 200 次中的 106 次 |
| 搜索代码的 bash 调用 | 58 次 |
| 每次模型调用的输入 token（中位数） | 40–45k |

运行测试是 shell 的最大单项用途，而且每次运行的完整输出都会进入上下文。完成度门控也只能靠匹配命令字符串「猜测」一条 shell 命令是否是真正的测试运行。`run_tests` 同时解决这两点：一次调用运行正确的测试，模型看到有上限的摘要，门控拿到结构化结论。

## 2. 工作方式

```text
模型 ── run_tests(files=[...]) ──► RunTestsTool.invoke
                                     ├─ discovery.discover_tests(root)       （有缓存；只读项目文件）
                                     ├─ tool.plan_runs(...)                  （tests > files 映射 > 全量）
                                     │    └─ mapping.map_files_to_tests(root, files)
                                     ├─ runner.run_framework(fw, targets)    （argv、超时、解析、落盘）
                                     └─ runner.render_summary(results)       （≤ max_summary_chars）
               ToolOutput(success=True, data={content, outcome, passed_languages, results})
      ImplementCompletenessRail.after_tool_call ── evidence.parse_run_tests_evidence
                                     └─ ImplementationStateMachine.record_verification_evidence(languages, success)
      CodeExecutionDisciplineRail.after_tool_call ── 同一证据 → 清除「验证检查点」提示
```

### 2.1 框架发现（`verification/discovery.py`）

只读取项目文件，不 import 项目代码，不启动子进程。

| 框架 | 识别依据 |
| --- | --- |
| pytest | `pytest.ini`；`pyproject.toml` 中的 `[tool.pytest…]`；`tox.ini`/`setup.cfg` 中的 `[pytest]`/`[tool:pytest]`；`conftest.py`；否则按 pytest 默认规则命名的测试文件（`test_*.py`、`*_test.py`），范围为 4 层目录以内，包括项目根目录 |
| unittest | Python 项目（`pyproject.toml`/`setup.py`/`setup.cfg`/`tox.ini`）但没有任何 pytest 迹象 |
| vitest / jest | `package.json` 依赖中有 `vitest` / `jest` / `ts-jest` |
| npm test | `package.json` 中有真实的 `scripts.test`（忽略 npm 默认占位脚本） |
| go test | `go.mod` |
| cargo test | `Cargo.toml` |

测试文件扫描按广度优先进行且有上限（最多 400 个目录、4 层深）。与 pytest 本身一致，它跳过隐藏目录、`node_modules`、`venv`、`build`、`dist`、`site-packages`、`*.egg-info` 以及含 `pyvenv.cfg` 的目录，并且不跟随符号链接。

结果按工作区根目录缓存，任一探测文件或根目录发生变化即失效。没有 Python 框架的结果不会被复用，因此会话中后来新写的测试文件在下一次调用时就能被发现。

**仅凭测试文件名识别的项目。** 当 pytest 是从文件名而不是配置识别出来时，`run_tests` 会先检查项目解释器（§2.3）能否 import pytest。该检查是一个很短的子进程；结果为「能」时会按解释器记住。如果没有 pytest，且测试文件使用 `unittest`，则改用 `python -m unittest` 运行，摘要中会注明。否则调用返回 `error`，说明中写明解释器以及解决办法：在项目环境中安装 pytest、设置 `modes.code.run_tests.python`，或用 `bash` 运行测试。

什么都没有识别到时，错误信息会列出检查过的全部内容。

### 2.2 选择运行哪些测试（`tool.plan_runs`、`verification/mapping.py`）

每个 `tests` 与 `files` 条目先做校验：路径部分（可选的 `::node::id` 之前）在跟随符号链接后相对工作区根目录解析，必须位于根目录内；以 `-` 开头的条目直接拒绝，因此目标永远不会被当作运行器选项。任一条目被拒绝时整个调用失败，并在错误中指出该条目。

1. 传了 `tests`：精确运行这些 id，按语言分组（`tests/test_x.py::test_y`、`web/a.spec.ts`、`./pkg`）。
2. 传了 `files`：把每个修改过的源文件映射到测试：
   - 文件本身就是测试文件时直接选中；
   - 任意位置的同名测试（`test_foo.py` / `foo_test.py`；`foo.test.ts` / `foo.spec.ts` / `__tests__/foo.ts`）；
   - Go：文件所在的包目录（`./dir`）；
   - Python：反向 import 索引——`import` / `from … import` 行提到被修改模块的测试文件（支持 `src/`、`lib/` 布局）；
   - 某语言没有映射到任何测试时，默认返回 `no_tests` 并提示显式传 `tests`；`fallback_whole_suite: true` 时改为运行该语言的全部测试，并在摘要中说明。
3. 都没传：运行检测到的全部测试套件（模型明确要求时）。

遍历会跳过 VCS、依赖与缓存目录，并有上限（2 万个文件；最多扫描 2000 个测试文件的 import）。

### 2.3 运行（`verification/runner.py`）

- 不经 shell，直接用 argv，绝不使用内置解释器。Python 解释器按以下顺序选择：已设置的 `modes.code.run_tests.python`、`<root>/.venv/bin/python`、`<root>/venv/bin/python`、`$VIRTUAL_ENV/bin/python`，最后是 `PATH` 上的 `python` / `python3`。桌面用户通常没有激活的 shell，因此优先使用项目自己的虚拟环境。
- pytest 的命令为 `python -m pytest -q -rfE --no-header --tb=short -p no:cacheprovider <extra_args> -- <targets>`；jest 同样在 `--` 之后放目标；vitest、go、unittest 以位置参数传目标（目标已校验不以 `-` 开头）。
- `extra_args` 是唯一的选项通道，按运行器使用**允许列表**校验（`verification/argpolicy.py`），只允许选择、筛选或调整输出格式的选项：

  | 运行器 | 允许的选项 |
  | --- | --- |
  | pytest | `-q` `-v` `-x` `-s` `-l` `--lf` `--ff` `--nf` `--sw` `--no-header` `--no-summary` `--strict-markers` `--runxfail` `--disable-warnings` `--maxfail N` `-k EXPR` `-m EXPR` `--deselect ID` `--durations N` `-r CHARS` `--tb STYLE` `--capture MODE` `--color` `-n N` `--timeout N`（及对应长选项） |
  | unittest | `-v` `-q` `-f` `-b` `-c` `--locals` `-k PATTERN` `--durations N` |
  | jest | `--ci` `--silent` `--verbose` `-i`/`--runInBand` `--bail` `--no-coverage` `--coverage=false` `--detectOpenHandles` `--forceExit` `--no-cache` `-t`/`--testNamePattern` `--maxWorkers` `--testTimeout` |
  | vitest | `--silent` `--no-file-parallelism` `--no-coverage` `-t`/`--testNamePattern` `--bail N` `--retry N` `--maxWorkers` `--testTimeout` |
  | go | `-v` `-short` `-failfast` `-race` `-cover` `-run RE` `-skip RE` `-count N` `-parallel N` `-cpu LIST` `-timeout D`（单横线或双横线） |
  | cargo | `-q` `--release` `--no-fail-fast` `--lib` `--bins` `--tests` `--doc` `--workspace` `--all-features` `--no-default-features` `--locked` `--offline` `--frozen` `-j N` `-p NAME` `--features F` `--test NAME` `--bin NAME`、测试名筛选，以及 `--` 之后的 `--exact` `--nocapture` `--ignored` `--include-ignored` `--show-output` `--test-threads N` `--skip NAME` |
  | npm 脚本 | `scripts.test` 直接运行 `jest` / `vitest run` 时使用对应列表；否则拒绝 `extra_args` |

  其余一律拒绝，包括：裸位置参数（会成为绕过 `tests` 路径约束的额外测试路径）、`@argfile` 展开、组合短选项（除非每个字母都是允许的无值选项）、以 `-` 开头的独立取值。加载代码或配置的选项（`-p`、`-c`、`--rootdir`、`--config`、`--setupFiles…`、`-toolexec`、`-Z` 等）、写文件的选项（`--junitxml`、`--debug`、`--logfile`、覆盖率报告）以及把输出发往外部的选项（`--pastebin`）都不在任何列表中。
- 子进程环境中移除 `PYTHONSAFEPATH`、`PYTHONNOUSERSITE`、`PYTHONHOME`，避免启动脚本导出的变量让仓库根目录的 `import <pkg>` 失败。会注入运行器选项、插件或包装程序的变量（`PYTEST_ADDOPTS`、`PYTEST_PLUGINS`、`NODE_OPTIONS`、`GOFLAGS`、`RUSTC_WRAPPER`、`RUSTC_WORKSPACE_WRAPPER`、`CARGO_BUILD_RUSTC_WRAPPER`、`RUSTFLAGS`、`CARGO_ENCODED_RUSTFLAGS`、`RUSTDOCFLAGS`）也会移除，除非设置 `inherit_runner_env: true`。
- 超时是整次调用的一个预算：依次运行的多个框架共享它，剩余不足 5 秒的框架记为 `timeout`（未启动）。输出通过工具自己持有的管道读取：测试进程退出后，仍持有其输出的子进程有 2 秒时间，随后杀掉进程组并关闭管道，因此测试遗留的后台进程不会把已完成的运行变成超时。无论是否超时都会杀掉进程组；已脱离到独立会话（`setsid`）的子进程会存活，但失去管道。
- 内存中的输出有上限：保留前 1 MB 和最后 4 MB 用于解析和摘要。
- 完整输出写入 `<agent workspace>/run_tests/<时间>-<框架>-<id>.log`。该目录位于 agent workspace 内，Code 模式沙箱（`restrict_to_sandbox`）允许 `read_file`/`grep` 打开，且绝不会写进用户的代码仓库。单个文件上限为 `spill_max_bytes`（保留头部与尾部，中间以标记说明被丢弃的字节数），目录超过该上限时删除最旧的文件；2 分钟内的文件不会被其他调用删除，因此并发调用不会互相删掉输出。

结果（outcome）：

| outcome | 含义 | 对门控的影响 |
| --- | --- | --- |
| `passed` | 退出码 0 且至少*执行并验证*了一个测试（跳过、取消选择、xfailed、xpassed、unittest 预期失败、go「[no tests to run]」都不算） | 所运行语言的验证成功 |
| `failed` | 执行了测试且至少一个失败 | 验证失败 |
| `timeout` | 超过 `timeout` 秒被杀 | 验证失败 |
| `no_tests` | 没有验证任何东西：未收集到、全部跳过、只有预期失败、go 包中没有匹配的测试、JS 运行器输出中没有可解析的计数，或未映射到测试且回退关闭 | 不计证据 |
| `error` | 收集/用法错误、找不到运行器、无法解析的退出 | 不计证据 |

有失败用例的运行仍然是**成功的工具调用**（`success=True`）：模型看到的是摘要而不是错误。只有「未检测到测试框架」/「没有可运行的内容」返回 `success=False`。

### 2.4 门控证据

`ImplementationStateMachine.record_verification_evidence(languages, success, command)` 设置与 shell 路径相同的字段（`verification_attempted`、`verification_succeeded`、`verification_revision`），但已验证的语言由调用方显式给出。之后再次编辑同样会使验证过期，且每种被修改的语言仍需各自的测试通过。原有的 bash 命令正则路径保持不变；两种证据并存，以最近一次为准。

按语言判断证据（`data.language_outcomes`），而不是看整体 outcome：整体 `outcome` 只有在所有框架都通过时才是 `passed`，否则 Python 通过而 npm 没有测试时，Python 的通过会被丢掉。任一语言失败或超时即为失败证据；否则只要有语言真正通过就算证据，门控仍要求每个修改过的语言都在 `passed_languages` 中。

## 3. 配置

在 `modes.code.tools` 中列出 `run_tests` 即启用（随附的配置模板已列出）。从列表中删除即可关闭工具、其提示段以及 swarm 元素。已有安装保留自己的 `config.yaml`，不会自动获得 `run_tests`，需要手动加入 `modes.code.tools`（以及 `run_tests` 配置块）。

```yaml
modes:
  code:
    tools:
      - run_tests
    run_tests:
      timeout: 600               # 每次 run_tests 调用的总预算秒数（模型可以要求更短，不能更长）
      max_summary_chars: 6000    # 摘要上限，约 1.5k token
      spill: true                # 完整输出写入文件
      spill_dir: ""              # 为空 = <agent workspace>/run_tests
      spill_max_bytes: 52428800  # 单个文件与目录上限，先删最旧的；0 = 不限
      python: ""                 # 解释器路径；为空 = .venv → venv → $VIRTUAL_ENV → PATH
      fallback_whole_suite: false  # 修改的文件映射不到测试时是否跑该语言全量
      inherit_runner_env: false    # 是否把 PYTEST_ADDOPTS / NODE_OPTIONS / GOFLAGS / RUSTC_WRAPPER 等传给测试
```

| 键 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `timeout` | 数字 | `600` | 整次调用的总预算，多个框架依次运行时共享；限定在 5–7200；工具卡同时声明「预算 + 60 秒」为 agent-core 外层超时（默认 300 秒，否则会先于工具自身超时被截断） |
| `max_summary_chars` | 整数 | `6000` | 限定在 500–50,000 |
| `spill` | 布尔 | `true` | 关闭后不写文件，模型只能看到摘要 |
| `spill_dir` | 字符串 | `""` | 显式目录必须在沙箱内可读才有意义 |
| `spill_max_bytes` | 整数 | `52428800` | 单个文件与目录上限；`0` 表示不限 |
| `python` | 字符串 | `""` | 显式解释器路径或命令名；为空按 §2.3 的顺序 |
| `fallback_whole_suite` | 布尔 | `false` | 关闭：未映射的修改返回 `no_tests` 并要求传 `tests`；开启：运行全量（大仓库开销大） |
| `inherit_runner_env` | 布尔 | `false` | 关闭：移除 Agent 环境中的运行器选项变量；开启：传给测试（适用于依赖这些变量的环境） |

权限：模板在 `permissions.tools` 中把 `run_tests: allow` 列在 `bash: allow` 旁边，权限层把它归为代码类工具（`dynamic_execution`，高风险）。自动权限模式下，不属于 JiuwenBox 执行工具的代码类工具一律转人工审核（`requires_manual_execution_provider_review`），因此 run_tests 在该模式下不会被自动放行。执行 shell 命令前需要确认的部署也应把 `run_tests` 设为 `ask`。

沙箱模式：run_tests 在宿主机上启动测试进程，而不是经由 JiuwenBox。Code 会话的 SysOperation 处于沙箱模式（`OperationMode.SANDBOX`）时，适配器与 swarm 元素都不注册该工具；若之后 SysOperation 被切换为沙箱，已有实例会拒绝每次调用。此时测试命令应通过沙箱内的 bash 运行。这样模板中的 `run_tests: allow` 不会绕过沙箱。审批请求显示工具参数（`files`、`tests`、`extra_args`）；解析后的完整命令行在工具结果中（`data.results[].command`）。

工具参数：`files`（列表）、`tests`（列表）、`extra_args`（列表，运行器选项，须在允许列表内）、`timeout`（整数）。

## 5. 如何确认它在工作

- 工具已注册：适配层日志 `[JiuwenSwarmCodeAdapter] Tool run_tests registered from config`。
- 调用结果第一行是机器可读的，例如 `run_tests: outcome=failed passed_languages=-`，随后每个框架一行、失败用例 id 及回溯尾部，以及 `full output: <路径>`。
- 完整输出文件位于 `<agent workspace>/run_tests/` 下。
- 编辑后一次通过的运行之后，下一次模型调用时 `implement_completeness` 与 `code_execution_discipline` 提示段消失。

## 6. 限制

- 映射是启发式的：能找到常规命名的测试和直接 import；通过 fixture、插件或动态 import 覆盖的测试需要显式传 `tests`（或开启 `fallback_whole_suite`）。
- Python 是一等支持；jest/vitest/npm、go、cargo 尽力识别与解析；Rust/C 的修改总是运行整个 `cargo test`。
- 发现只读取工作区根目录的配置（`pytest.ini`、`pyproject.toml`、`setup.cfg`、`tox.ini`、`package.json`、`go.mod`、`Cargo.toml`）。`backend/pyproject.toml` 或 `packages/*/package.json` 形式的 monorepo 只能部分识别（或被识别为普通 unittest）；请把子项目作为工作区打开，或显式传 `tests`。
- jest/vitest 使用 `npx --no-install`，需要事先安装。
- 工具以 Agent 的权限在宿主机上运行项目自己的测试代码：参数校验阻止模型把它指向项目外或通过运行器选项加载额外代码，但测试本身（以及项目的 `conftest.py`、`package.json` 脚本、`build.rs`、项目 `.venv` 中的解释器等）不受限制地运行，与开发者自己运行时相同。本地模式下请像管理本地 `bash` 一样用权限策略管理它；沙箱模式下该工具不可用（见 §3）。
- run_tests 不是 shell 工具，因此 shell 网络策略（例如 Shell 策略 MR 中的 `permissions.shell_network: deny`，或无头模式默认的 `deny`）不作用于它：测试代码仍可访问网络。需要时，请像评测框架那样在无网络的容器中运行无头任务。
- 模型可以编写测试代码，因此也可以写出伪造摘要的代码（例如在导入时打印「1 passed」而所有测试都被跳过）。解析器读取运行器输出，无法区分真实与伪造的摘要；门控证据的可信度取决于仓库中测试代码本身。
- npm 脚本识别是字面匹配：通过 `node node_modules/jest/bin/jest.js` 或 shell 串联命令运行 jest 的脚本不会被识别，此时拒绝 `extra_args`。
