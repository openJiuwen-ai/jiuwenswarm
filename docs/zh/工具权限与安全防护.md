## 小艺 Work 桌面完全访问权限

接入桌面行为风控的运行时中，`permissions.enabled: false`（界面“完全访问权限”）也执行权限判定，配置文件和界面模式不变。
明确匹配 `allow`、`deny`、`ask` 时，分别执行、拒绝或请求用户授权，并异步上报。
未命中规则时，云授权关闭则使用 `permissions.defaults`；云授权开启则等待一次云端授权。
有效云端响应中的 `REJECT` 拒绝执行，其他有效状态放行；超时、失败或无效响应回退到用户授权。
初始化、配置热更新和用户确认后重查均使用这一规则。未接入桌面行为风控的其他宿主保持原开关语义。

小艺 A2A 消息中的 `clientVariables.permission` 随请求传入权限上下文，并在工具权限快照的副本上应用 `default`、`auto_approve` 或 `full_access`，不写入共享 `config.yaml`，也不触发全局权限热重载。小艺通道装配本地 `PermissionRail`；首次判定、审批后重查均读取当轮档位，未携带档位的后续消息恢复共享配置。桌面行为风控仍按上述宿主规则保留安全检查。旧版本已改写的全局权限配置需要显式恢复为所需档位，升级不会推断并覆盖用户当前配置。

## Windows 沙箱运行时声明

Windows 内部托管沙箱在服务启动前声明常见运行时：未显式配置 `JIUWENBOX_TOOL_PATHS` 时，优先使用隔离 venv，解析其真实基础 Python，并从服务 PATH 识别标准 Node 和 Git/Bash 目录。声明交给 JiuwenBox 准备共享 ACL，避免每个会话重新授权运行时；显式工具声明保持优先。该行为不改变 Shell 审批规则，也不代表已覆盖任意运行时升级后的 ACL 变化。配置和缓存边界见[沙箱公共目录与环境变量配置](../../jiuwenbox/docs/沙箱公共目录与环境变量配置.md)。

受管 venv 的基础解释器使用宿主专属注册表记录钉扎；沙箱可写的 `pyvenv.cfg` 不能自行扩大授权目录。宿主是可信的：显式 `JIUWENCLAW_BASE_PYTHON` 优先于旧钉扎，切换时重新准备 venv；旧解释器已删除时回退宿主候选并重新准备。宿主删除或重建 venv 后，实际基础解释器与宿主独立选择一致即可更新钉扎，无需手工删注册表。正常启动仍复用已有钉扎，允许工具 Python 与 runner Python 不同。新建或恢复的 venv 必须先验证，再更新钉扎、运行 pip 和发布基础 Python 目录；只有 venv 元数据变化且无法匹配宿主选择时仍拒绝启动。

普通 venv 创建或供给失败仅告警，不发布不可用的 `JIUWENBOX_VENV_DIR`，仍从宿主选择基础解释器并注入 `JIUWENBOX_BUNDLED_PYTHON` / `JIUWENCLAW_BASE_PYTHON`；信任校验失败继续中止启动。Linux 已有 venv 解析失败会告警并尝试后续宿主候选，`pyvenv.cfg` 的 `home` 支持仅有 `python3` 的目录。可选 Python 来源解析失败仅告警跳过。

源码模式通过独立的 `JIUWENBOX_SERVICE_READ_ROOTS` 只读声明 `jiuwenbox/src`，使沙箱账号能导入 runner。技能目录不自动纳入共享只读范围，其原有读写、授权和撤权行为保持不变。此修复不解决新会话的技能依赖扫描耗时，也未增加每次启动的强制全量扫描。

JiuwenBox 对每个声明的只读根共用原有 ACL 遍历，仅当对象加固出现 Windows 错误 5 且无有效读拒绝时尝试字节码迁移。只删除当前沙箱账号所有、有同一规范根内源文件背书的 CPython 缓存；路径比较支持短路径别名和 `..`，删除前仍检查原路径中的链接和重解析点。目录（含空 `__pycache__`）、其他产物、宿主缓存和孤儿属主文件不会被自动删除或接管。必需对象失败继续中止初始化，暖缓存命中不另行扫树。

沙箱首跳 runner（`jiuwenbox.supervisor.win_exec`）由 `ProcessRuntime._create_windows` 在创建进程前设置 `PYTHONPYCACHEPREFIX`，第二跳命令由 `_create_process_as_user` 设置，缓存落到沙箱 Temp，沿用既有 workspace 回退。这不是 Swarm `ensure_running` 启动的宿主 box-server。显式 Python 参数或内部清空环境可改变默认缓存行为，源码只读 ACL 仍保持。

ACL 错误包含 `root/path/operation/owner_sid/object_type/winerror/migration/required`；只在失败时查询属主，诊断失败不替换原异常。`directory_not_cache`、`owner_mismatch` 等候选排除使用 DEBUG，必需对象失败仍为 ERROR；共享根日志包含缓存命中和耗时。无法自动处理时应停止相关进程，由宿主管理者核对声明范围及策略，重装、重建或明确修复对应运行时；不自动提权、接管所有权或大范围重置 ACL。

Windows 最终命令不接收四个服务声明键 `JIUWENBOX_SERVICE_READ_ROOTS`、`JIUWENBOX_TOOL_PATHS`、`JIUWENBOX_PATH_ALLOWLIST`、`JIUWENBOX_ENV_ALLOWLIST`，宿主继承白名单和 `JIUWENBOX_INJECT_ENV` 也不能绕过，大小写无关。服务声明不变，既有执行协议和宿主软删除设置保持原行为。

## FileGuard 配置与显式沙箱同步

AgentServer 提供以下配置 RPC（使用现有 AgentRequest/AgentResponse 封装）：

| 方法 | params | 行为 |
| --- | --- | --- |
| `permissions.file_guard.get` | `{}` | 返回 `file_guard` 配置 |
| `permissions.file_guard.update` | `{"patch": {...}}` | 更新 `enabled/defaults/workspace/paths`，不写沙箱配置；成功后异步刷新 Agent |
| `sandbox.files.sync` | `{}` | 将 FileGuard 路径读写规则整体替换到 `config.yaml` 的 `sandbox.files`，返回 `files` 和 `restart_required: true` |
| `sandbox.restart` | `{}` | 对所有活动 jiuwenbox 适配器应用最新配置并重建执行沙箱；等待完成，失败返回错误 |

`update` 的 `defaults/workspace` 按权限字段合并，`paths` 整体替换（空列表即删除所有路径规则）；省略路径权限字段即恢复继承，不保留旧 `exec`。Native FileGuard 路径规则缺省的权限继承 `file_guard.defaults` 对应字段；沙箱同步也先按字段继承默认读写权限，再校验是否可同步。`read: deny` 强制写入和执行也为 `deny`，不继承允许值；同步登记为读写均拒绝。例如：

```json
{"patch":{"paths":[{"path":"C:/Users/alice/.ssh","read":"allow","write":"deny"}]}}
```

同步仅支持当前主机存在的绝对路径，读写在继承默认权限后须为 `allow/deny`；不复制 `exec`、默认权限和工作目录权限，也不代表复制完整 FileGuard 策略。glob、ASK、不存在路径等不支持的规则逐条跳过，通过返回值 `skipped` 列出 `path` 和 `reason`，其余规则继续同步。全部跳过时 `sandbox.files` 更新为空列表；FileGuard 原始规则不变。冲突时优先保留读拒绝、其次只读，跳过与其冲突的更宽规则，不依赖配置顺序；最终有效规则整体覆盖 `sandbox.files`，不与旧沙箱规则合并。FileGuard 必须启用。只读转换为沙箱 `read_only`；禁止读写目前仅 Windows 支持，转换为 `windows.filesystem.deny_read/deny_write`。其他平台遇到具体路径读拒绝时明确报错且不写入，不再跳过后生成放宽策略。

同步生成的配置直接使用列表，空规则为 `files: []`：

```yaml
sandbox:
  files:
    - path: 'C:/Users/alice/.ssh'
      read: allow
      write: deny
```

`config.yaml` 的 `sandbox.files` 通过同步接口写入；旧对象形式读取时按 `[]` 处理，更新沙箱开关等字段时也将旧对象写回为空列表，不迁移旧规则。旧 `/sandbox files allow/deny/remove` 返回引导错误。原 `sandbox.files.get/set` **保持不变**，仍操作 `windows-policy.runtime.yaml` 并沿用原来的异步应用行为；不能用它回读同步结果。两路策略由 jiuwenbox 合并，已有禁止规则仍可能限制同步的允许规则。

两个同步操作均只保存配置，不表示活动沙箱已应用。界面“应用并重建沙箱”统一调用 `sandbox.restart`：先等待沙箱服务加载已保存的网络策略，再遍历顶层及会话子适配器，使用已同步的文件规则重建实例，对共享实例去重。网络策略副本变化时会重载沙箱服务；没有变化时复用健康服务。接口等待完成，返回 `restarted` 数量和 `status`，不重启 AgentServer。没有重建实例且没有服务策略重载时返回 `no_active_sandboxes`；服务策略已重载但无活动实例时可返回 `applied`、`restarted: 0`。

Windows 重启先完成旧实例的 ACL 清理，再创建新实例，避免旧实例删除时撤销新权限。创建失败会返回错误，旧实例已停止，需要重试重启；此次显式重建将活动执行器的本机失败回退关闭，失败不恢复旧权限或转到本机执行。复用同一执行器的适配器共享实际配置引用并去重重建。文件护栏有未保存修改时，同步文件护栏和重建均不可点击；同步网络护栏读取已保存的网络规则。

内部 box-server 重启或换端口时，runner 只有在确认自己管理的旧进程退出、完成 Windows Job 回收后，才收敛旧 URL 的 provider 缓存及待删除记录，保留删除生命周期钩子的严格失败语义；清理失败会阻止新服务启动，并在下次启动 / 重试时继续。不能仅凭 ConnectError、超时或端口变化忽略旧删除。外部服务不可达仍保留待删除状态并报错。

Windows 受管 box-server 无控制台，通过父子私有 stdin 管道请求正常 Uvicorn shutdown，不依赖 `CTRL_BREAK_EVENT`；源码和打包入口一致，兼容打包后 `sys.stdin` 为空。停止通道导入或写入异常仍进入原有信号 / terminate 兜底；非 Windows 且无 stdin 时不调用 Win32 API。HTTP 请求排空最多等待 5 秒，之后仍执行完整 lifespan 沙箱 / ACL 清理，runner 的原有 60 秒退出兜底保持不变。沙箱开关 RPC、TUI `/sandbox enable|disable` 和 `sandbox.restart` 共享同一把配置应用锁，配置写入、停止、严格清理和服务就绪按序完成后应答；开启不会提前覆盖正在关闭的配置。managed 配置调用的内部重启复用外层持锁，不重复取锁。真实 Windows 隐藏子进程退出测试标记为 `integration`，可用 `pytest -m "not integration"` 排除。

disable（包括旧 `/sandbox disable` 命令）与 restart 使用同一个删除入口，覆盖本 AgentServer 进程内所有已知 URL 的共享缓存和待删除记录，而非只清当前配置端点。disable 还移除全部会话 / 项目注册的沙箱 SysOperation，并停止自己管理的 box-server；停止失败也继续批量清理，严格清理失败时优先报告清理错误，清理成功后仍报告原停止错误。失败后再次提交同一关闭配置或命令会重试清理。restart 在所有活动执行器完成准备后、创建任何新实例前，再清理遗留作用域。批量清理会尝试全部匹配项：成功项立即收敛，失败项保留供重试，遍历结束后严格抛出首个错误；任一严格清理失败都不进入创建阶段。

新建会话和切换沙箱开关统一按当前开关校验执行器模式。已有会话在下一次空闲调用时检查；与开关不一致时自动重建运行时，恢复同一会话 ID 的历史，保留原实例配置、模式及子模式，并重新装配技能和工具。关闭选择本地 SysOperation，开启选择沙箱 SysOperation；支持同一会话反复开关，无需新建会话。重建在会话锁内进行，并发调用只重建一次；正在执行的会话继续使用旧模式，待空闲后切换。模式已经一致的会话继续复用，其他会话在各自下一次调用时处理。创建或重建后、启动会话交互前校验模式；失败返回期望模式、实际模式及配置重试提示，并清理未发布的运行时。开启沙箱但缺少有效端点时，新建会话的首次调用也会失败，不静默使用本地执行器。

运行时重建复用完整 `cleanup()`，会清除该会话的文件发送去重记录；切换后同一文件可能再次发送。

配套 agent-core 的批量清理与服务退役还会释放 Gateway 的 endpoint / provider 缓存及派生的 sandbox ID，防止同一会话重新开启后复用旧端口或旧策略；服务退役仅影响对应 URL，批量清理仅影响 JiuwenBox。批量清理期间阻止新的沙箱获取，等待已经发出的首次创建和自动重建返回，再清理其 ID；external 模式及受管服务停止失败后的清理也遵守此规则。DELETE 失败保留 pending，严格清理不提前报告成功。回归测试经过真实 SysOperation → Gateway → provider → HTTP client，仅模拟远端 HTTP，覆盖同端口 / 换端口、会话关闭后重新开启，以及创建与清理并发的失败重试。

Windows 实机回归：启用并创建沙箱后强杀受管 box-server，修改一项文件 / 网络规则以触发 `security.config.sandbox.update` 应用；即使服务换端口，也应恢复为 `saved: true, applied: true`，不再请求已确认退出的旧端口。若注入额外故障导致应用失败，排除故障后提交同一配置应重试成功。已应用且内容未变的配置仍允许幂等返回 `not_required`。随后关闭沙箱，确认会话 / 项目注册、旧 URL 缓存及待删除记录均收敛。另用不可达的 external 服务验证失败仍为 `saved: true, applied: false`，恢复外部服务后提交相同配置能够重试成功。发版需同时包含 agent-core 的 `retire_jiuwenbox_service` API 和本宿主改动。

## NetGuard 配置与显式沙箱同步

配置页顺序为：**沙箱 → 文件安全护栏 → Shell安全护栏 → 网络安全护栏**。沙箱卡片同一操作栏依次提供“同步文件护栏”“同步网络护栏”“应用并重建沙箱”。前两个按钮仅保存各自的规则，第三个按钮统一应用并重建；网络护栏卡片负责配置规则，不放置同步按钮。

### 配置接口（已有接口扩展 ASK）

| 方法 | params | 响应 payload / 行为 |
| --- | --- | --- |
| `permissions.net_guard.get` | `{}` | `net_guard`、`builtin_urls`、`enforcement_points`、`apply_mode: "hot_reload"`、`host_exit`、`warnings` |
| `permissions.net_guard.set` | `{"net_guard": {...}}` | 局部保存网络护栏配置，响应结构同 get；不自动同步沙箱 |
| `sandbox.network.get` | `{}` | `{"network": {"disable_all": false, "allow_domains": [], "deny_domains": []}}`；回读当前平台沙箱运行时策略副本中的用户网络配置 |

`net_guard` 可更新字段：`enabled`、`enforce_host_exit` 为布尔值；`defaults` 为 `allow/ask/deny`；`urls` 为 `{pattern: "allow"|"ask"|"deny"}`。省略字段保持原值，提交 `urls` 则整体替换用户规则，`{}` 清空用户规则。内置禁止规则运行时并入，同名规则不能改为 allow 或 ask。非法字段值返回 `BAD_REQUEST`。

```json
{
  "type": "req",
  "id": "net-guard-set-1",
  "method": "permissions.net_guard.set",
  "params": {
    "net_guard": {
      "enabled": true,
      "defaults": "allow",
      "urls": {"blocked.example.com": "deny", "review.example.com": "ask"}
    }
  }
}
```

ASK 在网页抓取工具执行前经权限中断询问。宿主 HTTP 出口逐跳检查：DENY 始终拦截；重定向目标命中 ASK 时在连接前中止，并返回需要审批的目标 URL，须以该 URL 单独发起工具调用重新审批，不在出口直接弹窗，也不把原 URL 的授权传给跳转目标。动态授权不能覆盖 DENY，沙箱内部进程的网络访问仍由沙箱策略控制。

多条规则同时命中时 DENY 优先，其次 ASK，最后 ALLOW；allow 不覆盖同时命中的 ask 或 deny。

### 新增接口 `sandbox.network.sync`

请求 `params` 必须为空对象。服务端从已保存的 `permissions.net_guard` 读取规则，客户端不能在此接口提交规则或指定放宽范围。前置条件：沙箱类型为 `jiuwenbox`，且 `permissions.enabled` 和 `permissions.net_guard.enabled` 均开启；不要求沙箱当前已启用。

```json
{"type":"req","id":"net-sync-1","method":"sandbox.network.sync","params":{}}
```

以上述网络配置为例，成功响应（Web WebSocket 封装）：

```json
{
  "type": "res",
  "id": "net-sync-1",
  "ok": true,
  "payload": {
    "urls": {"blocked.example.com": "deny"},
    "default": "allow",
    "skipped": [
      {"pattern": "review.example.com", "reason": "询问仅在工具调用前处理，不同步到沙箱"}
    ],
    "restart_required": true
  }
}
```

| 响应字段 | 含义 |
| --- | --- |
| `urls` | 本次写入 `config.yaml` 的 `sandbox.urls`，格式为 `{域名: allow或deny}`，整体替换原映射，不追加合并 |
| `default` | 本次保存到 `sandbox.network_default` 的默认动作，`allow` 或 `deny` |
| `skipped` | 被跳过的规则，每项为 `{pattern, reason}`；无跳过项时为 `[]`，部分跳过仍返回成功 |
| `restart_required` | 固定为 true，提示调用 `sandbox.restart` 统一应用 |

同步 `allow/deny` 的普通域名或 `*.域名`，并保存 `net_guard.defaults` 的 allow/deny 默认动作。**默认 deny 可完整投影，不再出现在 `skipped` 中**。默认 ask 仍以 `pattern: "defaults"` 报告跳过，沙箱默认动作使用 allow；ASK 域名规则也直接跳过，不映射为 DENY。完整 URL、端口及不支持的通配模式继续返回 `skipped`，不能把 URL 擅自放宽为域名。没有可同步域名时，`sandbox.urls` 写为 `{}`，默认 deny 仍然有效；原 NetGuard 规则保持不变。部分跳过仍返回成功，调用方应展示 `skipped` 中的实际限制，不能把保存成功当成完整同步。

与文件同步写入 `sandbox.files` 一致，网络同步只写 `config.yaml` 的 `sandbox.urls` 和 `sandbox.network_default`，**不改运行时策略副本，不启动、重载或重建沙箱**。响应 `default` 回显保存的默认动作，`ok: true` 只表示保存成功。示例同步结果：

```yaml
sandbox:
  files: []
  network_default: deny
  urls:
    example.org: allow
    blocked.example.com: deny
```

`sandbox.files`、`sandbox.urls` 和 `sandbox.network_default` 保存从对应 Guard 同步得到的待应用规则。之后调用 `sandbox.restart`，读取保存的快照，统一应用并重建沙箱；不会重新读取 Guard 规则或从运行时反向回写。修改 Guard 后需再次同步，才能更新快照。网络规则转换为当前平台运行时策略副本的域名允许 / 禁止列表及 `egress.default`，保留原 `disable_all`。默认 deny 时设置 `egress.replace_allowed: true`，以投影域名完整替换基底的允许域名、IP 和端口名单；空 IP/端口名单不会再追加继承基底的 80/443 放行，基底黑名单继续保留且优先拒绝。独立原生配置中的域名仍参与合并；`disable_all=true` 仍直接拒绝，包括允许域名。切回 allow 时移除投影的替换标记和空 IP/端口名单，恢复基底允许规则。旧配置缺少 `network_default` 时不覆盖原默认动作。统一配置服务也将仅修改 NetGuard defaults 视为网络策略变更并重新同步应用。

服务重载及实例重建会停止当前任务。`files` 默认是 `[]`，`urls` 默认是 `{}`，均表示空规则。AgentServer 启动内部沙箱服务时也按当前配置加载。自定义策略文件未使用平台运行时副本时，网络应用明确失败。

同一范围的自动创建和主动重建由 agent-core 的 JiuwenBox provider 共用生命周期互斥，旧实例撤权完成后才创建替代实例。配置应用期间暂停工具侧实例获取和丢失重建，返回可重试错误且不回落宿主执行；应用失败的作用域保持阻断，直到应用或回滚成功。普通同作用域创建仍通过互斥复用实例，避免多余实例清理时撤销保留实例的共用目录权限。`permissions.*.get` 等只读配置接口不等待耗时的沙箱应用锁，返回当前保存快照；读取成功不表示沙箱已应用。配置写入和应用继续串行，成功回执仍表示对应应用已完成。

`apply_sandbox_runtime_patch` 在 strict 和非 strict 更新中均传入当前 agent 的隔离作用域 key，避免非 strict 更新退回服务级缓存重建并绕过该作用域的互斥。撤权失败后再次调用 `sandbox.restart` 会先重试旧实例删除，成功后才创建替代实例；仅重试工具调用不会自动解除 pending 删除。`security.config.get`、`security.config.sandbox.get`、`security.builtin.get` 同样不等待应用锁，读取响应 `ok:true` 可以与嵌套 `apply` 中尚未完成的应用状态同时存在。

作用域解析失败时不调用 Core 删除或重建接口：strict 请求明确报错，非 strict 热更新记录失败并返回 `False`，均不会传入 `shared_key=None`。桌面仍使用参数为 `{}` 的 `sandbox.restart` RPC，后端为每个实际执行器构造 key；本次 Core 参数约束不要求桌面增加字段或修改调用。

**自动 apply 与会话回收**

- managed 权限写、原生沙箱配置写和启动恢复使用自动 apply：在服务更新前查询当前进程拥有的沙箱实例，按 `(base_url, isolation_key)` 去重，只重建仍有持有者的存活作用域或上次重建失败的作用域。从未创建、已被 idle 回收的作用域只更新启动策略，保持下次实际使用时创建。远端清单不可用时保守保留已知作用域以恢复服务，不将查询失败当成实例已销毁。
- 显式 `sandbox.restart` 保留主动重建已配置适配器的语义。两条路径都先清理旧 ACL，再安装替代实例，返回 `restarted` 和 `skipped`；不把部分完成报告为成功。
- 普通 `session.delete` 在停止当前轮次后清理会话适配器。共享项目仍有其他持有者时只释放当前引用；最后一个持有者等待远端删除、ACL 清理与 Gateway/provider 缓存失效，再注销 SysOperation。失败保留会话记录和可重试资源，返回 `DELETE_FAILED`，不得当成删除成功。
- managed `sandbox.enabled.get`、`startup_mode.get`、`limits.get`、`files.get`、`network.get` 同样绕开应用锁，返回保存快照；这些 getter 不提供生效确认。
- 本实现依赖配套 agent-core 的 `jiuwenbox_policy_update`、`get_live_jiuwenbox_scopes`、`release_jiuwenbox_scope`。发布时必须同时集成两仓修复，并将依赖锁定到包含这些接口的 Core 提交；不能只更新 Swarm。

**每日全量接入与验收**

真实策略变更仍可能执行完整 ACL 重建，客户端应为变更写与最终会话删除提供可配置等待预算，可先使用 300 秒并记录耗时。超时不等于服务端失败：保留原请求的完成等待，不立即补发恢复写。已知 revision 时可辅助读取 `security.config.get` 的对应 apply 状态；不能把其他 revision 的 `applied` 或队列前一个请求的成功当作当前请求完成。请求与 revision 无法关联时应停止该测试阶段并报告未确认状态，避免继续堆积恢复写。

teardown 必须检查 `session.delete` 成功回执。验收覆盖同项目共享、多项目反复创建/删除、idle 回收后 apply 不复活实例、失败重建恢复、重建期间 getter 可用，并重跑 chat → safety_guard → network sync → sandbox 全量链。仓内模拟测试不替代真实 Windows ACL 和每日全量验收。可通过 `[sandbox.apply]` 日志查看 `live_only/restarted/skipped/elapsed`；此 P0 不包含网络热更新或异步提前回包。

后台重建遇到旧沙箱 DELETE 失败时，由 Core 在同一删除任务内最多尝试 3 次，失败后间隔 1 秒再试。前一两次失败、后续成功时继续重建，用户无需再次修改配置；三次均失败才通过现有重启回执返回错误，包含尝试次数、最后失败原因和已阻止创建替代实例的信息。重试及失败后的 pending 状态都不允许跳过撤权创建新沙箱，也不回放之前失败的命令。并发清理共用一轮重试；取消调用不丢弃在途清理；删除钩子自身失败保持严格报错。页面、自动保存逻辑和按钮均未改变，不新增后台无限重试或自动重启服务的兜底。

通过同步响应或 `config.yaml` 回读待应用规则。`sandbox.network.get/set` 是独立的旧接口，仍操作运行时策略副本，不参与 Guard 同步流程，也不用于回读待应用的 `sandbox.urls`。统一应用以已保存的沙箱配置为准。

统一应用请求：`{"type":"req","id":"apply-1","method":"sandbox.restart","params":{}}`。成功 payload 示例：`{"restarted":2,"scope":"all_active_sandboxes","status":"applied"}`。要求沙箱已启用，自动服务重载支持 `startup_mode: internal`。external 模式仍重建实例以应用文件规则，响应另带 `network_status: "externally_managed"`，界面明确提示网络策略需由外部服务加载；不修改或重启外部服务，不声称网络规则已应用。内部服务启动 / 重载失败时不继续重建；任一实例重建失败也返回 `SANDBOX_RESTART_FAILED`，不把部分完成报告为成功，已保存规则保留供重试。

| 错误码 | 条件 / 典型错误信息 |
| --- | --- |
| `AGENT_NOT_READY` | Web 转发时 AgentServer 尚未就绪：`AgentServer is not ready` |
| `BAD_REQUEST` | 非空 params：`sandbox.network.sync accepts no parameters` |
| `BAD_REQUEST` | 非 jiuwenbox：`sandbox.network.sync currently supports jiuwenbox only` |
| `BAD_REQUEST` | 权限总开关或 NetGuard 未开启：`NetGuard must be enabled before synchronization` |
| `INTERNAL_ERROR` | 读取或保存 `config.yaml` 失败 |

统一应用阶段的策略副本写入失败或回读不一致（例如 `Sandbox network configuration could not be saved`）由 `sandbox.restart` 返回 `SANDBOX_RESTART_FAILED`。

Web 错误响应为 `{"type":"res","id":"net-sync-1","ok":false,"error":"...","code":"BAD_REQUEST"}`。AgentServer 内部沿用 `AgentResponse`：成功数据在 `payload`，失败时 `ok: false` 且 `payload: {"error": "...", "code": "..."}`；不要混用两层封装。

本文说明 JiuwenSwarm **工具调用权限**（`allow` / `ask` / `deny`）如何生效、与 **workspace 外路径**、**内置安全规则**、**用户审批持久化** 的关系，以及 **CLI `/add-dir`** 会改哪些配置。

配置主文件一般为 `~/.jiuwenswarm/config/config.yaml`；可通过环境变量 `JIUWENSWARM_CONFIG_DIR` 指向其它目录（与 [配置说明](配置信息.md) 一致）。

`mcp_exec_command` 是 AgentServer 内置命令工具，执行通过绑定的 `SysOperation.shell()` 路由。注册时使用 `get_mcp_tools(sys_operation=operation, agent_id=agent_id)`；多会话子 Agent 从其 `sys_operation_id` 获取同一实例。未绑定实例时返回错误，不直接启动宿主进程。沙箱模式复用连接器 CLI、`excluded_commands` 和 `fallback_on_failure` 的现有宿主执行规则，显式传递 `bash / sh / powershell / cmd`。后台请求同样交给该实例；provider 不支持时返回错误，不回退到工具内的宿主执行。权限护栏仍需由调用方装配，绑定执行路由不会自动启用 FileGuard。

## 2. 分层策略（`tiered_policy`）下，一次工具调用如何定级

以下对应 `evaluate_tiered_policy()`（`jiuwenswarm/agentserver/permissions/tiered_policy.py`）的**真实分支顺序**。参数指本次的 `tool_name` 与 `tool_args`（如 bash 的 `command`、读文件的 `path` 等）。

### 2.1 准备：`permission_mode` 与 `severity`

- `permissions.permission_mode`：`normal`（默认）或 `strict`。
- 参数级规则（内置或用户）若写了显式 **`action: allow|ask|deny`**，**直接**使用该动作，**不再**看 `severity`。
- 未写 `action` 时，用 **`severity`** 结合 `permission_mode` 映射为动作：

| severity | normal 模式 | strict 模式 |
|----------|-------------|-------------|
| LOW | allow | allow |
| MEDIUM | allow | **ask** |
| HIGH | **ask** | **ask** |
| CRITICAL | **ask** | **deny** |

未知 `severity` 按 **HIGH** 处理。

### 2.2 参数级规则如何算「命中」

- 规则必须包含当前 **`tool_name`**，且规则里列出的多个工具须属**同一类**（shell / path / network），否则该条规则被跳过。
- **Shell 类**：用 `pattern` 去匹配 `command` / `cmd` 整串（支持通配、`re:` 正则等）。
- **Path 类**：用 `pattern` 去匹配从 `tool_args` 里抽出的**路径形字符串**（常见键名 + 形似路径的值）；`re:` 时路径会先 `\` → `/` 再匹配。
- **Network 类**：当前产品设计为参数规则不匹配，见代码注释。

一次调用可以**命中多条**参数规则，后续用 **strictest** 合并（见 2.4）。

### 2.3 `evaluate_tiered_policy` 逐步流程（核心）

1. **整工具基线** `_baseline_level`：读 `permissions.tools.<tool_name>`。  
   - 若为 **`deny`**：**立即返回 DENY**，不再看任何参数规则、override、defaults。  
   - 若为 `allow` / `ask` / 未配置：先记下来，供后面无参数命中时使用。

2. **收集内置参数规则命中** `builtin_hits`（`builtin_rules.yaml` 经 `get_builtin_security_rules()`）。  
   - 若其中**任一**命中项为 **DENY**：**立即返回**（只根据内置命中做 `_finalize_hits`，内置 **DENY 优先于同层其它级别**）。

3. **收集用户参数规则命中** `user_hits`（`permissions.rules`）。  
   - 若其中**任一**命中项为 **DENY**：**立即返回**（用户参数级 **DENY** 在此阶段生效）。  
   - 注意：此处在 **`approval_overrides` 之前**，因此用户规则里的 **deny** 可以拦住后续本应命中的 override（override 不会被执行到）。

4. **旧式 `approval_overrides`**（仅 `action: allow` 的条目参与；`exact_operation` 对象授权在所有护栏之后判定，见第 5 节）：
   - 若**至少一条**对本次 `tool_name` + `tool_args` 匹配成功：**立即返回 ALLOW**，`matched_rule` 带 `tiered_policy:approval_overrides:...` 前缀。  
   - **不**覆盖第 2 步已返回的内置 DENY（因根本走不到这里）。**不**覆盖第 3 步的用户参数 DENY。

5. **若未因 override 返回**：若 **`builtin_hits` 非空**，则 **`_finalize_hits(builtin_hits)` 并返回**——**不再使用** `user_hits` 参与最终级别合并。  
   - 含义：只要内置层有**任意**参数级命中（且前面没有 deny、没有 override），**最终结果只反映内置命中**；用户 `rules` 里同一次调用上的其它命中**不会**与内置做「跨层 strictest」。

6. **若 `builtin_hits` 为空** 且 **`user_hits` 非空**：`_finalize_hits(user_hits)` 并返回。

7. **若参数级全无命中**：若整工具基线 **`bl` 已配置**（`allow`/`ask`），返回该级别及 `tools.<name>`。

8. 否则若存在 **`defaults."*"`**，解析为级别并返回。

9. 否则返回 **ASK**，`matched_rule` 为 `tiered_policy:fallback(no_config)`（引擎里可能再当作「无配置」处理）。

`_finalize_hits`：若命中列表里含 **DENY**，结果为 **DENY**；否则对命中项的 `allow/ask` 取 **strictest**（`deny > ask > allow` 严格序）。

### 2.4 引擎在 `tiered_policy` 之后还多做什么

在 `PermissionEngine.evaluate_global_policy_directly` 中，在拿到 `evaluate_tiered_policy` 的结果后还会：

1. **`maybe_escalate_shell_operators`**：若结果**不是**来自 `approval_overrides`，且工具为 shell 类，**allow** 可能因命令中含链式/注入风险字符被 **升为 ask**。  
2. **路径防护（可选）**：若路径层开启（`file_guard` / Legacy `external_directory`），用 `FileGuardChecker` 再判路径；与当前级别做 **strictest** 合并。

`check_permission` 路径上通常先算**不含**外部的 tiered 结果，再单独合并外部维（实现上与「一步算完」等价于对用户可见的合并效果，细节见 `core.py`）。

## 3. 内置安全规则 `builtin_rules.yaml`

- **包内默认**：`jiuwenswarm/resources/builtin_rules.yaml`。
- **用户覆盖**：与 `config.yaml` **同目录**下的 `builtin_rules.yaml`（即 `JIUWENSWARM_CONFIG_DIR` 或默认 `~/.jiuwenswarm/config/`），若存在则**优先加载**。

内置规则多为 **shell 高危命令**（删除、格式化、下载执行、提权等），部分条目带显式 `action: deny`。用户 `rules` 不能覆盖内置的 deny（内置 deny 先返回）。

## 4. 路径防护：`file_guard` 与 `external_directory`

路径访问由 **Pipeline B**（agent-core `FileGuardChecker`）判定，与工具级 tiered_policy（Pipeline A）做 **strictest** 合并。

### 4.1 `file_guard`（推荐）

```yaml
permissions:
  file_guard:
    enabled: true
    defaults: {read: ask, write: ask, exec: ask}
    # 绑定运行时 agent workspace（resolve_workspace_dir），路径不写死在 YAML
    workspace:
      read: allow
      write: allow
      exec: ask
    paths:
      - path: "/data/public"
        read: allow
        write: ask
        exec: deny
      - path: "**/.env*"
        match: glob
        read: ask
        write: ask
        exec: ask
```

- **独立开关**：`file_guard.enabled: false` 时整层路径防护关闭（含旧外部目录检查），不影响 `tools` / `rules`。
- **`workspace`**：按 R/W/X 放行**运行时** `workspace_root`（通常为 `~/.jiuwenswarm/agent/workspace`）；拿不到 root 时跳过该规则并打 WARN。Native **无** Legacy 式隐式 workspace 放行，须显式配置本项或 `paths`。
- **`trusted_dirs`**：TUI 项目 cwd / `/add-dir` 热更新目录，由引擎编译为前缀 allow（独立于 `workspace`）。
- **R/W/X**：同一路径可分别配置；Write/Exec⇒Read 蕴含，显式 `read: deny` 优先。
- **匹配**：`match: prefix`（缺省，最长前缀）或 `glob`。
- **Native vs Legacy**：显式配置 `defaults` / `workspace`（R/W/X）或 `match: glob` 时进入 Native；仅有 `external_directory` 时走 Legacy 投影（workspace 内隐式放行）。

### 4.2 `external_directory`（deprecated，只读兼容）

旧配置 `permissions.external_directory`（如 `"*": ask`、具名前缀 `allow`）加载期投影进 FileGuard Legacy，**行为与现网 ExternalDirectory 等价**。  
**新写入**（`/add-dir`、HITL「总是允许」路径）请写 `file_guard.paths`，不再写 `external_directory` 具名键。

## 5. 动态授权与交互协议

ASK 在工具调用前中断，用户可选本次允许、会话内允许、总是允许或拒绝。对象授权保存为 `approval_overrides` 中的 `match_type: "exact_operation"` 记录，Shell 拆分授权保存为多条 `match_type: "shell_subcommand"` 记录；`pattern` 为含 `scope` 和 `subject` 的 JSON 字符串。服务器生成对象范围和子命令，不接受客户端传入任意路径、域名或子命令。会话授权进入当前会话 overlay，永久授权进入用户配置；一次审批的子命令批量保存，永久保存不会顺带提升已有会话授权。

`exact_operation` 授权在所有护栏判定后解除匹配对象的 ASK；`shell_subcommand` 仅解除 Shell 内部的命令/工具 ASK 或未确定结果，随后仍合并 FileGuard、NetGuard 和 DeletionGuard，且保留整条命令的结构风险检查。两者均不修改整工具权限或 FileGuard 路径策略，也不能覆盖 DENY。恢复执行前重新检查策略；等待期间新增的 DENY 同样会拒绝执行。既有命令 override 和 `/add-dir` 目录信任逻辑保持原语义。

### 5.1 下发可选范围

沿用 `chat.ask_user_question` 事件。以下为事件 **payload 示例**，不是新的 RPC。`source` 为 `permission_interrupt` 时，每个 `questions[]` 可携带 `authorization_scopes`，元素为 `{value, label}`。客户端应按服务端实际下发的 `options[].value` 提交选择。

服务端和 Web 审批均默认选择可用的范围选项：文件为 `parent`，URL 为 `domain`，Shell 为 `subcommands`；用户可显式选择 `exact`。默认选择不代表自动批准。客户端未回传范围字段时也由服务端应用此默认；无可用范围时回退到精确授权，新审批不继承上一条审批的范围选择。

```json
{
  "request_id": "permission-1",
  "source": "permission_interrupt",
  "questions": [{
    "header": "操作授权",
    "question": "访问 https://api.example.com/data 需要授权",
    "multi_select": false,
    "options": [
      {"label":"本次允许","value":"approve"},
      {"label":"会话内允许","value":"session_allow"},
      {"label":"总是允许","value":"always_allow"},
      {"label":"拒绝","value":"reject"}
    ],
    "authorization_scopes": [
      {"value":"exact","label":"仅当前对象"},
      {"value":"domain","label":"域名（含子域名）：example.com"}
    ]
  }]
}
```

| 字段 / 值 | 默认及约束 |
| --- | --- |
| `authorization_mode` | 可选；省略时根据最终范围推导，`exact` 为 `allow`，其他范围为 `allow_with_scope`；显式 `allow` 且未传范围时使用 `exact` |
| `authorization_scope` | 省略时由服务端选择可用的 `parent`、`domain` 或 `subcommands`，无可用范围则 `exact`；显式值还需匹配当前对象类型 |
| `allow` + `exact` | 仅当前工具的已解析文件路径与访问动作、当前 URL，或完整原始命令与工作目录；不会把命令中的 `*` 当作授权通配符 |
| `allow_with_scope` + `parent` | 文件立即上一级目录及其子项，保留工具和访问动作限制；不能任意指定祖先目录 |
| `allow_with_scope` + `domain` | URL 的可注册域名及子域名，例如 `api.example.co.uk` → `example.co.uk`；保留协议与端口限制。IP、localhost、公共后缀不提供此选项 |
| `allow_with_scope` + `subcommands` | 一次审批生成多条精确子命令授权，可独立或组合复用；共享原调用的初始目录、工具、解释器和有效期，参数及通配符仍按字面匹配 |
| `allow_with_scope` + `exact` | 合法，仍按精确对象授权 |

Shell 拆分复用现有 AST，只在能完整覆盖命令时提供；无法可靠拆分、带重定向或外层解释器启动包装的命令回退到 `exact`，自定义 Shell 工具保守绑定全部参数并只提供 `exact`。bash、powershell、mcp_exec_command 的授权绑定真实 `workdir`（缺省时为执行上下文目录）及解释器 `shell_type`，未知的 `cwd` 参数不能替代执行目录。比如从 `E:\work` 调用 `cd repo && git status`，保存的 `cd repo` 和 `git status` 都绑定 `E:\work`，不将后一条改绑到 `E:\work\repo`；目录变化由 FileGuard 的本次路径检查处理。从 `E:\work` 单独执行或重新组合已授权子命令可复用，从其他初始目录调用则不匹配。未授权的子命令仍需审批，不提前执行已获准部分。

Core 到 Swarm 的持久化回调统一只用 `approval_grants: list[dict]`，会话和永久授权使用同一接口。单对象传单元素列表；单条 Shell 范围授权的批次包含子命令记录和当前调用的精确记录。一次记住只调用一次批量写入，保留会话 ID 和有效期，只保存本批授权，不携带合并快照中的无关授权。桌面端通过 `chat.send` 回传用户选择，不实现这个 Python 持久化回调。

显式 `approval_grants=[]` 在会话和永久保存入口均直接成功跳过，不读取或写入配置，不清空已有授权，也不退回保存整份快照。内部管理调用省略该参数（`None`）时仍保留原有快照处理方式。File、Net、Shell 默认范围授权和子命令组合复用保持不变。

旧的对象命令授权缺少解释器字段时不再匹配，需要重新审批。范围与有效期独立：选“本次允许”不会保存范围用于后续调用。旧客户端省略新增字段时也使用服务端默认范围；显式 `exact` 保留完整命令授权语义，已有精确授权不会自动转换为子命令授权。

普通权限审批和 ACP 审批的命令正文均显示触发审批时捕获的工作目录：优先使用工具的 `workdir`，缺省使用执行上下文目录。目录快照仅用于展示，不改写工具参数；审批后的上下文切换不会改变该审批显示的目录。

### 5.2 提交授权与有效期

沿用 `chat.user_answer`，在 `params.answers[]` 中增加两个可选字段。例如对上面的请求按域名在会话内允许：

```json
{
  "type": "req",
  "id": "answer-rpc-1",
  "method": "chat.user_answer",
  "params": {
    "request_id": "permission-1",
    "answers": [{
      "selected_options": ["session_allow"],
      "authorization_mode": "allow_with_scope",
      "authorization_scope": "domain"
    }]
  }
}
```

外层 `id` 标识本次 RPC，`params.request_id` 必须引用待回答的权限中断；使用原会话连接 / 路由发送。新增范围字段只用于 `permission_interrupt`，不改变普通问答或其它确认流程。

| 用户选择 | `selected_options[0]` | 内部 `ConfirmPayload` 核心字段 | 有效期 |
| --- | --- | --- | --- |
| 本次允许 | `approve` | `approved: true, auto_confirm: false` | 仅本次，不持久化 |
| 会话内允许 | `session_allow` | `approved: true, auto_confirm: true, persist_allow: false` | 当前会话 |
| 总是允许 | `always_allow` | `approved: true, auto_confirm: true, persist_allow: true` | 用户配置中的永久授权 |
| 拒绝 | `reject` | `approved: false, auto_confirm: false` | 拒绝本次，不生成授权 |

内部确认结构还含 `feedback`（默认空字符串）及上述范围字段。兼容旧调用方：`auto_confirm: true` 且 `persist_allow` 省略 / 为 null 时表示永久记住。Web 客户端应使用上表的明确选项。

无效枚举或无法解析的确认结构会重新询问；通过结构校验但组合非法（如 `allow/parent` 或命令使用 `domain`）会以 `[PERMISSION_DENIED]` 拒绝。用户拒绝返回 `[PERMISSION_REJECTED]`（或用户反馈）；策略新增 DENY 返回 `[PERMISSION_DENIED]`。保存失败会回滚本次内存配置并记录失败，当前已获批操作仍可能继续，不应把回答已接收当作持久化成功。

`chat.user_answer` 的 `accepted: true` 仅表示接收回答，不证明审批通过、规则持久化或工具执行成功；应继续观察中断 / 工具结果。动态授权不自动同步沙箱，也不覆盖沙箱的禁止规则。

## 6. `/permissions` 命令使用指南

TUI 中 `/permissions` 是管理工具权限与规则的快捷入口，支持 **交互式管理** 和 **命令行直设** 两种模式。

### 6.1 交互式管理（无参数）

```
/permissions
```

无参数调用时，会先请求 `permissions.tools.get` 和 `permissions.rules.get`，按 **ASK / DENY / ALLOW** 三级分组展示概况：

```
── ASK ──   工具 8 · 规则 22
── DENY ──  工具 1 · 规则 0
── ALLOW ── 工具 33 · 规则 0
```

随后弹出选择菜单，依次进入管理：

#### ① 选择权限组

```
[权限管理] 选择要管理的权限组:
  ASK（30 项）    工具 8 · 规则 22
  DENY（1 项）    工具 1 · 规则 0
  ALLOW（33 项）  工具 33 · 规则 0
  退出
```

#### ② 查看组内详情 + 管理

进入某个组（如 ASK）后，**工具** 和 **规则** 分开列出：

```
── 工具（8）──
  bash
  mcp_exec_command
  write_file
── 规则（22）──
  bash, mcp_exec_command (+1)(cat *)  pattern: cat *
  bash(ls *)                          pattern: ls *
  ...
---
+ 添加             添加工具或参数规则到当前组
返回上级           回到级别选择
```

选中某项后可：
- **移到 ALLOW / ASK / DENY** — 更改级别
- **删除** — 移除该工具或规则
- **返回** — 返回列表

#### ③ 添加新条目（工具或规则）

选择 `+ 添加` 后，输入一行文本，系统自动解析：

```
[添加到 ASK] 当前组: ASK | 添加工具: 输入工具名 (如 write_file) | 添加规则: 输入 工具名(匹配模式) (如 bash(ls *)) | Esc 取消
→ Other  ← 先选此项，再输入内容 (Esc 取消)
```

| 输入格式 | 效果 |
|----------|------|
| `write_file` | 添加工具权限，级别为当前组（ASK） |
| `bash(ls *)` | 添加参数规则，`tools: [bash]`, `pattern: ls *`, `action: ask` |
| `bash(re:.*rm -rf.*)` | 添加正则参数规则 |

> 必须先选中 `Other` 选项进入文本输入模式，再键入内容。按 Enter 提交，Esc 取消。

### 6.2 命令行直设模式

```
/permissions <allow|ask|deny> <tool_name>           # 工具级权限
/permissions <allow|ask|deny> <tool_name>(<pattern>) # 参数级规则
```

| 命令 | 效果 |
|------|------|
| `/permissions ask write_file` | 写入文件前需用户确认 |
| `/permissions allow bash` | 允许 bash 直接执行 |
| `/permissions deny bash` | 拒绝所有 bash 调用（最高优先级，会跳过参数规则） |
| `/permissions allow bash(ls *)` | 允许 `ls *` 直接执行 |
| `/permissions deny bash(re:.*rm -rf.*)` | 拒绝含 `rm -rf` 的命令 |

### 6.3 pattern 写法

- **普通文本**：字面匹配，如 `ls *`（glob 风格通配）
- **正则**：以 `re:` 开头，如 `re:.*\.env$`（匹配整条命令字符串）

### 6.4 action vs severity

`/permissions` 命令将用户设置的 `allow/ask/deny` **直接写入规则的 `action` 字段**，而非通过 `severity` 间接映射。引擎解析参数级规则时，若存在显式 `action`，则**直接使用该动作，不再查 severity 映射表**（参见 §2.1）。

这意味着：
- `/permissions deny bash(re:.*rm -rf.*)` → `action: deny` → **任何模式下都拒绝**（不依赖 `permission_mode`）
- `/permissions ask write_file(re:.*\.env$)` → `action: ask` → **任何模式下都需确认**

> **为什么不用 severity？** 之前的实现将 `deny` 映射为 `severity: CRITICAL`，但在 `normal` 模式下 CRITICAL 的实际效果是 `ask` 而非 `deny`，违背了用户意图。改为直接写 `action` 后，用户的 `allow/ask/deny` 意图得到忠实表达。

### 6.5 规则 ID 生成

- **命令行模式**：格式为 `cli_rule_<tool>_<pattern转义>`，例如 `cli_rule_bash_ls__`
- **交互式添加**：同上。ID 基于 `tool + pattern` 生成，不依赖 action，因此**同一条规则不会因 action 不同而重复创建**。重复添加会提示"该规则已存在"。

### 6.6 错误提示

| 情况 | 提示 |
|------|------|
| 级别不在 allow/ask/deny | `无效级别 "xxx"，仅允许：allow、ask、deny` |
| 工具名为空 | `工具名不能为空。` |
| 工具名含括号但无 pattern | 按工具级权限处理（括号部分被忽略） |
| 规则 ID 已存在 | `该规则已存在，请在列表中选择后修改。` |
| API 请求失败 | 显示具体 RPC 方法名和错误信息 |

### 6.7 与配置文件的对应关系

| 操作 | 写入的配置路径 | RPC 方法 |
|------|-------------|---------|
| 工具级权限设置 | `permissions.tools.<name> = "level"` | `permissions.tools.update` |
| 删除工具 | 从 `permissions.tools` 移除 | `permissions.tools.delete` |
| 创建参数规则 | `permissions.rules` 数组新增条目 | `permissions.rules.create` |
| 修改规则 action | `permissions.rules` 中对应条目的 `action` | `permissions.rules.update` |
| 删除参数规则 | 从 `permissions.rules` 移除 | `permissions.rules.delete` |
| 无参数查看 | 读取 `permissions.tools` + `permissions.rules` | `permissions.tools.get` + `permissions.rules.get` |

### 6.8 后端调用链路

```
permissions.ts (TUI 前端)
    ↓ ctx.request(method, params)
app-state.ts
    ↓ wsClient.request(id, method, params, timeout)
ws-client.ts
    ↓ JSON frame via WebSocket
Gateway (tui_connect.py)
    → 白名单校验（ALLOWED_METHODS）
    → 转发到 AgentServer
AgentServer (permissions_config_rpc.py)
    → dispatch_permissions_config_request()
    → update_permissions_tool_in_config / create_permissions_rule_in_config / ...
config.py
    → load_yaml_round_trip(config.yaml)
    → 修改 permissions 段
    → dump_yaml_round_trip(config.yaml)
```

共 **7 个 RPC 接口**：

| 方法 | 用途 |
|------|------|
| `permissions.tools.get` | 获取所有工具权限 |
| `permissions.rules.get` | 获取所有参数规则 |
| `permissions.tools.update` | 设置/更新工具级别 |
| `permissions.tools.delete` | 删除工具权限 |
| `permissions.rules.create` | 创建新规则 |
| `permissions.rules.update` | 修改规则（如改 action） |
| `permissions.rules.delete` | 删除规则 |

> **注意**：`/permissions` 设置的是全局工具权限。数字人/群聊场景下的 `owner_scopes` 权限需通过频道面板单独配置，详见 [频道](频道.md)。

## 7. CLI：`/add-dir` 与 `persist_cli_trusted_directory`

终端 TUI 中信任目录（如 `/workspace add` → `command.add_dir`）会调用宿主 `persist_cli_trusted_directory`，行为要点：

1. **`file_guard.paths`**：为解析后的目录写入一条前缀规则：`read: allow`、`write: allow`、**`exec: ask`**（目录信任 ≠ 默认可执行该树下二进制）。
2. **若使用带 overrides 的变体且 `schema` 为 `tiered_policy`**：可追加 **shell 类** `approval_overrides`（`match_type: command`）；**不再**写 path 类 override。
3. **Shell 侧 pattern**：仅生成正斜杠路径字面片段，避免 YAML 中 `\U` 非法转义；运行时对命令文本做 `\` → `/` 再匹配。

旧键 `external_directory.<dir>: allow` 仍可读（过渡期）；新写入只走 `file_guard.paths`。

## 10. 文件外发工具的本地源文件防护

`send_file_to_user` 对 `abs_file_path_list` 中的每个文件检查 FileGuard 读权限，兼容数组、JSON 数组字符串、历史 Python 数组字符串和单路径。`save_media_to_gallery`、`save_file_to_file_manager` 对 `url` 为本地路径的分支检查读权限；HTTP/HTTPS URL 和手机端保存不属于本地文件防护范围。三者使用 `permissions.file_guard` 的 `allow` / `ask` / `deny`，不要求源文件写权限。

本地源文件统一通过所属 Agent 的 `SysOperation.fs().read_file(mode="bytes")` 读取，启用 jiuwenbox 时使用沙箱文件读取接口；LOCAL 模式仍为本地后端。未绑定 SysOperation 或读取被拒绝时直接失败，不回退到宿主读取。

两个 `save_*` 工具上传受控读取到的字节。`send_file_to_user` 保留缺失文件跳过、按源路径和内容会话去重，以及下载流程。SysOperation 读取成功后，渠道投递和下载 token 直接使用源文件路径（团队模式为实体化后的工作区路径），不创建 outbound 快照或版本缓存；权限拒绝或后端读取失败时停止发送。相对源路径按 Agent 当前工作目录解析，不展开 `~` 或环境变量。投递端必须能够通过该路径访问同一个源文件；后续读取取得文件当前内容，移动或删除原文件可能导致投递失效。这是发送时的访问检查，不保证内容固定，也不代表每次下载都会重新鉴权。桌面端原有的按路径审核／上报去重逻辑保持不变，不保证同路径每次编辑都重新审核。FileGuard 审批不自动修改 jiuwenbox 策略；两层均须允许读取。

仅 `send_file_to_user` 在受控读取成功后签发带 `approved-outbound-file` 用途的签名下载令牌，允许下载该精确原路径，即使它位于 Web 服务固定目录之外。普通令牌（包括已有链接和 harness 导出）仍受目录限制。下载使用已检查的同一文件句柄，拒绝符号链接／junction 重定向，并保留大小、Range 和超时限制。URL 格式及普通令牌行为不变；下载时不重新执行 FileGuard 权限审批。

外发令牌同时绑定会话目录中随机 32 字节 `.outbound_download_key` 的摘要。每次请求均从磁盘校验，不缓存、不重建缺失会话；删除会话即撤销其外发令牌，重建同名会话也不能恢复旧令牌。并发或重复发送共享一个标识文件，不保存源文件副本或逐次发送记录。缺少会话标识的旧外发令牌、标识丢失或损坏均拒绝下载，需要重新发送签发有效令牌。撤销针对后续请求（包括 Range 重试），不强制中断已通过校验的传输，也不删除接收方已下载的文件。
