# 4 使用 Ops API

Ops API 是扩展调用宿主能力的入口。它把会话查询、界面渲染、文件读取、请求策略和其他平台动作按 namespace.method 的形式提供给 Handler。

本文按 Web Client、Gateway、AgentServer 三个宿主层次说明 Ops 的使用边界。阅读本文后，你应当能够回答四个问题：当前 Handler 拿到的 Ops 属于谁、一次 Ops 调用是否会进入新的事件链、返回结果代表了哪一层已经完成，以及某个方法当前处于什么状态。

## Ops API 如何工作

一次典型调用可以沿着下面的路径理解：宿主收到业务输入，EventBus 找到匹配的 Handler；Handler 执行时，平台把当前扩展包和当前会话绑定到这一个 Handler 的 Ops；Handler 再通过 Ops 调用宿主能力。

### 当前 Handler 的 Ops 从哪里来

普通 Handler 被调用时，平台会创建与本次调用绑定的 Ops 视图。这个视图至少带有两类上下文：

| 上下文 | 用途 | 开发者应如何理解 |
| --- | --- | --- |
| 扩展包身份 | 确定能力归属、方法登记范围和调用来源 | 它用于标识调用者，不等于自动获得所有权限 |
| SessionContext | 提供 session_id、可选 cwd 和其他会话元数据 | 它描述当前调用所在的会话；没有会话时，依赖会话的方法应按契约拒绝或返回相应状态 |

因此，session.cwd()、session.root()、session.model() 等方法通常不要求调用者再次传入 session_id。会话身份由当前调用上下文绑定，开发者不应从事件载荷中复制一个 session_id 覆盖它。

当前调用结束后，Ops 视图也就失去了原来的生命周期保证。不要把它缓存到模块全局变量、跨 Handler 复用，或直接交给脱离当前调用的后台任务使用。

### 如何阅读一个 Ops 条目

调用前先按下面的字段确认方法边界。7 参考文档中的能力条目也按这组字段组织：

| 字段 | 需要确认的内容 |
| --- | --- |
| 功能定位 | 方法解决什么问题，以及它属于 Web Client、Gateway 还是 AgentServer 的哪条业务链 |
| 调用时机 | Handler 在什么阶段调用，是否由宿主主动触发 |
| 输入 | 显式参数、当前上下文、默认值和限制 |
| 输出 | 返回对象、状态、回执或游标，以及它代表的完成点 |
| CORE 兜底 | 没有 USER 或 BUILTIN 接管时，平台如何完成默认动作 |
| 推荐用法 | 适用场景和不应交给扩展处理的部分 |
| 验证方式 | 正常、失败、边界和无外部依赖时如何隔离验证 |
| 状态 | 已支持、实现中、agent-core 已支持但 JiuwenSwarm 未接入，或设计中 |

尤其要看 CORE 兜底。CORE 不是“什么都不做”：真实业务动作由 CORE 执行默认动作，通知类事件则可能只校验可信上下文并返回回执。

### Ops 不等于当前事件链

Handler 处理完自己的逻辑后，是否继续调用当前事件链的下一个 Handler，仍由 Handler 自己决定。调用一个 Ops 方法，不会自动完成这件事。

~~~python
async def handle(event, ops, next_handler):
    cwd = await ops.session.cwd()

    # Ops 调用只完成一次会话查询；它不代替当前事件链的继续执行。
    result = await next_handler(event)
    return result
~~~

具体的 EventNext 规则见 [3.【事件】使用事件响应宿主流程](<3.【事件】使用事件响应宿主流程.md>)。如果 Ops 方法本身是一个动作方法，它可能会启动另一条事件链，但那仍然是另一条链，不能用来推断当前链已经继续。

## Ops 方法的两种调用方式

从开发者角度，Ops 方法首先分为查询方法和动作方法。这个区分比“方法名看起来像什么”更重要，因为它决定了调用是否产生副作用、是否会启动新的事件链，以及返回值应该如何解释。

| 类型 | 典型方法 | 主要用途 | 调用结果 | 事件链行为 |
| --- | --- | --- | --- | --- |
| 查询方法 | session.cwd()、session.root()、session.model()、session.repo()、session.messages()、session.turns()、session.usage() | 读取当前会话或宿主状态 | 返回值、空值、分页结果或查询状态 | 按查询契约读取；当前会话查询可由同名查询事件承载，CORE 使用原始服务或可信上下文，避免递归 |
| 动作方法 | ui.render(request)、session.append(note)、http.fetch(request) | 请求宿主执行动作 | 返回执行回执、状态、错误码或外部响应 | 通常启动新的动作事件链，或由对应宿主服务执行；不会替代调用者所在的当前事件链 |

这里的“查询”描述的是公开语义，不表示所有查询都绕过 EventBus。当前 session 查询方法使用同名事件承载查询，目的是让平台统一绑定当前 session、执行宿主侧校验并提供可观测的查询入口；查询事件的 CORE 不再通过公共 Ops 触发同名事件，而是直接读取原始服务或可信上下文。阅读具体方法条目时，应以该方法的事件行为说明为准。

### 查询方法：读取当前上下文

查询方法通常不改变会话状态，也不负责启动 Agent、发送消息或渲染界面。它们返回的内容只代表调用时刻的视图：cwd 可能为空，模型信息可能未知，usage 中的某个数值也可能暂时不可用。

不要把查询结果当成永久事实保存下来，也不要根据一次查询结果自行推断宿主已经完成了某个动作。

### 动作方法：请求宿主执行能力

动作方法往往会触发一个新的事件链，并由对应的宿主服务完成后续动作。例如，ui.render(request) 请求 WebUI 处理一次渲染；session.append(message) 请求会话服务追加一条 transcript-only 记录。

动作方法的返回值首先是宿主侧回执，不一定代表最终用户已经看到结果，也不一定代表外部系统已经完成处理。对跨进程、跨网络或异步投递的方法，必须按契约区分成功、拒绝、失败和未知。

## 读取一个 Ops 方法的契约

在调用任何方法前，至少确认以下内容：

1. 方法是否已实现，还是只出现在架构设计中。
2. 方法需要哪些显式参数，哪些身份和目标由当前上下文绑定。
3. 方法是否启动新的事件链，是否会改变状态或访问外部资源。
4. 返回值中的 status、error、revision、downloadUrl 等字段分别代表哪一层的结果。
5. 方法的失败、取消、超时和未知状态是否允许重试。

### Ops 命名与 namespace

Ops 使用 namespace.method 组织能力。namespace 表示能力归属，method 表示该归属下的一个稳定操作；例如 session.cwd() 表示读取会话工作目录，ui.render(request) 表示请求 UI 渲染。

开发者应遵循三条规则：

- 只调用 API 索引中已经登记的方法，不要因为某个宿主内部存在同名 Python 函数就直接依赖它。
- 不要把自己的 Handler 方法临时挂到已有 namespace，也不要用一个容易与平台能力冲突的名称覆盖现有方法。
- 新能力应先确定归属宿主、输入输出契约、权限边界和事件行为，再登记 namespace.method；不能先暴露一个没有稳定语义的方法名。

namespace 的归属也决定了调用边界。session 方法应使用当前会话上下文，ui 方法应接受宿主管理的渲染目标，Gateway 方法应由 Gateway 负责请求路由、浏览器连接、认证策略和受控出站；扩展不能因为“能拿到 Ops 对象”就越过这些边界。

### Ops 输入契约

输入契约不只包括参数类型，还包括参数的来源、默认值、可选值、校验责任和不可由调用者伪造的字段。

| 输入部分 | 应确认的问题 | 常见边界 |
| --- | --- | --- |
| 业务参数 | 参数是否必需，是否有默认值，空字符串和 None 是否有不同含义 | 不要把“未提供”当成“明确为空” |
| 调用身份 | 身份来自参数还是当前 Ops 绑定 | session_id、package_id、connection_id 等通常由宿主绑定或校验 |
| 目标位置 | 目标是否可由扩展选择，还是只能使用宿主返回的目标 | 浏览器不能自行声明 project_root 或物理连接 |
| 来源字段 | 事件来源、渠道、用户和连接信息由谁提供 | 不要从不可信的请求体复制来源身份 |
| 校验与限制 | 路径、长度、节点数、文件类型和权限由谁检查 | 以宿主校验为准，扩展侧校验只能作为提前失败的优化 |

例如，session.files(expanded_paths) 的 expanded_paths 是展开请求，不是根目录声明；session.read_file(path) 的 path 也不是让浏览器自行扩大读取范围的授权。服务端仍需根据当前会话和渠道上下文校验目录、文件类型和大小。

### Ops 输出契约

输出要回答两个问题：调用请求是否被宿主接受，以及目标动作是否已经达到调用者关心的完成点。不要只看一个布尔值或 HTTP 成功码。

| 输出形态 | 应如何解释 |
| --- | --- |
| 查询值 | 这是调用时刻的状态视图；可能是空值，空值不自动表示异常 |
| status | 表示方法定义的状态机节点，例如 delivered、rejected、delivery_failed；必须按方法条目解释 |
| error 或错误码 | 表示失败原因或宿主拒绝原因；不要用异常字符串替代稳定错误码 |
| revision、cursor 等游标 | 表示宿主的版本或分页位置，不等于客户端已经展示或消费 |
| downloadUrl | 表示宿主签发了受控下载入口，不表示调用者获得了任意文件读取权限 |
| unknown | 表示结果无法确认；除非契约明确允许，否则不要自动重试可能产生副作用的动作 |

返回值应保持在 API 契约规定的可序列化边界内。不要把连接、文件句柄、异步任务、EventBus 或 Handler 实例塞进 Ops 返回值。

## Web Client / WebUI Ops

WebClient 侧的扩展能力，重点是让扩展请求一个受宿主管理的界面变化，或者读取界面需要展示的会话文件。调用通常发生在服务端 Handler 中，WebUI 宿主负责校验目标和生成传输结果，最终由 WebClient 应用界面更新。

这条链路中的“成功”有层次差异：Ops 返回 delivered，通常说明宿主已经接受并完成了它定义的投递步骤；它不自动证明浏览器已经收到帧、前端已经挂载组件，或用户已经看见内容。

### ui.render：请求渲染一个声明式 UI 树

ui.render(request) 是当前已实现的动作方法。请求包含 RenderTarget、可选的 RenderNode 树和 replace 或 clear 模式；目标中的 connection_id 由服务端管理，扩展不应从浏览器请求体中伪造一个连接。

| 项目 | 说明 |
| --- | --- |
| 功能定位 | 向一个受宿主管理的 UI 槽位提交声明式渲染结果 |
| 调用上下文 | 当前 Handler 的扩展包身份、SessionContext，以及 WebUI 对目标槽位和连接的绑定 |
| 输入重点 | target、root、mode；组件、props、children 和 events 遵循 WebUI 组件 Props 权威规约 |
| 返回结果 | UiRenderOutput，至少包含 status 和 revision |
| 结果边界 | delivered、rejected、delivery_failed 的含义不同；delivered 不等于浏览器已完成展示 |
| 事件行为 | 作为 ui.render 动作启动新的渲染事件链，不推进当前 Handler 所在的事件链 |

示意代码如下。target_for_current_slot、build_declared_tree 和 record_render_failure 只是帮助理解调用位置的示意函数，实际组件和 Props 应以项目的权威规约和 API 条目为准。

~~~python
async def on_usage(event, ops, next_handler):
    request = UiRenderInput(
        target=target_for_current_slot(ops),
        root=build_declared_tree(),
        mode=RenderMode.REPLACE,
    )

    render_result = await ops.ui.render(request)
    if render_result.status != RenderStatus.DELIVERED:
        record_render_failure(render_result)

    # render 不会替代当前事件链的继续执行。
    return await next_handler(event)
~~~

调用方至少要处理三种情况：目标被宿主拒绝时修正 target 或结束本次操作；传输失败时记录可诊断信息；返回 delivered 后仍把它理解为宿主投递完成，而不是用户界面最终状态。

### session.files：读取受控的文件树

session.files(expanded_paths) 是当前已实现的只读能力，常用于 WebClient 的文件浏览器或扩展面板。它读取的是当前 session 关联的工作空间视图，宿主会限制目录深度、节点数量、单层数量、响应大小和展开目录数量。

~~~python
tree_result = await ops.session.files(expanded_paths=["src", "docs"])

if tree_result["status"] == "ready":
    render_tree(tree_result["treeData"])
else:
    show_tree_error(tree_result)
~~~

expanded_paths 只表示希望展开哪些目录，不表示扩展可以把根目录切换到任意位置。符号链接和非普通文件可能被跳过，响应也可能通过 truncated 或 readFailed 说明结果不完整；界面应展示这些状态，而不是把缺失节点默认为不存在。

### session.read_file：读取文件内容或受控下载入口

session.read_file(path) 同样是当前已实现的只读能力。宿主根据当前会话、渠道和用户上下文检查路径及文件类型，再决定返回小型 UTF-8 文本内容，还是返回受控的 downloadUrl。

~~~python
file_result = await ops.session.read_file(path=selected_path)

if file_result["status"] != "ready":
    show_file_error(file_result)
elif "content" in file_result["file"]:
    show_text(file_result["file"]["content"])
else:
    offer_download(file_result["file"]["downloadUrl"])
~~~

不要让 WebClient 自己提交 project_root，也不要把 downloadUrl 当作长期权限。服务端会根据目录、文件类型和大小执行限制；前端只消费返回结果并展示相应状态。

## Gateway Ops

Gateway 是外部请求、浏览器连接、认证策略和跨边界传输的宿主。它不负责 AgentServer 的业务状态，也不把请求头存在视为认证成功。Gateway Ops 的重点是请求应该如何路由、连接作用域资源如何清理，以及扩展如何使用受控的出站能力。

### gateway.request：在原生路由前处理请求策略

gateway.request 是 Gateway 在原生路由前提供的策略入口。它可以让 USER Handler 执行认证、限流、请求改写或业务消费，但不应在 Gateway 内复制 AgentServer 业务。

| 项目 | 说明 |
| --- | --- |
| 功能定位 | 在主 WebSocket RPC 或 Gateway HTTP 请求进入原生分发前提供策略入口 |
| 调用时机 | 请求进入原生分发前 |
| 输入 | GatewayRequestInput，包括 method、params、headers、request_context、session_id 等 |
| 输出 | GatewayRequestOutput，可表示 forward、local、consume 或 deny；forward 可以携带允许范围内的 params 改写 |
| CORE 兜底 | 校验 method；默认 route 为 forward，把请求交给原生分发；USER Handler 超时或异常时按 fail-open 规则继续 forward |
| 推荐用法 | 在边界层完成认证、限流和请求策略；不要把请求头或客户端字段直接当作可信身份 |

四种路由结果的含义不同：forward 继续原生分发，local 交给 Gateway 已登记的本地方法，consume 表示扩展已经应答，deny 表示扩展拒绝请求并跳过原生分发。

下面只展示处理形状。GatewayRequestInput、GatewayRequestOutput 和当前 Handler 参数的精确接口以 7 对应条目及本地类型声明为准：

~~~python
async def handle_gateway_request(event, ops, next_handler):
    request = CURRENT_GATEWAY_REQUEST

    if not ALLOW_REQUEST(request):
        return GATEWAY_DENY_OUTPUT

    # 继续原生路由，不能把策略 Handler 当成 AgentServer 业务处理器。
    return await next_handler(event)
~~~

### gateway.disconnect：清理连接作用域资源

gateway.disconnect 在 WebSocket 断开或 Gateway 主动清理连接时通知扩展。它的输入包括 connection、session_ids 等连接信息，不提供业务结果；CORE 负责清理连接相关实例和状态，但不影响其他连接。

扩展可以在这里释放自己的 connection 作用域资源，但不要把 gateway.disconnect 当作 session.end。会话结束和连接断开是两个不同的生命周期事件。

### Gateway ui.render：只处理 application 作用域

Gateway 的 ui.render 负责按连接向浏览器下发 application 作用域组件树。它与 AgentServer 会话槽位的渲染不是同一条寻址路径：application 目标由 Gateway 按 connection_id 寻址，conversation、task 和 message 目标由 AgentServer 按会话寻址。
| 项目 | 说明 |
| --- | --- |
| 输入 | UiRenderInput，包括 target、root、mode；application 目标必须包含由 Gateway 注入的 connection_id |
| 输出 | UiRenderOutput，包括 delivered、rejected、delivery_failed 和 revision |
| CORE 兜底 | 校验槽位、组件树、实例和预算；成功后按 ws_id 发送 webui.render；发送失败时回滚实例状态 |
| 使用边界 | 用于登录、设置和应用级页面；不要用 Gateway 渲染 AgentServer 的 session 槽位 |

因此，调用 ui.render 时不能从浏览器请求体中读取并信任 connection_id。连接由 Gateway 绑定，扩展只提交符合契约的渲染目标。

Gateway 当前支持 application.entry 和 application.sidebar.footer 两个应用槽位。conversation、task 和 message 槽位不属于 Gateway 的 application 渲染范围。

### ops.http.fetch：受控的 Gateway HTTP 出站

ops.http.fetch 由 Gateway 进程代扩展发起受控 HTTP 请求。它不是 AgentServer 的通用网络 API，扩展仍然受 allowed_hosts、协议、重定向、超时和响应体大小限制。

| 项目 | 说明 |
| --- | --- |
| 输入 | HttpFetchInput，包括 url、method、headers、body、timeout_ms、follow_redirects |
| 输出 | HttpFetchOutput，包括 status、headers、body、elapsed_ms、code |
| 默认限制 | 默认超时 3000ms，上限 5000ms；默认不跟随重定向；空白白名单拒绝所有出站请求 |
| 重定向 | 每次重定向都重新校验目标主机 |
| 失败行为 | 平台失败通过 code 返回，不把业务失败改写成成功结果 |

~~~python
result = await ops.http.fetch(
    HttpFetchInput(
        url=ALLOWED_URL,
        method="GET",
        headers=REQUEST_HEADERS,
        body=None,
        timeout_ms=3000,
        follow_redirects=False,
    )
)

if result.code is not None:
    handle_gateway_fetch_error(result)
else:
    consume_response(result.status, result.headers, result.body)
~~~

### Gateway 客户端能力的边界

client.local_storage.set/delete 只操作发起调用的浏览器；client.page.reload 只刷新当前页面，不自动重建业务状态。它们都不能替代 Gateway 的认证、连接绑定或 AgentServer 的会话状态。

Gateway 验证应覆盖四类路径：gateway.request 的 forward、local、consume、deny；USER Handler 超时或异常时的 fail-open；HTTP 白名单、超时、重定向和响应体上限；连接断开和过期 UI 实例的资源清理。

## AgentServer Ops

AgentServer 是事件链、Handler、Ops 和 Agent 业务的主要执行宿主。Web Client 和 Gateway 可以触发 AgentServer 事件，但不应直接访问 AgentServer 内部对象。AgentServer Ops 主要提供当前会话查询、会话历史动作、Agent/Tool 登记和受控资源访问。

### 会话查询方法

七个会话查询事件共享查询注册和校验逻辑。除 session.usage 外，事件输入为空映射；会话身份由 EventHandlerOps.session_context 绑定，不由扩展在输入中填写。

| 方法 | 功能定位 | 输入 | 输出和边界 |
| --- | --- | --- | --- |
| session.cwd() | 查询当前会话实际执行目录 | 空对象 | 绝对路径或 None；不使用进程 cwd 代替 |
| session.root() | 查询当前项目根目录 | 空对象 | 绝对路径或 None；无绑定时接受 None |
| session.model() | 查询当前会话主模型信息 | 空对象 | 规范化模型对象或 None；不把模型信息当作授权依据 |
| session.repo() | 查询当前工作区 Git 仓库事实 | 空对象 | root、remote、internal、name 等仓库信息或 None；不修改仓库状态 |
| session.messages() | 分页读取主会话历史 | limit、cursor | 消息列表和下一页游标；不要把历史读取当作写入 |
| session.turns() | 统计已提交用户轮次 | 空对象 | 非负整数或 None；不把模型步骤或工具调用混入 |
| session.usage() | 读取上下文用量快照 | breakdown、columns 可选 | context、rateLimits，可选 cost、breakdown；不重新测量 |

查询代码可以这样组织：

~~~python
async def inspect_session(event, ops, next_handler):
    cwd = await ops.session.cwd()
    model = await ops.session.model()
    usage = await ops.session.usage(breakdown="summary", columns=80)

    show_session_summary(cwd=cwd, model=model, usage=usage)
    return await next_handler(event)
~~~

这段代码没有传入 session_id，是因为当前会话身份由 Ops 上下文绑定。cwd 为 None 不一定是错误，model 为 None 也不表示扩展可以自行选择模型；usage 中缺少 cost 或某项限额也不应被扩展补成 0。

### session.append：追加会话历史记录

session.append 是历史记录提交前的扩展点。作为 Ops 调用时，它使用当前绑定的会话和包身份，进入独立的 session.append 事件链；它不会在 Handler 中启动 Agent，也不会自动渲染 UI。事件条目的输入包括 message、door、origin、uuid，输出包括 status、session_id、message_id，以及可选的 message、reason、uuid、history_record。

~~~python
async def add_note(event, ops, next_handler):
    note = {
        "id": "example-note-42",
        "message": {
            "type": "assistant",
            "content": [{"type": "text", "text": "这是一条由扩展追加的会话记录"}],
        },
    }
    receipt = await ops.session.append(note)
    handle_append_receipt(receipt["status"], receipt.get("reason"))
    return await next_handler(event)
~~~

追加操作有副作用。扩展要保存真实存储回执，并按 status、reason、message_id 和 history_record 处理结果；不要把一次追加当成普通查询，也不要在超时后无条件重复追加。

### agent.register 与 tool.register：登记运行时能力

这两个方法用于登记 Agent 类型和工具定义，不等于启动 Agent 或执行工具：
| 方法 | 功能定位 | 输入 | 输出和 CORE 兜底 |
| --- | --- | --- | --- |
| agent.register | 注册当前 Agent 可使用的子 Agent 类型 | AgentCard、prompt 和运行时支持的可选字段 | 返回 agent、agent_card 或 deny；CORE 核对 DeepAgent 绑定并把声明物化到运行时 |
| tool.register | 注册工具、RestfulApiCard 或 callable | 工具来源及 ToolCard | 返回工具名称或 deny；CORE 核对 Agent 后物化并登记工具 |

注册动作应发生在扩展加载或能力登记阶段。不要在普通业务 Handler 中伪造运行时实例，也不要把 tool.register 的成功当成 tool.call 已经执行。

### 文件系统、MCP 与状态资源

这些能力的共同边界是：由宿主提供受控服务，扩展通过契约访问，CORE 负责路径、超时、权限或服务状态校验。
| 能力 | 功能定位 | 关键输入/输出 | 使用边界 |
| --- | --- | --- | --- |
| fs.read | 读取文件内容 | path、mode、head、tail、line_range、encoding、chunk_size、only_read、timeout_ms；返回 status、path、content、mode、error | 使用 Agent 的 cwd、project_root 和 workspace 建立的可信路径；不直接使用不受控进程路径 |
| fs.list | 列举目录 | path、recursive、max_depth、文件类型、max_entries、timeout_ms；返回 entries、total_count、truncated、error | 遵守枚举预算，不递归扫描无界目录 |
| mcp.connect / mcp.call | 连接 MCP 服务并调用工具 | server_id、tool、arguments、timeout_ms；返回 connected、result、is_error、error 等 | 连接失败和对端错误必须保留，不能把空工具列表当成成功连接 |
| store.get / store.set | 读写扩展包持久化 JSON | key、default 或 key、value；按包隔离 | 用于用户偏好和扩展配置，不保存临时会话状态 |
| state.get / state.set | 读写扩展运行状态 | StateAddress、value、expected_version；返回 exists、value、version 或 CAS 结果 | 构树期间只读，交互回调中写状态；不能通过 package_id 访问其他包 |

FS 默认超时为 30 秒，上限 10 分钟；同名 Ops 重入由 OpsCallGuard 拒绝。MCP register/connect 默认 60 秒，call 默认 120 秒，上限 10 分钟。实际方法名和可用 namespace 以 API 索引为准。

### session.compact：接口存在但主流程尚未接入

session.compact 目前只有事件链和 Ops 接口，主流程尚未接入。未装配压缩服务时会拒绝调用，扩展不应把它当作生产会话压缩能力。

### AgentServer 验证路径

- 会话路径：在绑定和未绑定 SessionContext 两种条件下查询 cwd、root、model、repo、messages、turns 和 usage，区分缺失值、真实空值和拒绝结果。
- 历史路径：验证 session.append 的输入校验、真实存储回执和重复调用行为；确认它不会启动 Agent。
- 资源路径：验证 FS 的路径边界、读取窗口、超时和截断；验证 MCP 的登记、连接、工具调用以及对端错误。
- 登记与状态路径：验证 agent.register、tool.register 的登记结果；用两个扩展包分别读写 store，确认数据隔离；用不同版本条件调用 state.set，确认 CAS 结果。

## Ops 的依赖与生命周期

开发者需要关心的是“这个方法在什么上下文中可见、什么时候可以调用、调用结束后还能否使用”，而不是平台内部如何组装 Builder、注册表和服务实例。

### 能力可见范围

Ops 能否调用成功取决于三个条件：方法已登记，当前宿主提供该能力，本次调用具备所需上下文。方法存在于 API 文档中，不代表每个宿主、每个事件或每个 session 都一定可用。

例如：

- session.cwd() 需要当前调用有会话上下文；没有 session 时不能凭空构造一个工作目录。
- ui.render(request) 需要目标槽位和宿主连接满足 WebUI 契约；全局槽位与会话槽位的上下文可能不同。
- gateway.request 需要 Gateway 提供规范化的请求上下文；扩展不能用请求头是否存在代替认证判断。
- ops.http.fetch 需要 Gateway 的 allowed_hosts 和出站限制；方法本身不会放开网络访问。
- Gateway ui.render 只能按 application 作用域和当前连接寻址；它不会替代 AgentServer 的会话槽位渲染。

### 不要缓存或跨边界转交 Ops

一个 Ops 视图绑定了当前 Handler 的 package 和 SessionContext。缓存它会带来三个问题：后续调用可能错用旧 session，权限审计可能指向错误的扩展包，后台任务可能在原事件结束后继续使用失效上下文。

如果确实需要异步工作，应把方法契约允许的数据复制成普通的、可序列化的任务输入，并由宿主提供的后台任务或事件机制重新建立合法调用上下文；不要把原始 Ops 对象塞进队列。

## Ops 的状态、权限与资源

Ops 是能力入口，不是权限提升入口。扩展包身份用于说明“谁在调用”，SessionContext 用于说明“在哪个会话中调用”，真正的路径、目标、凭据和资源限制仍由对应宿主服务负责。

### 状态范围

阅读方法条目时，先确认状态属于哪一个范围：

| 范围 | 例子 | 注意事项 |
| --- | --- | --- |
| session | cwd、messages、usage、transcript | 依赖当前会话；会话结束后不应继续使用旧上下文 |
| instance | 当前 Agent 或扩展实例的临时状态 | 不要假设多个实例共享，除非契约明确说明 |
| package | 扩展包身份和登记信息 | 标识归属，不自动授予文件、渠道或模型权限 |
| process | 注册表、连接池和宿主级服务 | 扩展不应直接修改宿主全局状态 |

### 权限与敏感数据

路径、连接、用户身份、凭据和外部系统目标都属于敏感边界。扩展应当：

- 使用 Ops 返回的受控值，不从请求体中重新声明身份、根目录或物理连接。
- 不在日志或返回值中泄露凭据、完整下载令牌或不必要的个人信息。
- 不把“当前包能够调用某方法”解释成“当前包可以访问任意资源”。
- 对跨服务动作保存宿主返回的状态，不自行伪造“已发送”“已展示”或“已提交”。

## Ops 的并发、取消与重试

Ops 方法可能访问共享会话、文件系统、浏览器连接或外部渠道。除非方法契约明确说明幂等和并发规则，否则不要假设两个调用会自动串行，也不要假设取消会撤回已经提交给外部系统的动作。

开发者需要分别处理：

- 重入：同一个 Handler 或 session 是否可能同时发起多个调用。
- 幂等：重试是否会重复追加消息、重复渲染或重复发送外部消息。
- 超时：超时只说明调用方没有在期限内得到确认，不一定说明宿主没有执行。
- 取消：取消等待任务不一定能取消已交给宿主或外部系统的工作。
- 资源释放：文件、连接和临时任务由拥有它们的宿主负责释放；扩展不要持有超出契约的句柄。

最安全的默认策略是：对查询按方法契约处理缺失值和读取失败，对有副作用的动作先保存请求标识和已知状态，再根据明确的幂等或恢复契约决定是否重试。Gateway 的 route、HTTP 的 code、文件能力的 status 和 UI 的 delivery 状态都必须按各自条目解释。

## 如何选择 Ops 还是事件

可以用下面的判断快速定位扩展入口：

| 需求 | 优先阅读的入口 | 原因 |
| --- | --- | --- |
| 读取当前 session、模型、仓库或用量 | 对应的查询 Ops | 这是读取当前上下文的能力，不应通过修改事件载荷实现 |
| 请求 UI 产生一次渲染变化 | ui.render(request) 及 ui.render 事件 | 它需要宿主校验目标、连接和渲染结果 |
| 追加一条会话记录 | session.append(message) 及其事件契约 | 它有副作用，需要回执和一致性处理 |
| 观察或修改宿主事件处理流程 | 事件与 Handler | 事件决定匹配、顺序、EventNext 和异常传播 |
| Gateway 请求策略 | gateway.request 及其事件链 | 路由结果必须是 forward、local、consume 或 deny 之一 |
| Gateway 受控出站请求 | ops.http.fetch | URL、主机白名单、重定向、超时和响应体由 Gateway 校验 |
| application 级浏览器界面 | Gateway ui.render | 目标连接由 Gateway 绑定，不渲染 AgentServer 的会话槽位 |
| 读取或写入 AgentServer 受控资源 | fs、MCP、store、state 能力 | 路径、服务、包身份和版本条件由宿主校验 |
| 新增一个平台能力 | 平台侧的能力登记和 API 文档 | 普通扩展不能把内部函数直接变成公共 Ops |

一个简单的经验是：需要“读当前状态”时先找查询 Ops；需要“让宿主做一件事”时找动作 Ops；需要“改变哪些 Handler 会运行以及运行顺序”时回到事件模型。

## 常见错误

### 把 Ops 当成全局服务

错误做法是把一次 Handler 收到的 Ops 保存到全局变量，或者在另一个 session 的后台任务中继续使用。正确做法是让每次合法调用都使用它自己的上下文。

### 把动作回执当成最终结果

ui.render 返回 delivered 不等于用户已经看到界面；gateway.request 返回 forward 也不等于 AgentServer 已经完成业务处理。应按方法定义的完成点处理状态。

### 手动覆盖宿主绑定的身份

不要在 session 查询中自行传 session_id，不要让浏览器提交 project_root 或 connection_id 来替代宿主绑定，也不要用扩展包参数绕过 Gateway 的目标校验。

### 用动作方法代替 EventNext

session.append 或 ui.render 产生的新事件链，不是当前事件链的 next。Handler 是否继续执行后续 Handler，仍要按 [3.【事件】使用事件响应宿主流程](<3.【事件】使用事件响应宿主流程.md>) 的规则处理。

### 把请求头当成认证结果

gateway.request 提供规范化 headers 和 request_context，但 Gateway 不提供内置认证门禁，也不把 Authorization 非空当作认证成功。认证、匿名范围和错误应答由 USER Handler 明确处理。

### 把 Gateway 出站能力当成任意网络访问

ops.http.fetch 必须遵守 allowed_hosts、协议、重定向、超时和响应体大小限制。空白白名单拒绝所有出站请求，每次重定向都要重新校验目标主机。

### 把登记方法当成执行方法

agent.register 和 tool.register 只登记运行时能力，不代表 Agent 已启动或工具已经执行。需要执行 Agent 或工具时，应使用当前已登记且有稳定契约的宿主入口。

### 把未接入的接口当成生产能力

session.compact 当前主流程尚未接入；agent.offer、agent.spawn、agent.list 以及多数 Agent Loop 能力也没有稳定的完整接入。调用前先检查 [8.【API文档索引快查】OpenJiuwen 扩展 API 索引](<8.【API文档索引快查】OpenJiuwen 扩展 API 索引.md>) 的状态，不要根据规划名称自行拼接方法。
