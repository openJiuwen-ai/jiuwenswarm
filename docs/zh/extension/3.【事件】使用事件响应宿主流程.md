# 3 【事件】使用事件响应宿主流程

2 里的 Token Weather 扩展已经展示了一条完整路径：宿主发出 context.usage.updated，扩展读取会话数据，再通过 ui.render 更新界面。本章沿着这条真实路径，说明事件怎样进入宿主处理链，以及不同功能应该选择哪一类事件。

本文只把 7 中已有稳定登记、运行时接入和明确 CORE 行为的能力作为可执行示例。7 标记为实现中或设计中的事件，只用于说明边界，不应直接写进扩展。事件的输入、输出、状态和验证方式，以 [7.【API文档完整版】OpenJiuwen 扩展参考](<7.【API文档完整版】OpenJiuwen 扩展参考.md>) 为准。

## 事件先这样运行起来

### 从 Token Weather 看一条真实链路

AgentServer 在一次请求完成后发布 context.usage.updated。事件输入携带 session_id、request_id、token 用量、上下文窗口和模型等信息。

Token Weather 的 USER Handler 收到事件后，调用 ops.session.turns() 和 ops.session.usage() 查询当前会话，再调用 ops.ui.render() 更新 Web Client。扩展没有接管宿主的用量处理，因此最后继续调用 next_handler。

~~~python
def register(self, registrar):
    registrar.register_event_handler(
        "context.usage.updated", self.on_usage, {}, "user"
    )

async def on_usage(self, event, ops, next_handler):
    turns = await ops.session.turns()
    usage = await ops.session.usage(breakdown="summary")
    logger.info("session usage: turns=%s usage=%s", turns, usage)
    return await next_handler(event)
~~~

Token Weather 在同一个 context.usage.updated Handler 中继续调用 ops.ui.render(UiRenderInput(...))，把用量状态渲染到 message.assistant.meta 和 conversation.input.below。上面的代码体现了事件扩展最常见的形态：事件负责挂到宿主流程上，Ops 负责读取或改变平台能力，next_handler 负责让原有流程继续完成。

如果扩展只需要记录用量，可以只读取 session.turns 和 session.usage；如果还要展示面板，才需要调用 ui.render。事件本身不是查询接口，也不是 UI 绘制接口。

### 一条事件为什么会有多层 Handler

公共事件链按 USER → BUILTIN → CORE 处理。USER Handler 放扩展逻辑，BUILTIN Handler 负责平台规则，CORE Handler 负责默认动作或可信上下文校验。

    USER Handler → BUILTIN Handler → CORE Handler

USER Handler 调用 next_handler(event) 后，事件才会进入后续层。没有调用 next_handler，当前 Handler 返回的结果就会成为这条链路的结果；这适合拒绝、消费或完全接管事件。

next_handler 只推进当前事件链，不会自动重试，也不会在异常后回滚已经完成的副作用。一个 Handler 不应对同一事件调用两次 next_handler。

Ops 和 next_handler 不是同一个动作。调用 ops.session.usage() 会发起一次查询事件链，调用 ops.ui.render() 会发起一次渲染事件链；它们不会把当前正在处理的事件推进到下一层。

如果事件代表真实业务动作，CORE 要完成原有平台动作；如果事件只是通知，CORE 可以只校验可信上下文并返回真实回执。CORE 处理查询或写入时应使用内部服务，不要在同名事件的 CORE Handler 里再次调用同名公开 Ops，否则会重新触发同一事件。

### 事件从哪个宿主进入

扩展包的 `manifest.json` 中 `package.domain` 决定它挂在哪个宿主。Web Client、Gateway 和 AgentServer 各自创建事件总线，事件不会自动跨宿主传播。

| 架构层 | 代码中已注册的事件 | 主要职责 |
| --- | --- | --- |
| Web Client | ui.render、ui.ready、ui.click、ui.change、ui.press_enter、ui.select、ui.search、ui.clear | 渲染扩展 UI，接收用户交互 |
| Gateway | gateway.request、gateway.disconnect | 处理连接上的请求准入和连接生命周期 |
| AgentServer | session.start、session.attach、session.detach、session.end | 处理会话生命周期 |
| AgentServer | session.send、session.receive、session.append | 处理消息投递和历史追加 |
| AgentServer | context.usage.updated | 接收一次请求完成后的用量通知 |
| AgentServer | session.cwd、session.root、session.model、session.repo、session.messages、session.turns、session.usage | 查询会话上下文和历史数据 |

有些事件在不同宿主都出现，例如 ui.render。名称相同不代表事件总线相同，扩展必须在正确的宿主中注册。

Web Client 的交互通常先通过 webui.dispatch 或 Gateway 请求进入，再由对应宿主转成 ui.* 事件。AgentServer 的 session.* 和 context.* 事件则由会话运行时直接触发。

7 中的 ui.unmount、ui.blur、ui.focus、ui.scroll 以及 prompt.* 事件仍缺少稳定公开输入输出或完整运行时接入。本章不把它们当作可直接开发的事件。

### 事件如何被发现并进入事件总线

扩展包加载后，extension.py 中的 register_handlers 会向当前宿主的事件总线注册 USER Handler。宿主 bootstrap 先注册事件类型、BUILTIN Handler 和 CORE Handler，再由 ExtensionManager 加载已安装的扩展包。

事件类型注册和 Handler 注册是两件事。前者定义输入、输出和 CORE 默认行为，后者定义扩展在哪些输入上参与处理。只写了 Handler，但事件没有在宿主 bootstrap 中注册，扩展不会因为事件名存在就自动生效。

正常事件分发前，宿主先完成 Ops Build。事件总线再按 USER、BUILTIN、CORE 的层级组织处理链；USER 和 BUILTIN 的优先级高于 CORE，CORE 位于兜底位置。不要把某个文件的加载顺序当作业务顺序。

匹配到的 Handler 会在事件开始分发时确定。Handler 执行过程中再修改注册表，不会改变这一次事件已经选定的处理链；需要新增或调整扩展时，应通过扩展加载生命周期完成。

## 开发前先选对扩展点

### 先判断需求是否是事件需求

先问需求是不是要挂在一条已经存在的宿主流程上。如果需要观察、修改、拒绝或消费这条流程，使用事件；如果只是调用一个可复用的平台能力，优先使用 Ops。

| 需求 | 优先选择 | 实际例子 |
| --- | --- | --- |
| 在会话开始时读取工作目录并初始化扩展状态 | session.start 事件 | session_start 示例 |
| 在消息发送前脱敏或拒绝 | session.send 事件 | session_delivery_policy 示例 |
| 在接收消息时决定是否消费 | session.receive 事件 | session_delivery_policy 示例 |
| 在历史追加前修改或拒绝文本 | session.append 事件 | session_history_audit 示例 |
| 对 Gateway 请求做鉴权并决定路由 | gateway.request 事件 | auth_login_demo 示例 |
| 渲染面板或响应按钮 | ui.render、ui.ready、ui.click 事件 | state_counter、Token Weather |
| 查询会话用量、轮次或工作目录 | session.usage、session.turns、session.cwd 等 Ops | session_usage_info 示例 |
| 保存扩展自己的计数或面板状态 | state Ops | state_counter 示例 |

不要为了调用一个不稳定的内部函数而新增事件。也不要依赖调用顺序、进程当前目录、调用方传来的 package_id 或客户端字段来替代宿主校验。

设计稿中出现的事件名也不能直接当作可用 API。只有在宿主 bootstrap 中完成注册，并且 7 的 API 条目标记为支持，才可以写进扩展。

### 读一个事件契约时要看什么

7 的每个事件条目都按相同的问题组织：它解决什么问题，什么时候触发，输入是什么，返回什么，CORE 默认怎样处理，扩展适合观察、修改还是短路。

开发时先确认事件的输入类型和输出类型，再看 CORE 的默认行为。不要根据事件名猜字段，也不要假设返回一个对象就能阻止宿主继续执行。

例如 gateway.request 的输出包含 handled、route、params、response、error 等字段；session.send 的拒绝结果和 session.receive 的消费结果不是同一种语义。返回类型决定了宿主如何继续。

## 按架构层和功能定位开发事件

### Web Client：渲染与交互事件

Web Client 事件解决两类问题：ui.render 把 UI 树发送到某个 slot，ui.ready、ui.click、ui.change、ui.press_enter、ui.select、ui.search、ui.clear 传递用户交互。

渲染目标包含 scope、slot、package、instance 以及连接或会话上下文。application 目标由 Gateway 按连接寻址；conversation、task 和 message 目标由 AgentServer 按会话寻址。

渲染事件的 Matcher 通常要锁定 target.package_id、target.slot_id 和 target.instance_key。state_counter 使用同一个 PANEL：

~~~python
PANEL = {
    "target.package_id": "sample.counter",
    "target.slot_id": "conversation.input.below",
    "target.instance_key": "counter.panel",
}
~~~

这种 Matcher 先筛掉不属于本扩展的面板，再由 Handler 处理自己的输入。空 Matcher 会匹配所有事件，不适合直接放在 ui.click 或 ui.render 上。

ui.ready 在前端实例挂载后经 webui.dispatch 上行。CORE 会校验当前连接、包、slot、instance 和 revision，并返回 UiActionOutput。state_counter 的 on_ready 先调用 next_handler，确认宿主接受 ready，再初始化 ops.state 并调用 ops.ui.render。

ui.render Handler 通常读取 ops.state，用 replace 修改 UiRenderInput.root，再继续 next_handler。CORE 会校验组件树、目标实例和预算，返回 delivered、rejected 或 delivery_failed，以及 revision。扩展不应直接向 WebSocket 发帧。

ui.click 等动作事件通常先让 CORE 校验活动实例，再判断 action 是否属于本扩展。state_counter 在 next_handler 返回后获取自己的 action，再用锁保护状态更新；多个点击同时到达时不能直接做无保护的读改写。

Web Client Handler 常用的 Ops 是 ops.ui.render 和 ops.state。需要展示当前会话信息时，可以调用 ops.session.usage 或 ops.session.turns，但要确认事件上下文已经绑定到会话。

### Gateway：请求准入与连接生命周期

Gateway 的核心事件是 gateway.request。它接收 method、params、session_id、connection_id、user_id、channel_id、headers、transport 和 request_id 等字段，输出 route 为 local、forward、consume 或 deny。

gateway.request 在原生路由前为扩展提供请求策略入口。输入还包括 request_context；forward 可以携带允许范围内的 params 改写。CORE 对合法请求的默认结果是 route=forward，超时或异常时也按 fail-open 继续原生分发。

auth_login_demo 展示了典型的准入策略：对应用 UI、静态资源和 ping 继续交给后续处理；其他请求先校验 token。校验通过时返回 forward，失败时通过 ops.ui.render 展示登录界面，并返回 route=deny。

认证由 gateway.request 的 USER Handler 负责。Gateway 提供规范化 headers 和 request_context，但不把 Authorization 非空或请求头存在视为认证成功。

~~~python
result = await next_handler(event)
return replace(result, handled=True)
~~~

上面的写法适用于“保留宿主默认路由，同时补充 handled 等结果字段”的场景。完全拒绝时则直接返回 GatewayRequestOutput，不再调用 next_handler。

gateway.disconnect 只表达连接已断开，适合释放 Gateway 侧的连接状态。它和 AgentServer 的 session.end 不是同一件事，断开连接不等于会话已经结束。

Gateway 的 UI 只支持 application.entry 和 application.sidebar.footer 两个应用槽位。Gateway Handler 可以使用 client.local_storage.set/delete、client.page.reload 和 ops.http.fetch，但不能把 Gateway Handler 当成 AgentServer Handler 使用。两个宿主的事件总线、Ops 上下文和状态边界是分开的。

### AgentServer：会话生命周期和用量通知

session.start、session.attach、session.detach、session.end 适合处理会话的建立、连接变化和结束清理。需要初始化扩展状态时，可以在 session.start 中查询 cwd、root、model 等会话信息。

session.start 在权限、模型和执行目录绑定完成后、首条原生输入前触发，每个激活实例最多一次。输入包含 cwd、surface 和 isInteractive，CORE 使用宿主可信的 SessionContext 校验并返回实际 cwd。扩展不能通过事件输入伪造另一个 package 的目标。

session_start 示例在 on_start 中调用 ops.session.cwd()、ops.session.root() 和 ops.session.model()，把结果保存到扩展自己的 workspace 状态，然后继续 next_handler。它没有修改宿主会话属性。

session.attach 表示客户端与主会话建立关联，session.detach 表示关联解除；它们都不是 session.start。session.end 只在主会话真正停稳、资源即将释放时触发，单轮完成不会触发。attach、detach 和 end 的 Handler 应分别管理界面关联资源和会话资源。

context.usage.updated 是一轮 chat 完成后的异步通知。它适合记录用量、更新面板或触发统计，不适合阻塞主响应链；当前也没有统一覆盖所有工具路径。宿主会隔离通知分发异常，不应让已经完成的对话失败。

如果使用 context.usage.updated 更新面板，要用 session_id 和 request_id 做去重。state_counter 还用锁保护状态写入，避免同一会话的并发通知覆盖彼此的结果。

### AgentServer：消息、历史和业务策略

session.send 用于发送前的策略处理，session.receive 用于接收侧的策略处理，session.append 用于向会话历史追加内容。三者都适合在已有流程上做观察、改写、拒绝或消费。

session.send 的输入包括 target_session_id、text 和 input_mode，输出是投递回执或 deny；session.receive 的输入包括 origin、text 和可选 event，输出是 text 或 consumed；session.append 的输入包括 message、door、origin 和 uuid，输出是实际存储回执。

session_delivery_policy 对 session.send 做两种处理：文本以 [manual] 开头时返回 SessionSendDenied；其他文本先脱敏手机号，再构造同类型事件交给 next_handler。

~~~python
rewritten = replace(event.value, text=redact_phone(event.value.text))
return await next_handler(Event(event.event_type, rewritten))
~~~

这里必须保持原事件类型，不能把改写后的数据交给另一个不相关的事件。改写的是当前事件输入，不是通过 Ops 重新发起一条业务流程。

session.receive 可以返回 SessionReceiveConsumed 表示消息已被扩展消费；如果不消费，就调用 next_handler，并根据返回的 receipt 记录处理结果。send 和 receive 的 session_context 分别绑定消息来源和目标会话。

session.append 的 Handler 可以为文本块加前缀，或返回 SessionAppendRejection。扩展如果要额外追加一条审计记录，应调用 ops.session.append，但不要在 session.append Handler 里递归调用同一个追加操作。

session_history_audit 使用 matcher={"door": "note", "origin.kind": "extension"} 只处理扩展产生的 note。它用 ops.session.messages() 读取历史，用事件 Handler 处理追加策略，两者职责不同。

session.compact 当前只有事件链和 Ops 接口，主流程尚未接入；session.authorize 返回受控授权句柄，不把真实凭据交给扩展。两者都不应被当作普通会话生命周期事件使用。

### AgentServer：查询事件和能力 Ops

session.cwd、session.root、session.model、session.repo、session.messages、session.turns 和 session.usage 是七个查询类事件。除 session.messages 的 limit、cursor 和 session.usage 的 breakdown、columns 外，它们的事件输入为空映射；会话身份由 EventHandlerOps.session_context 绑定，CORE 返回宿主当前的会话数据。

其他事件需要会话信息时，直接调用相应 Ops。例如 session_usage_info 在 context.usage.updated 中调用 ops.session.turns() 和 ops.session.usage(breakdown="summary")，而不是手动构造 session.usage 事件。

不要在 session.usage 的 Handler 中再调用 ops.session.usage()，也不要在 session.messages 的 Handler 中再次调用 ops.session.messages()。这会从当前查询事件重新进入同名事件链，形成递归或重复处理。

文件、MCP、状态和客户端能力属于 Ops 边界。扩展只是读取文件、调用 MCP、保存自己的状态或发起 UI 更新时，直接调用对应宿主提供的 Ops；只有需要拦截、改写或拒绝一条已有平台流程时，才新增事件 Handler。

### AgentServer：能力登记与未接入事件

agent.register 和 tool.register 是已经有 agent-core 事件与 Ops 的登记能力。它们用于声明可用的 Agent 类型或工具，不等于启动子 Agent，也不等于执行工具。

agent.offer、agent.spawn、agent.list，以及 turn.*、tool.call、process.*、skill.prompt 和 prompt.* 在 7 中仍标记为实现中或设计中。当前不要根据这些名称直接注册 Handler，也不要用 agent.register 或 tool.register 的 CORE 行为替代它们。

## Handler 的三个决定

### Matcher 怎么写

Matcher 是事件输入的字段子集匹配。匹配器中的每个字段都必须在事件输入中精确相等；点号路径可以访问嵌套映射或对象属性；空字典匹配所有事件。

常见的稳定 Matcher 包括：

~~~python
{"target.slot_id": "conversation.input.below"}
{"target.package_id": "sample.counter"}
{"origin.kind": "peer-send-message"}
{"door": "note", "origin.kind": "extension"}
~~~

UI 事件应优先使用 target.package_id、target.slot_id、target.instance_key 和 action 等宿主字段。消息事件应优先使用 origin.kind、door 等事件契约字段。

Matcher 适合做结构稳定的粗筛，不适合做 token 校验、权限判断或依赖外部状态的业务规则。auth_login_demo 的 token 校验放在 Handler 中，是因为它不是固定事件字段匹配。

如果 Handler 对整个事件类型都要观察，可以使用空 Matcher，但要控制副作用。context.usage.updated 的全量观察适合记录和统计，不适合无条件渲染或修改所有会话。

### 什么时候调用 next_handler

| Handler 目的 | 做法 | 实际例子 |
| --- | --- | --- |
| 只观察并保留宿主行为 | 读取输入后调用 next_handler(event) | session_usage_info |
| 修改输入后继续 | 用同一事件类型构造新输入，再调用 next_handler | session.send 脱敏 |
| 在默认结果上补充信息 | 先取得 next_handler 结果，再 replace 结果 | auth_login_demo |
| 拒绝请求 | 返回拒绝类型，不调用 next_handler | session.send、session.append |
| 消费事件 | 返回 consumed 结果，不调用 next_handler | session.receive |
| 处理自己的 UI 动作 | 通常先让 CORE 校验，再更新状态 | state_counter 的 ui.click |

是否先调用还是后调用，取决于扩展要保护什么。要让 CORE 先校验活动实例，就先 next_handler；要在宿主处理前拒绝或改写，就先做策略判断。

next_handler 只能在当前 Handler 仍处于执行状态时使用，而且只能推进同一事件类型的后续链。不要把它保存到后台任务，不要在一次 Handler 中调用两次，也不要把它当作重试机制。

### 什么时候调用 Ops

| 事件场景 | 可以考虑的 Ops | 目的 |
| --- | --- | --- |
| ui.ready、ui.click、context.usage.updated 更新面板 | ops.state、ops.ui.render | 读写扩展状态并渲染 UI |
| session.start 或用量通知读取会话信息 | ops.session.cwd、root、model、turns、usage | 查询宿主事实 |
| session.send、session.receive 处理消息上下文 | 当前 Handler 的 EventHandlerOps.session_context | 使用宿主绑定的来源或目标会话，不在输入中伪造身份 |
| session.append 做审计或读取历史 | ops.session.append、ops.session.messages | 追加审计内容或读取历史 |
| Gateway 鉴权失败后展示登录界面 | Gateway 提供的 ops.ui.render、client 能力 | 渲染提示并控制客户端 |
| Gateway 访问受信任的外部服务 | ops.http.fetch | 受 allowed_hosts、超时、重定向和响应体大小限制 |
| 扩展需要保存计数、缓存或配置 | 当前宿主支持的 state、store Ops | 保存扩展自己的数据 |

Ops 的可用性由宿主和当前上下文决定。不要把 AgentServer 的 session Ops 直接用在 Gateway Handler 中，也不要假设每个事件都已经绑定 session。

## 事件结果和可靠性

### 输入、输出和 CORE 默认行为

扩展 Handler 应使用 7 条目定义的输入和输出类型。输入校验、目标实例是否活动、slot 是否存在、渲染预算和路由字段的合法性，优先交给 CORE 或宿主完成。

CORE 是事件链的默认兜底，不是一个可以随意绕过的实现细节。没有特殊策略时调用 next_handler，通常就是让事件回到宿主的默认行为。

事件输入中的宿主事实不能靠扩展调用方填写来建立信任。session.start 的 cwd、Gateway 的用户和连接上下文、UI 的活动实例，都由宿主上下文参与校验。

### 并发、取消和异常

事件总线会在分发前确定匹配的 Handler；异步 Handler 执行期间不应改变匹配结果。需要保护扩展状态时，使用锁或 compare-and-set，并用 session_id、request_id 等稳定键去重。

next_handler 的作用域是当前任务和当前事件类型。事件结束后不能继续使用它，也不能把它放进后台任务。需要异步通知时，应创建独立任务，并明确它的异常和生命周期。

事件总线不会自动重试或回滚。Handler 已经调用的 Ops 产生的副作用，不会因为后续 Handler 失败而自动撤销；需要幂等时，应在扩展自己的状态或业务键上实现。

context.usage.updated 本身是后台通知，宿主会隔离它的分发异常。Gateway intercept 对 gateway.request 设有超时，超时或异常时按原参数继续 forward；扩展不能依赖请求一定等待到 Handler 完成。

取消和宿主级 CORE 错误应继续向调用方传播。USER 或 BUILTIN Handler 的普通失败是否被记录并跳过，以具体宿主实现和事件契约为准，不要在扩展中假定所有异常都能拦截。

### 按事件族验证

7 为每个能力族提供了对应的隔离验证路径。开发事件时至少覆盖以下结果：

| 事件族 | 正常路径 | 失败或边界路径 |
| --- | --- | --- |
| Web Client 渲染与交互 | 合法 RenderNode、活动实例和有效 revision 可以得到渲染或动作回执 | 未知组件、超限树、过期 revision 和错误 slot 被拒绝，且不产生副作用 |
| Gateway 请求 | 分别验证 forward、local、consume、deny，并验证允许范围内的 params 改写 | Handler 超时或异常时 fail-open；连接断开后清理 connection 作用域资源 |
| 会话生命周期 | 验证 start、attach、detach、end 的触发时机和资源范围 | 单轮完成不触发 end；错误关联或错误身份不能清理其他会话资源 |
| 跨会话消息与历史 | 验证 send、receive、append 的放行、改写、拒绝、消费和真实回执 | 目标无权限、重复 uuid、非法字段和递归追加不能产生重复写入 |
| 查询与用量通知 | 验证 cwd、root、model、repo、messages、turns、usage 的真实值或缺失值 | 未绑定 SessionContext、读取故障、重复 request_id 和后台通知异常要分别处理 |

具体输入字段、输出类型和错误码以 7 对应条目为准；没有稳定登记的规划事件只验证“当前不可用”，不写伪成功测试。

### 开发时的最小检查

1. 确认事件已经在对应宿主的 bootstrap 中注册，并且扩展 domain 正确。
2. 从 7 确认输入、输出、CORE 默认行为和当前支持状态。
3. Matcher 只使用事件契约中稳定的字段，并验证它不会误匹配其他扩展。
4. 明确 Handler 是观察、改写、拒绝还是消费，并据此决定 next_handler 的位置。
5. 逐一检查 Ops 的宿主、会话上下文、权限和副作用。
6. 为并发通知、重复 request_id、超时和异常路径补测试。
