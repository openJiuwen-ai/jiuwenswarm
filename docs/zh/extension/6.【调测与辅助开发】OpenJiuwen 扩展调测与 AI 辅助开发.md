# 6 OpenJiuwen 扩展调测与 AI 辅助开发

本文说明扩展没有按预期工作时，应该先看哪一层、保留哪些证据，以及如何用最小测试复现问题。内容覆盖扩展包、事件、Handler、Ops、状态、WebUI 和跨进程调用；不新增事件或 Ops，只使用当前实现已经提供的入口。

排查时不要从页面现象直接跳到 Handler 内部。一次扩展调用通常经过下面的链路：

~~~text
Package
  -> manifest.json / install / reload
  -> package.query 确认当前状态
  -> 真实业务入口触发 Event
  -> 事件匹配条件筛选 Handler
  -> USER Handler
  -> BUILTIN Handler
  -> CORE Handler
  -> Handler 调用 Ops
  -> AgentServer / Gateway / WebUI 消费结果
~~~

其中，Ops 调用可能再次触发独立的事件链；WebUI 和 Gateway 还会增加目标校验、请求路由和传输结果。问题停在哪个边界，决定了下一步应该看哪类证据。

## 先判断问题停在哪一层

先把现象分成“包没有生效”“事件没有进入处理链”“处理链执行了但结果不对”“结果没有到达用户”四类，再按顺序检查。

| 现象 | 先检查 | 可以确认什么 |
| --- | --- | --- |
| 安装成功但扩展没有效果 | ActivationReport、package.query、generation | 包是只安装了、已经激活，还是仍在运行旧版本。 |
| 事件报未知或状态错误 | 事件名、事件登记、ops.build 时机 | 事件是否存在，EventBus 是否已经完成装配。 |
| Handler 没有日志 | 真实业务入口、事件输入、match_pattern | 事件是否真的触发，Handler 的匹配条件是否命中。 |
| Handler 执行但默认行为消失 | next_handler 调用和返回值 | Handler 是观察、改写，还是有意短路了下游。 |
| Ops 方法不存在 | 命名空间、方法名、ops.build 结果 | 方法是否已经由宿主构建，调用是否属于当前公开能力。 |
| 状态偶尔少写一次 | session_id、读取版本、写入 reason | 是会话隔离错误、并发冲突，还是重复事件。 |
| 页面没有显示 | ui.ready、target、status、下行 request_id | 没有贡献、实例无效、事件未命中，还是传输失败。 |
| Gateway 显示成功但业务没有变化 | request_id、ok、accepted、status、code | 只是请求收到响应，还是业务事件真正被接受和消费。 |

## 第一步：确认扩展包已经加载并处于当前版本

安装目录中存在文件，不代表包已经激活。排查时分别记录安装、激活和业务验证结果。

### 查看安装或重载 Report

管理接口返回的 ActivationReport 至少要看以下字段：

- status：当前操作是 SUCCESS 还是 FAILED；
- error.code、error.message、error.params：失败的稳定错误码及其参数；
- package_id：本次操作影响的包；
- previous_generation、current_generation：重载前后的代码代次。

常见错误可以先按下面的方向处理：

| 错误码 | 优先检查 |
| --- | --- |
| EXTENSION_MANIFEST_INVALID | `manifest.json` 的包 ID、版本、入口路径和字段结构。 |
| EXTENSION_SOURCE_INVALID | ZIP 根布局、路径逃逸、符号链接和包根目录。 |
| EXTENSION_LOAD_FAILED | 入口模块导入、create_extension()、register() 和 Handler 的可调用性。 |
| EXTENSION_HANDLER_LEVEL_FORBIDDEN | 包是否试图登记不允许的 Handler 层级。 |
| EXTENSION_PACKAGE_EXISTS | 同一 package_id 是否已经激活，当前操作是否应改为重载。 |
| EXTENSION_PACKAGE_BUSY | 是否仍有在途 Handler 或 Ops 调用。 |
| EXTENSION_DEPENDENCY_NOT_MET | 宿主版本和包依赖是否满足 `manifest.json` 的条件。 |

### 用 package.query 核对当前事实

安装或重载返回失败、超时或连接中断时，先查询一次当前状态，再决定下一步。查询结果可以确认包当前是否激活，但不能反过来补造原操作成功。

重点记录：

- package_id 和版本；
- generation；
- install_path；
- 当前激活状态；
- 已登记 Handler 数量或管理接口返回的相关信息。

如果 generation 没有变化，当前业务仍可能使用旧代码。如果包已经激活但页面没有变化，继续检查事件是否发生，不要停在包状态这一层。

使用 jiuwen-extension-package-dev 时，可以执行：

~~~text
python "<SKILL_ROOT>/scripts/manage_package.py" query "<package_id>"
python "<SKILL_ROOT>/scripts/manage_package.py" reload "<package_id>"
~~~

### 不要把状态核对当成自动重试

管理适配器在操作结果丢失或状态不明确时，可以查询一次当前状态；查询失败时保留原操作错误和 query_error。它不会因为查询到包处于激活状态，就把原来的安装或重载操作改写成成功，也不会递归查询。

因此，排查管理问题时要同时保存：

1. 原始操作的 request_id 和 Report；
2. 后续查询得到的状态；
3. ZIP 的版本和校验信息；
4. 当前 generation 和 install_path。

## 第二步：确认事件真的被触发

登记事件类型和登记 Handler，只能让 EventBus 认识这类事件，不会自动让业务发布事件。

例如：

- context.usage.updated 需要在会话用量汇总完成后由宿主触发；
- ui.click 需要先经过 WebUI 上行适配器，再进入事件链；
- session.send 需要从真实的会话发送入口进入，直接手动触发 EventBus 不能代替业务入口的授权和状态检查。

### 先看事件错误码

| 错误码 | 含义 | 优先处理方式 |
| --- | --- | --- |
| EVENTS_UNKNOWN_EVENT_INVALID | EventBus 没有登记这个事件类型。 | 检查事件登记函数是否执行，以及事件名称是否拼写一致。 |
| EVENTS_STATE_INVALID | ops.build 尚未成功，或在 Build 后重复执行、修改装配状态。 | 检查唯一的 Bus 装配和 Build 时机。 |
| EVENTS_PAYLOAD_INVALID | 事件输入、输出或 SessionContext 不符合契约。 | 使用事件定义中的输入、输出和会话上下文类型。 |
| EVENTS_REGISTRATION_INVALID | 事件、Handler 或匹配条件登记不合法。 | 检查重复登记、Handler 层级、匹配结构和异步签名。 |
| EVENTS_MATCH_INVALID | 匹配函数抛出异常或返回的不是布尔值。 | 保持匹配函数同步、无副作用，并返回 bool。 |
| EVENTS_NEXT_INVALID | EventNext 被跨调用保存、重复使用或跳到不允许的事件。 | 只在当前 Handler 调用中使用当前的 next_handler。 |
| EVENTS_OPS_INVALID | Ops 命名空间、方法或 Build 结果不合法。 | 检查完整方法名和唯一的 ops.build 登记。 |

### 用真实入口区分“没有触发”和“没有命中”

开发阶段可以在 Handler 第一行增加临时日志，同时在真实业务入口记录事件名和请求标识：

~~~python
import logging

logger = logging.getLogger(__name__)


async def on_usage(event, ops, next_handler):
    session = ops.session_context
    update = event.event_input
    logger.debug(
        "extension handler entered: event=%s session=%s request=%s",
        event.event_type,
        None if session is None else session.session_id,
        getattr(update, "request_id", None),
    )
    return await next_handler(event)
~~~

这条日志没有出现时，优先检查包状态、真实触发入口和匹配条件。日志出现后，再检查 Handler 是否调用了 Ops、是否继续了下游，以及返回结果有没有被宿主消费。

session_query_audit 示例在查询前后分别记录事件和调用来源。这样的两段日志可以区分：

- 没有进入 Handler；
- Handler 进入了，但下游拒绝；
- 下游有结果，但结果没有被上层消费。

日志中不要打印消息正文、令牌、认证头、文件内容或完整模型输出。

## 第三步：检查事件匹配条件和处理链

### 匹配条件不命中时，Handler 不会拿到 Ops

扩展 Handler 注册时通过 match_pattern 限制输入范围。空映射 {} 表示不增加输入筛选；点路径条件例如 {"origin.kind": "extension"} 或 {"target.slot_id": "conversation.input.below"}，要求当前事件输入中存在相同的字段和值。

排查顺序如下：

1. 事件名称是否与登记时完全一致；
2. 事件输入中的字段是否存在；
3. 字段类型是否一致；
4. 点路径是否指向对象属性中的正确层级；
5. 包重载后是否已经使用新的 Handler 实例；
6. 事件输入在进入处理链后被改写时，是否误以为 EventBus 会重新匹配。

EventBus 会在事件链开始时确定本次命中的 Handler 集合。后续 Handler 改写输入，不会重新执行匹配。未命中的 Handler 会穿过处理链，也不会创建该 Handler 的 Ops。

### next_handler 决定默认行为是否继续

扩展 Handler 主要有三种写法：

- 观察：记录输入或结果，调用一次 next_handler(event)；
- 改写：构造同一事件类型的新输入，再调用一次 next_handler；
- 短路：返回事件定义允许的结果，不调用 next_handler。

session_delivery_policy 示例展示了三种结果的实际写法：

~~~python
from dataclasses import replace

from openjiuwen.core.events import Event
from jiuwenswarm.extensions_v2.event_types.session_send import SessionSendDenied


async def on_send(event, ops, next_handler):
    value = event.event_input
    if value.text.startswith("[manual]"):
        return SessionSendDenied(deny="This request requires a manual send.")

    text = value.text.replace("13800138000", "[phone]")
    rewritten = Event(event.event_type, replace(value, text=text))
    return await next_handler(rewritten)
~~~

next_handler 不能保存给后台任务，也不能在一个 Handler 中无条件调用两次。前者会使用已经失效的调用上下文，后者可能重复执行 CORE 或其它下游副作用。

### 区分 Handler 故障和 CORE 或契约故障

当前 EventBus 对普通 USER、BUILTIN Handler 的一般异常会记录错误并跳过当前 Handler，让处理链继续尝试下游。错误日志包含 event_type、handler_id、handler_level、package_id 和异常信息。

这意味着主流程没有报错，不代表扩展执行成功。需要分别判断：

| 故障位置 | 常见表现 | 下一步 |
| --- | --- | --- |
| USER/BUILTIN Handler | 扩展日志中断，主流程可能继续。 | 查看 Handler 错误上下文和输入；确认是否需要让异常继续传播。 |
| 匹配函数 | 事件在进入处理链时失败。 | 检查匹配函数的输入类型、返回值和副作用。 |
| CORE Handler | 事件链无法产生合法平台结果。 | 检查事件输入/输出契约和宿主业务实现。 |
| ops.build 或登记阶段 | 事件尚未能正常运行。 | 检查装配顺序、重复登记和 Handler 层级。 |

开发阶段可以在自己的 Handler 中记录一次带上下文的异常，但不要在 Handler 内部用无条件重试掩盖错误。

## 第四步：定位 Ops 和状态问题

### Ops 调用会启动独立的事件链

ops.session.turns()、ops.session.usage()、ops.session.append() 和 ops.ui.render() 不是当前事件的隐式下游，它们会分别触发新的事件链。

例如，context.usage.updated Handler 调用 ops.session.usage() 时，需要依次确认：

1. 当前 context.usage.updated 是否命中；
2. session.usage 是否已经登记并命中其 Handler；
3. session.usage 的 CORE 是否返回合法结果；
4. 当前 Handler 是否把结果用于状态更新或 UI 渲染。

session_usage_info 示例的核心路径如下：

~~~python
async def on_usage(event, ops, next_handler):
    turns = await ops.session.turns()
    usage = await ops.session.usage(breakdown="summary")
    logger.info(
        "session usage: session=%s turns=%s usage=%s",
        ops.session_context.session_id, turns, usage,
    )
    return await next_handler(event)
~~~

建议对主动调用的 Ops 记录调用前和调用后的同名操作。session_id 应来自宿主绑定的 ops.session_context，不要从事件正文或浏览器参数猜当前会话。

### 找不到 Ops 方法时，先查 Build 和命名空间

ops.命名空间.方法() 能否调用，取决于宿主在唯一的 ops.build 链中是否登记了对应命名空间和方法。

常见问题包括：

- 命名空间没有登记，触发 EVENTS_OPS_INVALID；
- 方法名拼写错误；
- 调用了 API 索引中尚未实现的方法；
- 在 Build 完成后尝试添加或替换方法；
- 把一次 Ops 调用误认为会自动推进当前事件链。

扩展包默认只消费宿主已经构建的公开 Ops。现有能力不足时，应记录为平台缺口，不要在包内创建新的 Bus、Registry 或 ops.build Handler。

### 用版本和原因定位状态写入失败

ops.state 和 ops.store 的读写结果本身就是诊断证据。以 state_counter 示例为例：

| 结果字段 | 排查意义 |
| --- | --- |
| snapshot.exists | 当前会话是否已经有状态。 |
| snapshot.version | 本次写入使用的并发版本。 |
| StateSetResult.is_set | 写入是否成功。 |
| StateSetResult.reason | 是否为 version_conflict、初始化失败或其它原因。 |

遇到“偶尔少加一次”时，先记录 session_id、状态键、读取版本和写入 reason，再判断是不是并发或重复事件。不要把进程级全局变量当成跨会话状态，也不要把 version_conflict 直接改成无条件覆盖。

## 第五步：定位 WebUI、Gateway 和 AgentServer 边界

### WebUI：先看目标和状态，再看组件树

WebUI 事件的目标由 session_id、slot_id、package_id 和 instance_key 共同确定。调试时先记录目标 key 和事件结果，再检查渲染树内容。

常见结果及下一步如下：

| 结果 | 先排查 |
| --- | --- |
| no_contribution | `manifest.json` 是否声明了该槽位，package_id 是否在当前贡献目录中。 |
| no_handler | Handler 是否登记，事件和匹配条件是否命中。 |
| invalid_instance / inactive | instance_key、slot_id 和 ui.ready 生命周期。 |
| delivered / rendered | 事件链已经产生渲染结果；继续检查浏览器连接和前端消费。 |
| unavailable / render_failed | ops.ui.render()、目标会话、传输层和连接状态。 |

安装或重载不会自动重放已经发生的 ui.ready。包已经激活但页面没有显示时，先让页面重新挂载、刷新连接或重新进入会话，再判断 Handler 是否失效。

RenderTransport 会为下行帧生成 webui-* request_id。发送失败会记录失败日志并返回失败；这只能说明传输失败，不能说明浏览器已经展示组件。应用级槽位还要检查 connection_id，不能只用 session_id 判断目标。

### Gateway 与 AgentServer：沿请求链路定位

Python Handler 在 AgentServer 进程中执行。Gateway 侧主要观察请求和响应，至少保留：

- request_id：关联一次请求和响应；
- session_id、channel_id：确认路由和会话边界；
- ok：网络请求是否得到响应；
- accepted、status、code：业务事件是否接受、处理或拒绝。

ok=True 不等于扩展业务成功。例如 WebUI 适配器可以在没有贡献时返回 ok=True、accepted=False、status="no_contribution"。

跨进程问题按下面的链路检查：

~~~text
Gateway request_id
  -> AgentServer adapter
  -> ExtensionEventBus.trigger
  -> Handler / Ops logs
  -> AgentResponse(request_id, ok, payload)
~~~

如果 AgentServer 没有事件入口日志，检查网络方法、适配器注册和请求参数；如果事件入口有日志而 Handler 没有日志，回到包状态和匹配条件；如果 Handler 有日志而用户没有看到结果，检查结果消费方和最终状态。

## 第六步：用最小测试复现问题

测试的目标不是启动完整服务，而是固定一个真实事件、一个真实处理链和一个可控的宿主结果。最小测试可以使用 pytest、真实 ExtensionEventBus 和测试宿主替代完整服务。

建议每个扩展至少覆盖：

- 命中和未命中；
- 调用一次 next_handler 后继续；
- 改写输入后的结果；
- 短路结果；
- Handler 异常；
- 取消和超时；
- 重复调用和会话隔离；
- WebUI 目标、状态和生命周期；
- 安装、重载、卸载和状态未知。

按架构层次选择现有测试入口：

| 层次 | 当前测试 | 重点断言 |
| --- | --- | --- |
| 事件和 Handler | tests/unit_tests/extensions_v2/test_session_delivery_events.py | 继续、短路、重复 next、取消、存储失败、卸载占用和真实业务入口。 |
| 查询和用量 Ops | tests/unit_tests/extensions_v2/test_session_ops.py、test_session_usage_ops.py | 方法是否已 Build、参数和会话上下文、底层结果及错误传播。 |
| 状态 | tests/unit_tests/extensions_v2/test_state_persistence.py | session_id 隔离、版本条件、重复事件和 version_conflict。 |
| WebUI | tests/unit_tests/extensions_v2/webui/test_webui_events.py、test_webui_adapter.py | 目标校验、ui.ready、ui.* 状态、贡献声明和错误码。 |
| 包管理 | tests/unit_tests/extensions_v2/management/test_management_serialization.py、test_management_recovery.py | Report 编码、generation、查询补证和结果未知。 |

从单个文件开始执行：

~~~text
uv run pytest -q tests/unit_tests/extensions_v2/test_session_delivery_events.py
uv run pytest -q tests/unit_tests/extensions_v2/webui/test_webui_events.py
~~~

单元测试只能证明事件链和扩展行为，不能证明 Gateway 已接通或真实页面已经显示。跨进程或浏览器问题仍需沿 AgentServer、Gateway 和 WebUI 边界做集成验证。

## 第七步：用稳定字段串起日志

当前没有统一的扩展 trace 对象。开发者可以先在自己的日志中保持字段稳定：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| package_id、package_version | ops.package_metadata | 区分扩展包和代码版本。 |
| session_id | ops.session_context | 区分会话和状态作用域。 |
| request_id | 事件输入、AgentRequest 或 WebUI 帧 | 关联请求、用量更新和跨进程回执。 |
| event_type | event.event_type | 关联当前事件链。 |
| slot_id、instance_key | UiActionInput.target | 定位页面贡献和实例生命周期。 |
| status、code、reason | 事件输出、Report、StateSetResult | 区分业务拒绝、传输失败和状态冲突。 |

推荐使用 logging.getLogger(__name__)，在包级别配置日志级别。不要在每个 Handler 中重复实现日志系统，也不要把原始消息、文件内容、认证信息和完整模型输出写入默认日志。

## 建议优先补齐的低成本能力

下面几项不需要改变扩展模型，适合优先补到开发体验中。它们是平台改进建议，不是当前已经存在的公共接口。

| 能力 | 最小实现 | 可以解决的问题 |
| --- | --- | --- |
| 事件调用摘要 | 在 EventBus 现有调用边界记录 event_type、命中 Handler 数、耗时、结果状态和错误码；默认关闭正文。 | 区分未触发、未命中、Handler 报错和 CORE/传输失败。 |
| 开发日志开关 | 为扩展相关 logger 提供统一 DEBUG 开关或开发配置。 | 不修改每个包的日志级别，也能观察事件链。 |
| 轻量测试夹具 | 提供以真实 ExtensionEventBus 为核心的 pytest fixture，配套测试宿主、会话、WebUI Transport 和常用 Ops 替代实现。 | 在不启动完整服务的情况下复现事件和结果。 |
| 包状态诊断输出 | 在 package.query 基础上稳定输出 package_id、版本、generation、安装目录和激活 Handler 数。 | 区分“已安装”和“已激活”，确认重载是否生效。 |
| WebUI 诊断摘要 | 统一输出 target.key、event、accepted、status、code 和下行 request_id。 | 定位贡献声明、实例生命周期和传输失败。 |

这些能力只服务于开发期诊断，不要求把内部注册表或完整日志暴露给业务扩展。实现后应同步补充对应的测试和 API 索引。

## 使用 jiuwen-extension-package-dev 进行 AI 辅助扩展开发

jiuwen-extension-package-dev 将“希望宿主出现什么效果”转换成一套可验证的独立 Package 开发流程。它负责查找当前宿主已有的事件、Ops、包加载和 WebUI 入口，并把源码、测试、ZIP、激活状态和业务验证分开记录。

### 这个技能负责什么

技能的工作路径可以概括为六步：

1. **确认目标环境：** 找到实际运行宿主使用的 Python、openjiuwen.core 和 jiuwenswarm 版本及导入位置。
2. **匹配已有能力：** 从 Core 事件和 Ops、Core 包加载、Swarm 扩展和 WebUI 固定入口开始，确认事件已登记、真实业务已触发、匹配条件可用、Ops 方法已构建。
3. **开发独立包：** 在包目录中维护 `manifest.json`、README、入口模块和扩展实现，不把业务代码放入平台内置事件目录。
4. **隔离测试和打包：** 验证真实加载、Handler 发布、事件结果、失败、取消、隔离和 UI 行为，再用正式脚本生成最终 ZIP。
5. **安装并核对状态：** 通过已有 extensions.v2.* 管理协议安装、查询、重载或卸载，核对 Report、版本、generation 和实际安装目录。
6. **验证真实效果：** 回到原有业务入口确认用户能看到或使用结果，并分别记录“ZIP 已生成”“包已激活”“业务效果已验证”。

### 技能指定的扩展开发 spec

| 范围 | 固定约定 |
| --- | --- |
| 环境阅读 | Core 事件与 Ops 从 CORE_ROOT/openjiuwen/core/events/ 查；包加载与生命周期从 CORE_ROOT/openjiuwen/core/extension/ 查；Swarm 事件、Ops 和 WebUI 从 SWARM_ROOT/jiuwenswarm/extensions_v2/ 查。 |
| 包布局 | ZIP 根目录直接包含 `manifest.json`；package.id 为 1–128 个字符；入口模块必须是包内真实 Python 文件，不能是 __init__.py，路径段不能包含点号；通常包含 README、包模块、create_extension() 和 register(registrar)。 |
| `manifest.json` | 校验 package.id、版本、`extensions[].runtime`、扩展入口、宿主版本条件、requires.host、requires.packages 和 UI contribution；入口路径必须落在包根内。 |
| 事件和 Handler | 只复用宿主已有、已登记且真实触发的事件；默认登记 USER Handler，使用公开 ExtensionRegistrar.register_event_handler() 和 match_pattern；包身份由宿主注入，不在包内伪造。 |
| Ops | 只调用当前宿主已构建的公开 Ops；不因为包的需求就新增 Ops、修改 ops.build、登记新的 Ops namespace 或创建第二套 Bus。 |
| 状态和 UI | 状态按会话或业务实例隔离；使用现有 ops.state/ops.store；UI 复用现有槽位、组件和 Props，并保留 target、会话和活动实例校验。 |
| 测试 | 覆盖命中、未命中、继续、短路、失败、取消、重复调用、会话隔离、UI 状态和生命周期；最终 ZIP 要再做一次加载验证。 |
| 安装验证 | 安装报告和 package.query 分开记录；结果未知时只查询一次，不把当前状态倒写成原操作成功。 |

这套 spec 的重点是复用已有平台能力、独立交付、可回滚和证据可核对。

### 技能划定的边界

技能可以做的事情：

- 根据目标效果选择现有事件、匹配条件、Handler 和 Ops；
- 创建或修改独立 Package，维护 README、测试和最终 ZIP；
- 使用隔离宿主和正式管理接口验证加载、激活、重载、卸载和业务结果；
- 在安装失败、状态未知或平台能力不足时给出可核对的错误和缺口。

技能不会做的事情：

- 修改 Core、AgentServer、Gateway 或 WebClient 源码来补齐不存在的扩展入口；
- 新增内置事件、真实业务触发点、CORE Handler、通用 BUILTIN Handler 或新的 ops.build 能力；
- 在包内创建自己的 EventBus、Registry，绕过 `manifest.json`、Registrar、权限和目标校验；
- 把源码修改、ZIP 生成、包激活和真实业务效果混写成一个“已完成”；
- 在没有明确认证和目标实例时猜测服务地址、复制浏览器登录状态或直接写安装目录绕过管理接口。

当技能发现没有合适的事件、真实触发入口、Ops、UI 槽位或客户端认证方式时，正确结果是报告平台缺口，而不是生成一个看似完整但无法生效的 Package。

### 用技能的证据链定位问题

技能产物和平台证据可以按失败位置对应起来：

| 失败位置 | 先查什么 |
| --- | --- |
| ZIP 无法加载 | `manifest.json`、ZIP 根布局、入口导入、EXTENSION_* 错误和隔离加载结果。 |
| 包已加载但没有行为 | package.query、generation、真实触发入口、match_pattern 和 Handler 登记。 |
| Handler 执行但结果不对 | next_handler 是否调用、短路结果是否符合事件输出契约、Ops 结果是否被消费。 |
| UI 包已激活但页面空白 | ui.ready 是否重新发生、贡献声明、target key、status/code 和下行传输结果。 |
| 安装命令超时 | 原始 operation_status、随后一次查询得到的当前状态、ZIP 与运行侧文件是否一致。 |

技能提供的是开发闭环和证据整理能力。运行中的 Handler 仍应按事件、Ops、WebUI 和跨进程边界分别定位。

### 常用命令

正式 ZIP 和运行状态应使用同一份产物核对：

~~~text
python "<SKILL_ROOT>/scripts/build_package.py" "<Package 源码目录>" "<输出 ZIP 路径>"
python "<SKILL_ROOT>/scripts/manage_package.py" install "<最终 ZIP 路径>"
python "<SKILL_ROOT>/scripts/manage_package.py" query "<package_id>"
python "<SKILL_ROOT>/scripts/manage_package.py" reload "<package_id>"
python "<SKILL_ROOT>/scripts/manage_package.py" uninstall "<package_id>"
~~~

打包脚本负责校验和生成 ZIP，不执行包代码；管理脚本负责安装、查询和生命周期操作，不代替真实业务或浏览器验证。两者都不能代替事件链日志和 Handler 结果检查。
