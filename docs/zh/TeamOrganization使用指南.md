# Team Organization 使用指南

Team Organization 在 Agent Team 之上组织多个独立 Team。每个 Team 继续管理自己的成员；各 Team Leader 通过共享任务池、可靠消息和组织工作空间共同完成一个根任务。

> Team Organization 目前通过 Team Leader 自主调用 `org_*` 工具运行，没有单独的 `/organization` 命令。请先进入 Team 模式，再用明确的提示词要求 Leader 创建组织、专家 Team 和任务树。

---

## 一、适用场景

适合使用 Team Organization 的任务通常具备以下特点：

- 需要研发、测试、调研、审核等多个专业团队协作。
- 各团队需要独立上下文和成员，但共享任务状态与交付物。
- 子任务结果需要上游 Team 明确验收。
- 希望任务、消息和汇总过程在中断后恢复。

单个 Team 内可以完成的角色分工，仍建议使用普通 Agent Team。Team Organization 当前同一时间只处理一个非终态根任务。

## 二、运行前配置

本文使用源码仓库中的 Web 界面复现两个协作场景：先从专家团广场进入 Owner Team 完成简短报告，再介绍从前端创建通用 Owner Team 的投资初筛用例。不需要获取开发者本机的专家团文件。准备 Git、uv、Python（版本范围以仓库 `pyproject.toml` 为准）和 Node.js/npm，参考[开发者指南](developer_guide.md)。克隆包含 Team Organization 功能的代码后，在仓库根目录执行：

```bash
uv sync --locked
uv run --no-sync jiuwenswarm-init
```

依赖来源以当前 `pyproject.toml` 和 `uv.lock` 为准，普通用户按仓库提供的锁文件同步即可，无需安装本地 agent-core。维护者联调时可以在本地把 `openjiuwen` source 改为 agent-core 源码路径并设置 `editable = true`，同步更新锁文件；这类本地依赖配置不应提交到远端。首次初始化后按[快速开始](Quickstart.md)配置模型与凭据；已有工作区不必重复初始化。需要指定官方 Python 包源时使用 `uv sync --locked --default-index https://pypi.org/simple`，不改变锁文件中的源地址。

配置默认位于 `~/.jiuwenswarm/config/config.yaml`。以下片段应合并到初始化生成的配置中，不要覆盖整份文件、模型或其他已有设置。Team Organization 复用 `modes.team.jiuwen_team`，不需要新增顶层 `organization` 配置：

```yaml
modes:
  team:
    jiuwen_team:
      team_name: jiuwen_team
      lifecycle: persistent
      teammate_mode: build_mode
      spawn_mode: inprocess

      leader:
        member_name: team-leader
        display_name: 团队领导
        persona: "项目负责人，擅长跨团队拆解、验收和风险协调"

      agents:
        leader: $agent_leader

      workspace:
        enabled: true

      transport:
        type: inprocess

      storage:
        type: sqlite
```

其中 `$agent_leader`、普通成员及 Summary Team 使用的模型都必须能解析到有效配置；未单独指定模型的 Agent 继承 `models.default`。保留初始化生成的模型路由，填好服务地址、模型名称和凭据，启动后在模型配置界面确认连接测试通过。模型需要支持工具调用。用例一仅分析给定假设，不需要联网获取资料；用例二需要能访问指定的公开网页和代码文件，访问失败时不能用模型猜测的内容代替证据。

Summary Team 会读取同一份 Team 默认模型配置；如果默认模型缺失，Summary Team 无法启动。当前 Team Organization 为同进程版本，参与组织的 Team Leader 由同一 AgentServer 进程管理，并共享同一 `TeamDatabase` 实例与本机工作空间。联调建议使用 SQLite 和 `inprocess`；仅改用 PostgreSQL 不会开启跨进程组织协作。

Team Organization 使用现有实验特性配置，默认关闭，同时控制前端组织视图和后端组织能力。在用户配置文件 `~/.jiuwenswarm/config/config.yaml` 中增加：

```yaml
experimental:
  team_organization_ui_enabled: true
```

也可以在 Web 的「更多 → 配置 → 实验特性」中开启 Team Organization。此开关决定新构建 Team 的 `enable_organization`：关闭或缺省时不挂载 `org_*` 工具，也不恢复已有组织绑定，普通 Team 成员协作仍可使用；Web 和 TUI 的组织运行都依赖此开关。已有配置中其他 `experimental` 项应保留。

后端在 Team 构建时读取开关，不会因界面切换立即卸载正在运行的组织。更改后请完整重启后端（包括常驻 Runtime Worker），再创建新的 Team 会话；如果已有组织任务在运行，先停止该任务。仅刷新网页或重启连接层不会重建已有运行实例。关闭开关不会删除组织数据库或交付物。

## 三、用例一：从专家团广场进入 Owner Team

本用例使用商业策划、技术洞察和代码架构设计三个专家团，为一个 10 人团队的内部知识问答助手生成简短可行性报告。三个领域成果分别由不同专家团从共享任务池认领，验收后使用 `SUMMARY_TEAM` 模式汇总。适合先检查组织创建、专家团加入、认领、验收和最终报告交付是否能跑通。

### 3.1 启动 JiuwenSwarm

完成第二节的依赖同步和工作区初始化后，先安装前端依赖。在仓库根目录执行（Windows PowerShell 同样适用）：

```bash
cd jiuwenswarm/channels/web/frontend
npm ci
cd ../../../..
uv run --no-sync jiuwenswarm-start dev
```

该命令同时启动后端和 Vite 前端，内部已执行 npm run dev，不需要在第二个终端再启动一次前端。首次运行或前端依赖变化后执行 npm ci；后续依赖未变时可以在仓库根目录直接启动。访问终端打印的 Web UI 地址，端口以实际输出为准。

打开 Web 后，确认模型连接可用、Team Organization 实验开关已开启。不要把网页能打开等同于后端运行时就绪；目录和会话请求失败时先检查启动日志中的运行时加载错误。

### 3.2 在专家团广场准备和使用主团队

在「专家管理 → 专家团广场」安装以下三个专家团，并确认它们显示为已安装或可使用：

| 专家团 | 用途 | 广场模板领域标签示例 |
|--------|------|----------------------|
| 商业策划专家团 | 当前主团队，创建组织、认领整体事项并验收成果；完成用户价值和功能范围意见 | business-planning |
| 技术洞察专家团 | 自主认领技术路线与风险子任务 | technology-insight |
| 代码架构设计专家团 | 自主认领模块划分子任务 | software-architecture |

能力标识以已安装模板实际返回的标签或 capabilities 为准，不根据中文名称猜测；规则见[专家团与汇总配置：广场安装、标签与组织能力](TeamOrganization专家团与汇总配置.md#13-广场安装标签与组织能力)。Summary Team 由框架按需创建，无需手动安装。

在「商业策划专家团」卡片上点击「使用」。界面会进入新的 Team 会话并选中该模板，输入区显示其名称和头像。将下一节提示词作为首次消息发送，系统装配当前主 Team；其 Leader 创建 Organization 后成为 Owner。不要在已经构建的 Team 会话里更换专家团模板。

另外两个专家团只需安装，不必分别点击「使用」或预先开启会话。Owner 根据提示词从已安装目录选择模板，在当前会话中创建独立 Team 并邀请入组。安装的是模板，加入 Organization 的是运行实例；其他会话中已经运行的 Team 不属于本用例的复用对象。

看不到已安装模板时，确认服务使用的工作区与安装工作区一致，刷新广场列表并检查安装状态。若是自定义工作区，初始化和启动都应使用相同的 JIUWENSWARM_DATA_DIR。测试请使用新会话，不要为了重新准备模板删除已有数据库。

### 3.3 发送测试提示词

将下面的提示词作为一条完整消息发送。简短执行要求也应写入子任务描述，才能传递给被唤醒的专家团。篇幅要求用于控制工作范围，不保证模型在固定时间内结束。

```text
请使用 Team Organization，完成一份“10 人团队内部知识问答助手”的简短可行性报告，并采用 SUMMARY_TEAM 汇总模式。

场景：成员上传内部文本说明，通过提问查找答案；回答附带文档来源，文档没有答案时明确告知。第一版只考虑这些功能。

请由当前商业策划专家团创建组织，邀请已安装的“技术洞察专家团”和“代码架构设计专家团”加入。请创建并认领整体事项，将汇总模式设置为 SUMMARY_TEAM。

将以下三个独立子任务发布到共享任务池，按对应专家团的实际能力标签设置认领条件。不要委派，也不要直接指定执行团队，由不同专家团 Leader 自主认领：

1. 商业策划：给出一项用户价值及第一版功能范围。
2. 技术洞察：给出一条简单技术路线及两项主要风险。
3. 代码架构：列出三个核心模块及各自职责。

请把以下要求写入每个子任务的描述和验收条件：只根据上述假设做简短分析，成果不超过 100 字；不联网、不生成文件、不编写代码、不继续拆分任务，不扩展为全面调研。各团采用必要的最少内部协作，完成后及时提交成果。你也需要自行认领并完成商业策划子任务。

三个子任务全部完成并验收后，请启动独立 Summary Team 的汇总任务。汇总团队只整合已验收成果，输出一份 300 字左右的中文报告，不追加研究或新任务；完成后提交报告并结束汇总任务。

最后请由 Owner 在当前会话直接展示完整报告正文，并完成整体事项。不要只回复状态、文件路径或“正在等待”。其他专家团执行期间不要反复轮询或催促，等待完成通知后继续。
```

### 3.4 预期结果

测试通过时，应观察到以下里程碑：

1. 商业策划 Team 创建组织，技术洞察和代码架构两个 Team 成功加入。
2. 商业策划 Team 认领整体事项；三个子任务进入共享任务池，由三个不同 Team 自主认领，未使用委派。
3. 三项短意见均提交并通过整体事项负责人的验收。
4. 首次需要汇总时自动创建一个独立 Summary Team；本轮共三个领域 Team 和一个 Summary Team。
5. Summary Task 执行完成并正式提交汇总报告，根任务最终为 `COMPLETED`。
6. Owner 会话直接展示约 300 字报告正文；切换到其他 Team 时，下侧显示对应专家团名称和头像，对话内容彼此隔离。

组织面板保留任务池和待评审列表，可检查实际任务状态；不要以运行状态圆点或主团队口头回复“已完成”代替验收和汇总结果。先等本轮完成或确认执行已停止，再在 Owner 会话补充以下检查提示词：

```text
请检查刚才的协作过程，不要创建新工作：说明三个子任务分别由哪个专家团认领，是否均已完成并通过验收，独立汇总团队是否已提交报告，整体事项是否已经完成。
```

## 四、用例二：先从前端创建 Owner Team

此用例保留公开资料投资初筛场景。Owner 从前端新建普通 Team，负责投资与财务和整体事项；法律合规、技术尽调与 Coding、市场与商业专家 Team 则从已安装模板创建并加入组织。与用例一相比，本用例需要准备领域模板和访问公开资料，建议在简短报告用例跑通后再尝试。

### 4.1 准备专家团与主团队

完成第二节配置，并按 3.1 节启动 Web。在专家团广场安装职责合适且具有对应领域能力的以下三个模板；如果广场没有所需模板，按[专家团与汇总配置：通过界面手动配置专家团](TeamOrganization专家团与汇总配置.md#12-通过界面手动配置专家团)中的负责人、成员、提示词和标签材料手动创建，创建成功后自动安装。无需运行模板生成脚本，也无需手写安装登记。

| 参与团队 | 准备方式 | 领域标签示例 |
|----------|----------|--------------|
| 投资与财务 Owner Team | 在前端新建普通 Team，由提示词明确财务职责并自行认领该领域子任务 | — |
| 法律合规专家团 | 安装或手动创建模板，由 Owner 创建运行实例并邀请 | legal |
| 技术尽调与 Coding 专家团 | 安装或手动创建模板，由 Owner 创建运行实例并邀请 | coding |
| 市场与商业专家团 | 安装或手动创建模板，由 Owner 创建运行实例并邀请 | market |

标签以实际安装模板提供的能力为准，不能仅凭名称保证匹配。其余三个专家团只需安装，不必单独启动；Summary Team 仍由框架按需创建。

回到任务页面，新建会话，在输入区选择「集群模式」（Team），不选择专家团模板。首次发送下一节提示词，系统按默认 Team 配置构建主团队，由其 Leader 创建组织并担任 Owner。不要在用例一已绑定商业策划模板的会话中更换模板来运行此用例。

### 4.2 发送测试提示词

将下面的提示词作为一条完整消息发送。

```text
请由当前 Team 负责投资与财务分析，联合已安装的法律合规、技术尽调与 Coding、市场与商业三个专家团，对 Zed Industries 做一次快速公开资料投资初筛。最终请直接向我交付建议正文。

这是一项协作流程联调，不是完整尽调。只回答一个问题：是否值得进入下一轮正式尽调？仅使用以下三个公开来源；不要扩展检索、调查竞品融资或估值、克隆代码仓、构建代码或运行测试：

- 公司与产品：https://zed.dev/about
- 开源和许可证说明：https://zed.dev/software-overview
- 代码仓：https://github.com/zed-industries/zed

请由当前 Team 建立协作组织并担任 Owner，邀请法律合规、技术尽调与 Coding、市场与商业三个专家团加入。请创建并认领整体事项，再拆分以下四项领域工作。本用例请使用 SUMMARY_TEAM 模式，由独立汇总团队整合四项已验收成果。当前 Team 的投资与财务意见也必须作为一项可验收的正式成果，由你自行认领并完成。

请把以下四项工作放入共享任务池，等待具备相应能力的专家团认领，不要直接指定给某个内部成员。每项只交付一份短意见：正文不超过 120 个汉字（URL 和代码路径不计入），包含一项已确认发现、一项风险或待核验事项，并标注最多一个上述来源链接。不再拆分内部研究工作，也不要撰写长报告。

1. 投资与财务：依据公司介绍，指出一项投资前提，以及下一轮必须索取的一项财务材料。
2. 法律合规：只看官方许可证说明，指出一项许可证事实和一项待核验风险。
3. 技术与 Coding：实际查看公开代码仓的 README、许可证文件，以及 Cargo.toml 或一处核心代码/配置；指出一项有文件路径依据的工程事实和一项待核验风险。
4. 市场与商业：只依据产品介绍，指出一项产品机会和一项商业不确定性。

每项完成后，由认领整体事项的负责人先验收；四项都通过后再汇总。其他专家团执行期间不要反复轮询或催促，等待完成通知后继续；不要提前结束整体事项。

最终直接展示一份 400～600 个汉字的中文投资建议，不要只报告状态、文件路径或“正在等待”。建议必须包括：

- 明确结论：建议推进、附条件推进或不建议推进；
- 四个领域各自最关键的一条依据；
- 进入下一轮正式尽调前必须核验的事项，以及结论的不确定性。

不允许虚构营收、估值、客户数量、融资条款或安全结论。无法由上述公开资料确认的内容，一律写为“待核验”。
```

### 4.3 预期结果

测试通过时，应观察到以下里程碑：

1. 前端创建的普通 Team 担任投资与财务 Owner，创建协作组织，另外三个专家 Team 成功加入。
2. 整体事项由投资与财务 Team 认领；四项领域工作进入共享任务池并由能力匹配的 Team 认领。
3. 投资与财务意见也形成独立子任务成果，而不是只存在于当前 Team 的内部记录。
4. 四项短意见均完成并由整体事项负责人验收通过。
5. Organization 首次需要汇总时懒加载一个 Summary Team，而不是为每个来源创建 Summary Team。
6. Summary Task 从 `WAITING_SOURCES` 进入执行并完成，根任务最终为 `COMPLETED`。
7. 最终回复直接展示 400～600 字建议正文，并把无法确认的信息标为“待核验”；开启实验界面后，可在组织面板刷新查看任务和验收状态。

本用例验证的是协作流程，模型生成的正文、执行时间和具体工具调用顺序不保证每次相同。不要只以主团队回复“已完成”作为通过依据，应在组织面板确认四项成果已验收、汇总完成且最终正文已展示。先等本轮完成或确认执行已停止，再在同一会话补充以下检查提示词：

```text
请检查刚才的协作过程，不要创建新工作：告诉我有哪些专家团参与、四项工作是否都已完成并通过验收、最终汇总是否完成，以及最终建议保存在哪里。如有尚未处理的团队消息，也请说明。
```

## 五、常见问题

联调时还应检查实验开关和团队隔离：

1. 开关关闭或配置项缺省并重建后端运行时时，普通 Agent、Team 模式、历史恢复和停止操作仍按原流程运行，不显示组织入口；新 Team 不应拥有 `org_*` 工具，也不能通过提示词创建组织。
2. 开启开关后，在 Team 模式发送上述提示词，确认团队选择器出现参与的专家 Team，组织面板显示任务和验收状态。
3. 切换到某个专家 Team，询问「请解释你刚才最关键的一条发现，不要新增研究或任务」，确认输入、回复和思考属于该 Team；切回 Owner Team 后不混入专家对话。
4. 在专家对话运行中停止，确认停止的是所选专家请求，而不是主团队正在执行的任务。暂停、恢复等控制意图不支持定向专家请求，不应退回控制主团队。
   解散组织后，由组织临时创建的专家 Team 和 Summary Team 停止，团队选择器自动回到主团队；主团队仍可继续聊天或重新组建组织。已安装的专家团模板、历史消息与交付物保留，原本独立存在的受邀团队只解除组织绑定。
5. 关闭开关后，组织视图和事件订阅撤销，回到主会话。完整重启后端，再新建 Team 会话要求创建组织，确认后端没有组织工具；将配置改回开启并重建运行时后，检查组织协作能否恢复。

这些检查不能代替真实模型联调。自动化回归通过后，仍需使用可用模型、合法 AgentGroup 包和独立测试会话完成上述流程。

当前实验界面隔离专家消息历史。后台专家 Team 和 Summary Team 已完成的回复片段会保存，即使浏览器断连，刷新后选择对应 Team 仍可恢复。正在生成的文本在下一个输出边界或轮次结束时保存。专家工具执行历史的完整恢复不在本次界面范围内。

| 现象 | 检查项 |
|------|--------|
| 同一专家团在新会话创建组织报 `organization already belongs to team` | 组织 ID 在共享 `team.db` 中全局唯一，旧会话遗留组织未解散会占用同名 ID。升级 agent-core 后框架会自动为冲突 ID 追加 `-N` 后缀，以 `org_create_organization` 返回的实际 `organization_id` 为准；旧数据也可先回原会话调用 `org_dissolve_organization` 清理 |
| `org_list_expert_groups` 返回空 | AgentGroup manifest、安装状态以及同名冲突；按能力过滤时还需检查 capabilities |
| 前端看不到已安装的专家团 | 手动创建是否成功、是否已安装、当前是否为 Team 模式；刷新模板列表并检查实际工作区 |
| 输入区不能选择专家团模板 | 是否已在当前会话构建 Team；新建未发送消息的会话再选模板 |
| `npm run dev` 启动失败或端口已占用 | 是否执行过 `npm ci`、是否又手动启动了前端；`jiuwenswarm-start dev` 已包含前端启动 |
| 专家团可见但无法匹配领域任务 | 检查专家目录返回的实际能力；未配置 capabilities 的模板使用领域标签，显式 capabilities 优先；介绍文字不作为能力，修改模板后使用新 Team 会话 |
| 专家 Team 创建后未入组 | Team 是否成功激活、是否共享 Owner 的 `TeamDatabase` |
| Summary Team 启动失败 | 默认模型是否可解析，Owner Team 是否已有数据库和 workspace |
| 子任务完成但父任务无法结束 | 子任务是否已有 `ACCEPTED` 审核，修复任务是否正确关联 |
| 最终文件找不到 | workspace 是否启用；组织本机工作空间和任务中的产物路径是否一致 |
| 重启后没有继续执行 | 是否使用同一 session 和持久化 storage，Team 是否已重新激活 |

排障时保留启动终端输出，并检查当前用户工作区的 `logs/`。优先查找 `ExpertGroupCatalog`、`ExpertTeamLauncher`、`SummaryTeamLauncher` 相关日志，结合组织面板的任务状态区分“尚未完成”和“已完成但待验收”；不要为了重试直接删除原有工作区或数据库。
