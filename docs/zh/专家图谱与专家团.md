# 专家图谱与专家团

小艺 Work 的专家图谱把已安装的单专家归一化为带版本的能力节点，通过交付契约、能力互补和显式关系发现专家团候选。候选可一键物化为 beta3 原生 `agent_group`，无需修改 `agent-core`。图谱表达“哪些专家适合协作”，并不要求每次任务把所有成员都执行一遍；真正的执行子图由主理人针对当前 Query 动态生成。

## 完整链路

```text
专家来源
  → ExpertInventory（校验、去重、冲突隔离）
  → ExpertGraph（可交接、能力互补、重叠和冲突关系）
  → 能力子图挖掘（3～6 个互补专家、无冲突）
  → beta3 AgentGroup renderer
  → 主理人按 Query 选择 1～N 位成员并生成本次执行子图
  → beta3 scheduler 执行选中任务，主理人汇总交付
```

已有专家团会作为参考节点进入图谱，但不会再次成为新专家团成员，避免 beta3 不支持的 team-of-teams。历史 `package_type=agent_template` 单专家会显示为 `needs_conversion`，转换为 beta3 `packageType=agent_template` 并通过真实包校验后才可参与组团。

## 协作契约

协作字段位于单专家 `manifest.json` 的 `metadata.collaboration`，未知字段不会影响专家独立安装和使用：

```json
{
  "contractVersion": "xiaoyi.expert-collaboration.v1",
  "reusable": true,
  "inputs": [
    {
      "id": "insight.json",
      "mediaType": "application/json",
      "schema": "xiaoyi.insight.v1",
      "visibility": "internal"
    }
  ],
  "outputs": [
    {
      "id": "campaign.html",
      "mediaType": "text/html",
      "schema": "xiaoyi.rendered-html.v1",
      "primary": true,
      "visibility": "public"
    }
  ]
}
```

只有 `mediaType` 与 `schema` 都精确匹配，图谱才建立 `can_feed` 可执行交接边。格式相同但 schema 缺失或不一致时只产生 `needs_adapter`；标签、Skill 或显式关系得到的 `complements`、`overlaps`、`conflicts` 用于发现、路由和解释，不能冒充已经发生的运行链路。

专家团包保存成员池、能力卡、推荐路线和真正不可违反的约束，不保存唯一必跑 DAG。主理人先理解当前 Query，再选择最小必要的 1～N 位成员：独立任务并行，有交接依赖的任务串行，不相关成员不创建任务。中间 JSON 写入共享工作区 `.expert-handoffs/`，大产物通过路径和摘要交接；主理人负责最终汇总。每个成员保留自己专家包中原始 Skill 名称和 Skill ownership，顶层专家团不会把所有 Skills 无差别注入所有成员。

候选协议中的 `routeExamples` 是可解释的常见路线，不是执行命令；`routingPolicy.mode=leader_selected` 表示主理人按需选人。旧版 `workflow` 字段继续兼容，但在动态协议中只作为 playbook 参考。静态能力图、专家团组成图和 Query 运行图是三种不同视图，前端不得把它们混成一条固定调用链。

## RPC

WebChannel 将下列方法原样转发给 AgentServer：

- `experts.inventory.refresh`：重新读取真实专家来源。
- `experts.graph.build`：生成或返回当前进程图谱；`force=true` 强制重建。
- `experts.graph.get`：只读取进程内快照；没有快照时返回 `graph: null`。
- `experts.teams.mine`：按当前 `graph_id` 挖掘候选，拒绝过期图谱。
- `experts.teams.materialize`：仅允许物化服务端刚挖掘出的候选，重新 fetch 成员并再次拒绝 nested team。

物化采用 staging + 原子提交，绝不覆盖已有同名包。若成员版本变化或图谱过期，调用方必须重新构图和挖掘，不能提交自定义成员路径绕过校验。

## 本地验证

源码验证环境需要显式启用本地专家来源：

```bash
export JIUWEN_EXPERT_LOCAL_DIRS=1
```

`scripts/prepare_expert_graph_demo.py` 可把多个现有单专家目录统一转换到 beta3 schema，并从独立 JSON 注入协作契约。脚本不覆盖已有包，也不会改动原始专家；`examples/xiaoyi_expert_graph_demo/collaboration_contracts.json` 仅是示例数据，不进入生产图谱逻辑。

附件中的现有专家团不会被嵌套为 team-of-teams，但可将非主理人成员安全地扁平化为独立专家节点。扩池脚本必须保留 `SKILL.md` frontmatter 中的原始 Skill 名称、隔离凭据和敏感配置、避免覆盖重复 ID。专家发现阶段可以采用轻量门禁快速扩充候选；真正的成员选择、权限、任务依赖和不可伪造的数据边界仍在每次 Query 的执行计划上严格校验。

## 后续扩展边界

本期入口是已安装专家和经过安全检查后扁平化的专家团成员。后续 Skill 图谱发现 Skill-Pack 时，只需复用统一归一化入口把 Skill-Pack 转为带 `metadata.collaboration` 的 beta3 单专家；ExpertGraph、子图挖掘、物化和 UI 协议无需改写。Query 级条件分支、失败重规划和多层团队预留协议边界，本期先完成单成员、串行与并行的动态选人主链路。
