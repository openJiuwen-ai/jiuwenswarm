# 仓库感知工具（code_search / find_symbol / symbol_outline / 仓库地图）

仓库感知工具让 Code 模式以结构化方式理解一个代码仓库：带排序的代码搜索、按名称的符号导航（语言服务器优先、正则兜底）、以及在系统提示中注入一次的仓库地图。它们替代模型原本手写的 `ls` / `find` / `grep -rn … | head` / `cat` 管道，并附带一条明确规则：答案只能来自工作树。

English version: [Repo-Aware Tools](../en/RepoAwareTools.md).

---

## 动机

改动前在 SWE-bench Pro 上的试跑数据（10 题，`deepseek-flash`，密闭评测）：

| 观察 | 数值 |
|---|---|
| 工具调用分布 | bash 43%、edit_file 25%、read_file 20%、grep 7%、glob <1%、**LSP 0%** |
| 每题工具调用（中位数） | 57（同题 opencode 基线：19） |
| 每题 token（中位数） | 2.6M（基线 0.34M） |
| 门控关闭时尝试 `git log --all` / 访问 GitHub 找修复的题数 | 7 / 10 |

大部分 `bash` 调用是搜索管道，原始输出一直留在上下文中。已挂载的 `lsp` 工具一次都没被调用，原因有三层：

1. **被渐进式工具策略隐藏。** agent-core 的 `DeepAgent` 在 `progressive_tool_enabled: true` 时用 `_DEFAULT_DIRECT_TOOL_NAMES`（`openjiuwen/harness/deep_agent.py`）作为暴露策略；不在该内置列表里的工具（`lsp`、`list_files`、`enter_worktree`…）一律注册为 **DEFERRED**，只能通过 `tool_search` / `tool_call` 触达。桌面端日志可见：`visibility | direct=[ask_user, bash, edit_file, …, grep, read_file, …]` 里从未出现 `lsp`。
2. **提示词里没有它。** Code 提示词把所有查找都路由到 `grep`/`glob`，从未提到 `lsp`。
3. **没有安装语言服务器。** 评测容器和新开发机上都没有 `pyright-langserver`、`typescript-language-server`、`gopls`、`rust-analyzer`，即使调用也只会报错。

新工具在卡片上显式声明 `exposure=DIRECT`（卡片显式值优先于注册策略），被提示词点名，并且不依赖任何语言服务器即可工作。

## 新增内容

| 组件 | 位置 | 作用 |
|---|---|---|
| `code_search` 工具 | `jiuwenswarm/agents/harness/code/repo_tools/code_search.py` | ripgrep 驱动（纯 Python 兜底）的搜索；按文件分组、排序、±N 行上下文、限量 |
| `find_symbol` 工具 | `repo_tools/symbols.py` | 按名称查找符号的定义和/或引用；有 LSP 用 LSP，否则按语言正则 |
| `symbol_outline` 工具 | `repo_tools/symbols.py` | 单文件的符号列表（行号 + 层级）；LSP `documentSymbol` 或正则 |
| `RepoMapRail` | `repo_tools/repo_map.py` | 每个工作区向系统提示注入一次有上限的仓库地图 |
| 共享引擎与工具函数 | `repo_tools/_common.py` | 根目录约束、ripgrep 发现与 `--json` 解析、Python 兜底、排序/渲染 |
| 适配层接线 | `server/runtime/agent_adapter/interface_code.py` | `_TOOL_BUILD_NAMES` 条目、`_build_repo_map_rail` 固定 Rail |
| Swarm 接线 | `agents/swarm/providers/{tools,code_rails}.py`、`registry.py`、`config_specs.py` | `swarm.repo_tools`、`swarm.repo_map`，供 code 团队成员使用 |
| 提示词 | `agents/harness/code/prompt/code_prompt_builder.py` | 路由到新工具；禁止用 git 历史 / 网络去「找答案」（用户明确要求查历史时仍允许） |
| 配置 | `resources/config.yaml` 与两个分布式团队模板 | tools 列表条目、`modes.code.repo_tools`（含 `ignored_dirs`）、`modes.code.repo_map` |

### 数据流

```
模型 ── 工具调用 ──► CodeSearchTool / FindSymbolTool / SymbolOutlineTool
                        │  root = 适配层根目录解析（运行时工作区 → project_dir → cwd）
                        │  所有路径都必须位于 root 之内
                        ├─ LspBridge.available(file)?（仅 find_symbol / symbol_outline）
                        │      是 → call_lsp_tool(workspaceSymbol | findReferences | documentSymbol)
                        │      否 → 按语言的正则启发式
                        ▼
                 CodeSearchEngine
                    ├─ ripgrep --json --no-require-git -C N（OPENJIUWEN_RG → SDK 内置 → PATH）
                    └─ 纯 Python 遍历 + re（无 ripgrep 或 ripgrep 无法运行时；工作线程，同一时间预算）
                        ▼
                 FileHits → 排序（匹配数↓，源码 > 测试 > 第三方，路径更短）→ 截断 → 渲染
                        ▼
模型 ◄── ToolOutput.data.content（文本）+ 结构化字段（files/matches/engine/truncated）

RepoMapRail.before_model_call ── 每个工作区根目录的首次调用 ──► cached_repo_map(root)
                                                                └─► PromptSection "code_repo_map"（优先级 60）
```

工具直接以搜索路径为 `cwd` 执行 ripgrep，不经过 sys_operation 的 shell。路径约束由 `contain_path` 强制：任何解析到工作区之外的 `path` / `file_path` 都会以可读错误拒绝。

## 工具说明

### `code_search`

| 参数 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `pattern` | string | 必填 | 正则（ripgrep/Rust 语法，同时也是合法的 Python `re`）或纯文本 |
| `path` | string | 工作区根 | 相对根目录的子目录或文件 |
| `glob` | string 或 list | 无 | ripgrep 风格 glob，`!` 排除（`*.py`、`src/**/*.ts`、`!**/tests/**`） |
| `language` | string | 无 | python、javascript、typescript、go、rust、java、kotlin、csharp、c、cpp、ruby、php、swift、scala、shell、markdown、yaml、toml、json |
| `literal` | bool | false | 按纯文本匹配 |
| `case` | smart / sensitive / insensitive | smart | smart = 模式在正则转义之外没有大写字母时忽略大小写（`\S` 不算） |
| `context` | int 0–10 | 3（配置） | 每个匹配前后的上下文行数 |
| `max_results` | int 1–200 | 40（配置） | 所有文件合计的匹配上限 |

模型看到的输出：

```
5 matches in 3 files
== src/pkg/cart.py (2 matches)
       5:     def total(self):
  >    6:         return compute_total(self.items)
       7:
…
```

结构化字段：`engine`（`ripgrep` | `python`）、`total_matches`、`total_files`、`shown_matches`、`truncated`、`timed_out`、`files[{path, matches[{line, text}]}]`。

排序规则：匹配更多的文件在前；相同时源码目录优先于测试目录、再优先于第三方/生成代码；再按路径长度。即使仓库没有 `.git`（`--no-require-git`）也遵守 `.gitignore`。此外 `modes.code.repo_tools.ignored_dirs`（默认只有版本控制、依赖/工具缓存与编辑器目录：`.git`、`node_modules`、`__pycache__`、`.venv`、`.tox`、`.mypy_cache`、`.pytest_cache`、`.ruff_cache`、`.next`、`.cache`、`.idea`、`.vscode`、`.jiuwenswarm` 等）在任意深度被跳过。`dist`、`build`、`target`、`logs` 这类构建产物**不在**默认列表里，因为真实项目会用这些名字放源码；需要跳过时写进 `.gitignore` 或 `ignored_dirs`。正则非法时返回工具错误，而不是「0 matches」。ripgrep 的其他失败都会让本次调用改用内置搜索，并在标题中注明：ripgrep 无法启动或崩溃（被信号杀死——例如 macOS 在启动时杀掉带隔离标记的二进制——或退出码不是 0/1/2）时，还会在 10 分钟内不再使用它；普通的 ripgrep 错误且没有输出（退出码 2）时，下次调用仍会再试 ripgrep。若 ripgrep 报错的同时仍有匹配输出，则保留这些匹配并在标题中附加警告。行截断到 300 字符，跳过 2 MB 以上的文件，ripgrep 超过 30 s 被终止并标记结果为部分。

### `find_symbol`

| 参数 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `name` | string | 必填 | 单个标识符 |
| `kind` | definition / references / all | definition | 列什么 |
| `file_path` | string | 无 | 固定语言；与 `line` 一起时启用精确的 LSP 引用查询 |
| `line` | int | 无 | `file_path` 中符号所在的 1 起始行号 |
| `language` | string | 由 `file_path` 推断 | 未给文件时的语言 |
| `path` | string | 根 | 限定搜索范围 |
| `max_results` | int | 20（配置） | 每一节的上限 |

引擎选择：

| 情形 | 定义 | 引用 | 大纲 |
|---|---|---|---|
| LSP 管理器已初始化**且**该文件类型有服务器应答 | `workspaceSymbol(query=name)` | 给了 `file_path` + `line` 时 `findReferences`，否则正则 | `documentSymbol` |
| 该文件类型没有语言服务器，或 LSP 未初始化 | 按语言的定义模式（语言未知时取全部语言的并集） | 词边界搜索，定义行标注 `[definition]` | 感知缩进的正则大纲 |
| LSP 调用失败或超时（`lsp_timeout`） | 正则 | 正则 | 正则 |

每个结果标题都标明引擎，例如 `Definitions of compute_total (ripgrep): 2` 或 `(lsp)`。LSP 路径只使用**已经在运行**、且负责该文件扩展名的服务器（读取 `LSPServerManager.get_status()`，绝不调用 `get_or_start_server`）；启动服务器仍由 `LspRail` 负责，因此 `find_symbol` 不会因等待服务器启动而阻塞。

定义模式按语言维护在 `symbols.py::_DEFINITION_PATTERNS`，必须同时是合法的 Rust 正则（ripgrep）与 Python `re`：不能用环视、不能用反向引用。

### `symbol_outline`

| 参数 | 类型 | 默认 |
|---|---|---|
| `file_path` | string | 必填 |
| `max_symbols` | int | 200（配置） |

```
src/pkg/cart.py: 5 symbols (regex)
  L6     function compute_total
  L10    class Cart
  L11      method __init__
  L14      method total
```

正则大纲覆盖 python、javascript/typescript、go、rust、java/kotlin/csharp/scala、c/cpp、ruby、shell 与 markdown（标题）；其他语言走通用关键字扫描。二进制文件与目录会被拒绝。

### 仓库地图

`RepoMapRail` 对每个工作区根目录构建一次地图（进程内 5 分钟 TTL 缓存），作为 `code_repo_map` 提示段加入系统提示，优先级 60（紧随会话指引之后）。同一会话内保持字节不变以便提示缓存生效；根目录变化（切换项目、进出 worktree）时替换。

内容依次为（超出 `max_chars` 时裁剪）：文件数与语言构成的头部；根目录下的清单文件；包（pyproject / package.json / go.mod / Cargo.toml / 非测试目录下的 Python 包）；测试目录；检测到的命令（配置了 pytest 时的 `pytest`、`ruff`、`mypy`、`tox`、`nox`、npm/pnpm/yarn 脚本、`go test`、`cargo test`、`mvn`、`gradle`、`cmake`、`rspec`、Makefile 目标）并附「使用前请核实」；到 `depth` 深度的目录树（每目录文件数，叶子层最多列 12 个文件名）；最后一行提示模型使用工具。点开头目录、`IGNORED_DIRS` 与 `.gitignore` 条目均跳过。在 JiuwenSwarm 仓库自身（1 174 个文件）上，地图 5 997 字符，约 10 ms 构建。

### 读取策略

用户禁止读取的路径，`read_file` 与 `grep` 会被拒绝。仓库工具搜索整个仓库，无法在不拒绝所有搜索的前提下事先按路径拦截，因此改为对每个结果按文件过滤（`repo_tools/read_policy.py`）。策略每次调用都重新读取，热更新的权限与修改后的项目策略立即生效。

| 来源 | 何时生效 | 隐藏什么 |
|---|---|---|
| 权限引擎：生效的 Global ⊕ User ⊕ Session 权限，按对该文件的 `read_file` 评估 | 仅当 `permissions.enabled` 为 true，与 `read_file` 受检查的条件相同 | 工具/参数规则的 `deny`；路径层（`file_guard`，含包内敏感路径如 `.env*`、`.ssh`）的 `deny` 或 `ask` |
| 仅拒绝的项目策略 `<project>/.jiuwenswarm/permissions.yaml`（Shell 策略包） | 该包存在且 `permissions.project_policy.enabled` 不为 false 时 | `deny_read` 与 `deny_paths` 条目 |

- **结果：** 被隐藏文件中的匹配被丢弃。只要读取策略生效，头部就带有固定提示 `files denied by the read policy are left out of these results`，无论是否真的丢弃了结果。工具从不显示被隐藏文件的数量或名称：数量会让模型通过搜索猜测的字符串来判断被禁止的文件是否包含它。LSP 结果同样按文件过滤；过滤后为空的 LSP 结果与原本为空的结果处理方式完全相同，两者输出一致。
- **显式路径：** `path` 或 `file_path` 指向被隐藏的文件、或内容全部被禁止的目录时，拒绝并提示 `not readable under the read policy`。对被隐藏文件的 `symbol_outline` 被拒绝。
- **仓库地图：** 被隐藏的文件与完全被禁止的目录既不列出也不读取。策略变化时重建地图；策略不变时提示保持字节不变。
- **符号链接：** 同时按字面路径与解析后的路径检查，项目内的符号链接无法暴露被禁止的目标。
- **失败即关闭：** 评估单个文件出错时隐藏该文件。构建策略出错、或项目策略文件存在但不可用时，拒绝搜索并不注入地图。
- **为何 `ask` 也隐藏：** 搜索无法逐文件请求批准。模型仍可对该文件调用 `read_file`，照常向用户请求批准。

## 配置

所有键位于 `config.yaml`（及两个分布式团队模板）的 `modes.code` 下。默认值即 `jiuwenswarm/resources/config.yaml` 中的值。

```yaml
modes:
  code:
    tools:
      - …
      - code_search          # 从列表移除即关闭该工具
      - find_symbol
      - symbol_outline

    repo_tools:
      code_search:
        max_results: 40      # 1–200，单次调用合计匹配数
        context: 3           # 0–10 行上下文
        rg_path: null        # 指定 ripgrep；null = OPENJIUWEN_RG → SDK 内置 → PATH
      symbols:
        max_results: 20      # find_symbol 每一节的上限
        max_outline_symbols: 200
        lsp_timeout: 10.0    # 秒；LSP 调用超时即退回正则
      ignored_dirs:          # 三个工具与仓库地图在任意深度都跳过的目录名；
        - .git               # 写完整列表即覆盖默认值（版本控制 + 缓存 + 编辑器目录）；
        - node_modules       # dist/build/target/logs 故意不在其中——请用 .gitignore
        - __pycache__        # （完整默认列表见配置模板）

    repo_map:
      enabled: true          # false：不挂载 RepoMapRail，不注入任何内容
      depth: 2               # 1–4
      max_chars: 6000        # ≈ 1.5k token
```

关闭后的行为：移除三个工具名并设 `repo_map.enabled: false` 后，唯一剩余的变化是提示词文本（+856 字符，约 210 token），其中告知模型在工具不存在时退回 grep/glob。

Swarm 的 code 配置通过 `config_specs._repo_tools_params` / `_repo_map_params` 读取同样的键；`swarm.repo_tools` 只构建 `modes.code.tools` 中列出的工具。

环境变量：`OPENJIUWEN_RG`（或 `ICODE_RG`）指向 ripgrep 二进制。

**没有 ripgrep 时**自动使用内置的纯 Python 引擎。它在工作线程中运行，扫描时不会卡住其他会话或流式回复；与 ripgrep 使用同样的 30 秒时间预算，最多扫描 20 000 个文件。任一上限提前结束扫描时，结果标题会明确说明（「built-in search (no ripgrep) stopped at its file/time limit after N files; results may be incomplete …」），而不是悄悄返回「没有匹配」。大仓库上它明显慢于 ripgrep，因此从源码运行时建议安装 ripgrep：

| 平台 | 命令 |
|---|---|
| macOS | `brew install ripgrep` |
| Debian / Ubuntu | `sudo apt install ripgrep` |
| Fedora | `sudo dnf install ripgrep` |
| Windows | `winget install BurntSushi.ripgrep.MSVC` 或 `choco install ripgrep` |
| 任意平台（Rust） | `cargo install ripgrep` |

也可以用 `OPENJIUWEN_RG`（或 `modes.code.repo_tools.rg_path`）指向已有的二进制。在 macOS 上，仍带隔离标记的下载文件会在启动时被系统杀掉；用 `xattr -d com.apple.quarantine /path/to/rg` 去掉标记即可。即使不处理，工具也会自动改用内置搜索，并只记录一条警告。

```
[JiuwenSwarmCodeAdapter] Tool code_search registered from config

[JiuwenSwarmCodeAdapter] Tool symbol_outline registered from config

ProgressiveToolRail 的可见性日志（新工具名必须出现在 `direct=` 中）：

```
[ProgressiveToolRail][DEBUG] visibility | meta=['tool_call', 'tool_search'] | direct=['ask_user', 'bash', 'code_search', 'edit_file', 'find_symbol', …, 'symbol_outline', …]

## 限制

- 正则启发式是近似：动态生成的名称、宏和非常规排版可能漏掉；结果里的引擎标签让模型能衡量精度。要获得精确结果请安装语言服务器（`npm i -g pyright`、`typescript-language-server`、`gopls`、`rust-analyzer`），`LspRail` 会自动接入。
- `find_symbol` 走 LSP 的引用查询需要位置（`file_path` + `line`）；否则使用词边界搜索。
- 读取策略覆盖权限引擎与项目策略，不覆盖用户钩子；PreToolUse 钩子看到的是搜索参数，而不是每个结果文件。
- 仓库地图是快照；会话中新建的文件能被搜索到，但在缓存过期或工作区切换前不会出现在地图里。
- Python 兜底引擎与仓库地图按 git 的语义应用 `.gitignore`：子目录中的 `.gitignore`、`!` 取反、锚定、仅目录模式、`**` 以及 `.git/info/exclude`；有测试验证它们与 ripgrep 忽略的文件一致。未覆盖：用户的全局排除文件（`core.excludesFile`）。兜底的 smart-case 以「正则转义之外出现大写字母」判定大小写敏感，常见模式与 ripgrep 一致，个别边界情况可能不同。
- `find_symbol`/`symbol_outline` 只在有匹配的语言服务器已运行时走 LSP；没有 `LspRail` 启动的服务器时始终使用正则启发式。
- 提示词规则只针对「找答案」；不影响 `git status`/`git diff`，也不影响用户明确要求的 blame/log。`--implement` 无头驱动器（另一改动）应在续跑提示中使用更严格的无条件版本；不在本改动范围内。
