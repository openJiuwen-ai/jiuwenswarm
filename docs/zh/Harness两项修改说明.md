# Harness 两项修改说明

## 一、改完以后，怎么判断有没有变好

### 现状

评分 Agent 虽然会打出 0.30、0.79、0.95 这样的分数，但系统最终只记“通过”或“不通过”：低于 0.8 记 0，达到 0.8 记 1。

这会漏掉实际变化：0.30 提高到 0.79，系统认为没有进步；0.95 降到 0.81，系统也看不到退步。

修改也要经过多次筛选、组合和重跑，前面表现好的修改，后面可能没有保留下来。

### 改成什么

**使用llm judge给出的实际连续分数。** 得 0.79 就记 0.79。

分两步判断。这里的“基线”，就是本次修改前每道题的分数，两步都用这份分数比较。

**第一步：先测这次要改善的题。**

每道目标题都必须满足：**新分数 > 这道题的基线 + 0.05**。例如原来 0.60，必须超过 0.65；刚好 0.65 不行。多道目标题分别检查，不能靠平均分掩盖某道题没有改善。

**第二步：把所有题重新跑一遍。**

下面三个条件必须同时满足：

| 检查什么 | 保留修改的条件 |
| --- | --- |
| 每道目标题 | 得分高于这道题的基线，不要求再次多出 0.05 |
| 每道其他题 | 得分不低于这道题的基线减 0.05；刚好少 0.05 可以 |
| 所有题的平均分 | 高于修改前的平均分；不要求多出 0.05 |

例如有三道题，这次只改善 A：

| 题目 | 修改前 | 先测目标题 | 再测所有题 |
| --- | --- | --- | --- |
| A：目标题 | 0.60 | 0.70 | 0.64 |
| B：其他题 | 0.80 | 不测 | 0.75 |
| C：其他题 | 0.70 | 不测 | 0.73 |
| 平均分 | 0.700 | — | 约 0.707 |

这次修改可以保留：A 第一次超过 0.65，第二次仍高于 0.60；B 只下降 0.05；C 有提高；三题平均分也提高了。

如果 B 得 0.74，即使平均分提高，也不保留。如果 A 第二次只有 0.60，或者所有题平均分没有提高，也不保留。

两步都通过才保留，否则继续用修改前的版本。评估报错或缺少题目结果，不能算通过。不会一直重跑，直到碰到高分为止。

每个修改后的版本单独决定是否保留，不再等一轮结束后删掉部分修改、重新拼一个版本再决定。原有的代码检查和行为检查继续保留。

## 二、评分时，让 Agent 看见修改前的结果

### 以前怎么做

评分 Agent 主要看题目、评分标准、参考答案，以及这一次做出来的东西。它看不到修改前实际交付了什么、当时为什么得那个分数。

因此，两次评分缺少直接对照，可能出现同样的缺陷，一次扣得多、一次扣得少。

### 改成什么

给修改后的版本评分时，同时提供：

- 这道题修改前的回答、代码、文档等实际交付内容。
- 当时的分数、各项得分和扣分理由。
- 这次修改后的回答和文件。
- 相同的评分标准。

让评分 Agent 逐项对照，说明这次哪些地方变好了、哪些问题还在、哪些地方退步，再给本次结果打分。

例如，上一次得 0.60，原因是“功能基本完成，但缺少错误输入的测试”。这次增加了测试，评分 Agent 就应该检查测试是否真的覆盖了这个问题，再决定加多少分，不能只看见多了一个测试文件就加分。

评分明细直接放进请求；文件较大时，提供 Agent 能实际打开的只读副本，让它按需查阅。

再次运行时，仍提供同一份修改前的材料。但不告诉评分 Agent“这个新版本第一次得过多少分”，避免它照着旧高分打分。

旧评分只是参考。如果发现旧评分有误，可以指出原因，但不能自行改掉比较用的旧分数，也不能默认改后的版本一定更好。这些对照材料只交给评分 Agent，不交给做题的 Agent。
