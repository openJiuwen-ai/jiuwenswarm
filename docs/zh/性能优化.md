# 消息链路性能优化

本文记录一轮针对「对话中 LLM 以外的耗时」的完整排查：**埋点 → 定位 → 修复 → 用日志验证**。
既是优化结果的归档，也是后续排查同类问题的操作手册——第一节的埋点是常驻能力，遇到"消息卡住了"
时按 `[AgentServer]` 前缀 grep 就能定位到具体段落。

排查涉及两个仓库：本仓库（链路埋点、适配器装配）与 `openjiuwen`（agent-core，日志与探测层面的修复）。
文中标注 `agent-core` 的条目需要对应版本的 openjiuwen 才生效。

## 总体效果

同样是 `query=你好` 的单 agent 冷启动首轮对话：

| 阶段 | 改动前 | 改动后 | 变化 |
|---|---|---|---|
| chat input → entering streaming | 2.049 s | 1.039 s | −49% |
| `BEFORE_INVOKE` rail 链 | 624.2 ms | 16.5 ms | −97% |
| `BEFORE_INVOKE` → `ON_USER_MESSAGE` 黑盒 | 1.62 s | ~3 ms | 已消除 |
| `BEFORE_MODEL_CALL` | 89.9 ms | 60.6 ms | −33% |
| **非 LLM 合计** | **4.45 s** | **1.12 s** | **−75%** |

非 LLM 部分在四次测量中稳定在 1.08~1.38 s，方差极小；总时长的起伏（3.54 s ~ 12.13 s）全部由
LLM 首 token 的波动解释，与本轮改动无关。

team 模式另有一处 30 秒级卡顿，根因见 [vision 能力探测](#四vision-能力探测阻塞-2030-sagent-core)。

## 一、链路埋点

排查开始前没有办法回答"消息到了哪一步、卡在哪一段"，所以先在关键节点埋了日志。全部走 agent-core
的 `server_logger`，与 agent 内部日志落在同一条流里，统一 `[AgentServer]` 前缀便于按链路 grep。

### 埋点清单

| 位置 | 文件 | 日志 |
|---|---|---|
| AgentServer 入口 | `server/agent_ws_server.py` | `chat input received` |
| 单 agent 主路径 | `server/runtime/agent_adapter/interface_deep.py` | `message entering runner streaming`（含 `prepare_ms`） |
| 单 agent 注入路径 | 同上 | `message entering runner interaction inject` |
| 单 agent 首帧 | 同上 | `runner streaming first chunk`（含 `elapsed_ms` / `chunk_type`） |
| session adapter 创建 | 同上 | `session adapter created`（含 `create_instance_ms` / `start_interaction_ms`） |
| team streaming | `server/runtime/agent_adapter/team_helpers.py` | `team message entering runner streaming` + 两条首帧 |
| team interact | `agents/harness/team/team_manager.py` | `team message entering runner interact` |
| 每轮运行时装配 | `server/runtime/agent_adapter/interface_deep.py` | `runtime config applied`（分段明细，见下） |

入口点只对 `chat.send` 打点，文本取 `request.params["query"]`；单 agent 的两个 choke point 取
`inputs["query"]`（真正送进 agent 的完整 prompt）。`agent` / `deep` / `code` / `claw` 各模式共用
`process_message_stream_impl`，所以一处覆盖全部模式。

### team 首帧要分两条

初版把 runner 吐出的第一个 chunk 当首帧，这是**错的**——team 流上跑的大多是框架控制事件
（`team.runtime_ready`、`tool.use`、`team.member`），模型 token 往往在它之后好几帧才来：

| 日志 | 含义 |
|---|---|
| `team runner streaming first event` | 从调用 runner 到流活起来，量的是团队启动开销 |
| `team runner first model output` | 真正的 TTFT，带 `received=N` 与 `event_type` |

模型输出的判定为 `{"chat.delta", "chat.final", "chat.reasoning"}`。`chat.reasoning` 特意算进去——
推理模型先吐思维链，那才是第一个 token 落地的时刻。

已知精度取舍：判定在 `_is_leader_output` / `_is_teammate_output` 过滤之后，若某个被过滤帧里先有
模型输出，TTFT 会偏晚。team 模式下这类帧基本都是框架事件，代价可接受。

### `prepare_ms` 的分段明细

`message entering runner streaming` 里的 `prepare_ms` 是一个聚合值，它的主体是每轮都要跑的
`_update_runtime_config`。这一步再拆成十段单独计时，避免"知道慢但不知道慢在哪"：

```
[AgentServer] runtime config applied: session_id=... mode=agent total_ms=128.4
  cwd_seed=2.1 rail_setters=0.4 runtime_state=3.2 rails_for_mode=61.5
  user_interaction=0.2 tools_for_mode=48.7 session_tools=7.3 acp_tools=0.1
  prompt_for_mode=4.8 memory_tools=0.1
```

总耗时超过 `_SLOW_RUNTIME_CONFIG_MS`（50 ms）才打 INFO，否则走 DEBUG，正常请求不会污染日志流。
计时写在 `finally` 里，所以中途抛异常的那一轮同样会输出——此时最后一个出现的段名就是它卡住的位置，
抛异常的那段不会被记为已完成。

计时器本身是 `jiuwenswarm/common/stage_timer.py::StageTimer`，同类的"聚合数字要拆段"场景可以直接复用。

### 冷启动的 rail 构建明细

`create_instance` 里最大的一块是 rail 构建（实测约 223 ms / 361 ms）。同样逐个计时，输出按耗时倒序，
慢的排最前：

```
[AgentServer] agent rails built: adapter=JiuWenSwarmDeepAdapter count=18 total_ms=214.7
  skill_rail=131.2 permission_rail=38.4 context_processor_rail=21.0 ...
```

超过 100 ms 才打 INFO（rail 只在建 agent 时构建，不在每轮热路径上，所以阈值比上面那条高）。
agent 与 code 两个模式共用同一个构建循环 `_instantiate_rails`，两边都有这条日志，`adapter=` 区分。

### 日志中的用户内容

埋点会记录用户 query 的前 200 字符，便于把一次慢请求对回具体输入。这是用户内容落进长期日志，
可以关闭：

```yaml
logging:
  preview_user_content: false
```

或设环境变量 `JIUWENSWARM_LOG_PREVIEW_USER_CONTENT=0`。关闭后计时数据照常记录，文本部分替换为
`<N chars omitted>`。截断实现统一在 `jiuwenswarm/common/log_preview.py`（此前散落三份各写各的）。

### agent-core 侧的配套埋点

- **rail 链计时**：`AgentCallbackContext.fire()` 前后计时，≥100 ms 走 INFO，放在 `finally` 保证异常也记账
- **慢 callback 点名到类**：`trigger()` 本就算了 `execution_time` 却从不输出，补上 INFO；用
  `__qualname__` 而非 `__name__`，于是能定位到 `SkillUseRail.before_invoke` 而不是"某个实现了该钩子的 rail"
- **invoke 准备段分段**：`BEFORE_INVOKE` 与 `ON_USER_MESSAGE` 之间原本没有任何事件，1.62 s 完全不可见；
  拆成 interruption_state / context / system_prompt / skills / tools 五段

## 二、root DeepAgent 在关键路径上被构建，但 chat 从不使用它

**现象**：一次请求内工具注册、SubagentRail、context processors、checkpoint restore **各跑两遍**，
伴随成片 `Tool id already registered; refreshing` 与 `Duplicate tool ability detected` 告警。

**根因**：不是同一个 adapter 跑两遍，而是**两个 adapter 各建了一个完整 DeepAgent**。
`AgentManager.get_agent()` 创建 root adapter 并跑完 `create_instance()`，`process_message_stream_impl`
随即委派给 per-session child adapter 再跑一遍。root 那个 DeepAgent 在 chat 路径上从不使用
（不调 `start_interaction()`，controller 从未启动），只被一批非 chat RPC 当句柄。

**改法**：root 的 `create_instance()` 在跑完便宜的配置缓存段后早退，昂贵段改为按需构建。

- `interface_deep.py`：新增 `_skip_own_instance_build()` / `ensure_instance()`（双重检查锁）
- `interface_code.py`：code 模式 `create_instance` 同样早退
- `interface.py`：facade 新增 `async def ensure_instance()`；`get_instance()` 保持纯访问器语义
- **消费点改造**：需要 DeepAgent 句柄的非 chat 路径（harness package、session fork、plan 模式切换、
  rewind、定时任务、远端成员引导等）统一改为 `await ensure_instance()`；`_resolve_rewind_agent`
  由同步改 async
- **配套**：`reload_agent_config()` 原本在 `_instance is None` 时直接 raise，会被惰性化撞上。
  拆出 `_apply_reload_config_snapshot()` 与 `_fan_out_reload_to_session_adapters()`，root 未构建实例时
  走轻量路径（刷新配置快照 + 级联 session adapters），child 未初始化仍 raise

**验证**：SubagentRail / context processors / checkpoint restore 各 2 次 → **1 次**；
资源日志 272 → 174 条（−36%）。

## 三、进程级资源的所有权与回收

`Runner.resource_mgr` 是进程级全局注册表，而 adapter 是按 session 创建、销毁的。两者生命周期不匹配，
导致三类泄漏。

### 工具注册按 owner 隔离

所有 adapter 此前共用 `AgentCard.id='jiuwenswarm'` 作为工具 owner，于是并发 session 的同名工具
互相覆盖，每建一个 session adapter 就把上一个的工具 remove/add 一遍。

改为 `_tool_owner_id()`：session adapter 用 `jiuwenswarm_s_<session>`，root 用 `jiuwenswarm_root`。
`AgentCard.id` 保持不变——它是 checkpointer key 的实体段，必须跨重启稳定，与工具所有权是两件事。

> 两类 owner 分处不同命名空间（`_s_` 前缀）而非共用一个扁平后缀：session id 来自客户端，
> 一个名为 `root` 的 session 否则会产出与 root adapter 完全相同的 owner id，正好复现要消灭的碰撞。

### 共享还是独占，由 card 说了算

判据统一为 `ToolCard.stateless`（openjiuwen `AbilityManager.add_ability` 的同一份契约），
实现收敛在 `jiuwenswarm/common/tool_ownership.py`：

| 声明 | 注册 id | 重复注册 | 卸载 |
|---|---|---|---|
| `stateless=False`（默认） | `{name}_{owner}` | `refresh=True` 重新绑定 | 从全局注册表移除 |
| `stateless=True` | 裸 id | `skip_if_exists=True` 幂等 | 只脱离本 agent，全局保留 |

默认值 `False` 是安全的一侧：共享实例被按 agent 注册只是多几个对象，而独占实例被当共享注册会把
第一个 session 的状态钉死在整个进程上。

需要共享的用 `mark_stateless()` 在**构建处**声明（模块级 `@tool` 单例、以及 skill / symphony
这类背后是进程级 manager 的工具包），这样创建路径与热更新路径读到的是同一个声明，不会一边按共享
注册、另一边按独占重建。

### SysOperation 引用计数

移除一个 SysOperation 会连带移除由它派生的十余个 fs / shell / code 工具，而 sandbox 模式下多个
adapter 会按 isolation key 复用**同一个** SysOperation。单个 adapter 的 cleanup 不能拆掉兄弟还在用的
注册，于是引入进程级引用计数：

- 重建 agent 时**先 retain 新的、再 release 旧的**，同 id 重建时计数不会中途归零
- 计数为 0 才真正 `remove_sys_operation`，且只移除仍在注册表里的
- 释放一个从未持有的引用时打警告并跳过，而不是把别人的资源摘掉

计数只覆盖走 adapter 的持有者。直接向 `Runner.resource_mgr` 注册 SysOperation 的代码
（`auto_memory.extraction_runner`）在计数之外，目前安全的前提是那些 id 私有、不参与 isolation key
复用；将来若有新注册方可能与 adapter 共享 id，必须一并接入计数。

### 子 agent 的 SysOperation 复用

`_agent_def_to_subagent_config` 此前不设 `AgentCard.id`，默认值是随机 uuid，于是每次 Agent 工具调用
都注册一个新的 SysOperation 及其派生工具，永不回收。改为按定义名派生稳定 id
（`subagent_{name}`），让 `create_deep_agent` 走 get-or-create 路径。

### cleanup 收尾

adapter 销毁时调用 `AbilityManager.teardown_tools()` 回收本 agent 的独占注册，并释放持有的
SysOperation 引用。这两步是上面所有 id 约定的兑现点——注册 id 与 teardown 的查找规则必须完全一致，
否则实例会泄漏到进程结束。

## 四、vision 能力探测阻塞 20~30 s（agent-core）

**现象**：一次 team 请求 78.7 s 中，两次探测合计 **49.2 s**（占 63%）。

**根因**：`probe_image_support()` 发一张 32×32 红色 PNG 问颜色，非流式、`max_tokens=1024`、
超时上限 30 s。三个问题叠加：图片没送达上游、推理模型没关 thinking（烧掉 1028 / 785 个 reasoning
token）、探测非流式串行阻塞。而且结论注定为 `False`，等待纯属白费。

探测结果还不缓存：`config.enable_read_image_multimodal` 的作用域是单个 DeepAgent 实例，每 new 一个
就探一次（一次请求累计 170 次）。只影响 team 路径——deep / code 模式已把该字段解析为 bool。

**改法**（均在 agent-core）：

- `DeepAgentSpec` 补 `enable_read_image_multimodal` 字段（此前 pydantic `extra="ignore"` 静默吞掉），
  tiny agent 与 team 成员在未表态时兜底 `False`
- 探测重写：进程级 `(api_base, model_name) → bool` 缓存、`max_tokens` 1024 → 8、超时 30 s → 5 s、
  `extra_body` 带上 GLM / Qwen / OpenRouter 三家的关 thinking 开关（网关不认则去掉重试一次）、
  改为后台调度并按 key 去重、空回复判 inconclusive 而非 `False`

**实测**：28.59 s → 1.63 s，缓存命中 0.0000 s。

> **行为变化**：team 成员现在默认 metadata-only 读图。换到支持 vision 的模型时不会自动启用，
> 需要在 blueprint 的 agent spec 里显式写 `enable_read_image_multimodal: true`。

## 五、其他已修复问题（agent-core）

### `SysOperation.read_file()` 把文件全文写进结构化日志

`End to read file` 事件带 `method_result=self._safe_model_dump(success_result)`，而
`ReadFileResult.data.content` 就是文件全文。单条日志最大 46,592 字节，一次会话此类日志 135 行 3.2 MB，
还要同时写 3 份日志文件。

基准对照（7 个文件共 201 KB）：裸 `read_text()` 1.76 ms、加跨进程读写锁 6.67 ms、
`_safe_model_dump` 0.01 ms，而 `logger.info(..., event=带全文)` **133 ms**。

改法是在 `_create_sys_operation_event()` 单点截断，一次覆盖 fs / shell / code 共 21 个调用点。
**验证**：7 条日志 117.57 ms → **6.76 ms**（17×）。

### 读 SKILL.md 只要 front matter，却读了整个文件

`_load_description()` 只取 `description` 一个字段，但 `_load_yaml()` 读的是 15~46 KB 的完整文件。
改为先 head 读 64 行探测 front matter，超出的文件自动回退全文读取。

**验证**：7 个 skill 的 description 与全文解析完全一致；`_prepare_skills` 冷启动 217 ms → **22.50 ms**，
热态 0.31 ms。

### 跨进程锁数据库孤儿泄漏

临时目录下堆积 **19,298 个** `.db` 文件。`cleanup_expired_locks()` 只处理本进程租用过的锁，
进程一退出它创建的 db 就成了无主孤儿，而每个新锁都要在这个越来越大的目录里创建文件。

改为每个清理周期扫描 lock_dir，把超 TTL 且不在活跃集合中的 `.db` 排入清理队列（限流 200 个/次），
删除仍走原有的"只删能拿到独占写锁的"逻辑。

### system prompt 里的重复注入

DeepAgent 与 ReActAgent 各维护一个 prompt builder，完整 prompt 被当成 identity 再包一层，导致
`<system-reminder>` 说明块出现两份。改为只把 identity 写进 `prompt_template`，其余段交回共享 builder。

| | 改前 | 改后 |
|---|---|---|
| 普通 agent（en） | 4814 字符，2 份 | 4209 字符，1 份 |
| 普通 agent（cn） | 1726 字符，2 份 | 1476 字符，1 份 |

全局生效：主 agent、team leader、每个成员、每个 subagent 的**每一次**模型调用。

### tiny agent 的多余足迹

模块 docstring 写着"no tools except the optional structured-output tool"，但代码没这么做。

| | 改前 | 改后 |
|---|---|---|
| 资源注册 | 16 个 + 全部注销 | **1 个**（structured_output） |
| checkpoint | restore + save + sqlite 落盘 | **0** |
| system prompt | 1230 字符 | **27 字符** |

## 六、遗留事项

1. **`create_instance_ms` 仍有 637~642 ms** —— child adapter 的必要装配（工具注册 + 17 个 rail +
   `ensure_initialized` + MCP server 注册含网络探测）。要再降需结构性改动：rail 懒加载，或跨 session
   复用不可变部分。
2. **体感优化优先于继续抠时间** —— 让首帧更早出现（等模型时先推占位状态）比继续压这 0.9 s 更有效。
3. **蓝区网关不支持多模态** —— 网关内部会把多模态 content 拍平成纯文本，该端点上 vision 类功能
   不可用，验证多模态代码需换 endpoint。
4. **`responses_utils.py` 丢 image_url**（agent-core）—— `OpenAIAccount` provider 走 Responses API 时，
   `_content_as_text()` 只拼接文本块，`image_url` 被静默丢弃。当前触发路径没走到，未修。
5. **探测的假阳性风险**（agent-core）—— `probe_image_support` 判定是 `"red" in content.lower()`，
   单色红图且无否定校验，某个模型恰好幻觉答 "red" 会被误判为支持 vision。
6. **单 agent 惰性化的回归覆盖** —— 已有单测覆盖懒构建与并发只建一次，但下列端到端路径建议实跑：
   code 模式 plan / normal 切换、harness package 激活与停用、session fork、配置热更新的 root 轻量路径。
