# 云文档协同（Co-scribe）

## 1. 概述

Co-scribe 让 agent 成为共享云文档里的一名协作者。平台凭证握在部署主人手里，也只有主人能授予任何权限；协作者在批注里 @ 它就能叫到它，而它**只在批注圈中的那段文字里**改、只在这篇文档的值守开着时改，并且每一次写入都留下回执。

```
你        （选中一句话，添加批注）   @docs-agent 这句话收紧一点
Agent     ⏳ 正在处理…  →  ⏳ 正在读取文档…  →  ⏳ 正在核对批注选区并写入…
Agent     已直接修改并以黄色高亮标出。
          不满意可 @ 我说明；要撤销这次改动，请用平台的版本历史。
```

三个界面共用一套机械：

| 界面 | 谁在场 | 能做什么 |
|---|---|---|
| **文档里的批注** | 没有人——这是无人值守回合 | 在圈中的段落内有界直改，或在线程里作答 |
| **Jiuwen 对话** | 你 | 读、列、回复、改正文、按区域写、加页、新建/共享/回收站——每次写入先问你 |
| **「云文档」面板**与文档工作台 | 部署主人 | 纳管文档、逐篇开关值守、查看授权与写入的完整记录 |

支持 Google 与飞书两个平台，**三种格式：文档、表格、幻灯片**。与平台相关的部分全部收在一个 provider 接口后面。

云盘里的 markdown 文件曾经也在服务范围内，2026-09-08 起退出：`.md` 上的批注既不带锚点也不带引文，而其他每种格式的编辑窗口都是从选区算出来的，所以无人值守的一轮没有任何东西能约束它。纳管时还在服务范围内的会在启动时自动退管，平台上的东西不动。

**默认关闭。** `clouddoc.enabled: false` 时 watcher 根本不会被构造。开关在**应用插件**页的 Co-scribe 卡片上；只有开启时侧栏才出现「云文档」入口。

## 2. 接入

### 2.1 给 agent 一个身份

agent 需要**属于它自己**的身份，而不是借用你的：这样它的修改在文档历史里与你的分得开，收回它的权限也不必动你的账号。

**Google。** 在 [Cloud 控制台](https://console.cloud.google.com/)建项目，启用 **Docs、Drive、Sheets、Slides 四个 API**，创建服务账号并下载 **JSON 密钥**。账号地址（`name@project-id.iam.gserviceaccount.com`）就是 agent 在所有文档里的身份。个人 Google 账号下的服务账号没有云端硬盘空间，所以它能改共享给它的文档，不能名下持有新文档——新文档请你自己建好再共享给它。

**飞书 / Lark。** Co-scribe 通过官方 `lark-cli` 驱动平台，始终以 `--as bot` 行事。先用 `lark-cli config init --app-id … --app-secret-stdin` 注册一次应用（密钥留在 CLI 自己的存储里，不过命令行），再写一个小凭证文件供部署指向：

```json
{"app_id": "cli_xxx", "app_secret": "…", "bot_open_id": "ou_xxx", "profile": "cli_xxx"}
```

`bot_open_id` 是 agent 认出自己批注的依据；租户的 `whoami` 不一定带它。两种密钥文件都放在仓库之外——**拿到它的人就能以 agent 的身份行事。**

### 2.2 共享文档

把文档共享给 agent 的地址，给**编辑者**权限。仅给评论权不够，而且失败方式是静默的：Google 不再返回 revision id、权限列表开始返回 403、而评论仍然读得到——agent 看起来正常，却永远写不进去。这种文档在准入时被拒，在面板里显示为「仅评论权」并给出改法。

飞书上把应用加为文档（或所在知识库）的协作者。要让面板**自动发现**文档，把应用加为团队知识库空间的成员：发现是沿着已纳管文档所在的空间走的，应用不是成员的空间会答 `131006`，面板会告诉你该把它加进哪个空间。

### 2.3 建立连接

把密钥路径写进 `config.yaml`：

```yaml
clouddoc:
  enabled: true
  connections:
    - credentials_file: /secure/path/to/key.json
      documents: []            # 链接或裸 id；面板会自动填
```

或者打开**云文档**面板在那里添加——粘贴密钥路径、粘贴 JSON、或直接选文件。上传的密钥存到 `<工作空间>/config/clouddoc-keys/`（0600），配置里只留路径。一个连接 = 一个平台账号；**同一篇文档只属于一个连接**。面板上的增删立即生效并写回 `config.yaml`。

### 2.4 纳管文档

共享就是纳管。打开面板、点**刷新**、以及每五分钟一次的后台发现（`auto_discover_shared`）会把账号能编辑的文档全部纳管——Google 是共享给它的一切，飞书是已纳管文档所在知识库空间里的一切。列表够不到的文档（空间之外的飞书文件、应用刚建的文档）把链接粘进表格底部的输入框、点**纳管**（或回车）：先校验，通过即纳管，纳不了会当场说明原因；纳管结果会写明值守是关是开。

两条路的结果完全一样，值守策略也一样：

- **纳管**是指文档进入这个连接的轮询列表并写入 `config.yaml`：从此每次轮询都读它的评论，重启后照样在。自动发现只增不减——它列不到的文档不会因此被取消纳管；只有逐篇探测到平台确认文档已不存在或已取消共享，才会退役。所以一篇粘链接纳管的飞书文档，哪怕永远不在任何知识库空间里，也会一直被值守轮询，@ 照样能被看见。
- **值守（写授权）默认不开**。`auto_watch_on_adopt` 默认 `off`：无论文档是发现来的还是粘来的，纳管后 agent 只能读和回复，@ 不会触发直改。要让它直改，在该行打开值守——这会签发一份带期限的授权，写进授权记录和审计日志；或者把 `auto_watch_on_adopt` 设为 `apply_scoped`，那时两条路都会在纳管时自动签发，面板会在纳管结果里说明。

**纳管不授予任何权限。** 新纳管的文档只被轮询，别的什么都不做（`auto_watch_on_adopt: "off"`）：协作者在那里 @ 了 agent，只会被告知一次值守没开、谁能开。

### 2.5 打开值守

**值守**那一列就是开关。关 = 这篇文档永远不派发回合；开 = 一次 @ 换来一次有界直改。打开要点两下（这是一份长期委托），关闭立即生效。勾选多行可以一起开或关。没写明期限的值守 **30 天后过期**；文档记录里可以续 30 天或改为永久，过期与撤销都留墓碑，不会有东西悄悄把它重新签发。

## 3. 在批注里用

1. 选中要改的那段——选区就是边界，不只是上下文。
2. 添加批注并 **@ agent 的地址**（批注本身或它下面的回复都行）。@ 是两个平台上唯一的召唤方式；Google 的「指派给」字段不读。
3. 说你要什么。几秒之内（轮询间隔，5–30 秒）agent 会贴出占位，把进度写进去，然后要么改、要么答。

agent 能改的范围由代码从选区算出：`exact` 是选区本身；批注者自己的话可以把它放宽到所在的**整句 / 整行 / 整段**（「这句」「这行」「这段」），不会更宽，档位会在回帖里披露并记进回执。越界的修改整批拒绝。Google 上改动会**黄色高亮**，回执提供撤高亮；飞书的写入通道不带高亮，回帖改为逐条列出改动。

**追问**需要再 @ 一次：不带 @ 的回复会作为线程上下文被读到，但不会叫醒 agent。提问只得到回答，不会有修改。同一处文字上两条互相矛盾的批注它不裁决——会说明并请你们协调。agent 从不结帖，结帖是读者的验收。

**撤销靠平台的版本历史**（Google「版本记录」，飞书「历史版本」）。回执里保留了修改前的原文，只想撤回这一批的人可以照着放回去。

表格和幻灯片有一些平台限制，批注前值得知道——见第 5 节。

## 4. 在对话里用

对话里 agent 能到达所有连接下的每一篇已纳管文档。纳管多篇时必须告诉它是哪一篇——在你自己的话里出现标题、链接或 id；代码不允许它替你挑，只能反过来问你。每次写入先要你确认，并返回**回执编号**。

| 工具 | 作用 |
|---|---|
| `clouddoc_list_documents` | 已纳管的文档，带格式与平台 |
| `clouddoc_read` | 正文纯文本；表格与幻灯片另返回每个有地址的格子/文本框，以及共有几张工作表或几页 |
| `clouddoc_list_comments` / `clouddoc_reply_comment` | 读线程、回线程（已解决的不回） |
| `clouddoc_batch_edit` | 多处文本替换一次原子提交；可声明服务于某条批注（`for_comment_id`），此时受与无人值守路径同样的边界约束 |
| `clouddoc_write_region` | 声明一个单元格区域或幻灯片文本框应当变成什么——移动、交换、清空都是一次写入 |
| `clouddoc_add_page` | 新增工作表或幻灯片页，返回之后写入用的地址 |
| `clouddoc_create_document` / `share_document` / `trash_document` | 生命周期动作，各有回执；共享地址必须来自你的话 |
| `clouddoc_workmode_get` / `edit` | 部署级工作方式文件 |

工具强制的规矩：**先读后写**（共享文档随时会被别人改）；Google 上以及所有表格、幻灯片的正文是纯文本，markdown 记号会被拒绝；区域内有公式格则整批拒绝；幻灯片的演讲者备注只在你要求写备注时才写；同一篇文档有无人值守回合尚未处理时，对话里不改正文。

从面板或输入框上方的文档芯片**打开一篇文档**，会在工作台标签里显示平台自己的编辑器，下方停靠本会话的对话条，右侧是这篇文档的回执与值守。每个会话各有自己的一组标签（最多六个）。

## 5. 格式与平台限制

| | Google | 飞书 |
|---|---|---|
| 写入高亮 | 有，结帖或手动清除 | 无——回帖逐条列出改动 |
| 乐观锁 | 文档与幻灯片有；**表格没有** | 没有——每次区域写入都回读，对不上时回执标为「未验证」 |
| 一次写多处 | 可以 | 一次只写一处 |
| **文档**上的批注锚点 | 引文 | 引文（128 字截断，无标记） |
| **表格**上的批注锚点 | 单格：该格的值；多格框选：**什么都没有** | 引文前带格子地址（`D2 …`） |
| **幻灯片**上的批注锚点 | 点中的形状，或引文 | 引文；一批区域须在同一页 |
| 新增页 | 按名字加工作表；加带标题框和正文框的一页 | 按名字加工作表；加页需要标题（内容完全相同的请求会被合并成一页） |

**从批注改表格。** 批注落在哪一格只能从引文反推：值在表里重复的格子无法从批注定位，Google 上多格框选根本不存引文，一条批注只授权一个格子。请对值唯一的格子批注，或到对话里按 A1 直接改。

**幻灯片。** 点中整个形状留下的批注授权那个形状；还没有文本框的页无法从批注写入——先在对话里加一页。

## 6. 配置

```yaml
clouddoc:
  enabled: false
  connections: []                 # 每个平台账号一条（见 2.3）
  poll_interval_seconds: 30       # 5–600；面板提供 5/10/15/30
  turn_timeout_seconds: 540       # 启动时钳到传输层上限之下
  session_max_turns: 50           # 单文档会话跑满后轮换
  auto_discover_shared: true      # 五分钟一次的自动纳管
  discover_interval_seconds: 300
  auto_watch_on_adopt: "off"      # "apply_scoped" 则纳管即签发值守（相当于批量签字）
  model_name: ""                  # 无人值守回合用的模型；每篇文档可另钉一个
  mode: mandate                   # 或 direct：无回执、无无人值守派发
  workmode_file: ""               # 工作方式文件；默认在 config 目录下
  conventions_marker: "co-scribe 约定"   # 也决定内置工作方式模板的语言
  agent_roster: []                # 其它 agent 的飞书 open_id：agent 写的 @ 永远不算召唤
  dispatch_rate_max: 10           # 每篇文档滚动窗口内的派发上限：防回环刹车
  dispatch_rate_window_seconds: 120
  rail:
    max_quote_chars: 400          # 兜底；provider 实测的上限优先（418 / 128）
    max_insert_chars: 2000
    max_edits: 10
```

所有可配置串——约定标记和两个词表里的每一项——两两不得相等、不得互为前缀，启动时校验，不通过就拒绝启动。

**权限。** `permissions.enabled: true` 时，无人值守回合持有的四个工具必须是 `allow`，因为没有人能回答确认：`clouddoc_read`、`clouddoc_list_comments`、`clouddoc_apply_for_comment`、`clouddoc_reply_comment`。对话里的写入默认 `ask`。**Full Access**（没有确认通道）下，授出权限或无法撤销的动作——新建并共享、共享、移入回收站、以及回执账本不可用时的任何写入——会被拒绝而不是静默执行；面板会有横幅说明。

**模式。** `mandate` 是完整机械。`direct` 是刻意的基线：纳管加直接编辑，没有回执、没有无人值守派发；开着时面板一直挂横幅。

## 7. 记录

每次写入之前先落一条 **pending** 回执，之后落 **applied** 或 **aborted**，记录在写入原语内部，模型既跳不过也关不掉。两者之间崩溃留下的 pending 由启动时的清扫判为 **unknown**，不猜；区域写入回读不一致的判为 **applied_unverified** 并写明差在哪。

面板里的**文档记录**把三样东西放在一条时间线上：授权谱系（签发、续期、撤销、过期）、派发与拒绝、写入。可导出 CSV——导出的是当前视图的快照，不是账本本身。值守注册表是现状，审计日志只追加、经得起撤销和再签发，回执账本是写入。三者都在 `<工作空间>/config/` 下，通用文件工具写不了它们。

## 8. 没人盯着时靠什么

护栏是代码，不是提示词：

- 无人值守回合只持有**四个工具的闭集**，文档与批注由派发方绑定——模型传来的文档参数会被绑定值覆盖；
- **编辑窗口**从选区几何算出；可机械判定的指令（「剪短」「删掉 X」）在写入前对照编辑核对；区域写入回读；
- 写前检查点重读值守：撤销、过期、档位变化会拦下正在进行的写入；
- 回帖声称改了而账本没有记录的，在线程里被机械纠正；
- 服务账号或名册上的 agent 写的东西永远不构成召唤，每篇文档的**速率刹车**在一个轮询周期内掐断指针回环；
- shell 里调平台命令行的写入一律拒绝，只放行明显的读；机械自己的文件对通用文件工具只读。

## 9. 文档约定

协作者可以留一条以约定标记开头的顶层批注，为这篇文档设定写作约定：

```
co-scribe 约定
句子尽量短。
产品名首次出现时用全称。
```

只约束**风格**；其中关于 agent 能改什么、谁的批准算数的内容一律忽略，回复永远不算，多条时以最早的一条为准。部署自己的风格在工作方式文件里，可以在对话里改。

## 10. 限制与排查

- **延迟**：每 N 秒轮询意味着平均 N/2 的等待，再加回合自身约六秒的往返，占位才出现；模型的工作在那之后。
- **配额**：所有纳管文档共享账号配额；每篇文档每轮至少一次评论查询。
- **单实例**：两个 gateway 共用一份状态文件会各自派发同一个触发。
- **企业策略**：部分租户禁止域外服务账号；请贵方管理员建一个域内的。

| 现象 | 原因 |
|---|---|
| @ 了没有任何反应 | 这篇文档的值守是关的（agent 会在线程里说一次）、文档没纳管、或 @ 的是另一个 agent 的地址 |
| 「这篇文档的值守没有开启」 | 到云文档面板打开，然后再 @ 一次 |
| agent 回了话但没改 | 批注是提问；或修改越出了窗口；或同一处有两条互相矛盾的批注——回帖会说明是哪一种 |
| 「引用文本在这张表里出现 N 次」 | 该格的值重复；对值唯一的格子批注，或到对话里按 A1 改 |
| 「The user does not exist」（飞书 20008） | 工作表名不在这个工作簿里——用 `clouddoc_read` 核对，或用 `clouddoc_add_page` 新建 |
| 权限修好了文档仍显示未共享 | 点**刷新**；连续失败的文档每次启动只重查一次 |
| 面板说某个飞书连接无法自动发现 | 把应用加进它点名的知识库空间，或粘链接纳管 |
| 一篇文档从列表里消失了 | 它被退管了：平台上已删除或取消共享，且在丢弃之前经元数据查询确认 |
