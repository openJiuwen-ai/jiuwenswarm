# 上下文瘦身（Code 模式）

> 让工具输出别占着模型窗口：工具结果入库时先裁剪 shell / grep / 文件读取输出；对话变长后再把旧结果换成一行摘要。配置位于 `modes.code.context_diet`；英文版见 [ContextDiet](../en/ContextDiet.md)。相关：[上下文压缩](上下文压缩.md) 介绍 agent-core 基于阈值的压缩器，本功能在其之上工作。

## 1. 动机

SWE-bench Pro 10 题试跑（deepseek-flash，20 次无头运行）测得 Code 模式的 token 去向：

| 指标 | 数值 |
|---|---|
| 每次模型调用输入 token 中位数 | 58.7k（最大 151k） |
| 每次调用的固定部分（系统提示 10.6k + 技能 2.0k + 工具 schema 13.2k） | 25.8k |
| 窗口内工具结果，每次调用中位数 | 32.7k（最大 125k） |
| 每次运行产生的工具结果文本 | 2.42M 字符 / 902 次调用 |
| 按工具分 | `read_file` 54%、`bash` 41%、`grep` 4%、编辑 <1% |
| 单次 `read_file` 结果中位数 / p90 | 3.0k / 19k 字符 |
| 单次 `bash` 结果中位数 / p90 | 1.1k / 3.3k 字符（最大 60k） |

每条工具结果都会在之后的每次调用中被重新发送：一份 20k 字符的测试日志读一次，在本轮结束前还要再付 30 次 token。agent-core 只在窗口接近上限或连续 4 次完全相同的调用（`tool_loop_compact`）时才压缩，其 `ToolResultWindowProcessor` 也没有接进 JiuwenSwarm。上下文瘦身在两个位置补上这一环。

## 2. 工作原理

```
工具执行 ──► ToolMessage ──► [ContextDietTrimRail.after_tool_call] ──► 上下文引擎
                                  │ 保留头/尾/信号行                        │ on_add_messages
                                  │ 完整输出落盘                             ▼
                                  ▼                              [ContextDietShellWindowProcessor]
                  <agent 工作区>/context_diet/<session>/…      [ContextDietReadWindowProcessor]
                                                                   旧结果 → 一行摘要
                                                                   + [[OFFLOAD: handle, path]]
```

### 2.1 入库裁剪 —— `ContextDietTrimRail`

* 挂钩 `after_tool_call`。agent-core 允许 Rail 改写 `ctx.inputs.tool_msg`（真正进入上下文的 `ToolMessage`）；UI 事件流与其他 Rail（执行纪律、完成度）使用的结构化 `tool_result` 不受影响。
* Shell（`bash`）：输出超过 `bash_max_lines` **或** `bash_max_chars` 时，保留前 `bash_head_lines` 行、后 `bash_tail_lines` 行（`Exit Code` 在这里），以及中间最多 `max_signal_lines` 条「信号行」（带原始行号）。信号行分两轮挑选：先取**强**信号（error / fail / traceback / exception / assert / panic / fatal / denied / not found、pytest 的 `E    ` 行、回溯帧、非零退出码），再用剩余名额取**弱**信号（warning / note / deprecated / skipped），因此 300 条 warning 挤不掉 3 条 error，`PASSED` 行根本不算信号；强信号超出名额时标记行会写明落盘文件里还有多少条失败。其余替换为一行标记，写明省略行数与落盘路径。行数少但单行极长（压缩后的 JSON 等）则逐行截断。
* 打印文件内容或差异的 shell 命令（**源码打印**）按 `read_file` 对待，保持完整：`cat 文件`、`head`/`tail 文件`、`sed -n '1,60p' 文件`、按 NR 取行的 `awk`、`git diff` / `git show` / `git log -p` / `git blame`、`diff a b`、上下文不少于 5 行的 `grep`/`rg`，以及打印 `inspect.getsource(...)` 的 Python。判断是纯词法的（`context_diet/source_print.py`）：管道必须以这类查看命令开头，且后续各段只截取行区间（`| head`、`| sed -n 'N,Mp'`），因此 `cat x | grep y` 仍按普通输出裁剪。同一条命令里还运行测试或构建（`pytest`、`python -m pytest`、`npm test`、`make`、`go test` 等）时不豁免，因为测试日志正是裁剪的对象。日志与临时文件不算源码：同一命令中先写入再查看的文件（`pytest > /tmp/out.log; sed -n '1,40p' /tmp/out.log`）、`/tmp` 下的路径、`*.log`，以及瘦身自己的落盘文件。超过 `source_print_max_lines`（默认 2,000）行时保留前若干行并落盘其余部分；含有超过 2,000 字符单行的源码打印（压缩代码、单行 JSON）按普通 shell 输出逐行截断。`trim.exempt_source_prints: false` 恢复旧行为。
* `grep` / `glob`：超过 `grep_max_lines` 行 → 保留前 `grep_head_lines` 行 + 计数 + 落盘路径。
* `read_file`（可选，`read_file_max_lines > 0`）：超过上限 → 保留前 N 行并提示 `read_file(offset=N)` 续读；模型自己指定了 `limit` 的读取不做处理；不落盘（文件本来就在磁盘上）。
* 落盘目录：`<agent 工作区>/context_diet/<session>/<tool>_<call id>.txt`，或 `trim.spill_dir`。agent 工作区取自 cwd ContextVar 的 `get_workspace()`（默认 `~/.jiuwenswarm/agent/workspace`，随 `JIUWENSWARM_DATA_DIR` 移动），它是 Code 模式文件沙箱（`restrict_to_sandbox`）允许的三个根目录之一，所以标记行里的 `read_file` / `grep` 提示能真正读回全文；若 agent 工作区恰好等于项目根或 shell cwd，则改用共享 agent 工作区目录——绝不写入项目目录。每个会话目录受 `trim.spill_max_bytes` 限制（默认 50 MB），超出先删最旧文件，刚写入的文件总是保留。
* 纯函数位于 `jiuwenswarm/agents/harness/code/context_diet/trim.py`，只处理字符串与 dict，可离线回放到已记录的 transcript 上估算收益。

### 2.2 轮中压缩 —— 窗口处理器

* agent-core `ToolResultWindowProcessor` 的两个子类，通过 `ContextEngine.register_processor()` 注册，由适配层（`_build_context_processor_rail`）追加到 Code 配置的 `ContextProcessorRail`；预置压缩器链不变。
* 当受管工具的结果超过 `keep_last_k` 条时，最旧的被改写：小于 `min_offload_chars` 的直接改为一行摘要；更大的通过 agent-core 的卸载存储（会话 `offload/` 目录，无工作区时为内存）落盘，并替换为摘要 + `[[OFFLOAD: handle=…, type=…, path=…]]` 句柄。已有的「Context Compression and Recovery」提示段告诉模型如何按句柄重载。
* 摘要格式（`summarize_tool_result`）：`bash \`pytest -q\` → exit 1; FAILED tests/test_x.py::test_y`、`grep /def foo/ src → 12 lines`、`read_file src/app.py (L1–L400)`。
* `edit_file` / `write_file` 不在 `tool_names` 中，编辑历史原样保留。
* `compaction.exempt_source_prints` 开启时（默认），shell 源码打印（见 §2.1）不进入 shell 窗口，与 `read_file` 默认 `read_keep_last_k: 0` 一致。

### 2.3 提示去重

用 `context_engine_config.enable_context_debug: true` 抓取真实系统提示（`context_debug/llm_request.jsonl`）并按标题切分：没有任何 60 字符以上的句子重复出现，但有三处 JiuwenSwarm 段落复述了模型已经收到的工具描述——todo 数量规则（`todo_create` 自带）、「工作目录在命令间保持」（`bash` 描述自带）、委派规则段落（agent-core 的 *When to delegate* 段与 `subagent_spawn` 描述自带）。已删除。

| Code 模式首次模型调用（本分支实测） | 之前 | 之后 |
|---|---|---|
| 系统提示 | 37,568 字符 ≈ 10.7k token | 36,921 字符 ≈ 10.5k token |
| 工具 schema（21 个工具） | 46,779 字符 ≈ 13.4k token | 不变 |

剩余固定成本主要在 agent-core 拥有的文本中，见 §6 的建议：仅 `task_tool` 的 schema 就有 8,751 字符（其中描述 7,341，逐条列出 Playwright 能力），`bash` 7,651（描述 4,826），渐进式工具三段提示 3,743。度量方法：同一份首次调用 dump 中 `tools` 数组各条目的 JSON 序列化长度与其 description 字段长度；提示段按标题到下一标题计。

## 3. 配置参考

所有键位于 `modes.code.context_diet`。`preset` 选择一组命名默认值；在 `trim` / `compaction` 下显式写出的键优先于预设；缺省键取预设值，越界值会被夹到合法范围。随包模板只写 `preset`、开关与落盘设置，其余可调项以注释列出，因此切换预设只需改一行。

| 键 | `default` 预设 | `aggressive` 预设 | 含义 |
|---|---|---|---|
| `preset` | `default` | — | `default`（交互与无头均推荐）或 `aggressive`（实验性、需手动开启；重复读取约翻倍，但每次调用的输入更少，见 §3.1）；未知值回退为 `default`。 |
| `trim.enabled` | `true` | `true` | 挂载裁剪 Rail；`false` = 工具结果原样入库（引入前行为）。 |
| `trim.bash_max_lines` | `45` | `30` | shell 输出超过该行数触发裁剪（最小 20）。 |
| `trim.bash_max_chars` | `2500` | `1800` | 或超过该字符数（最小 1000）。 |
| `trim.bash_head_lines` | `20` | `15` | 保留开头行数（最小 5）。 |
| `trim.bash_tail_lines` | `15` | `12` | 保留结尾行数（最小 5），退出码在此。 |
| `trim.keep_signal_lines` | `true` | `true` | 保留中间的失败信号行，强信号（error / fail / traceback / assert…）优先。 |
| `trim.max_signal_lines` | `25` | `20` | 信号行保留上限。 |
| `trim.grep_max_lines` | `40` | `30` | grep / glob 结果超过该行数时截断…… |
| `trim.grep_head_lines` | `30` | `25` | ……到这么多行。 |
| `trim.read_file_max_lines` | `0` | `250` | `0` = 不裁剪读取结果。 |
| `trim.exempt_source_prints` | `true` | `true` | 打印文件内容或差异的 shell 命令按文件读取对待，保持完整（§2.1）。`false` = 旧行为。 |
| `trim.source_print_max_lines` | `2000` | `2000` | 上述输出的安全上限：超过则保留前若干行、其余落盘。`0` = 从不裁剪。 |
| `trim.spill_dir` | `""` | `""` | 完整输出落盘目录；空 = `<agent workspace>/context_diet/<session>`（沙箱内、项目外）。 |
| `trim.spill_max_bytes` | `52428800` | `52428800` | 每会话落盘上限（50 MB），超出删最旧文件；`0` = 不限。 |
| `compaction.enabled` | `true` | `true` | 注册窗口处理器。 |
| `compaction.shell_keep_last_k` | `4` | `3` | 保留最近 N 条 bash / grep / glob 原文；`0` = 关闭。 |
| `compaction.read_keep_last_k` | `0` | `6` | `read_file` 的同类窗口；`0` = 关闭。 |
| `compaction.min_offload_chars` | `800` | `600` | 更小的旧结果就地摘要，不写卸载文件。 |
| `compaction.summary_chars` | `240` | `240` | 摘要行最大长度（80–2000）。 |
| `compaction.exempt_source_prints` | `true` | `true` | shell 源码打印不进入 shell 窗口。`false` = 旧行为。 |

若裁剪后的文本不比原文短（标记与落盘路径可能比删掉的几行还长），本次裁剪会被放弃，结果原样入库，Rail 以 DEBUG 级别记录 `[ContextDiet] <tool> result kept whole: skipped=trim_not_shorter`。

`default` 不裁剪 `read_file` 的原因：模型刚读的文件通常就是下一步要改的，缩短或摘要后可能改变它生成的 `old_string`。首个版本假设 shell 与搜索输出只是观察结果、不是编辑依据。对 shell 来说这并不成立：2026-10-02 的评测中，default 预设裁剪的 79 条 shell 结果里有 35 条来自打印文件内容或差异的命令（`sed -n`、`cat`、`tail 文件`、`git diff`、`inspect.getsource`、`grep -A 30`）。这类输出现在按文件读取保持完整（§2.1）；测试日志、构建输出与普通搜索仍会裁剪，完整文本随时可以再读。

### 3.1 默认值的依据

首个版本使用 shell 120 行 / 6000 字符、grep 150 行。在第 1 波 SWE-bench Pro A/B 评测（10 题，deepseek-flash）中，这组阈值在 475 次工具调用里只触发 13 次：几乎所有结果都低于阈值。`default` 预设按该次评测 base 臂的真实工具结果拟合：

| 工具 | 结果数 | 字符 p50 / p75 / p90 / 最大 | 行数 p50 / p75 / p90 / 最大 |
|---|---|---|---|
| `bash` | 156 | 1,419 / 3,349 / 5,786 / 25,364 | 26 / 60 / 119 / 407 |
| `grep` | 32 | 2,138 / 4,564 / 6,650 / 25,306 | 15 / 75 / 123 / 263 |
| `read_file` | 101 | 4,450 / 10,766 / 31,772 / 60,000 | 80 / 228 / 621 / 1,372 |

用同一批结果回放裁剪器：

| 设置 | `bash` 被裁 / 省字符 | `grep` 被裁 / 省字符 | `read_file` 被裁 / 省字符 |
|---|---|---|---|
| 首个版本（120 / 6000 / 150） | 156 中 16 / 16% | 32 中 3 / 23% | 101 中 0 / 0% |
| `default` 预设 | 156 中 57 / 37% | 32 中 11 / 62% | 101 中 0 / 0% |
| `aggressive` 预设 | 156 中 75 / 44% | 32 中 13 / 66% | 101 中 10 / 18% |

`read_file` 结果体量最大（该臂共 106 万字符，bash 为 42 万），因此无头预设会裁剪它；交互使用保持完整。压缩窗口从 8 降到 4，因为典型任务约 16 次 shell 调用，窗口 8 很少生效。

无头 / 评测配置（harness 一个 `--set` 即可）：

**首次评测（2026-09-28），已被下方复测取代。** 20 题 SWE-bench Pro（deepseek-flash、门控开、密闭评测）中，使用 `aggressive` 预设的一臂重复读取文件是两次相同基线运行的 1.7–2.3 倍（267 次 vs 116 次与 150 次；重复读取占比 71% vs 58–62%），read_file 调用由 201–242 增至 376。基线重复运行表明，20 题规模下总 token 与续跑上限命中次数在相同配置间波动很大，无法把 token 变化归因于该预设；而重复读取的增幅明显超出这一波动。原因是 read_file 窗口：较早的读取结果被折叠为一行摘要后，模型会再次读取，额外读取又触发门控的探索上限；read_file 裁剪本身只触发 13 次。该预设保留用于实验；推荐（包括无头评测）使用 `default`（不动 read_file，只对 shell/grep 开窗口）。

**注意（真实形态复核，2026-09-29）：** 上述评测所用实现有缺陷。agent-core 以模型原始 JSON 字符串传递工具参数，而裁剪 Rail 只在参数为 dict 时才读取，因此显式要求超过 250 行窗口的 `read_file` 仍被裁剪，重读提示也丢失了文件路径。每臂受影响的此类读取为 7–26 次，很可能贡献了部分实测的重复读取。缺陷已修复，并已重新评测。

**修复后复测（2026-09-30）。** 相同 20 题、deepseek-flash、门控开、密闭评测，对照同一天、同一镜像的基线：

* 共有 31 次显式要求超过 250 行窗口的 `read_file`，没有一次被裁剪，修复在真实运行中有效。
* 重复读取仍明显增加：318 次 vs 147 次（占比 74% vs 57%）。首次评测的这一部分结论成立。
* 每次模型调用的输入下降：逐题配对 0.78 倍（95% 置信区间 0.70–0.87），20 题中 18 题更低。
* 净 token 没有增加：逐题配对 0.91 倍（置信区间 0.71–1.15），总量 0.79 倍；费用 $6.73 vs $8.51。解决 14 vs 13 题，基线解决的题目没有丢失。20 题规模下这些差异都在噪声范围内。

因此在本评测中该预设并无害处：它以更多的重复读取换取更小的单次调用上下文，净效果不差于 `default`，可能更省。它仍为实验性、需手动开启，默认仍为 `default`；是否作为无头默认值需要更大规模的评测。

以下配置为实验性、需手动开启（见上方复测）：

```yaml
modes:
  code:
    context_diet:
      preset: aggressive
```

完全关闭（A/B 的 off 臂）：

```yaml
modes:
  code:
    context_diet:
      trim: {enabled: false}
      compaction: {enabled: false}
```

## 4. 如何确认它在工作

* AgentServer 启动日志：
  * `[JiuwenSwarmCodeAdapter] ContextDietTrimRail create success (preset=default bash_max_lines=45 …)` 或 `… disabled by modes.code.context_diet.trim.enabled`
  * `[JiuwenSwarmCodeAdapter] context-diet compaction processors added: ContextDietShellWindowProcessor(keep_last_k=4, tools=[…])`（`aggressive` 预设下为 `keep_last_k=3`），随后 agent-core 打印 `context processors initialized: … ContextDietShellWindowProcessor=…`
* 每次保留源码打印：`[ContextDiet] kept bash source print whole (sed -n, 61 lines)`。
* 每次改写：`[ContextDiet] trimmed bash 18342→2210 chars (omitted 402 lines, kept 3 signal lines, spill=~/.jiuwenswarm/agent/workspace/context_diet/<session>/bash_call_3.txt)`
* transcript 中模型看到以 `[context-diet]` 开头的行；被改写的 `ToolMessage.metadata` 带 `context_diet: {kind, original_chars, trimmed_chars, omitted_lines, kept_signal_lines, spill_path}`，被压缩的消息带 `context_diet_summary`。
* `context.usage` 事件的 `parts.messages.tokens` 相应下降。
* 落盘文件：`ls ~/.jiuwenswarm/agent/workspace/context_diet/<session>/`；让 agent `read_file` 其中一个即可确认沙箱放行。

## 5. 限制

* 裁剪发生在工具执行之后：工具本身的耗时与磁盘写入不变，只有模型看到的文本变小。
* 信号行正则是启发式（英文测试框架与编译器词汇 + pytest 的 `E    ` 行）；措辞不同的失败可能落在省略段，但仍在落盘文件里，且结尾通常带汇总行。强信号多于 `max_signal_lines` 时标记行会说明。
* 源码打印的判断是词法层面的：通过变量、`$(…)` 循环、`xargs cat`、`find -exec cat` 或脚本查看文件时识别不到；项目内普通命名的日志（如 `out.txt`）会被当作文件。同时查看文件和运行测试的命令按测试运行裁剪。在评测记录上，它准确识别了 79 条被裁剪 shell 结果中人工标注的全部 35 条源码打印，没有误判；在 25 组运行的 8,569 条不同 shell 命令中，有 13%（1,156 条）被识别为源码打印。
* 压缩摘要是抽取式而非模型生成，便宜但简短；需要时按 `[[OFFLOAD]]` 句柄重载全文。
* 两个窗口按工具组全局计数而非按文件：`read_keep_last_k: 6`（`aggressive` 预设） 时第 13 次读取会挤掉最旧的一条，即便那是正在编辑的文件。交互式使用建议保持关闭或设大。
* 落盘文件以明文保存完整命令输出（包括环境变量转储）。它们位于用户数据目录下，按会话受 `trim.spill_max_bytes` 限制；没有按时间的过期清理。

## 6. 给 agent-core 的建议（不在本次改动内）
