# SpreadsheetBench Verified 13-1：耗时波动与重复测试

**额外脚本由执行 Agent 自行生成，未收到看护纠错或打断。它声称测试新增数据，实际只复制原输入再检查一次。已加入明确的最终提交工具，但整题执行仍未证明稳定。**

## 为什么追加脚本

原题明确提到今后会新增带标题的数据区，因此测试新增输入有任务依据。但上一轮全双工产物 `test_solution.py` 只执行 `shutil.copy2`、重新处理原输入，再检查固定行的汇总、排序和公式；没有插入任何新数据。失败分支只打印错误，仍退出 0，不能可靠报告失败。

该轮两边看护发送消息和打断均为 0。框架等待模型自行结束，模型说“已经完成”后仍可继续调用工具，因而没有阻止无效重复检查。生成这段脚本的一次模型请求耗时 116.0 秒；不能把这 116 秒算成脚本执行时间。

## 为什么同模型同题仍差很多

- 上轮第一轮就分叉：普通组输出 68 token 做文件检查，全双工组输出约 850 token 写较长检查脚本。此后历史记录已不同，后续请求也不再相同。
- 上轮执行模型累计用时 264.1 / 595.4 秒，输出 5,727 / 8,437 token；Bash 仅 5.2 / 4.5 秒。主要差额发生在模型请求内，包含生成与服务等待。
- 本次两策略初始请求捕获仅发现 SDK 的随机 `context_message_id` 不同。SDK 转成 API 消息时丢弃该元数据；提示、工具、模型参数一致。已修正语义指纹，保留原始指纹用于诊断。
- 本次真实收尾短测，两边初始语义 SHA256 同为 `bd183ada61358b4caaed0eff5111418bbbed15b11f0091a7570a9f0e58039dd4`，第一步仍分别选择 `cat task.txt` 和 `ls -la`。同输入、temperature=0 不能保证该在线模型服务每次复现；具体服务端原因没有证据判定。
- 旧流程还将剩余秒数写入工具反馈。即使动作相同，服务耗时不同也会改变下一轮提示，进一步放大差异；现已移除，只保留调用次数预算。

指纹取自 SDK 模型调用边界，并采用 SDK 的消息与工具转换，不代表捕获了最终 HTTP 字节。首块/首次内容延迟也不等于纯排队时间。

## 已改什么

普通和全双工共用相同改动：

1. `VerifyAndFinish` 将最终检查和提交合并。要求产物已保存、检查退出 0、检查前后产物版本不变，接受后由 SDK 结束本轮，无需再请求模型写结束语。
2. 缺产物、检查失败、检查期间改动产物时拒绝提交，允许修复后重试。正在进行的看护复核仍会处理，后到纠错可开启新一轮。
3. 提示合并必要检查、真正修改测试输入、使用断言，避免无改动的重复自检；记录请求指纹和首次输出延迟。

**工具只能执行提交约定，不能判断模型写的检查是否充分，也没有读取隐藏答案。模型仍可能迟迟不用它，或自行给出不充分的检查。**
