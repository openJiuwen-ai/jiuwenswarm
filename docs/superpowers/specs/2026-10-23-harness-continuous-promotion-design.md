# Harness 连续评分与复评晋级修改方案

> 历史方案：评分晋级规则已由用户提供的 [Harness 两项修改说明](../../zh/Harness两项修改说明.md) 替代。当前采用逐目标首评 + 一次全量重跑，不再采用下文的额外确认轮、全量首次提升 0.05 或历史高分作为下一轮基线的规则。其余内容仅供追溯，不作为当前实现规范。

日期：2026-10-23。状态：用户已要求实施两项核心修改，代码已落盘并完成一次独立只读审阅；未运行测试、构建或真实模型验证。可选的 Behavior Check unknown 降级未实施，行为证据检查继续保留，连续分模式下数值门槛改用分数提升。

参考现状：[Harness 晋级评分现状](../../zh/Harness晋级评分现状.md)。

## 1. 用户要求与本方案的设计选择

用户要求（按最新澄清）：改用连续分；第一次提升必须超过 0.05；同一候选后续复评时，分数严格大于其冻结基线即可保留。此前提出的“允许低于基线 0.05”规则取消。

用户补充要求：候选的 LLM Judge 必须看到同题基线的实际产物与评分，以便对照同一 rubric 评分。此要求同时适用于候选目标预检、全量首评与后续确认/复评。

这里的 0.05 定义为 0..1 分数上的固定绝对分差，即 5 个百分点，不是从重复实验计算出来的样本标准差，也不意味着某种统计置信度。

为形成可实施方案，以下是本方案推荐、尚待用户确认的设计选择：

1. 正式晋级按完整候选包逐个决策。每个候选从当前正式 Best 生成，完成目标预检、全量首评和一次全量确认后，即更新 Best 或回退；Epoch 保留为预算与调度层。这会替换现有的 Epoch 末筛选、删除修改、重组包再评估的晋级路径。
2. “比较基线”指生成候选时，父版本 Best 已记录的正式比较分；任务最初的 H0 另行保存，不把所有未来候选都与最初 H0 比较。
3. 正式晋级的 0.05 作用于同一全量题集的平均分；目标题的 0.05 只用于局部预检，不替代全量判定。
4. 同一候选的复评分必须严格大于其冻结比较基线；等于或低于基线均不保留。不设置允许退步的复评容差。
5. 首次全量显著提升后，默认追加一次真正重新运行 Solver 和 Judge 的全量确认。确认次数固定为一次，失败后不自动反复重抽。
6. 额外的流程简化建议：Behavior Check 的模型归因和 unknown 改作诊断，不单独否决分数达标的候选，机器验证条件继续保留。这是对现有验收流程的调整，不是连续计分必然要求，需随本方案确认。

保留原 Epoch 筛选流程、只替换评分也是可选路线，但需要同时维护局部历史凭证、累计包凭证、删改后的新包凭证。结合当前重复评估与重组失效的问题，推荐本方案的整包决策路线。

## 2. 连续评分协议

### 2.1 单题分

LLM Judge 已有可信 rubric 权重汇总出的连续总分。新模式中直接写为 case.score，不再先按 0.8 转换成 0/1：

```text
case.score = rubric_continuous_score
case.passed = case.score >= judge_success_score
```

保留 passed 作为“达标情况”的展示和诊断字段。passed 不再决定正式评分、局部改善或是否允许晋级；0.79→0.81 不因越过 0.8 得到额外奖励，0.95→0.81 也会真实显示退步。

连续总分继续由程序依据 rubric 汇总，沿用可信权重与扣分逻辑，不能改成直接相信模型随口给出的总分。

其他 judger/backend 必须声明其 score 的取值和来源：有原生归一化连续分就使用；只有确定性通过/失败的 judger 可以继续贡献 0/1，但元数据标明 binary。不能因为 metadata 里存在某个数字就自动当作可信连续分。

### 2.2 局部和全量分

```text
target_score = mean(本候选固定目标集合的 case.score)
full_score   = mean(本任务固定全量集合的 case.score)
```

本版继续题间等权；题内 rubric 权重照旧。一个集合中全部题必须齐全且有效，不能忽略缺失题再求平均。

例如五题中仅一题提高 0.20，其余不变，全量平均只提高 0.04，因此不满足全量超过 0.05 的晋级规则。局部成功与全量显著提升是两个不同结论。

所有正式判定使用未作展示舍入的分数。浮点比较统一使用 epsilon=1e-9：首次增量须大于 threshold+epsilon；复评增量须大于 epsilon，数值误差范围内视为相等，不能晋级。前端展示小数不能参与判定。

### 2.3 有效低分与无效评估

- 答错、遗漏交付、可判定的未完成：按 rubric 得到真实的低分或 0，参与评分。
- Solver 耗尽步数但留有可供 Judge 判定的产物：允许按实际产物评分，同时记录 budget_exhausted。
- Judge 请求失败、Judge 结果无法解析、评分缺失、执行基础设施故障、题集缺失或 skip：评估无效，不能凭历史高分放行，也不能伪装成正常 0 分。

本方案不扩大既有基础设施重试预算。已有有界重试结束仍无效时，本候选停止晋级，保留上一正式 Best 并记录原因。

### 2.4 给候选 Judge 提供基线产物与评分

当前 `LlmAsJudgeJudger.judge()` 调用 `prepare_judge_workspace()`，只复制本次产物、回答、执行证据与 reference；`request.json` 没有基线产物或历史评分字段。需要扩展真实输入链路，不能只在 prompt 里要求“参考基线”，却没有提供证据。

**基线选择。** 每道候选题匹配同一 case、任务输入、rubric 和评分模型配置的父版本基线评估。使用产生该候选冻结比较分 B 的同一份全量评估，取其中这道题的产物和连续分；不能给单题 Judge 填入全量平均分，也不能换成父版本最新一次更低的复评分。候选首次评分和复评使用同一个冻结基线证据引用。

**提供内容。** 请求中直接包含同题基线连续总分、逐 rubric 项得分/扣分、理由与证据引用，以及来源版本、case_id 和 eval_ref。还要提供基线最终回答、实际交付文件、必要的执行证据；不能只给一个历史分数或无法访问的原始日志路径。

建议复用当前 Judge 隔离证据机制，增加只读 `baseline/` 区域：

```text
evidence/
  request.json                   # 本次任务、rubric、候选响应、基线分与对照说明
  artifacts/                     # 本次候选实际产物
  baseline/
    assessment.json              # 同题基线连续分、逐项分、理由与证据
    response/                    # 基线最终回答，较长内容无损分页
    artifacts/                   # 基线实际产物快照
    execution_trace.json         # 有必要时提供的执行证据
    manifest.json                # 文件清单、哈希、来源与缺失状态
```

小型评分明细直接放进 `request.json`；大文件通过清单、相对路径与现有只读工具读取，基线和候选均允许无损分页。要求 Judge 按 rubric 先搜索并阅读相关产物；日志优先搜索 error、warning、budget、timeout 等相关线索及其上下文，不要求整份读完。进入内联/closeout 路径时也必须保留相同的基线资料；证据过大则使用支持读取的 Agent 路径，不能静默删掉基线内容后继续评分。

**评分方式。** Judge 按同一 rubric 给候选的实际产物逐项打绝对分，再解释相对基线新增满足了哪些要求、哪些缺陷仍存在、哪些能力退步。历史评分是对照依据，不是标准答案；不要求候选分一定高于基线，不允许直接按“基线分加若干分”代替逐项证据评分，也不把基线产物的正确内容算作候选交付。

输出保留现有 behaviors/forbidden_hits，另加结构化 `baseline_comparison`：基线来源、基线单题分、逐 rubric 项改善/不变/退步及双方证据、发现的历史评分疑点。模型不负责决定晋级；候选连续总分仍由程序依据候选各项得分与可信权重计算，程序再计算分差。

若 Judge 发现基线旧评分与其产物不一致，应记录疑点并按 rubric 评价本次产物，不能悄悄改写冻结 B。是否重建基线属于新的显式评估操作，不能在同一次候选决策中移动基准。

**首评与复评的信息边界。** 复评仍提供冻结的父版本基线产物与评分，但不提供该候选首评高分 H、晋级所需分数或待确认结论。历史提升凭证由编排程序保存和使用，避免 Judge 围绕候选旧高分维持分数；这不影响用户要求的基线对照。

**首次 H0。** 任务最初的 H0 没有更早的比较对象，按相同 rubric 独立评分，标记 `comparison_role=initial_anchor`；后续候选标记 `comparison_role=candidate` 并要求基线资料齐全。首轮本来就没有基线，不能因此形成循环依赖。

**完整性。** 基线本身确实没有交付文件时，提供真实的空清单、回答和评分，属于可用的基线证据；已知曾存在的基线文件因丢失/损坏不可读取时，属于证据缺失，不能假装成基线原本没做。后者停止候选评分并记录无效评估，不能静默降级为没有基线的单独评分。

**传递与缓存。** 从编排层建立独立 `BaselineJudgeContext`，经 TeamEvaluator、CaseRunner 传给 Judge 与证据组装层，不把历史评分写进 Solver 能看到的任务输入。LLM Judge 路径必须实际使用它；后端直接返回 JudgeResult 的路径也须显式支持此协议，否则拒绝作为该模式的候选评分来源。确定性 exact/script judger 保持自身语义，不强行增加模型比较。

提升协议标记包含 `baseline_reference_v1`。基线内容、评分明细、来源评估和协议指纹均纳入候选评估缓存身份；比较基线变了，旧候选评分不可直接复用。H0 的 initial_anchor 是明确的角色例外；候选首评和确认必须匹配同一基线上下文。每次 Judge 保存 `baseline_context.json` 与实际证据清单，保证以后能核对它究竟看到了哪份基线。

## 3. 三个分数与一个历史凭证

每个候选冻结并分别记录：

| 字段 | 含义 | 能否被较低复评分覆盖 |
| --- | --- | --- |
| comparison_baseline_score B | 候选产生时父版本的正式比较分 | 不能 |
| first_improved_score H | 本候选第一次有效全量首评分，且 H-B>0.05 | 不能 |
| latest_evaluated_score C | 本候选最近一次有效全量评估的真实分数 | 随复评更新 |
| improvement_proof | 首次显著提升的评估引用及版本、题集、协议身份 | 不能移植给其他内容 |

另存 historical_peak_score 仅用于展示历史最高分，后续随机出现的峰值不会自动抬升正式比较分。

父版本为 H0 时，B 取 H0 的有效全量基线分。父版本已晋级时，B 取父版本的 first_improved_score，而非它较低的 latest_evaluated_score。

这意味着：后续搜索的正式比较分只会上升，不会因改用较低复评分而降低下一轮提升门槛。最新实际测量值仍照实显示，绝不能以历史高分冒充最近一次表现。

凭证必须绑定：候选可执行包的规范化内容指纹、父版本身份和 B 的来源、逐题基线产物与评分上下文指纹、全量题集及其输入/参考答案/外部文件指纹、评分协议与模型配置指纹、评估范围、首评 trial_id 与 eval_ref。仅仅路径相同、候选名称相同、来自同一个提案，都不够。

## 4. 晋级规则

### 4.1 首次全量评估：建立提升凭证

```text
有效且完整的全量首评 H - B > 0.05
```

满足后进入“已观察到提升，待确认”，还没有更新正式 Best。

若没有超过，包括恰好提高 0.05，不建立凭证、不自动追加确认、不晋级。局部目标题的历史高分不能绕过这一步。

### 4.2 一次全量确认：沿用该候选冻结的 B

对同一候选原封不动重新运行全量题集，得到 C：

```text
存在匹配的 improvement_proof
且本次评估有效、完整、同题集同协议
且 C > B
```

满足后正式晋级。若 C-B 仍超过 0.05，标记“确认显著提升”；其余严格大于基线的结果标记“首次显著提升，复评仍有提升”。两者均可以作为正式 Best 和发布对象。

复评不需要再次超过 0.05，但必须有正向提升。它不能与“最新测量仍显著提升”混为一谈，也不能允许等于或低于基线的结果。

若 C<=B，则判定复评没有提升，回到上一正式 Best；若 C 无效，则判定确认不成立，保留上一正式 Best。两种情况保留历史首评凭证用于审计，但本次不能发布该候选。

### 4.3 后来再复评

同一版本后来的显式复评，继续使用该版本的冻结 B 和已有凭证，不把 B 更新为上一复评分。每个确认流程不额外无限追加复评。

若当前正式 Best 的后续有效复评等于或低于其冻结基线，则取消它作为当前可发布对象的资格，回退到最近一个已完成确认、未失效的祖先版本；没有这样的祖先时回到 H0。历史分与历史晋级事件保留，不篡改已记录的结论。

若后续复评仅因基础设施或 Judge 解析故障而无效，记录 inconclusive，保留此前已经确认的 Best 资格和最近有效实测分。没有取得有效新分数本身不证明该版本退步。它与“新候选首次确认无效、尚无资格晋级”的情况分开处理。

普通评估记录、缓存命中、一次调试 Judge 调用，不自动触发正式回退；只有带版本身份和决策用途的显式确认/复评才能改变正式状态。

### 4.4 边界举例

假设 B=0.60：

| 首次全量 H | 确认全量 C | 决策 |
| --- | --- | --- |
| 0.64 | 不执行 | 未超过 0.05，不晋级 |
| 0.65 | 不执行 | 恰好 0.05，不晋级 |
| 0.72 | 0.68 | 确认显著提升，晋级 |
| 0.72 | 0.62 | 首次显著提升，复评仍有提升，晋级 |
| 0.72 | 0.6001 | 复评严格大于基线，晋级 |
| 0.72 | 0.60 | 等于基线，不晋级 |
| 0.72 | 0.57 | 低于基线，回退 |
| 0.72 | 缺分/基础设施故障 | 确认无效，保留父版本 |

0.72 首评、0.62 确认的版本晋级后，下个候选比较基线为 0.72，必须首评超过 0.77，而非以 0.62 为基线只需超过 0.67。

若正式比较分已达到 0.95，受最高 1.0 与严格大于 0.05 的约束，已经没有可晋级空间，记录 threshold_saturated 并结束本次优化；需要继续时，用户可在新任务降低阈值。

## 5. 完整流程与评估复用

```text
冻结任务题集、评分协议、阈值与 H0
  → H0 完整连续基线评估
  → 从正式 Best 生成一个完整候选
  → 工程检查；有界 Repair
  → 目标题预检
  → 全量首评；首次提升须 > 0.05
  → 同包全量确认一次；须 > 冻结基线
  → 满足则原子更新正式 Best；否则回退
  → 从正式 Best 继续下一个候选
  → 发布最后一个具有效晋级凭证的完整包
```

### 5.1 目标预检

目标集合在候选运行前确定并冻结，不根据跑出来的高分挑题。与父版本同一目标集合比较，目标平均分提升须超过 0.05。父版本逐题基线取自其正式比较分对应的同一份全量评估，不能混用较低复评中的逐题分数。达标后才补齐全量首评；未达标仍可把有效逐要求进展用于本 Batch 的有界局部修复，但不能直接更新正式 Best。

去掉“所有原失败目标必须从 0 变 1”“之前通过过的题必须一直 passed”等二值门槛。全量采用平均分标准，因此某一题回退可能被其他题进步抵消；逐题差异必须留档并展示。本版不额外引入一个隐藏的逐题回退否决线。

这也意味着局部显著提升的方向之外，还可能存在多题各自小幅提升、整体有效的方向。当前目标预检是计算开销上的筛选，可能漏掉这种候选；需要探索此类提案时将目标集合设为全量，使用相同 0.05 总分规则，无需新增另一套晋级算法。

### 5.2 哪些题真正重跑

首轮目标结果与全量首评属于同一 evaluation trial：包、题、协议相同即可复用目标结果，全量只补缺失题。相同包的 residual_source 从这些结果派生，不再为刷新 Source 重跑同一题。

全量确认是独立 trial，明确绕过结果缓存，重新运行全部 Solver 和 Judge。它是有意采样波动的唯一默认重复。只重新 Judge 同一份答案无法测量 Solver 路径波动，不能冒充全链路确认。

有 N 道题、k 道目标的完整成功候选，默认开销为 k+(N-k)+N=2N 次 case 运行，基础设施有界重试另计。局部失败只花 k 次；全量首评未显著提升则总共 N 次，不追加确认。

### 5.3 多提案与 A+B

A 完整晋级后，B 才可以基于 A 生成，因此 A+B 必须作为新内容包完成自己的首评和确认。A 的凭证不能自动授权 A+B。

A 未晋级，下一候选从上一正式 Best 生成；局部 Repair 的临时子版本可以保留在同一有界尝试链内，但不能伪装成正式父版本。中间子版本的高分凭证不移植给最终修改后的子版本。

取消 Epoch 末按提案删文件、拼保留能力、再做 selected_full 的晋级路径。Epoch 的诊断、尝试预算和时间线可以保留，不能再同时存在另一套更新 Best 的决策。

### 5.4 哪些门槛保留

保留加载、导入、语法、Harness 协议兼容、必需机器校验、真实文件变更、有效评估、完整覆盖等工程门槛。明确承诺调用某 Tool/Skill 的变更，保留可机器核实的调用条件。

建议将 Behavior Check 的解释、unknown 和策略归因纳入诊断报告；不再仅凭一个模型说“无法确认行为改变”否决已经通过有效全量评分与确认的候选。明确的机器证据失败仍阻止工程验收。此项属于第 1 节明确列出的额外流程简化建议，不默认为用户已批准的要求。

## 6. 搜索与停止条件

修复题选择从“只找 passed=false”改为连续分缺口：优先未达满分且有可操作失败证据的题，结合逐要求证据排序。0.81 达标但有缺口的题仍可以优化。

保留已有 Epoch、Batch、每 Batch Repair 的有界预算；沿用当前 max_repair_rounds_per_batch=3 等配置。预算耗尽、没有可优化题、无新候选或 threshold_saturated 均以明确原因结束。不会因最后没有新 Best 而发布 H0 并宣称优化成功。

首次高分是一个采样观测，可能来自 Solver 波动或 Judge 误判；本规则能实现用户期望的保留政策，不能证明高分答案一定正确，也不能证明 0.05 是实测噪声幅度。本次不把 Judge rubric 结构化改造或多次统计采样强行捆绑进来。

## 7. 配置与版本兼容

建议在编排配置中增加独立 policy，避免复用当前语义不明且部分未生效的 candidate_* 参数：

```yaml
promotion:
  policy_version: continuous_margin_v1
  score_mode: continuous
  min_improvement: 0.05
  confirmation_runs: 1
```

本版 confirmation_runs 固定支持 1，保留字段用于明确运行协议，不开放任意次数；设计多次采样时另定聚合规则。min_improvement 须为 [0,1] 的有限数值，整个任务运行期间冻结，默认 0.05。复评固定要求严格高于冻结基线，不另设容差参数。

旧二值评分任务保持原 policy，只读展示与旧协议恢复不变；不在中途把旧评估改造成新分数。切换连续协议或阈值后启动新任务。缓存、状态和 checkpoint 都带 policy_version 和协议指纹，防止跨模式复用。已有连续诊断分可用于离线分析，不追认旧任务已经按新规则完成确认。

## 8. 状态、前端与发布

### 8.1 唯一决策记录

新增单一 promotion_decision，记录 candidate/parent/package 指纹、B/H/C、阈值、目标与全量范围、所有 eval_ref/trial_id、证明凭证、工程检查结果、状态与原因码。保存首评分或凭证必须先于发布决定；确认完成后以同一个原子 checkpoint 更新 decision 和正式 Best 引用。

恢复运行时：首评已落盘则不重新抽一次首评；已完成确认则不重跑确认；确认 trial 中已完成且身份匹配的题可续跑，仍属于同一次确认，不增加确认次数。进程崩溃不能制造无限次“重新确认直到高分”的机会。

建议原因码包括 first_improvement_observed、insufficient_improvement、confirmed_improvement、confirmed_positive_gain、reevaluation_not_improved、evaluation_invalid、engineering_failed、threshold_saturated。

### 8.2 展示

任务主面板显示当前正式 Best 的最近实际全量分，同时列出 H0 初始分、当前版本首次提升分、历史最高分和本版比较基线。沿用 best_score 时将其明确为最新有效实测值，增加 best_reference_score 保存正式比较分，绝不混用。

候选时间线区分：目标预检通过、全量首评显著提升、待确认、正式晋级、复评仍有提升、复评无提升回退、无效评估。局部 accepted 不再渲染成 promoted。每项都可跳到对应评估与日志。

### 8.3 发布

发布唯一依据是当前正式 Best 的已完成有效决策，并核对包内容指纹。只取得局部通过、只有首评高分、确认未完成、确认失败，都不能发布为优化成果。

发布稳定目录沿用现有 run/published/current/r<hash>/ 与 run/member_optimizations/current_harness_refs.yaml。新指针在复制并核验成功后原子替换。没有相对 H0 晋级的候选时输出 no_improvement，不发布一份 H0 并标成 optimized。

后续正式复评导致撤销当前 Best 时，把本任务发布指针回到有效祖先；回退发布失败必须显示独立失败状态。本方案保持既有显式安装/回退模式，不由实验结果自动切换运行中的服务。已安装版本若被本任务撤销，界面标明其评估已失效与可用回退版本，由已有入口执行运行时回退；后续安装请求必须拒绝已撤销的版本。不能把“实验发布指针已回退”描述成“运行中的 Harness 已经回退”。

## 10. 验收场景（计划，不代表已经执行）

1. Judge 返回 0.59，case.score 保持 0.59，passed=false；五题平均值包含全部连续分。
2. B=0.60，H=0.65 不晋级；H=0.6501 可以建立凭证。
3. B=0.60、H=0.72，C=0.62 或 0.6001 可以保留；C=0.60 或 0.57 不通过。
4. 没有首评提升凭证时，C=0.62 不能仅凭严格高于基线而晋级。
5. 单题局部高分不冒充全量凭证；五题总分仅提高 0.04 不晋级。
6. 一题跨越 passed 阈值不增加跳跃奖励，原通过题略低于 0.8 不触发旧保护集合否决。
7. A、A+B、删除 B 后的 A：按实际包内容和协议匹配；A+B 不能借用 A 凭证，相同 A 可识别其已有凭证但仍遵守确认状态。
8. 首次目标结果只在同一 trial 内补齐全量；确认使用独立 trial，真实重跑 Solver 和 Judge。
9. 首评 0.72、复评 0.62 后，下个候选使用 0.72 比较基线，不降低下一轮门槛。
10. 丢题、skip、Judge 解析失败、NaN/无穷/越界 score 不按真实 0 分或正常复评处理；正常任务失败的真实 0 分照常入均值。
11. 首评高分后断点恢复、确认途中恢复、确认落盘后恢复，不多抽首评或确认，不重复正式晋级。
12. 局部通过但全量失败、首次提升但确认失败、没有新 Best，均不误发布 H0 或失败候选。
13. 正式 Best 后续复评失败时，祖先恢复与任务发布回退一致；已安装版本独立标记失效，不能误报服务已经回退或再次安装失效版本。
14. 旧任务/旧缓存不被新 policy 混用，0.95 比较分能正确停止搜索。
15. 首次确认无效不能晋级；已经确认的 Best 后续复评仅基础设施无效时记录 inconclusive，不撤销此前有效资格。
16. 候选 Judge 的请求与只读工具确实能读到同题基线回答、产物、连续分、逐项理由；输入的是单题分，不是全量平均分。
17. 首次 H0 无比较对象仍可独立评分；后续候选缺失已存在的基线文件不得静默评分。真实空交付与文件丢失能够区分。
18. 候选复评使用同一基线快照，但请求不包含候选此前高分；内联/closeout 路径不丢失对照证据。
19. 基线评分或产物变更使缓存失效；基线证据不会出现在 Solver 的任务输入中。基线旧评分疑点被留档，冻结 B 不被模型改写。
