# 特性设计方案文档模板与维护规范

## 1. 文档作用说明

### 1.1 特性设计方案文档的作用

特性设计方案文档将一个明确的行为变更转化为可实现、可验证、可追溯的设计。它记录问题从哪里来、本次解决到哪里、方案如何工作、为什么采用该方案、为什么排除其他方案，以及设计时已知的限制与待验证前提。

读者应能通过文档回答：在什么输入、状态或用户操作下，行为将发生什么变化；哪些模块承担责任，哪些接口和数据受影响；正常与异常路径如何闭合；与既有契约如何衔接；实现需要修改哪些位置；用什么证据证明本次承诺成立。后续维护者还应能查明某个设计选择成立的前提，以及前提改变后为什么需要修订。

设计文档是开发前的设计资产；features 是开发落地后实施与决策归档。设计变更返回设计阶段确认，开发事实始终保存在 features。设计意图、已实现行为和实际验证结果须分别写明，不能用“方案已确认”“代码已合并”代替实现或验收结论。

### 1.2 阅读对象与使用场景

- **设计与评审人员：** 核对问题、范围、责任边界、方案取舍及与架构和已有契约的关系。
- **开发与协作人员：** 查明接口、状态、执行步骤、源码修改点和适用的迁移要求，依据明确的交接边界开展实现。
- **测试与维护人员：** 查找场景、复现入口、实际结果和已知限制，判断变更是否覆盖承诺范围，并追溯后续修订的原因。

适用于新功能、连贯的重构、接口或状态语义调整，以及需要保留设计依据的行为修复。一次连贯的设计变更通常维护一份文档，可以覆盖多个实现步骤或多个提交；是否需要拆成独立特性，以责任、行为和验收边界为依据。

### 1.3 本文的使用目的

本文提供设计写作与维护指导，覆盖问题与目标、设计前提、总体方案与取舍、详细设计、实施影响、验证方案和设计限制；开发归档的指导仍保留，并注明其维护位置。复杂方案按实际变更展开接口、配置、数据、状态、并发、恢复、算法或资源等设计内容。

设计方案应保留 **why / why-not**：既说明选择，也说明选择的依据与被排除方案的代价。本模板同时规定编号、验证和历史修订的一致性检查，避免编号碰撞、验证计划与结果混写，以及失效结论继续被当作当前规则。

本文提供通用模板和维护规范，不编制具体特性的方案、目录索引或进度台账。第 2 节说明统一模板的用法，第 3 节规定填写与维护口径；实际使用时以所属目录的 `AGENTS.md` 和已确认的架构、spec 为准。

## 2. 模板

### 2.1 使用方法

复制 [design.md](../assets/templates/design.md)，替换 `〈占位内容〉`，删除填写提示及不适用的扩展小节。实际文档标题写成“〈特性名称〉设计方案”；已有模块采用其他标题形式时沿用其约定。不将本文的作用说明和维护规范复制为具体方案正文。

先明确问题、目标和本次边界，再核对约束与假设，填写方案及取舍，随后列出实施影响与验证设计。开发前写清预期行为、验证方案与通过条件，不预置执行结果。开发后的实际决策、偏差、执行证据和交付结论由 jw-dev 归档至 features。

特性设计文档必须做到**内容合理、逻辑层次清晰、图文并茂、表述易于理解**。填写及修订均按“编写质量与图表规范”落实这四项要求，交付前按“维护后的一致性检查”核对。

所有占位值都是填写提示，不代表已确认需求、真实接口或通过结论。未知项写明“待确认：问题、责任方、影响”；不适用项说明原因。相对链接以实际特性文档所在目录为基准，不直接沿用模板目录的路径，也不链接尚不存在的文件。

需要交叉引用时，建议将设计决策编号为 `D-01`，候选方案编号为 `R-01`，验证场景使用所属特性前缀，例如 `〈F-ID〉-V-01`。已有 spec 或开发计划定义不变量、验收 ID 时直接沿用，不再分配同义编号，也不要求为每个段落编号。章节引用优先使用名称；删除或合并可选内容后可整理章节序号，并核对所有引用。

### 2.2 结构选择与按需扩展

使用同一份模板，按下表选择展开程度。基础内容均须回答对应问题，简单特性可以简写；“关键决策”“替代方案与排除理由”“验证通过条件”“已知设计限制”保留明确入口，不另建一套基础版或扩展版正文。

| 主体章节 | 要回答的问题 | 填写口径 |
| --- | --- | --- |
| 管理字段 | 这是什么设计、谁负责、是否确认？ | frontmatter 为唯一来源；负责人、状态、日期保留在设计中，有计划时链接计划条目 |
| 背景、目标与范围 | 为什么改，行为将怎样变化？ | 基础；说明问题、关键场景、目标及本次边界 |
| 设计约束、假设与待决问题 | 哪些条件已确认，哪些前提或选择仍需核实？ | 基础；集中维护本次相关前提，无未决项时简述核对结论 |
| 总体方案与设计取舍 | 核心机制是什么，为什么这样选？ | 基础；概览、关键决策及真实候选的排除理由 |
| 详细设计 | 各模块怎样实现承诺的行为？ | 基础；责任、关键保证和执行流程须明确；涉及关键类、函数或接口时给出定义与说明，其他小节按涉及程度选择 |
| 影响面与实施设计 | 修改哪里，怎样接入并独立验证？ | 基础；实施影响、必要顺序及文档同步 |
| 兼容与迁移 | 旧调用、数据和会话怎样处理？ | 按需；有影响时展开，无影响时在实施影响中保留核对结论 |
| 验证设计与通过条件 | 开发后怎样证明方案成立？ | 设计保留场景、准备和预期；实际执行、结果和结论写入 features |
| 设计风险与已知限制 | 有哪些不确定前提或已确认的设计限制？ | 无则说明；开发后发现的缺口和遗留记录在 features |
| 日期评审与设计修订 | 何时讨论、确认或修改了方案？ | 按实际日期记录，不使用递增评审版本；实施经过记录在 features |

可选内容按三种情况处理：**涉及且本次改变**，展开设计；**涉及但沿用已有机制**，简述沿用内容及核对结论；**不涉及**，删除可选小节。基础章节内无假设、待决问题或遗留时据实说明，不虚构条目。表格适合字段、状态转移和比较；复杂流程、决策及异常处理优先使用短段落或列表，删除不需要的示意表。

按行为选择扩展内容，不为套用模板创造新机制：

| 触发条件 | 应展开的设计内容 |
| --- | --- |
| 新增或调整核心类、关键函数或扩展接口 | 类的职责、继承或组合关系、关键属性与方法；函数完整签名、参数、返回值、异常及副作用；接口定义、实现方与调用约束 |
| 公共 API、工具、消息或事件变化 | 签名或 Schema、参数与默认值、互斥条件、错误语义、身份和关联字段、消费者及兼容策略 |
| 状态或生命周期变化 | 状态定义、转移条件与主体、持久化位置、事件顺序、重复操作及清理语义 |
| 异步、并发或跨进程交接 | 排队与消费方式、锁或 CAS 边界、提交与通知顺序、竞态窗口、取消后后台执行及资源收尾 |
| 持久化、缓存或恢复变化 | 事实权威、命中条件、读写顺序、原子性、崩溃窗口、恢复粒度及旧数据处理 |
| 外部 SDK 或平台适配 | 核实的版本与能力、映射规则、可选依赖、真实对端验证和已确认限制 |
| 身份、授权或敏感数据处理变化 | 可信身份来源、授权范围及校验时机、撤权与未知结果处理、路径与会话隔离、脱敏和失败关闭边界 |
| 跨仓或宿主接入 | 两侧职责与契约、已有组件映射、配置与端口注入、接入顺序、示例状态、组件验证与真实联调边界 |
| 配置、装配或提示词变化 | 配置入口、优先级、能力门控、生效时机、序列化与恢复、不同消费路径及多语言一致性 |
| 判定、路由、排序、配额或缓存规则变化 | 输入输出、规则顺序、冲突与兜底、边界值；必要时使用伪代码或真值表 |
| 文件、目录、连接或后台资源的生命周期变化 | 创建、持有与释放主体、命名或路径派生、隔离、保留与清理条件 |
| 页面或用户交互变化 | 页面入口、触发操作、加载与异常状态、接口协作、可观察结果及适用的真实联调 |
| 观测、性能或资源限制变化 | 事件或指标归属、计量口径、开销与阈值、超限行为、隔离及实测条件 |

无需前端的基础能力不强行增加页面；无需恢复承诺的简单行为不强行设计检查点。对尚未支持的能力明确拒绝或限制，不用空方法、占位成功或不可验证的扩展承诺掩盖边界。

### 2.3 可复制的模板

模板正文按问题、方案、详细设计、实施影响、验证设计、风险、日期评审与交接组织。可选小节按实际变更选择；实际执行、证据和实施决策归档交给 features。

各章填写后应形成可理解的设计叙述，不能只保留问题清单、空表或图。围绕核心方案选用架构图、流程图、状态图和时序图，具体适用条件见“图型选择与图文表达”；图表放在对应叙述附近，并解释重要关系及条件。

> 唯一可复制模板见 [design.md](../assets/templates/design.md)。该模板整合了设计管理字段、详细设计骨架和按日期评审记录；本 reference 只维护使用与写作指导。


## 3. 维护规范

本部分使用章节名称指代“可复制的模板”中的具体方案内容，不使用本文的外层章节编号。删除或合并可选内容后，保持章节职责和稳定 ID 的引用一致。

### 3.1 内容归属与唯一维护位置

| 文档 | 主责内容 | 引用方式 |
| --- | --- | --- |
| Overview / 架构 | 整体目标、职责、边界与跨模块约束 | 设计引用背景与约束，不重复完整架构 |
| designs | 开发前方案、备选取舍、验证设计、评审和设计管理字段 | 作为开发依据；开发后归档引用稳定设计标识 |
| specs | 当前有效且可核验的契约 | 设计说明拟变更点；定稿后由开发阶段同步 spec |
| features | 开发落地后实施、实际决策、偏差、验证证据与遗留 | 引用设计和 spec，不复制整篇设计，不反向回填开发事实到设计 |
| 开发计划 | 工作拆分、依赖、执行顺序与交付安排 | 引用设计负责人及状态；执行任务分工与设计负责人区分语义 |

负责人、设计状态、创建 / 更新 / 批准日期等管理字段保留在设计 frontmatter，其他文档链接该处，
不因存在独立计划而移除。设计状态不代表测试通过或实际交付结论。
接口 Schema、数据结构及关键算法可在方案中定义目标行为；已有 spec 时引用其定义，说明拟变更及依据。
设计中的验证方案定义场景与通过条件；features 记录实际验证，两者通过相同场景标识关联。

### 3.2 建档、命名与元信息

1. **按需在开发前建档。** 先阅读相关架构、spec、既有 feature 及模块约定，核对设计前提和既有取舍；按所属目录规则需要方案时，确定范围后建立或更新对应方案，再开展代码开发。
2. **以连贯方案为设计单位。** 独立行为和验收范围可拆成独立设计，通过关系链接说明前置、延续或替代。实施、接线、实际测试及开发决策集中到关联 features，不复制为第二份设计。
3. **遵循本目录命名。** 设计阶段新文档使用 `designs/proposals/D-YYYYMMDD-HHMM-<slug>/design.md`；开发阶段归档使用 `features/<module>/F_YYYYMMDD_HHMM_<slug>.md`。时间为 Asia/Singapore、精确到分钟；完整标识创建后保持稳定。
4. **防止覆盖。** 不再分配递增号或预留号。同一分钟通过主题区分；完整名称重名先确认是否续写同一文档，否则细化主题。已有文档不改名，引用完整标识或链接。
5. **日期含义保持明确。** created 记录设计首次建立日期，archived-date 记录设计资产归档日期，两者不相互覆盖。评审与方案修订按日期记入设计评审表，同步 updated，不维护递增 version。设计不存放实现版本或 commit，实际版本只写在 features 的验证证据中；历史字段保留兼容。
6. **成熟度与归档分别表达。** “草稿 / 已确认”只说明当前方案是否已有实际确认依据，不表示实现或验收完成，也不额外设置审批门槛。归档日期记录归档事件，不作为成熟度选项；修订影响原确认结论时据实调整成熟度和确认依据，已替代内容在演进记录中标明。
7. **依据与验证摘要据实填写。** Refs 只使用真实来源。设计只陈述验证方案与通过条件，不填写执行摘要或交付结论。features 的验证摘要从实际证据推导，前后基线分别标注，不将预期通过写成实际结果。
8. **管理字段唯一维护。** 设计负责人、评审人、设计状态与日期保留在设计 frontmatter，计划和归档引用该来源。实施任务分工、实际结果和交付结论由开发阶段管理，不复制为设计状态。

历史文件按原位置保留；采用增量归档方式时新增、补充或标记替代关系，不通过删除旧方案抹去设计依据。若实际目录另有命名或归档规则，以该规则为准。

### 3.3 编写质量与图表规范

#### 3.3.1 编写质量要求

特性设计文档的编写与维护必须满足以下四项要求：

| 质量要求 | 编写与维护要求 |
| --- | --- |
| **内容合理** | 围绕本次目标、范围和实际约束展开，方案与取舍有依据，责任、接口、状态、流程及异常处理相互闭合；详略与特性复杂度相称，避免无关内容、重复说明和无依据的保证。 |
| **逻辑层次清晰** | 从问题与前提到总体方案、详细设计、实施及验证逐层展开，同层级按一致主题组织；标题准确，关键概念先定义后使用，前后引用及因果关系明确。 |
| **图文并茂** | 用架构图或简明流程图解释核心方案，按需要用流程图、状态图和时序图展开复杂过程，配合表格比较字段、责任和取舍；图表紧邻对应叙述，正文解释关键关系、条件和边界，图文术语及语义一致。 |
| **表述易于理解** | 使用准确、直接的语言，明确动作主体、作用对象、条件和结果；术语及缩写首次出现时解释，复杂机制结合必要的有限示例，避免含糊指代、术语堆砌和过长句子，使读者能复述主链路并定位责任及限制。 |

#### 3.3.2 图型选择与图文表达

按要解释的问题选择以下图型，围绕本特性核心设计配图，不固定图的数量，也不要求每份方案包含全部图型。简单特性可用一张简图说明主要关系或流程；复杂方案将总体关系和关键过程分层表达，避免一张图混合所有模块、状态和执行步骤。

| 图型 | 要解释的问题与适用条件 | 主要放置位置 | 正文需说明的内容 |
| --- | --- | --- | --- |
| **架构图** | 本次涉及的模块协作、调用方、外部边界及依赖；必要时分别画上下文和内部关系 | 方案概览；模块责任 | 参与方、职责、边界与箭头含义；限定在特性相关范围 |
| **类图** | 关键类之间的继承、组合、依赖及接口实现关系较复杂 | 关键类与函数设计；接口定义 | 类与接口的职责、关键成员、关系含义及实例作用域；限定在本次相关符号 |
| **流程图** | 操作或算法的步骤、判断、分支、异常处理及恢复路径 | 正常执行流程；异常处理；算法与规则或恢复设计 | 条件、执行主体、各分支结果及后续允许动作 |
| **状态图** | 多阶段生命周期、状态转换和终结条件 | 状态机与生命周期 | 初始态与终态、转换条件和主体、确认依据及禁止的推进 |
| **时序图** | 多主体交互、并发、异步交接、等待及提交确认 | 相关交互、并发、持久化与恢复设计 | 顺序范围、等待条件、提交或确认点及失败后的责任 |

- 使用内嵌 Mermaid 保留可编辑源码；架构图与流程图可用 `flowchart`，类图可用 `classDiagram`，状态图可用 `stateDiagram-v2`，时序图可用 `sequenceDiagram`。按表达目的组织节点和连线，不以绘图语法代替关系说明。
- 图有明确主题，紧邻相关文字；解释重要箭头、条件、状态和确认点，必要时补充图例。表格用于平行比较，不能代替适用的设计图；装饰性图片不能代替方案说明。
- 图、表和正文使用相同术语、身份、状态及作用范围。模块连线不自动代表统一事务、顺序或恢复保证；这些保证必须在正文明确成立条件与实现边界。
- 修订时同步核对相关图源、正文、表格、图例与引用。已有图能够解释同一关系时直接引用，不在多个章节重复维护同一张图，不为配图补造模块、状态或恢复能力。

### 3.4 设计输入、方案与取舍的维护

背景与关键场景维护问题、行为变化和本次边界，不重复验收清单。设计约束、假设与待决问题集中维护方案前提，区分已确认事实、待核实条件和未确定的选择；核实或解决后更新其性质与对设计的影响，不保留失效问题作为当前阻塞。

总体方案概述机制，关键决策维护选择依据与代价，替代方案维护排除理由，详细设计维护责任和技术行为。四者通过必要的 ID 或章节名称关联，不重复抄写同一段方案。关键不变量已有正式定义时引用原编号，目标与不变量分清适用条件及验证方式。

- **决策随依据更新。** 实现发现新事实或前提变化时，核对受影响决策、候选排除理由及验证场景，记录实际变化，不把普通修改清单重复登记为决策。
- **候选关系可追溯。** 实际候选关联对应决策，区分拒绝、暂缓和范围外；没有真实讨论时照实说明，不为满足模板虚构比较。
- **拒绝理由有适用前提。** 某方案因旧能力缺失、旧 SDK 限制或原范围而被排除时，说明这些前提。后续前提变化可以推翻旧结论，但必须补充新证据和替代关系。
- **确认记录只反映真实发生的确认。** 有既有评审要求时记录相关结论；没有要求时不为使用模板额外设置审批门槛。待确认事项注明影响，不伪称用户已裁决。
- **图、表与正文同步维护。** 设计关系或语义变化时，按“图型选择与图文表达”更新相关图表和说明，不能只改其中一种表达。

代码片段可用于给出关键类、函数和接口的精简定义，伪代码用于说明难以通过文字表达的机制；均注明是目标设计还是当前实现，不复制整份源码。定义须配合职责、参数、返回值及行为约束说明，不能只有签名而没有语义。文件列表说明“修改什么、为什么修改”，不能用路径清单替代方案。

### 3.5 按需内容与章节职责

每次新增或改变行为，重新核对相关可选内容是否适用。涉及且改变时展开，沿用时记录核对结论，不涉及时删除可选小节；不以“按需”为由省略本次承诺必需的设计，也不保留大量空表格。

- 关键类与函数设计说明代码责任及定义，接口定义与消息契约说明调用边界及交接语义；类方法与独立函数分别维护，重复签名或字段通过引用保持唯一来源。已有符号核对源码和导出，目标符号明确标注设计状态及计划位置，不以内部方法冒充公共 API。
- 接口概览与字段定义分开；配置、生效及能力门控在配置小节维护，定义、文案和注册条件同步核对。
- 数据模型说明事实归属，状态机说明动态转换，正常流程说明提交与交接，异常小节说明失败后的事实和处置，各自引用已有定义。
- 并发说明覆盖窗口，恢复说明恢复粒度，两种保证分别验证。读取历史、重新发起请求或恢复页面不自动证明原任务能继续执行。
- 算法与规则、资源与文件布局仅在本次涉及变化时展开；术语、单位和身份作用域写在相关定义中，不另建通用术语词典。
- 安全与授权专题说明可信来源、隔离及校验边界，关联正常流程、拒绝路径和验证场景；沿用公共权限引擎时说明复用关系，不把提示词、同一根目录或身份标识当作授权证明。
- 跨仓与宿主适配专题说明两侧责任、组件映射和接入方式，实施顺序在实施设计中维护，真实联调结果在验证记录中维护；接入骨架明确标注未实现部分，不当作生产适配已完成的证据。
- 外部适配、交互、观测及性能沿用按需专题。外部能力在版本或环境变化时复核，理论收益与实测结果分别标注。

兼容检查保留核对结论，有影响时展开兼容与迁移，统一说明旧调用、旧数据及已有会话的处理。回退范围按实际能力表达，不扩展为完整发布或运维流程。

### 3.6 实施影响与验证证据（分阶段使用）

实施清单依靠源码检索确认真实生产者、消费者、配置、存储、导出和使用入口，不只凭记忆列“主要调用点”。跨模块变更注明每个模块的责任和交接契约，避免把协作方的全部实现默认纳入本项。

设计文档维护场景、预期与准备条件；以下实际执行、证据效力和交付结论指导供 jw-dev 使用，记录位置为 features，不写回设计文档。执行记录维护实际结果，验证结论据此判断承诺覆盖情况。沿用已有验收 ID，关联必要的关键行为和不变量，不另建完整追踪矩阵或重复验收标准。

并发、超时、故障和恢复等场景需有可构造、可观察的验证条件及清理方式；缺少这些条件时说明验证缺口，不将“计划增加测试”视为已有证据。不为使用模板新增测试框架。

每项实际记录至少说明 **验证范围 → 版本与环境 → 可复现入口 → 实际结果 → 未覆盖边界**。验证命令是实际执行的命令；日志较长时保存到独立记录并链接，不把整段终端输出贴入方案。

- 单测或 fake SDK 可证明逻辑、映射和消费契约，不能自动证明真实 SDK、子进程或远程系统可用。
- 真实握手可证明配置、目录或连接能力，不能自动证明模型请求、工具调用或完整业务链路成功。
- 人工验证应记录前置、操作和观察结果，不能仅写“手动跑通”。真实联调注明对端版本及必要环境。
- 性能、稳定性或竞态修复须记录负载、计量或竞态构造条件；通过次数不替代明确断言。
- 失败、跳过、未执行和待核对分别记录；既有失败写明依据及受影响范围，不能把有失败的测试描述为全量通过。
- 部分场景通过仅证明相应范围；本次承诺的整项验收、真实交付节点及产品开放条件各自核对。

验证证据可以包含当时的提交或 PR 版本，方便复现，但不放入元信息形成提交后反复回填。实现变化后重新判断旧证据是否仍有效；不能复用旧结果证明尚未验证的新行为。结论变化时同步 features 内的验证摘要及计划中的证据入口，不向设计管理字段复制实际结果。

### 3.7 开发过程中的更新与同步（由 jw-dev 使用）

1. **方案形成时：** 明确行为变化、本次范围和设计前提，填写总体方案、取舍、必要详细设计与验证计划。将待确认项及影响集中维护，同步计划中的特性及设计入口。
2. **实现过程中：** 发现消费点遗漏、竞态、SDK 限制或原方案不可行时，先在 features 记录“原判断 → 新证据 → 最终做法 → 影响与验证”；需要改变目标方案时返回 jw-design，经确认后按日期修订设计。不得等交付时才补写为事后解释。
3. **契约变化时：** 同步对应 spec、feature、受影响的模块约定和必要使用说明；更新开发计划中受影响的范围、依赖及验收关联。
4. **行为核对时：** 以源码、测试和实际运行证据核实当前事实。已经失效的路径、接口或枚举及时更正；历史决策仍有解释价值的，标明当时适用范围和替代位置。代码事实与已确认设计不一致时记录差异，按所属目录要求处理，不把意外实现自动认定为新的架构。
5. **归档时：** 核对实际范围与原承诺，在 features 补全执行记录、验证结论、限制及文档同步情况；设计仅维护必要的归档管理字段；更新唯一进度维护位置中的状态与证据。文档写完或 PR 合并本身不等于验收完成。
6. **后续变化时：** 延续原特性的修复或补充按日期记录；独立变更新增 feature 并双向链接。新增范围不冒充原范围已完成，旧证据保留并注明适用边界。

是否在开发前新增或修改特性设计，按所属目录的 `AGENTS.md` 判断；实现纠偏、普通局部调整和文字修改不因使用本模板而强制新建 feature。定稿契约同步主责 spec；架构调整按已有授权和适用规则处理，本模板不新增审批门槛。

需要计划时按所属目录规则建立，维护任务分工、执行状态、开发顺序及交付证据；设计负责人、设计状态和日期仍在设计中维护；无独立计划时按任务需要维护执行记录，设计管理字段仍留在设计中，不为填写模板强制建计划。认领、开工、阻塞、验证和完成变化时，更新该唯一位置；feature 保留技术证据、实际决策与实施偏差，计划引用这些记录，其他文档通过链接查阅当前管理信息。

### 3.8 风险、遗留与设计演进（区分设计资产与实施归档）

设计保留开发前方案与日期评审；features 保留实际实施的来龙去脉，spec 描述当前有效契约。以下开发后的遗留、证据和修复记录均写入 features。维护历史并不意味着保留失效表述作为当前指令。

风险记录尚未发生但影响本次设计或交付的不确定性；遗留记录已经明确的缺口和限制。风险核实后，更新设计前提及方案，必要时转为关联的遗留项；不要在风险、假设和遗留中分别维护同一问题。没有本次相关风险时不套用通用风险清单。

设计变化经确认后更新目标方案并追加日期评审记录；实施归档后续修订时，在 features 末尾增加带日期的记录，并在被替代结论就近注明“已由〈日期 / 文档或章节〉替代”。全文应能直接判断哪条规则当前有效。纠正路径、错别字或失效链接可直接更新；推翻设计取舍时保留原理由及新证据，不另建变更日志文件。

遗留分清未实现、未验证、已发现缺陷、有意保留限制和范围外工作，说明具体影响及后续触发条件。解决后保留原项，补充日期、解决位置与验证；不能仅删掉条目，让后续维护者失去因果依据。旁发现问题只有影响本次方案或验证时才展开，独立问题链接到后续入口。

完整 diff 和修改历史由版本控制保存；设计文档记录关键变化及依据，不逐条抄写 commit message。

### 3.9 提交与规则适用范围

文档、实现和验证作为同一个工作单元同步维护，具体提交拆分、scope、issue footer 及归档要求遵循被修改模块的规则。

采用本模板本身不新增提交要求，也不授权自动提交、改写架构或重编号历史文档。

### 3.10 维护后的一致性检查

1. 问题、关键场景、目标行为和本次范围明确，验收要求没有重复维护。
2. 已确认约束、假设与待决问题分清，核实方式及对设计、实现或交付的影响已说明。
3. 概览、决策和详细设计职责清楚；候选真实，取舍、成立前提和实现体现可追溯。
4. 责任、不变量、关键类与函数、接口、配置、数据、状态、图表及正常与异常路径一致，相关并发与恢复保证分别说明；关键符号的职责、完整定义或来源、参数与返回值、异常及副作用明确，类关系与接口实现关系可追溯，目标设计与当前实现分清。
5. 详细设计的可选内容按涉及程度取舍，没有关键遗漏或大量空表；涉及安全与授权时，可信来源、隔离、校验和失败关闭边界明确；兼容影响有核对结论，必要迁移及回退边界明确。
6. 实施影响覆盖实际生产者与消费者；跨仓或宿主接入的两侧责任、契约、注入位置及示例状态明确；已确认契约与 spec 一致，架构调整有所属目录要求的确认依据。
7. 设计中的验证预期与 features 中的实际记录、结论分开；必要场景能构造和观察，执行版本、环境与证据由实施归档追溯。
8. features 的验证摘要与结论一致，前后基线含义明确；设计没有预填实际结果，失败、跳过或模拟验证不被扩大解释为整项完成。
9. 设计确认、实际开发与验证结论分别表达；设计管理字段以 frontmatter 为唯一来源，评审按日期修订，开发事实只在 features 维护。
10. 风险与遗留性质清楚，核实和解决结果已更新；被替代结论注明日期与当前入口，历史依据得以保留。
11. **内容合理：** 内容围绕本次范围，详略适当，设计与取舍有依据，没有无关堆砌、重复内容或无依据的承诺。
12. **逻辑层次清晰：** 整体与局部、概念与流程层次分明，标题准确，概念先定义后使用，前后引用与因果关系清楚。
13. **图文并茂：** 核心方案有适用的设计图，复杂关系或过程按需使用架构图、流程图、状态图或时序图；重要关系和条件有文字说明，图源、图例、表格及正文一致。
14. **表述易于理解：** 主体、对象、条件和结果明确，术语及缩写有解释，读者能理解主链路并定位责任、保证及限制。
