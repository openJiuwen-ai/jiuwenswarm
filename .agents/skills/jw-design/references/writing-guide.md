# 设计写作准则

提炼自原 swarm-design-docs/AGENTS.md 的写作规则，适用于方案形成与评审。

- 面向人类评审，先讲具体场景、问题与责任关系，再引入类名、字段或函数。
  没读过实现代码的工程师也应能理解设计为何成立。
- 调查以当前代码和测试为准；已有 feature、spec 与设计提供背景，不替代代码事实。
  不一致处区分当前实现、目标方案与未验证假设，将实施影响明确交给开发阶段。
- 分别陈述已实现、接口占位、已知缺陷和待验证目标，不把接口存在写成行为已经可用。
- 叙述解释机制，图展示协作与流转，真实签名和数据结构说明契约；三者按需要组合，
  不用长段代码或表格替代设计说明。时序优先 Mermaid，其他关系可用 ASCII 或附件图。
- 关键方案写清架构职责、数据流与时序、接口与模型、关键流程、配置；按所选模板裁剪，
  不为了填满模板虚构对象或增加无关机制。
- 每条主要决策说明选择、依据、代价和被否决的备选，记录成立前提与边界。
- 设计确认、实际实现和验证结果各自独立。开发中的实际实施、决策、偏差、验证和遗留由 jw-dev
  归档到 features，不回填设计。设计仅保留预期方案、验证计划、管理字段和按日期记录的评审修订。
