# 架构详细设计文档模板与维护规范

## 1. 这份文档的用途

### 1.1 架构详细设计文档的作用

架构详细设计文档用来说明系统如何组成、各模块如何协作，以及哪些规则必须始终遵守。它在设计概览的基础上，进一步解释模块分工、处理流程、数据管理和故障处理，为开发、评审和后续维护提供共同依据。

读完文档，应能回答：系统负责什么，各模块分别做什么；一项工作从输入到结果要经过哪些步骤；谁可以修改状态，怎样判断工作已经完成；遇到重复请求、故障或权限变化时，系统应该怎样处理。每个重要步骤都要交代清楚责任、条件和结果。具体类、字段和代码步骤放在对应的特性方案中。

文档还应说明为什么采用这些设计、它们依赖哪些前提，以及有什么限制。这样，各模块可以分别开发，又能按照相同的约定协作；后续修改时，也能判断是否影响整体设计。

### 1.2 阅读对象与使用场景

- **设计和评审人员：** 检查目标是否明确、分工是否合理、数据由谁管理，以及重要规则是否完整。发现没有人负责、相互等待或缺少依据的设计。
- **开发和协作人员：** 了解本模块接收什么、产出什么、与其他模块如何配合，以及失败后由谁处理。判断实现或修改是否符合整体设计。
- **测试、运维和维护人员：** 了解完成条件、故障影响和恢复方式，找到具体方案及验证记录。

文档用于方案设计、模块间协作、开发前评审、修改影响分析和人员交接。请分别说明“设计要求是什么”“目前实现了什么”和“验证结果是什么”。设计定稿不代表功能已经实现或通过验收。

### 1.3 如何使用本文

第 2 节提供可复制的模板，并说明怎样选用章节。第 3 节说明内容应该写在哪里、怎样表达清楚，以及修改后需要检查什么。使用时先遵守目标目录的 `AGENTS.md` 和已有文档约定；JiuwenSwarm 开发与文档维护要求见 [仓库 AGENTS.md](../../../../AGENTS.md)。

模板帮助组织内容。具体对象、交互方式、并发策略和技术方案，需要根据目标模块确定。

## 2. 模板

### 2.1 使用方法

复制第 2.3 节代码块中的 Markdown，填写 `〈占位内容〉`，完成后删除提示和不适用的示例。标题使用“〈模块或产品名称〉详细架构设计”，文件名建议为 `<slug>-architecture.md`，不带日期；已有命名和存放规则时沿用原规则。本文第 1、3 节是使用说明，无需复制到实际架构文档中。

填写时，先明确目标和范围，再解释核心概念、模块分工和关键模块的工作方式，接着用主流程和关键协作机制说明模块怎样共同工作，最后说明状态、数据、故障处理，并用完整场景检查设计。尚未确认的前提写明“待确认”，说明谁负责确认、影响哪些行为。只填写系统实际需要的内容。

架构设计文档必须做到**内容合理、逻辑层次清晰、图文并茂、易于人类理解**。这是编写、修改和交付时必须满足的约束：具备相关领域基础、但未参与设计的读者，应能通过正文及其明确引用，解释系统定位、主要对象、模块职责、主流程和关键异常处理，无需先阅读源码或依赖作者口头补充。编写时参考第 3.3 节，交付前按第 3.7 节检查。

模板使用 `#` 表示文档标题、`##` 表示主体章节、`###` 表示子章节，需要进一步细分时使用 `####`。下文“架构第 1～12 节”指复制后的正文。新文档可以调整章节并连续编号；修改已有文档时，保留被其他文档引用的章节号和锚点，避免原链接失效。

图表是填写示例，请替换为实际关系，并解释箭头、状态和完成条件。相对链接应从实际架构文档所在目录计算。相关方案还未建立时，说明由谁编写，不添加不存在的文件链接。

### 2.2 如何选择和调整章节

正文依次说明“这是什么 → 有哪些核心概念 → 由哪些模块组成 → 各模块怎样工作 → 模块怎样共同完成工作 → 共同遵守什么规则 → 怎样检查设计”。十二节提供完整的组织示例，可以根据模块复杂程度合并或细分。

表中的“通用”内容，每份架构文档都应说明，允许合并章节。“如适用”内容，系统涉及相应能力时再展开。**不适用**的主题可以删除，并简要说明原因；**需要但尚未设计或验证**的内容，应在架构第 12.2 节记录负责人和影响。

| 内容 | 要回答的问题 | 什么时候需要 | 建议写法 |
| --- | --- | --- | --- |
| 文档说明 | 是草案还是已确认设计？目前实现了什么？ | 通用 | 放在正文前，说明日期、维护人、依据和阅读顺序 |
| 定位、目标与范围 | 这是什么？解决什么问题？负责到哪里？ | 通用 | 用一句话定位、主要职责和短例子建立整体认识，引用完整需求文档 |
| 核心概念与共同规则 | 对象分别是什么？有什么关系？哪些规则必须遵守？ | 通用 | 解释含义和生命周期，列出规则及详细说明的位置 |
| 架构总览与模块分工 | 系统有哪些部分？内部和外部分别负责什么？ | 通用 | 架构图、职责表和依赖说明；不在这里展开模块内部设计 |
| 关键模块设计 | 单个模块怎样完成自己的工作？ | 关键模块通用；简单模块可与分工说明合并 | 按模块说明工作方式、调用约定、配置和资源管理，完整字段和算法引用对应方案 |
| 模块协作与处理流程 | 多个模块怎样共同完成一项工作？ | 主流程通用；复杂协作机制按需展开 | 第 5.1 节串起主流程，第 5.2 节按机制说明触发、交接、等待和失败责任 |
| 状态与完成条件 | 谁修改状态？怎样判断工作完成？ | 完成条件通用；有多阶段状态或异步事件时展开 | 简单模块可与流程合并，复杂模块单独说明状态转换 |
| 数据管理 | 数据由谁维护？以哪里的记录为准？ | 数据归属通用；有持久化或跨存储操作时展开 | 说明数据用途、更新责任和保存要求，无需列出物理表结构 |
| 故障与恢复 | 失败后怎么办？不知道结果时怎么办？ | 基本失败处理通用；有外部写入或恢复能力时展开 | 说明影响范围和处理责任，不支持恢复时写明限制 |
| 权限与资源限制 | 谁能访问什么？资源不足时怎么办？ | 有多主体、共享、并发、敏感操作或额度限制时展开 | 说明在哪里检查、检查什么，以及不满足条件时如何处理 |
| 运行保障与版本维护 | 如何发现问题？数据和版本变化时如何保持正确？ | 系统能保证什么应通用说明；其他内容按实际能力展开 | 说明成立条件和限制，数值目标提供依据，操作步骤引用具体方案 |
| 场景与架构检查 | 这些模块能否共同完成工作并遵守规则？ | 通用 | 用代表性场景解释全过程，并指出验证要求写在哪里 |
| 选择与待确认问题 | 为什么这样设计？依赖哪些前提？还缺什么结论？ | 通用；没有待确认问题时写“无” | 记录重要选择、未验证前提及问题负责人 |

简单同步模块可以合并流程与状态、数据与资源管理的说明。复杂系统可分别说明入口、调度、通信、文件或长期作业。合并或拆分时，仍要让读者找得到每项责任、规则和限制。

**模块与机制怎样分工：** 模块是系统的组成单元，机制描述模块的工作方式或模块之间的协作过程。架构第 3 节介绍模块组成和职责；第 4 节解释单个模块内部怎样工作；第 5.1 节串起一次工作的主流程；第 5.2 节展开跨模块的触发、调用和交接。状态、保存、恢复和权限规则分别在第 6～9 节选定主要位置维护，其他章节引用。

例如，窗口管理模块怎样组织上下文、保护前缀缓存和选择换窗时机，放在第 4 节；换窗时怎样协调执行器、归档存储和模型额度，放在第 5.2 节；归档与保存顺序放在第 7 节，失败后的处理放在第 8 节。无需在各处重复完整设计。

多 Agent 系统可在模块设计中说明成员的执行方式，在协作机制中说明团队如何配合；执行器可说明模型循环、上下文准备和工具使用；服务端可说明接入、调度、管理和查询。具体内容取决于实际职责。同一套状态或并发规则不一定同时适用于团队、会话和单次调用。

部署、扩展、AI 和查询设计影响本模块分工或正确性时，再放入对应模块或协作机制中说明，无需新增必填章节。宿主或协作模块必须提供的保证，可以集中列在架构第 3 节或可选附录中；正文引用同一份清单。

````markdown
〈如有助于查阅，可在正文后增加协作保证清单、规则索引或简短变更记录等附录。正文引用同一份清单；完整接口定义、实施调整和历史方案引用配套文档或版本历史，不必复制到架构正文。〉
````

## 3. 维护规范

### 3.1 各类内容应该写在哪里

| 文档 | 主要写什么 | 架构文档怎样引用 |
| --- | --- | --- |
| 设计概览（Overview） | 整体目标、范围、工作方式和主要设计结论 | 进一步解释分工、交互和规则，与概览保持一致 |
| 详细架构 | 系统组成、模块设计、协作流程、对象、状态、数据管理和共同规则 | 本文说明当前设计，开发进度在计划中记录 |
| 规约（spec） | 已确认且可以核验的接口、状态和规则 | 引用相关约定，无需复制完整字段定义 |
| 特性方案（feature） | 接口字段、数据结构、算法、代码修改、交互和验证记录 | 说明方案必须满足的架构要求，并提供链接 |
| 开发计划 | 特性划分、依赖、交付节点、负责人、排期、状态和证据 | 引用统一计划，不另列一份进度表 |
| 运维或验证记录 | 配置、指标、操作步骤、环境和执行证据 | 说明质量要求、故障处理责任和限制，引用相关记录 |

架构说明模块需要提供什么能力、保存什么记录，以及必要的提交顺序和故障处理规则。具体方法签名、字段、表与索引、锁和事务算法、Prompt 文本、代码修改及测试步骤，写入对应特性方案；已经定稿的接口和规则同步规约。某项实现选择直接影响架构正确性时，在架构中保留必要前提和限制，细节仍引用具体方案。

完整验证清单、开发阶段和支持范围按目录约定统一维护。架构只说明需要保证什么、能力开放前要满足什么条件，并提供相关链接。

同一规则选一个主要位置详细说明，其他章节引用即可。下表帮助区分容易重复的内容，编号指可复制模板的架构正文。

| 主要位置 | 重点说明什么 | 与其他章节怎样分工 |
| --- | --- | --- |
| 第 2 节：核心概念与共同规则 | 对象含义、关系和生命周期；关键规则索引 | 第 4 节说明实例与资源的管理，规则细节引用第 6～9 节 |
| 第 3 节：架构与模块分工 | 模块组成、职责、依赖和外部保证 | 第 4 节展开工作方式，第 5 节展开协作过程 |
| 第 4 节：关键模块设计 | 单个模块的内部工作方式、调用约定、配置和资源管理 | 只概述相邻模块的约定，跨模块顺序放在第 5 节 |
| 第 5.1 节：主流程 | 一次工作的完整路径、每步责任与结果 | 复杂协作引用第 5.2 节，不展开全部内部设计 |
| 第 5.2 节：关键协作机制 | 触发、参与模块、交接顺序、等待和失败责任 | 模块内部设计引用第 4 节；状态、保存和恢复规则引用第 6～8 节 |
| 第 6 节：状态与确认 | 怎样转换状态，怎样判断完成 | 流程、故障和场景采用相同规则，不另设完成标准 |
| 第 7 节：数据与一致性 | 以什么记录为准，谁能写入，何时生效 | 第 8 节据此说明故障后怎样核对和处理 |
| 第 8 节：故障与恢复 | 失败或结果未知后怎样暂停、核对和继续 | 第 10 节概括系统保证和限制，不重复恢复步骤 |
| 第 9 节：权限与资源限制 | 授权依据、隔离范围、额度和容量的使用条件 | 模块和协作流程引用这里的规则，不另设权限或预算标准 |
| 第 10 节：运行保障与版本维护 | 整体保证、运行监控、保留、删除和更新规则 | 具体过程引用相关章节，实施步骤引用对应方案 |
| 第 11 节：完整场景 | 用例子推演模块如何共同工作，指出验证要求 | 采用前文规则，不新增状态、接口或完成条件 |

### 3.2 怎样把设计说清楚

1. **分清设计与现状。** 写明是草案还是已确认设计，哪些已有实现，哪些前提仍待验证。设计确认、代码完成、验证通过和能力开放分别说明。
2. **先说谁负责，再说怎么做。** 每项重要记录都要说明由谁管理、谁可以修改。其他模块读取、展示或核对时，不能绕过负责模块修改记录。外部操作结果以哪个系统为准，也要写清楚。
3. **说明规则适用于哪里。** 顺序、防止重复、唯一执行、隔离和预算规则都要说明对象、范围、前提及检查位置。某个步骤正确，不代表整个系统都有相同保证。
4. **区分不同状态和完成条件。** 工作完成、一次执行结束、上下文更新、文件生成、结果送达和页面显示可能是不同事实，分别说明各自的确认依据。
5. **不知道结果，不等于没有发生。** 超时、断流、读取到旧副本或丢失确认回复时，先说明去哪里查询、由谁核对、哪些操作暂时不能继续，不能直接认定对象不存在或操作没有发生。
6. **根据已确认记录恢复。** 说明原版本、恢复引用、已提交进度和外部回执分别有什么作用。缓存、展示文本或文件存在不能代替业务进度；无法保证安全接管时写明限制。
7. **在实际操作时检查动态条件。** 权限、资源和资料来源变化后，说明怎样通知相关模块、何时重新检查。接收或启动时检查过一次，不代表后续操作始终有效。
8. **写出代价和限制。** 说明重要选择对可用性、等待、复杂度和兼容性的影响。没有依据的性能、容量和恢复时间写为“待确认”，注明由谁确定。

### 3.3 文字、结构、图表与链接

#### 3.3.1 编写质量要求

编写和修改文档时，都要满足以下要求。**易于人类理解是架构设计文档的交付约束**，不能用章节齐全、表格填满或术语准确代替。目标读者是具备相关领域基础、但未参与本次设计的设计、开发、测试和维护人员。

| 质量要求 | 怎样做到 |
| --- | --- |
| **内容合理** | 每项设计都围绕目标、有依据，分工、流程、状态和异常处理相互一致。详略与模块复杂程度相称，删除无关和重复内容。 |
| **逻辑层次清晰** | 先讲整体，再讲细节；先解释概念，再描述流程。同级标题围绕相同层次组织，标题与内容对应，前后关系清楚。 |
| **图文并茂** | 用图解释组成和过程，用表比较职责、数据和选择。图表放在相关文字附近，正文解释重要关系和条件，名称与含义保持一致。 |
| **易于人类理解** | 用直接的语言说明谁在什么条件下做什么、产生什么结果。首次出现的术语和缩写给出解释，相近概念说明区别；复杂机制用必要例子和图表解释。读者无需先读源码或依赖作者口头补充，就能通过正文及明确引用解释定位、模块分工、主流程和关键异常处理。 |

先说设计结论，再解释条件、理由和限制。一段集中解释一个问题，长句拆成步骤或短段落。保留必要的技术术语，并用熟悉的语言解释含义；同一对象和模块始终使用同一名称。

填写提示要分清基本说明与按需展开的内容。正文应把提示改写为设计结论和解释，避免只列问题、术语或孤立的表格。涉及先后关系时说明顺序，涉及例外时说明条件，涉及失败时说明责任和后续动作。

写到什么程度才够？读者应能回答下表中的问题。相关信息可以通过章节引用提供，无需反复描述。

| 主题 | 读者应能回答 |
| --- | --- |
| 定位与概念 | 系统为谁完成什么？关键对象有什么区别，彼此是什么关系？ |
| 模块分工 | 这件事由谁负责？交接后谁接着处理？ |
| 关键模块设计 | 模块接收什么，怎样处理，输出什么？为什么采用这种工作方式？ |
| 主流程与协作机制 | 一项工作怎样开始和结束？复杂协作在何时触发，各模块怎样交接？ |
| 交互约定 | 开始前需要什么条件？成功、被拒绝或结果不明时，下一步怎么做？ |
| 状态与确认 | 何时允许变更或完成？谁确认？根据什么继续工作？ |
| 故障与恢复（如适用） | 可以继续、可以重试，还是必须先核对？由谁处理，依据和限制是什么？ |
| 设计选择 | 为什么这样选？依赖什么前提？接受了什么代价？ |

下面只演示表达方式，不要求每个模块都具备相应能力：

> 含糊表述：“系统保证可靠执行。”
>
> 清晰表述：“确认接收后，系统保存工作记录。进程退出后，恢复模块根据已保存的记录核对进度。外部写入结果未知时，不立即重复写入，由负责该操作的模块查询并确认结果。”

#### 3.3.2 结构、图表、编号与链接

按要解释的问题选择图，不必使用所有图型。整体关系和复杂过程分别画，避免一张图塞入所有模块、状态和执行步骤。

| 要解释什么 | 适合用什么图 | 文字还要说明什么 |
| --- | --- | --- |
| 系统与外部的关系，或内部模块组成 | 架构图；外部关系与内部组成分层画 | 谁参与、负责什么、箭头表示什么 |
| 处理步骤、判断和分支 | 流程图 | 分支条件、负责模块和处理结果 |
| 对象生命周期和状态变化 | 状态图 | 何时允许变化、确认依据和禁止的转换 |
| 并发、异步交接和确认 | 时序图 | 哪些操作有先后关系、等待什么、失败由谁处理 |

- 按定位、概念、模块分工、模块设计、协作流程、共同规则、场景和设计选择的顺序组织内容。根据阅读需要分章，不必照搬代码目录。
- 使用内嵌 Mermaid 保留可编辑的图源码，重要箭头在正文中解释。
- 图表与正文使用相同名称和范围。逻辑模块不一定是独立服务，逻辑记录不一定是独立表，连线不代表事务保证。
- 并列比较用表格，顺序步骤用编号列表，解释原因、条件和限制用完整段落。表格和图只在有助于理解时使用，简单内容不强制填表或画图。
- 新文档可以连续编号；已有章节号、锚点及重要规则或决策 ID 保持稳定，删除后不用于其他内容。
- 拆分章节、调整顺序或移动文件后，检查导航、正文引用、图表名称，以及其他文档指向这里的链接。必要时保留旧锚点或说明替代位置。
- 优先使用相对链接。跨仓链接指向明确文件，复制模板后按实际目录重新计算路径。
- 没有内容时不创建空白规约、方案或章节；需要后续编写的材料说明负责人和影响。

### 3.4 什么时候更新，需要同步哪些文档

| 发生什么变化 | 架构需要改什么 | 还要同步哪里 |
| --- | --- | --- |
| 目标、入口或范围调整 | 目标、范围、需求对应设计及受影响场景 | 概览、需求文档、开发计划 |
| 模块分工或依赖变化 | 架构图、分工表、交接方式及兼容要求 | 协作模块架构、概览、相关规约和方案 |
| 模块工作方式或协作机制变化 | 第 4 节模块设计、第 5 节主流程及关键协作机制，以及受影响的共同规则 | 相关规约、特性方案、协作模块设计及验证要求 |
| 对象归属、状态或完成条件变化 | 对象定义、共同规则、状态转换和数据管理 | 规约、方案、查询或交付模块设计 |
| 并发、事件或提交规则变化 | 适用范围、竞争处理、交接和结果未知时的处理 | 存储与执行方案、协作约定、验证设计 |
| 权限、共享、资源或外部操作变化 | 检查位置、隔离范围、核对方式和恢复限制 | 权限、工具、文件或投递方案及相关规约 |
| 保留、删除、备份或版本兼容变化 | 数据依赖、未完成操作、清理和更新规则 | 运维、迁移方案、相关规约和验证记录 |
| 实现或验证发现设计前提不成立 | 已有能力、未验证前提、限制及相关设计选择 | 验证记录、方案、概览和计划 |
| 字段、算法或代码调整，整体设计不变 | 通常无需改正文；必要时更新文档链接和现状说明 | 特性方案；接口约定变化时同步规约 |
| 认领、排期、PR 或测试进度变化 | 通常无需修改；实际能力或保证范围变化时更新说明 | 开发计划和验证记录 |
| 术语、目录或章节位置变化 | 名称、导航、锚点和相对链接 | 引用本文件的文档和协作模块文档 |

设计含义发生变化时，更新所有相关说明。正文、图、表、场景和设计选择描述同一件事时，要一起修改，不能只在末尾追加新结论而留下矛盾。修订日期使用实际修改日期，未改动的文档无需刷新日期。

### 3.5 修改文档的步骤

1. **查明修改依据。** 是需求变化、约定调整、实现变化，还是新发现的验证结果？保留来源，不用推测替换已经确认的结论。
2. **判断写在哪里。** 改变整体分工、数据管理、权限、完成条件或共同规则的内容，写入架构；局部实现选择写入特性方案，已确认的接口变化同步规约。
3. **遵守确认要求。** 按目标目录的 `AGENTS.md` 和已有授权判断是否需要确认。需要时说明修改内容、原因和影响。模板本身不新增审批，一般文字或链接修正不额外要求确认。
4. **修改相关设计。** 一并更新受影响的范围、分工、对象、交互、状态、数据、故障和场景。增加新的保证时，要写明谁负责、依赖什么条件，并确认提供该能力的模块能够满足要求。
5. **同步协作文档。** 交接方式变化时核对双方设计，说明谁提供什么、谁使用、失败后谁处理。定稿约定同步规约，实施与验证记录写入方案，范围和进度写入计划，整体结论同步概览。
6. **处理待确认问题和旧结论。** 已解决的问题写回正文，未解决的写明负责人、影响和确认条件。正文只呈现当前设计，旧选择和理由通过决策记录、特性方案或版本历史保留。
7. **检查修改结果。** 按第 3.7 节检查，更新日期及相关链接。尚未验证的要求或前提，不能因为文档修改完成就写成已通过。

**JiuwenSwarm 内使用：** 调整架构时，按 [仓库 AGENTS.md](../../../../AGENTS.md)明确变化范围、原因、契约影响和验证方式，同步受影响的设计与实现。是否需要确认由已有授权和适用规则决定，模板不新增审批门槛。模板用于其他目录时，遵守该目录的要求。

### 3.6 怎样保持文档简洁

能用几段解释清楚的主题，无需单独成章。入口、状态管理或故障处理责任不同，才考虑拆分。合并章节不能省略必要的分工、确认依据和故障处理规则。没有持久状态、预算或自动恢复能力时，直接说明限制。

简单模块可以合并架构第 3、4 节，用一段职责和工作方式说明配合一组主流程步骤。没有复杂跨模块协作时，第 5.2 节简要说明即可；没有必要比较的内容，用段落代替空表。上下文管理等主题较大时，可独立成章，但仍区分模块设计、协作步骤和共同规则，并同步导航与引用。

增加内容前，先判断它是否影响整体设计。参数、字段、类名、页面细节、命令和测试日志放入对应方案；直接影响系统保证的内容，在架构中保留结论、前提和限制。完整接口定义、验证清单和开发计划引用即可。说明设计优点不能代替证明它满足要求。

团队、会话、单次调用和长期作业可能遵守不同的并发规则；知识、文件和私有状态也可能采用不同的权限或发布方式。根据目标模块的实际职责选择，不直接套用其他模块的规则。

### 3.7 交付前检查清单

按第 2.2 节判断带有“如适用”的检查项是否需要。确实不适用时简要说明原因；需要但尚未确定的内容，记录问题及影响。

#### 3.7.1 设计说明是否完整一致

- [ ] 写明文档类型、维护人、模块、日期和依据，分别说明设计、实现和验证结果。
- [ ] 目标、范围、外部关系和关键需求一致，解释了影响架构选择的因素。
- [ ] 模块分工、交接和依赖清楚，对象及数据管理方式一致，同一记录没有相互冲突的管理者。
- [ ] 模块组成、模块内部设计和跨模块协作分工清楚；主流程能串起完整工作，关键协作机制有触发条件、步骤、确认依据和失败责任。
- [ ] 流程、交互约定、状态和完成条件一致，重要规则写明适用范围、条件和保证位置。

#### 3.7.2 相关能力是否有必要保证

- [ ] 如适用，说明记录怎样持久保存、跨存储提交怎样确认；缓存、索引和查询视图不能代替作为依据的记录。

- [ ] 如适用，恢复依据和继续条件可检查，接管限制、不支持的能力及验证前限制清楚。

#### 3.7.3 表达是否易于理解

按“具备相关领域基础、但未参与设计”的读者视角检查下列项目。不能只检查章节、图表和术语是否齐全；还要检查这些说明是否足以解释系统怎样工作。

- [ ] **内容合理：** 说明完整、详略适当，没有无关内容、重复描述或缺少依据的承诺。
- [ ] **逻辑层次清晰：** 先整体后细节、先概念后流程，标题准确，前后关系清楚。
- [ ] **图文并茂：** 整体关系有架构图，复杂过程有合适图表，文字解释重要关系和条件，图文名称及含义一致。
- [ ] **易于人类理解：** 不先阅读源码、不依赖作者口头补充，读者能通过正文及明确引用说清定位、核心对象、模块分工、主流程和关键异常处理。
- [ ] 首次出现的术语和缩写有解释，相近概念有区别说明；重要设计先给结论，再解释条件、理由和限制。
- [ ] 流程写清谁做、得到什么、怎样确认、失败后谁处理；必要例子和图表能帮助理解，没有只列术语、问题或表格。

#### 3.7.4 相关内容是否同步
