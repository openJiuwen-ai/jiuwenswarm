# 决策归属、续写与替代

在新建设计、feature 或 bugfix 前，先判断已有记录是否拥有这项决策。
本规则沿用现有文档分工和生命周期，不新增一种记录，不要求为机械或局部文字修改补造方案。

## 找到维护位置

按问题、公开符号、协议/配置键、模块路径和已有设计标识搜索相关 design、spec、feature、bugfix。
读到候选记录后核对实际代码与消费者，日期较新或标题相近不足以证明它是当前维护位置。
依据区分如下：

- AGENTS：适用的协作与模块约束；spec/协议：当前契约；design：目标方案及确认依据。
- feature：实际实施与决策因果；bugfix：故障现象、根因与修复证据。
- 同一决定在这些位置分别承担不同职责；相互引用，不把整份记录复制到每个位置。

维护位置按以下情况选择，简单任务可在现有正文或交接中说明，不必机械建表：

| 关系 | 处理 |
|---|---|
| 同一决策的实现完善、事实修正或同一故障的证据补全 | 续写现有记录，保留创建标识；不按提交数拆新文档。 |
| 同一主题内的局部实施替代 | 在现有 feature 的修订处记录原范围、新证据、变化与当前有效位置；未替代部分继续有效。 |
| 目标、关键契约或决策理由改变 | 回到 jw-design，形成可确认的变更或替代设计；不把意外实现当成方案批准。 |
| 独立新问题或新的重大取舍 | 新建相应记录，并链接相关旧记录，说明关系。 |

仅需实施修正时不强制新建设计；方向变化的确认要求按已有授权与适用规则判断。
没有记录过的备选方案写明未记录，不为填满模板杜撰讨论或批准。

## 替代判定

记录被完全替代前，核对仍在生产使用的代码、配置、公开接口、持久化/传输格式、恢复/兼容路径和消费者。
只删除一种实现、渠道、默认值或展示方式不构成完全替代；旧数据仍须读取时，旧义务仍然存在。

- 部分替代：标明具体章节/行为及继续有效的部分，双方互链；不将整份旧方案标成无效。
- 全部替代：当前维护记录说明旧方案的独有理由、备选方案、收益/代价、验证证据及尚存缺口被何处承接。
  需要防止误重引入时保留移除原因和重新引入条件，不以“Git 历史里还有”替代可发现的依据。
- 设计的正式替代使用 [生命周期](lifecycle.md) 中既有 supersedes / superseded-by 字段；
  feature/bugfix 用正文链接和适用范围表达，不伪造设计字段或给所有文档增加新的状态台账。

本规则不授权删除旧 feature/bugfix、改历史编号或批量整理文档。
保留现有只增不删约定；另行获准合并/删除历史资料时，先转移独有依据并修复所有入链。

## 事实更新与历史边界

当前 spec/协议的路径、符号、默认值和契约变化随实现同步；feature 保留当时实施与决策的因果，
后续修正使用已有“实施演进与修订”或相应正文记录，不把历史验证结果改成当前新版本结果。
归档设计继续作为历史方案，实际实施不回填设计；当前入口通过 spec 和相关 feature 链接定位。
现有 designs/archive 表示设计生命周期，不等同于 DSH 的冻结归档；不新增冻结目录、哈希封存或索引删除流程。

## 交接

设计交接说明已复用/新建的记录、与旧决策的关系和未决取舍。
开发交接说明本次是否改变既有决定、当前契约维护位置、替代范围及仍有效的限制。
检视核对这些关系与真实差异，不因缺少新增文档而忽略已有记录的有效更新。
