# Spec 文档模板与维护规范

## 1. 文档作用说明

### 1.1 Spec 的作用

Spec（设计规约）维护模块长期有效、已确认且可核验的契约，说明系统在指定范围和条件下应呈现什么行为。它为实现、调用、测试和后续变更提供共同依据，重点是接口、状态、边界、不变量及跨模块交接约束。

读者应能通过 spec 回答：哪些行为属于本模块，哪些由其他模块负责；调用需要什么条件，输入和输出分别意味着什么；关键事实由谁保存和修改，状态怎样合法变化；失败时返回什么、已经发生哪些副作用；哪些保证在并发、暂停、恢复或模式切换后仍须成立。契约应能转化为检查或测试断言，不能只写“保证一致”“支持恢复”等笼统目标。

Spec 是持续修订的契约快照。Overview 说明整体目标和工作方式，架构说明系统边界及跨模块约束，feature 解释具体方案、设计决策和变更原因，开发计划维护验收要求与执行进展。Spec 保留当前契约并链接这些依据，不积累实施过程或维护第二份进度台账。

### 1.2 阅读对象与使用场景

- **开发和接口调用人员：** 在实现或消费能力前确认公开入口、参数含义、适用条件和失败边界。
- **跨模块协作及设计评审人员：** 确认事实归属、交接协议、装配顺序和依赖约束，识别重复定义或责任缺口。
- **测试和维护人员：** 将不变量、行为矩阵、状态转移和错误语义转化为验证，判断变更是否影响既有调用方及持久数据。

Spec 用于开发前校准设计、接口协作、回归检查、变更影响分析和交接。契约变化时及时修订同一份文档，使当前实现、已确认设计与实际限制可以相互核对。

### 1.3 本文的使用目的

本文为编写和维护 spec 提供通用骨架、填写提示与一致性检查方法。

第 2 节提供填写方法、结构选择和可复制模板，第 3 节规定契约表达及同步检查。稳定条款编号、统一表格和检查清单用于方便填写和核对；协议、存储、运行时等主题可按需扩展。

JiuwenSwarm 内使用时遵循 [仓库 AGENTS.md](../../../../AGENTS.md) 及目标目录的补充规则；用于其他目录时以该目录规则为准。本文提供写作规范，不新增设计审批或提交门槛；提交组织和归档要求遵循所属目录的既有规则。

## 2. 模板

### 2.1 使用方法

复制第 2.3 节代码块中的 Markdown，替换 `〈占位内容〉`，删除填写提示和不适用的示例。实际文档标题使用“〈模块或主题名称〉规约”，文件名遵循所属目录规则；无既有规则时建议使用 `S_NN_<slug>.md`。本文自身是模板，保留在 skill 的 `references/`，不作为业务 spec 编号。不将本文第 1、3 节及第 2.4 节的表达示例复制为实际 spec 正文。

文档必须做到**内容合理、逻辑层次清晰、易于人类理解**。

先确认主题、设计依据、责任边界、术语和适用条件；依赖已有能力时明确复用与适配分工。再说明数据结构与事实归属，随后定义不变量、接口及必要的生命周期和跨接口行为，最后核对限制、兼容性和关联入口。已有权威定义直接引用，不为填满模板重复登记全部字段或规则。

正文描述已确认契约，并明确其与实现的关系。未确认方案放在 feature 或设计草案中；尚未实现的目标不得写成当前能力。确需保留已确认但待实现的契约时，在对应条款局部注明“待实现”、当前行为和适用范围，并链接唯一 feature / 计划，不维护第二份推进状态。

同一文档混合已实现与待实现条款时，分别标注受影响接口或行为，不仅在文档头部概括状态。“拟议”须明确是已确认但待实现，还是尚未确认；验收进度和执行结果通过计划或验证记录追溯。

裁剪时区分以下三种情况：

| 情况 | 含义 | 处理方式 |
| --- | --- | --- |
| 不适用 | 本主题不存在该行为或责任 | 删除不适用的小节或表格；容易误解时用一句话说明 |
| 未支持 | 行为与本主题有关，但当前没有能力保证 | 保留明确的限制及影响，不通过删除章节隐藏边界 |
| 未确认 | 决策尚未形成 | 在 feature 或设计草案中维护，不作为当前有效契约发布 |

复制后的文档使用 `#` 标题、`##` 主体章节、`###` 子主题。以下“正文第 1～7 节”指可复制模板中的章节，不指本文三大部分。裁剪后同步编号及内部引用；相对链接以实际 spec 所在目录为基准，不照搬模板路径或预填不存在的文件。

### 2.2 结构选择

完整骨架按“范围与条件 → 数据与归属 → 不变量 → 接口 → 生命周期 → 限制与兼容 → 关联与验证索引”组织。它提供展开顺序，不要求所有文档保留七章；模型可以合并到接口章，简短限制可以合并到范围章，无状态且无资源持有责任时可以删除生命周期章。

| 内容 | 要回答的问题 | 展开或合并条件 |
| --- | --- | --- |
| 元信息 | 规约主题、关联模块、修订日期和变更依据是什么？ | 固定放在正文前；设计依据、适用版本等字段按需增加 |
| 范围、术语与适用条件 | 谁负责什么？哪些概念、角色、作用域和模式影响条款？ | 基础内容；复杂术语分小节，已有定义直接引用 |
| 复用与适配边界 | 哪些能力复用已有契约？本模块补齐什么？哪些保证仍不具备？ | 涉及既有能力组合或宿主端口时在范围章展开；简单分工并入责任范围 |
| 数据结构与事实归属 | 对象如何关联？关键字段表示什么？谁保存和修改事实？ | 有独立模型时展开；简单模型并入接口章 |
| 不变量 | 在指定条件下哪些事实必须成立？ | 基础内容；引用已定义的对象与术语 |
| 接口契约 | 调用、校验、结果、副作用和失败分别是什么？ | 基础内容；局部规则按接口填写，共通规则只维护一次 |
| 状态与生命周期 | 状态怎样变化？资源怎样创建、结束和恢复？操作如何推进？ | 有独立状态、资源持有或恢复责任时展开 |
| 适用限制与兼容性 | 当前没有哪些保证？旧接口、旧数据或协议如何处理？ | 有独立内容时展开；简短内容并入范围章，不能遗漏相关边界 |
| 关联规约与验证索引 | 谁负责关联定义？怎样定位契约检查？ | 基础内容；简短链接或按需索引，不复制验收台账 |

进一步拆分时采用以下判断：

- **分小节：** 多个接口共享装配前置、失败或一致性规则时，在接口章集中定义；生命周期涉及多阶段或事件交接时，增加跨接口运行流程小节。
- **分章节：** 已有小节形成独立状态维度、协议或恢复责任，且需要单独阅读和维护时再拆章；不只因篇幅变长就增加章节。
- **分文件：** 出现可独立消费和维护的契约主题时再新建 spec；同一主题的行为调整优先修订原文，具体规则见第 3.8 节。

运行流程说明接受、提交、执行和通知的顺序；初始化装配说明构造、注册、绑定及依赖条件，两者分别组织。没有独立生命周期但存在跨接口交接时，运行流程并入接口章。事件载荷或文件格式定义在接口章，跨接口顺序在运行流程中引用，不维护两份协议。

权限、隔离、并发、资源限制及恢复只在契约涉及这些行为时补充。小规约可用短段落代替表格，没有公共函数时定义实际的事件、文件或协作协议；不为套用模板新增对象、机制或能力保证。

〈多种结束条件可能同时出现时，列明判定优先级、结局锁定时机和控制截止点；区分结局选定、状态保存及终态提交成功。没有对应竞争行为时删除此提示。〉

### 5.2 资源与持久化生命周期

〈按实际责任说明对象或资源的创建、绑定、释放和清理触发点；暂停、停止、删除等操作分别说明保留和清理范围。说明持久化来源、恢复入口、重建范围及不能恢复的状态；无对应责任时删除小节。〉

〈涉及恢复时，说明准入条件、原任务与新执行的身份关系、配置及授权边界；分别核对快照、日志尾部、当前有效指针和外部回执，按实际职责选择。区分缺失与确定为空，明确不能恢复的对象、必要引用的保留条件及未知 Schema 的处理。自动、显式或禁止恢复可用“条件 → 行为”矩阵表达；已形成终态或副作用结果不明时说明是否允许重跑。〉

### 5.3 跨接口运行流程（按需）

〈仅在多阶段、事件交接或跨模块推进时展开：输入 → 校验 → 提交权威事实 → 执行/通知 → 结束与清理。说明顺序和确认点，不展开内部算法或函数调用清单。〉

- **交接与完成：**〈各参与方负责什么；返回成功和后续事件分别证明什么；通知失败后已提交事实的处理方式〉。
- **持久化确认与部分成功：**〈各记录、内容、指针、回执的确认点及先后关系；跨存储是否有原子保证。中间步骤失败时保留哪些已生效事实，谁通过何种查询、重试或补偿继续推进〉。
- **等待与推进：**〈等待条件、条件提供者、继续推进者及退出条件；无等待上限时说明，不以“最终完成”替代规则〉。
- **中断与接管：**〈取消、暂停或重启后保留的事实和推进责任；引用对应生命周期及失败规则〉。

〈事件载荷引用第 4 节定义，流程不重新定义协议。必要时使用可编辑 Mermaid 图，图表与正文保持一致。〉

## 6. 适用限制与兼容性

- **当前限制：**〈本规约负责的能力未支持哪些入口、模式或保证及其影响；无则写“无”〉。
- **兼容边界（如有）：**〈旧接口、旧数据或协议当前是否受支持；新旧读写方能否共存；缺省及未知字段怎样处理〉。
- **替代关系（如有）：**〈被替代的条款及新维护位置；新旧契约同时生效时分别说明适用范围〉。

〈详细迁移方案及执行步骤链接 feature，推进状态链接唯一计划。已确认但待实现的契约在对应条款标注；本节只在需要时引用其限制，不复制条款或状态。简短内容可合并到第 1 节。〉

## 3. 维护规范

### 3.1 内容归属与事实表达

- **Spec 写契约。** 保留已确认的接口、协议、状态、边界及不变量；简短理由可以帮助理解，完整背景、方案比较、拒绝的方案和源码修改清单放在 feature。
- **架构写跨模块设计，计划写推进事实。** Spec 引用职责及验收依据，不复制负责人、排期、完成比例、PR 进度或完整测试日志。
- **代码和测试证明实现行为。** 文档中的接口名、默认值、错误码、状态枚举、路径和行为表须可与实现核对。发现差异时区分文档过时、实现缺陷和待实现设计，不能只因代码已有行为就将其追认为已确认契约。
- **未确认内容不能成为调用保证。** 草案和开放问题在设计文档中维护；已确认但待实现的条款明确标注当前缺口及适用范围。验证未执行时不能写“已通过”。

Spec 可采用基础章节、主题化分章、独立状态机和回归清单等不同组织形式。维护时检查内容是否完整，而不是要求所有文件机械地使用同一组标题；避免保留临时补注或重复元信息。

### 3.2 文件命名、标识与元信息

文件名和编号遵循目标目录规则。无既有规则时，建议采用 `S_NN_<slug>.md`：`S_` 标明文档类型，`NN` 为至少两位的递增序号，slug 使用小写英文及短横线，文件名不带日期。新建前检查现有文件及已分配编号，避免并行新增时发生冲突；无专门分配规则时按最大已用编号递增，不直接用文件数量推算，不复用或回填旧编号。

文档名称、编号和主题应一致。已有文件不因模板更新而批量重命名或重排编号；历史编号存在歧义时，引用完整文件名和主题，不只写 `S_NN`。确需改名或拆分时，在同一变更中修复入站链接并说明替代关系。

元信息集中维护类型、关联模块、最近修订日期和关联 feature；编号 / slug 按目录约定填写。每次修订更新“最近一次修订日期”为实际修订当天的 `YYYY-MM-DD`，避免正文再维护一份独立日期。关联 feature 使用可访问链接，无关联填“—”。元信息不填需提交后回填的 commit hash；具体实现版本或提交依据可以在链接的验证记录中追溯。

设计依据按需链接已确认的架构或设计章节；模型或共享术语的定义依据在范围章引用，避免重复抄录。依据发生变化时核对受影响条款，不能仅更新链接或用“冲突时以架构为准”保留相反的现行承诺。文档级状态说明只概括适用范围，逐项进度和验收事实在计划及验证记录中维护。

维护人、适用协议版本等字段仅在目标目录或契约需要时增加。规约版本与修订日期含义不同，不能以日期代替协议兼容范围，也不为纯文字修订虚构新协议版本。

### 3.3 条款、解释与约束用词

契约条款明确实现和调用方需遵守的规则；解释说明帮助理解条款，不额外增加保证；示例展示某种用法，不代表全部合法行为。关键保证写入明确条款，不能只藏在示例、图或代码注释中。示例只有一种事件顺序时，不能据此推导所有事件都保证该顺序。

“必须／不得”表达约束，“允许”表达合法选择，“建议”表达推荐。允许一种行为不等于保证所有实现都提供该能力，需要说明适用条件。对外行为契约说明调用方可以依赖的结果；内部设计约束说明模块必须怎样协作。容易误解的条款或接口局部注明性质，不要求给每段增加分类标签，也不把内部方法写入 spec 当作公共兼容承诺。

硬限制、可配置默认值和实测结果分别表达。达到硬限制后的行为属于契约，默认值是否可覆盖及何时生效需要明确；测量环境和实测结果在验证记录中维护，不能直接转写成长期性能保证。

### 3.4 不变量的写法

不变量采用“**适用条件 + 责任主体 + 必须成立的事实**”表达，一条约束应能独立判断是否违反。引用前文已定义的对象和术语，注明角色、模式、作用域及例外，区分始终成立的约束与只在初始化、提交或清理边界成立的约束；不能要求异步中间态满足只适用于完成时的条件。

建议使用稳定编号 `I-1`、`I-2` 等；跨文件引用附带 spec 链接。新增条款不随意重排已被引用的编号，废止或替代时说明新维护位置及影响范围。不将局部实现技巧、一般建议或未实现目标提升为系统不变量，也不要求所有段落增加编号。

### 3.5 接口、共通规则与失败边界

每个接口写清入口形态、调用方、前置条件、输入、成功输出、副作用和失败语义。输入说明覆盖必填与默认、缺省与空值、取值范围、单位及互斥条件；已有模型直接引用。配置说明校验与生效时机、声明值与实际生效值的关系。多角色或模式用行为矩阵列出合法组合、默认处理和拒绝路径，矩阵、示例与正文保持一致。

接口维护自己的特有错误和行为；多个接口共享的装配前置、幂等、冲突、超时、取消或异常转换规则集中维护一次，各接口引用。初始化装配说明构造、注册、绑定及依赖条件；运行顺序在生命周期或跨接口流程中维护，不混写或重复定义。

错误语义区分异常、结构化失败、空结果、降级和后台通知，并注明判定层、发生时机及已产生的副作用。部分成功和结果未知不能统一写成“失败，无影响”；提交后的通知失败是否回滚、如何查询确认，按实际保证说明。跨模块异常转换写明边界。

权限、隔离和资源限制只在相关契约中补充。授权需说明调用身份、对象作用域、检查位置及是否先于副作用；委托或后台执行注明实际身份，不以入口可访问代替对象操作权限。限额需说明计量对象、单位、生效时机及超限结果；无相应行为时不强行新增安全或性能章节。

涉及事件流、条件更新、知识使用或外部副作用时，按可复制模板第 4.3 节检查适用项。协议能力按实际保证填写；同进程协作不自动需要跨进程围栏，外部调用也不自动保证幂等。共通协议约束维护一次，映射表、行为矩阵及消费者引用同一规则。

### 3.6 数据结构与事实归属

数据结构说明对象关系、关键字段、语义、作用域和修改入口，区分配置、持久事实、内存状态、缓存与派生视图。对象表维护事实归属，字段表维护关键类型、默认值、单位和约束；可以使用短段落或只选一张表，不要求为全部内部字段建立台账。

创建、释放、持久化和恢复在生命周期章节维护，不在字段表重复登记。跨进程或存储契约注明必要的序列化形态及读写双方；路径、标识和常量引用权威定义。完整 Schema 已有唯一维护位置时直接引用，spec 只展开本规约负责的语义和约束，不复制另一份字段清单。

### 3.7 状态、生命周期与跨接口推进

有独立状态、资源持有或恢复责任时展开生命周期章节。状态机列明合法状态或字段组合、触发者、守卫、目标状态和失败后的结果；不同状态维度分别定义，未列出的转移明确处理方式。生命周期说明创建、绑定、释放和清理触发点；暂停、停止、删除等操作行为不同时分别描述保留范围和后续入口。

恢复说明持久事实来源、重建范围及不能恢复的状态。读取历史或重建视图本身不能证明原任务可恢复；没有恢复保证时明确限制，不以删除小节隐藏相关边界。

恢复涉及多种事实时，逐项说明快照、日志、当前指针和外部回执的作用及核对边界，不把任何单一记录视为全部事实。跨存储写入明确各自确认点、部分成功和继续推进的责任；指针或发布版本已生效后，后续失败是否允许回滚按实际契约说明。恢复前核对准入、身份、配置、权限及必要引用，不从超时或缺失回执推断可以重跑。

多阶段或跨模块交接时说明操作顺序、责任和确认点。请求接受、事实提交、执行完成和结果通知分别表示什么；事件载荷或文件格式引用接口定义，失败和竞争结果引用其唯一规则。流程只保留可观察的顺序与交接保证，内部算法、调用清单和源码步骤放在 feature。

多种结束条件竞争时定义优先级与判定截止点，说明锁定后到达的控制和迟到结果如何处理。结局锁定不能代替持久化确认；状态保存、终态提交或结果交接失败仍按各自错误规则处理。

涉及等待时说明等待条件、条件提供者、继续推进者及退出条件；无等待上限时明确说明，不以“最终完成”暗示有限时间保证。取消、暂停或重启后的事实保留与推进责任按实际契约说明。没有对应行为时裁剪提示，不为模板新增自动接管、补偿或严格顺序保证。

### 3.8 文档关系、兼容与拆分

同一责任范围内调整已有行为时修订原 spec；新增可独立消费和维护的接口、协议或生命周期主题时考虑新建。仅记录一次开发过程时写入 feature；文件变长时先调整小节，不自动拆文件。一个 feature 可以影响多份 spec，一份 spec 也可以关联多个 feature。

每个接口、模型或共享不变量指定唯一维护位置。关联文档说明“对方负责什么、本文件负责什么”；本文件可以概括交接点，但不复制完整定义。上层规约描述边界和依赖，下层规约展开具体行为，不维护两套同名状态机。

复用边界引用已有能力的权威规约，列明适用条件、本模块适配责任和仍未覆盖的保证。宿主端口或底层实现负责的保证写清承担方；形状校验、模拟实现或单次调用成功不能替代持久化、隔离及恢复保证的验证。选择理由和详细差距分析在 feature 维护。

兼容性只描述当前支持范围、旧接口和旧数据的处理边界，以及必要的缺省或未知字段语义；详细迁移步骤放在 feature，执行状态放在计划。新旧契约须同时生效时明确各自适用范围，不能直接覆盖旧定义。新增规约局部替代旧规约时，明确替代的接口、模式或条款，同时修订旧文档的相关正文及引用。不得只在新文档宣告“旧行为废止”，让旧文档继续对外承诺相反行为。历史方案和废弃原因链接 feature，现行 spec 保持当前契约清楚可读。

采用标准 Markdown 相对链接，必要时链接章节；实际路径按 spec 所在目录核对。文件或标题变化时检查引用方。Mermaid、状态表、目录树和行为矩阵都属于契约表达，随正文同步；Markdown 表格中的竖线须转义，示例代码注明语言，示意图不得扩大正文承诺。

### 3.9 更新触发与同步流程

| 变化 | Spec 中需要核对或更新的内容 | 关联维护位置 |
| --- | --- | --- |
| API、事件、配置或文件格式变化 | 形态、参数、默认值、输出、校验及错误语义 | 调用方、读写双方、相关 feature 及契约检查 |
| 状态或持久化行为变化 | 不变量、合法转移、字段生命周期、恢复和清理边界 | 状态定义、存储/恢复实现及相邻 spec |
| 角色、模式、并发或资源约束变化 | 适用条件、行为矩阵、门禁、超限及取消语义 | 消费方、模拟实现及验证记录 |
| 模块责任、复用边界、唯一入口或事实权威变化 | 范围、复用条件、适配责任、依赖方向、修改入口及关联规约分工 | 架构、Overview、目录约定及受影响 spec |
| 设计依据变化 | 受影响条款、当前实现缺口及新旧契约的适用或替代关系 | 已确认设计、相关 feature 及受影响 spec |
| 兼容策略或支持范围变化 | 当前承诺、旧接口/旧数据边界及替代关系 | 迁移 feature、调用方及相关计划 |
| 纯内部重构且契约不变 | 检查符号、路径、示例和链接是否仍准确 | 按目录要求维护实现或 feature 说明 |

按以下顺序维护：

1. **设计前读取。** 先读相关 spec、feature 及目录约定，核对既有边界和此前决策，识别本次可能改变的契约。
2. **确定范围和依据。** 按 [仓库 AGENTS.md](../../../../AGENTS.md) 判断是否需要新建或更新 feature，明确本次方案、实现范围和契约影响。涉及架构调整时，按已有授权和适用规则处理；普通契约同步不额外增加确认门槛。模板用于其他目录时，遵守该目录的要求。
3. **方案确定后同步。** 修订主责 spec，核对相关条款、接口、字段、状态表和图；新契约按独立主题新建文件。未实现条款保留明确标记，不先写成已完成事实。
4. **实现过程中核对两端。** 检查入口与消费方、写入与恢复方、事件发布与订阅方，以及模拟实现是否仍符合相同契约。契约调整同步相关 feature 和受影响的 spec；验收或依赖变化同步唯一开发计划。
5. **验证并如实记录。** 将受影响条款映射到适用检查；结果写入 feature 或验证记录，状态和交付证据写入计划。Spec 引用入口与必要结论，不复制全部执行日志。
6. **交付前检查。** 更新修订日期、关系及链接，检查旧表述是否残留。代码、测试和文档在同一工作单元中保持一致；提交组织遵循目标目录既有规则。

发现文档与实现不一致时，先判断哪一项过时或有缺陷。文档过时则修正文档；实现违背已确认契约则修实现或明确提出契约调整；涉及架构变更继续遵循目标目录确认要求。不得默默降低保证来掩盖实现缺口，也不沿用过时的实现细节。

### 3.10 验证索引与变更历史

Spec 维护预期契约，并用稳定条款或接口名称定位权威测试、命令或验证记录入口。简短索引可用列表，不强制新增表格；没有入口时照实说明。完整验收场景、测试步骤、环境、版本、日期及实际结果在 feature 或验证记录中维护，开发计划引用证据判断完成，不在 spec 复制台账。

检查覆盖本次改变的行为、不变量、错误路径和适用的状态、兼容边界。模拟验证只证明其覆盖范围；真实对端、跨进程或恢复行为属于承诺时需相应层级的验证。未执行、未知和失败如实标注，存在测试文件或更新修订日期均不能证明验证通过。

历史通过版本控制和关联 feature 追溯，spec 保持当前契约完整，不逐次追加实施日志。局部条款替代只说明对应范围，不将整个文档误标为废弃；后续任务、负责人及推进状态在 feature 或计划中维护。

### 3.11 维护后的一致性检查

1. **结构与裁剪一致。** 使用说明、结构表、可复制模板和维护规则对应；合并或删节后编号、阅读路径及内部引用已同步。
2. **范围与条件明确。** 主责、术语、角色、模式和作用域清楚；复用条件、适配责任和未覆盖保证有据可查；不适用、未支持和未确认分别处理，关键限制没有因裁剪消失。
3. **元信息准确。** 文件名、主题和编号相符，修订日期、关联 feature 及适用的设计依据已更新，链接能定位正确文档与章节。
4. **条款表达清楚。** 不变量可检查、引用稳定，契约与解释及示例不混淆；对外保证和内部约束没有产生错误的兼容承诺。
5. **接口完整。** 输入、校验、结果、副作用及失败语义一致，非法组合有明确行为；适用的顺序、去重、条件更新、授权传播、容量和副作用边界已核对；共通规则只维护一次，局部规则没有冲突。
6. **数据和生命周期对应。** 模型、字段、事实权威及修改入口明确；状态、结局竞争、恢复准入、清理、等待推进及跨存储确认点与图表及正文一致，部分成功没有被误写为全部回滚。
7. **限制与兼容清楚。** 当前支持范围和替代关系明确，旧文档不继续承诺已废止行为，迁移步骤及进度没有重复进入 spec。
8. **验证如实可追溯。** 检查入口可定位，模拟与真实验证不混淆；待实现目标、当前保证和执行结果分别表达。
9. **维护范围完整。** 关联 spec、feature、消费方及计划按影响范围同步；没有新增重复 Schema、验收台账或详细历史记录，架构调整符合目录要求。
