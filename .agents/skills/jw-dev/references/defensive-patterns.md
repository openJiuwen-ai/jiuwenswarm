# 从故障证据提炼防错模式

修复后判断根因是否揭示可复用的错误类别。只为已有证据支持、会改变后续实现/检视判断的约束提炼规则；
普通局部 typo、纯文案或单例偶发故障无需上升为全仓标准。
本文件是提炼方法，不是已经验证的故障目录，不把其他项目的经验自动登记为本仓事实。

## 提炼步骤

1. 以 bugfix 的复现、失败证据、根因和回归为来源，先找真实拥有该状态、资源或协议的模块。
2. 搜索现有 AGENTS/spec 和相关 bugfix，判断是已有约束被破坏、缺少回归，还是需要增加一条新约束。
   已有规则足够时修引用或补测试，不复制同义规则。
3. 写出适用条件、必须维持的关系、可观察失败、边界/反例、原始故障记录及回归入口。
   不保留无助于决策的逐步排查流水；没有重复案例时说明证据范围，不伪称反复发生。
4. 运行与修复匹配的回归；不变量需要负向对照时，验证非法状态会经真实入口因预期规则失败。
5. 将规则放在最低的有效维护位置，检视与开发只读取受影响领域的条目。

## 维护位置

- 模块协作/维护约束：在该模块已有 AGENTS 中保留简短规则，链接长期依据。
- 跨模块接口、状态机或资源不变量：更新所属 spec/协议，链接来源 bugfix 和回归用例。
- 故障证据与修复因果：继续保留在 bugfix；测试锁定行为，注释只说明局部非显然约束。
- 多模块确需共享时，才使用现有公共规则入口集中维护；不因为一次局部失败扩充根 AGENTS。

正文可用以下结构，按需要压缩，不要求新增固定格式文件：

> 适用条件 → 所属模块/权威状态 → 应保持的关系 → 会怎样失败 → 来源记录与回归 → 不适用情况。

例如可审视资源释放是否等待实际停止、异步状态是否能证明某次输入完成、多个独立结果是否分别报告；
这些只是查找问题的方向，只有本仓证据支持后才能写成具体规则，且需说明回调异常等语义的模块差异。

## 修订与复查

新证据推翻模式的适用范围时，修订当前规则并在原 bugfix/关联 feature 留下原因与替代链接；
不覆盖历史失败和验证事实，不把“提高防御性”作为新增冗余状态或吞错分支的理由。
检视确认规则有因果依据、落在真实执行边界、测试能暴露原故障，而不是只匹配文案或内部方法名。
