# 开发落地记忆与归档

规则沿用源技能的开发记忆结构，适用于 JiuwenSwarm 各模块。代码看 `git log` / 模块内 AGENTS.md，
本目录只承载**三类长期文档**——规约（specs）、特性变更（features）与缺陷修复（bugfix）。

## 目录用途

| 目录 | 用途 | 关联触发 |
|---|---|---|
| `specs/` | 模块设计规约：跨子模块的契约、协议、边界、不变量。**长期有效**，描述"系统是什么样"。 | 任何**模块设计规约变动**都必须同步更新对应 spec 文档；新规约 = 新 spec 文件 |
| `features/` | 特性变更归档：一次完整的设计/重构/新功能落地的来龙去脉。**只增不删**，描述"为什么这样改"。 | 每次特性更新提交代码前都必须归档；归档日期写进文档元信息 |
| `bugfix/` | 缺陷修复归档：一次线上/测试问题的现象、定位证据、根因与修复决策。**只增不删**，描述"为什么会坏、为什么这样修"。 | 根因涉及契约/不变量、或定位过程值得复用的缺陷修复必须归档；契约变了同步修订 spec |

`specs/` 是状态快照（描述当前），`features/` 是变更日志（描述过程），`bugfix/` 是故障档案
（描述失效）。当 spec 改了，通常对应一份 feature 或 bugfix 文档解释"为什么改成这样"。

## 命名与位置

- spec：`.agents/agent-docs/specs/<module>/S_NN_<slug>.md`，沿用现有编号。
- feature：`.agents/agent-docs/features/<module>/F_YYYYMMDD_HHMM_<slug>.md`。
- bugfix：`.agents/agent-docs/bugfix/<module>/B_YYYYMMDD_HHMM_<slug>.md`。
- 时间为 Asia/Singapore、精确到分钟，slug 使用小写英文和短横线。完整名称重名先确认是否为同一记录；否则细化主题，不覆盖。
- 已有编号和文件名不调整，不为 feature / bugfix 分配递增号；修订不改创建标识。

## 设计与实施归档边界

设计是开发前资产，管理字段留在设计中，评审按日期修订。features 是开发落地后的实施与决策归档，
引用设计标识，记录实际实现、实际取舍、设计偏差、验证证据及遗留，不复制整篇设计，不回填开发事实到设计。
可复制 [feature.md](../assets/templates/feature.md)，其验证与遗留骨架提取自原特性方案模板。

## 内容约定

### specs/ 文档结构（建议骨架）

```markdown
# <Spec 名称>

## 元信息
| 项 | 值 |
|---|---|
| 类型 | spec |
| 关联模块 | jiuwenswarm/<module>/<path> |
| 最近一次修订日期 | <YYYY-MM-DD> |
| 关联 feature | F_YYYYMMDD_HHMM_<slug>.md（可选） |

## 范围 / 边界
（这个规约管什么、不管什么）

## 不变量
（系统在任意时刻必须为真的事实）

## 接口契约
（公共 API 形态、参数语义、错误语义）

## 数据结构
（关键状态字段及其生命周期）

## 与其它 spec 的关系
```

### features/ 文档结构（简要骨架）

```markdown
# <Feature 名称>

## 元信息
| 项 | 值 |
|---|---|
| 日期 | YYYY-MM-DD |
| 范围 | <修改路径> |
| 测试基线 | <pytest 结果> |
| Refs | #<issue> |

## 背景
（这个改动为什么必要——上下文、历史、痛点）

## 数据结构 / 状态机
（如果改动触及数据模型，画清楚）

## 决策
（选了什么方案，每条决策对应代码层面的体现）

## 拒绝的方案
（评估过但没选的方案 + 为什么没选——避免后人重蹈覆辙）

## 验证
（测试 / 行为基线）

## 已知遗留
（这次没做但下次应该做的 follow-up）
```

### bugfix/ 文档结构（建议骨架）

```markdown
# <缺陷标题：一句话写清"什么条件下坏了什么">

## 元信息
| 项 | 值 |
|---|---|
| 日期 | YYYY-MM-DD |
| 严重程度 | <高/中/低 + 影响面> |
| 范围 | <修改路径> |
| 测试基线 | <pytest 结果> |
| 关联 spec | S_NN_<slug>.md（契约有变时必填） |

## 现象
（用户看到了什么；可观察到的日志 / 接口 / 数据证据）

## 根因
（证据链 + 代码层面的失效路径；写清复现条件）

## 决策
（修复原则与每处代码改动）

## 拒绝的方案
（评估过但没选的修法 + 为什么没选）

## 验证
（回归用例、修复前复现、测试基线）

## 已知遗留
（同类风险中这次没收紧的部分）
```

可以根据情况增减小节，但 **"决策"和"拒绝的方案"是 features / bugfix 的核心**，缺它们等于
没归档——commit message 已经写了 what，feature 文档要写 why-not。

## 同步与模块提交约定

修改前阅读相关 spec 与历史 feature / bugfix；实现、测试、spec 和开发记忆在同一工作单元内保持一致。
读取到与当前代码不一致的描述时，当场核实并更新，不能把历史意图当作当前保证。
每次 spec 修订更新“最近一次修订日期”；feature / bugfix 元信息不写需要提交后回填的 commit hash。

归档规则不新增提交权限，也不引入 agent-core 的专属拆提交规则。
提交组织遵循 JiuwenSwarm 根目录及目标目录约定，使用英文 Conventional Commits。
所有提交先展示具体计划并取得用户确认；PR 创建另按仓库授权规则处理。

## 反模式

- **把 commit message 复制粘贴当 feature 归档**：feature 要写 commit 写不下的东西（拒绝的方案、设计思路、未来 follow-up），不是 commit 的拷贝
- **靠 docs 维护代码行为**：实现行为是代码 + 单测的事；docs 描述意图与决策，不是 source of truth
- **不更新 specs**：如果模块契约改了但对应 spec 没改，下次重构时读 spec 的人会被误导。提交前自查
- **N 多个小 feature 文档**：一次连贯的设计变动归档为**一份** feature 文档，不要拆碎；多 commit 落地的特性也归档为一份，不按 commit 拆
- **在元信息里写 commit hash**：spec / feature / bugfix 元信息只写日期（`YYYY-MM-DD`），不写 commit hash——hash 需要"提交后回填"，来回反复且容易过时
