# JiuwenSwarm 代码检视

以 JiuwenSwarm 的技术方向和项目标准为主要检视依据，针对用户指定的代码范围形成有证据的结论。
接受本地工作区改动、单个或多个明确提交、连续提交范围，以及已确认基线与候选的分支差异；不要求存在 PR。

检视前读取适用的 [仓库技术标准](references/technical-route.md)、目标目录的项目指令及实际代码。
同目录存在 `AGENTS.override.md` 时优先于 `AGENTS.md`，更具体目录规则优先于上层规则；仍以用户和更高优先级指令为准。
技术参考带有来源版本，不将其中的历史实现描述直接视为当前事实；按待审版本重新核对适用标准。
范围确认、比较口径、证据验证、结果输出及复查按 [代码检视流程补充](references/review-workflow.md) 执行。
标准回答检查什么，补充流程说明怎样建立与报告证据，不重复维护两套标准。

## 技术方向与架构

- 核对模块职责、依赖方向、事实源、资源所有权、公共契约和已确认迁移计划。
  新引入的架构冲突属于重要风险；有意调整架构需说明原因、受影响调用链、迁移或退役安排及验证。
  现有过渡代码不能自动成为复制相同耦合的依据。
- 检查是否绕过 Runtime、Gateway/AgentServer、Channel、权限和持久化边界，是否新增并行实现、
  同一状态的竞争权威或重复生命周期控制。只应用与修改范围有关的标准。
- 核对受影响模式、渠道、配置、工具、会话、消息协议与错误路径之间的交互。
  同一共享概念的身份、状态和行为应在各入口一致，有意差异需有依据。
- 智能体改动按技术参考检查 openJiuwen Harness/Rail 契约及实际装配链，覆盖相关模式注册、
  生命周期、优先级、热更新、权限和团队成员 provider；对照候选实际使用的框架版本。

## 检视维度

| 维度 | 主要判断 |
|---|---|
| 整体架构 | 是否符合当前架构或已确认的演进方向？边界、依赖与所有权是否清楚？ |
| 功能交互 | 是否破坏相邻功能、模式和渠道，特别是共享会话、事件、权限与配置语义？ |
| 文档覆盖 | 受影响的用户、开发、API、配置、运维、迁移、示例与索引是否维护？先指出具体缺口，再判断文档缺失是否构成问题。 |
| 文档与代码 | 接口、默认值、状态、错误与示例是否符合实现？已实现行为与计划是否区分？ |
| 实现与声明 | 需求、设计、开发说明与测试计划中的声明是否实现并有证据？是否遗漏、隐藏或产生相反行为？ |
| 修改范围 | 是否夹带无关重构、依赖、锁文件、配置、生成资源、公共 API 或默认行为变化？必要扩展是否说明并核对影响？ |
| 代码规范 | 职责、命名、类型、错误、边界、复杂度、可读性是否符合适用语言与目录约定？遵守本地禁止格式化和静态检查的约束。 |
| 复用 | 是否复用现有协议、共享逻辑、组件、Rail、工具与生命周期入口？新抽象是否有独立职责，或制造第二条路径？ |
| 后续演进 | 是否引入阻碍已知方向的耦合、全局状态、永久兼容分支或难迁移数据契约？将有依据的阻碍与推测风险区分。 |

## 行为、兼容与交付

- **正确性与回归**：核对正常、边界、失败、重试、取消、并发、关闭与恢复路径。
  测试证明可观察契约；孤立单测不能代替实际调用链、装配和消费者验证。
- **兼容与迁移**：核对公共 API、E2A/事件、存储、配置、旧客户端与版本转换。
  有意破坏兼容需有明确决策和迁移方案。
- **安全与资源**：核对权限、不可信输入、敏感数据、文件与网络访问，以及任务、连接、锁和后台工作的所有权与释放。
- **运维与交付**：按影响检查性能、可观测性、依赖锁定、构建打包、平台支持与部署行为。
  定向单测通过不覆盖适用的上层测试或 CI 失败；没有对应证据时明确说明限制。

## 证据、结论与复查

仅将本次变更新建或明显加重的问题认定为变更引入；已有技术债作为上下文，除非本次改动依赖它。
固定基线、候选和完整范围，沿真实调用关系核对问题；疑点尚未验证时标明待核实，不冒充已确认缺陷。
按补充流程输出 P0–P3、精确位置、触发条件、实际与预期行为、影响和证据，同时交代覆盖范围与验证限制。
实现问题交给 `jw-dev`，方案缺口交给 `jw-design`；修复后重新固定候选并核对原问题及相关回归。

检视期间保持待审代码不变，不自动提交、切换分支、改写历史或启动多代理，不运行格式化或静态检查。
本技能不扩展远端平台操作权限；用户提供的 PR 信息可作为变更背景，不作为检视前置条件。
