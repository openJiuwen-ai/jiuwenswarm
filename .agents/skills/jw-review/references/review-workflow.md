# 代码检视流程与差异证据

本参考补充 [主技能](../SKILL.md) 的版本/范围固定、差异分析、疑点验证与复查。
项目技术定位与模块依据使用 [仓库技术参考](technical-route.md)，按实际影响选择读取。
针对明确的代码版本和变更范围开展检视，输出可定位、可复现、可交给开发处理的问题。
以用户目标、已确认设计、当前 spec 和实际代码为依据，沿执行路径判断变更是否正确。

## 输入与范围

接受以下输入：

- 本地工作区改动：明确是已暂存、未暂存，还是两者全部；范围内的新文件一并读取。
- 已确认的单个提交、连续提交范围，或明确列出的多个提交。
- 已确认基线和候选版本的本地分支差异，先将两端引用解析为具体 SHA。

记录工作区状态、范围、基线与候选版本、涉及模块，以及可用的需求、设计、spec 与测试证据。
用户已明确范围时直接使用；范围不明且会改变检视对象时先澄清，不自行选择提交或混入其他改动。
设计文档缺失时依据明确需求、现有契约和代码开展检视，并说明缺失依据对结论的影响。

本流程不要求存在 PR。主要使用本地仓库、代码、文档和测试证据；
已有 PR/CI 资料只作为对应版本的补充证据，不提供平台交互授权，不要求发布评论或改变远端状态。
检视期间保持待审代码不变；发现问题后交给开发处理，修复后进入复查。
不自动提交、切换分支、改写历史或启动多代理，不运行格式化或静态检查。
默认保持候选代码及文档只读；发现问题交接开发，不边检视边修复以致候选漂移。

## 检视流程

### 1. 固定候选与比较口径

先查看 `git status --short`，再按已确认范围读取差异：

| 范围 | 读取方式 |
|---|---|
| 已暂存改动 | `git diff --cached` |
| 未暂存的已跟踪文件 | `git diff` |
| 工作区全部已跟踪改动 | `git diff HEAD` |
| 范围内未跟踪文件 | 用 `git ls-files --others --exclude-standard` 定位后读取内容 |
| 单个提交 | `git show --find-renames <sha>` |
| 连续提交范围 | `git log <base>..<head>` 确认提交集合，`git diff --find-renames <base> <head>` 看净变化 |

连续提交范围的 `<base>` 是不包含在候选集合中的基线；若用户给出首个待审提交，
先确认是否包含该提交，再确定基线。显式列出的非连续提交逐个检查，不能用首尾差异代替指定集合。
合并提交需要确认相对哪个父提交检视；分支比较需明确是两端快照差异还是从共同祖先以来的改动。
合并提交有多个父节点，不能未经确认使用 `^` 选择其中一个作为基线。

记录完整的文件清单及新增、删除、重命名；目录外的调用者和消费者可作为上下文读取，
但报告中的问题要说明与本次变更的因果关系。

对纯提交或分支检视，代码与文档依据均读取对应版本；工作区中的新版 AGENTS、spec 或测试
不自动代表基线或候选。必要时使用 `git show <revision>:<path>` 读取两侧文件。
工作区检视同时考虑 staged、unstaged 与范围内新文件，不把 `git diff HEAD` 当成包含未跟踪文件的完整快照。
依赖锁、可选 extras、构建入口和包资源变化也列入范围；不只统计 Python diff。

### 2. 建立模块规则与契约上下文

按变更路径读取根规则、所属模块和受影响子模块的 AGENTS.md，以及实际引用的 spec、导出、测试和示例。
跨目录移动核对旧、新规则；跨模块调用同时核对两侧约束，不能用一份根规则覆盖所有模块。
没有模块 AGENTS/spec 时记录缺失依据，不为了完成检查表伪造规则或先建设全仓文档。

按实际风险维护简短依据清单；复杂跨模块改动可用下表，简单改动可写成紧凑条目：

| 受影响模块/路径 | 适用规则 | spec/协议/schema 文件及条款 | 基线/候选实现入口 | 测试与依据缺口 |
|---|---|---|---|---|

从模块入口、已有协议与 schema 查找相关行为、范围、不变量、接口和失败语义；
集中 spec 尚未建档时引用真实协议/类型及行为测试，不假定已有模块 spec 对照表。
涉及 core 时分别核对基线与候选的依赖版本；editable checkout 的验证结果单列，
不可将当前工作区的新规则、spec 或依赖实现直接归给待审提交。
features/bugfix 用于理解历史决策和拒绝的方案，design 用于核对目标及确认范围，不相互替代。
文档引用已迁往其他仓库时按索引或迁移说明定位；不将仍能搜到旧标识当成资料已读。

按真实调用关系追踪入口、注册/装配、核心逻辑、状态读写、输出和消费方。
如 AGENTS、spec、测试和代码互相矛盾，分别记录现状、预期与证据，核实是否由本次修改造成；
当前实现不是正确性的自证，旧文档也不是未经核实即可执行的规则。

使用 [上下文与流程](../../jw-dev/references/context-and-flows.md) 区分导航资料、当前契约、实际代码和运行证据。
跨边界变化核对产生方、载体、权威状态/派生投影、消费与恢复、失败和最终输出；记录未追通环节的影响。
结论区分已证实、推断和待核实，不因旧审计状态或未变的符号指纹跳过消费者变化。

### 3. 逐项审视变化前后与影响传播

按主技能的检视维度和适用技术参考开展差异分析；只引用文件名或罗列候选的函数不算完成检视。
对重要变化可以用下面的证据结构，不要求为每一行代码机械建表：

| 差异/触发场景 | 基线行为 | 候选行为 | AGENTS/spec/协议/设计依据 | 调用方与消费者 | 回归或复现证据 |
|---|---|---|---|---|---|

- **新增**：是否有真实需求、公共入口与消费者？声明的能力是否完成注册、装配、执行、持久化及清理？
- **修改**：对比签名、默认值、权限、错误、状态转移、事件顺序和副作用，而不只比较结果值。
- **删除**：核对公开导出、旧调用方、序列化/codec、恢复、兼容路径与示例，不能以仓内无直接引用判定可删。
- **移动/重命名**：核对 import、发现/注册机制、打包资源、路径语义及新旧目录约束。
- **条件路径**：检查默认/非默认配置、Work/Code/Plan/Team、受影响 Web/TUI/ACP/IM/Process CLI/SDK、流式/非流式、并发/取消和热更新/恢复的相关组合；不机械要求所有无关组合重测。
- **对称路径**：写入与读取、register/unregister、acquire/release、save/restore、请求与响应、start/stop 是否一起更新？
- **影响传播**：追踪枚举、schema、prompt、工具描述、renderer、持久化、前后端读模型、SDK、测试替身与下游读者，不能只改生产方。

仅报告可说明因果关系和可观察影响的问题。未经批准的契约变化、有意迁移和原有文档漂移分别判断；
已确认迁移需检查兼容策略与实际覆盖，不把任何差异都判成缺陷。
按风险说明已覆盖路径、未覆盖文件及其原因；范围变化或未读部分不能被“整体看起来合理”代替。

### 4. 验证疑点与回归证据

对疑点给出具体输入、状态或时序，核对完整调用链，必要时进行最小复现或运行相关行为测试。
提交范围与当前工作区版本不同时，在匹配候选的独立临时环境验证；
未对齐版本时不能将当前工作区的运行结果归给候选提交。

检查已有回归用例和实际消费方式，新增定向测试通过不能替代兼容性检查。
失败区分为本次引入、基线已有和环境受限；必要时用同条件基线对照。
记录执行命令、实际版本、依赖、结果与未执行项。仅运行与变化相关的行为测试，不执行格式化/静态检查。
Python 定向入口使用 `uv run pytest <实际测试路径>`，广泛回归按影响选择 `make test-unit`、
`make test-integration` 或 `make test`；执行前遵循仓库 Python 环境初始化要求。
前端从对应 `package.json` 选择相关 `npm run test:<功能>`；含类型检查的构建脚本不作为本地默认验证入口。
涉及 UI 的差异核对受影响交互、主题、窄屏、无障碍和中英文文案；共享组件检查真实调用方，
前端规则明确仅作用于本次触及代码时，不借检视要求全仓迁移。未进行浏览器验证时单列限制。
测试或复现会产生外部副作用时遵循用户授权。
证据不足的疑点明确标为待核实，不作为已确认缺陷；未运行测试不写成测试通过。

对本次模型/用户可见行为、副作用或生命周期差异，按
[行为证据](../../jw-dev/references/behavior-evidence.md) 检查真实入口、预期来源和必要负向对照。
审视快照预期 diff，不能把归一化吞掉的差异或自动刷新的工件当成正确性证明。
旧证据复用需核实版本/依赖/配置前提；失效或未确认的范围标为待重验。
关联记录的续写/替代按 [决策关系](../../jw-design/references/decision-records.md) 判断，不机械要求新建文件。

### 5. 输出结论与交接复查

先给出问题，按影响排序。每条问题包含：

- 严重度与简短标题：P0 紧急阻断，P1 高影响缺陷，P2 一般缺陷，P3 低影响改进。
- 精确文件和尽量小的行号范围；删除代码的问题注明基线侧位置。
- 触发条件、实际行为、预期行为、影响，以及代码或复现证据。
- 可行的修正方向；不要求在检视中直接实现修复。

结论同时说明检视版本、比较口径、覆盖模块、实际读取的 AGENTS/spec/协议、技术方向及规约符合性、
测试证据、未覆盖项与剩余疑点。文档同步缺口说明具体遗漏，不因没有某种文档机械判错。
没有发现问题时写“在上述范围内未发现可确认的问题”，并说明验证限制。
阻塞问题未解决或关键场景无法验证时明确指出，不能仅凭测试通过认定检视通过。

实现问题交给 `jw-dev`，方案缺口交给 `jw-design`；交接附范围、问题定位、证据和复查条件。
修复后固定新候选，复查原问题、修复引入的影响与相关回归。
输出结论前核对候选 SHA 和工作区差异是否变化；变化后说明旧结论覆盖范围并复查新增差异，
不将旧版本的结论直接沿用到新候选。
