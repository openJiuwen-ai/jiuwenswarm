# jw-testing

将开发交接信息整理成测试人员能够独立执行、结果能够追溯的转测文档。
模板与状态规则迁自原 agent_teams 设计文档实践，独立于 `jw-design` 的设计生命周期。

## 撰写步骤

1. 阅读关联设计、当前 spec、实际代码改动、开发计划和已有测试证据。
   分清计划行为、已实现范围、接口占位和已知缺陷；不以代码合并或方案批准推断测试通过。
2. 明确转测范围、排除项、目标版本、测试环境、依赖服务与数据准备、执行入口和验收依据。
   缺失的关键信息标为待确认，并说明影响；不编造环境、负责人、命令、结果或签字。
3. 使用 [testing.md](assets/templates/testing.md) 编写文档。
   按范围组织功能、边界、异常、兼容与必要的非功能场景，每项说明前置条件、操作步骤与可观察预期。
   用例关联设计或 spec 的具体行为，不用“功能正常”等笼统表述替代判据。
4. 单独记录计划用例和实际执行结果；已有证据注明环境、版本、命令或报告入口及适用边界。
   未执行、失败、阻塞分别说明；通过率等统计只根据实际执行记录计算。
5. 整理缺陷、严重程度、影响用例、风险、遗留与测试交接条件。
   原因分析和修复过程引用 `jw-dev` 的 bugfix 记忆，避免复制维护两份故障档案。
6. 按 [testing-lifecycle.md](references/testing-lifecycle.md) 记录真实评审与测试进展。
   仅要求撰写时交付草稿和待确认项，不自动推进到已测试或已验收。

## 存放与标识

- 默认输出 `.agents/agent-docs/designs/testing/<关联设计目录名>/testing.md`，附件放同目录 `assets/`。
  新设计使用 `D-YYYYMMDD-HHMM-<slug>`，Asia/Singapore、精确到分钟；旧 SDD 标识继续有效。
- 转测文档的 `id`、`design-id` 引用关联设计，`slug` 与目录主题一致。
  没有关联设计时优先遵循用户指定位置，以 feature / spec 作为依据，明确关联设计缺失，不虚构设计编号。
- 复用已有转测文档并记录迭代，不覆盖无关资料；不因模板更新重命名旧资料。
- 该输出目录目前被 Git 忽略，仅本地保存；本 skill 的规则和模板正常入库。
  不自动恢复目录跟踪，不将转测文档加入设计索引，不重新引入设计阶段的 testing 状态。

## 阶段交接

从 `jw-dev` 接收实际实现范围、变更版本、验证记录、限制与风险；可按现有资料独立撰写转测文档。
交付文档路径、用例范围、执行准备、证据、待确认项与当前状态。
用户要求执行测试时另按授权和仓库环境执行，只更新实际覆盖的结果；
不自动调用外部服务、提交文件、创建 PR 或写入审批结论，不运行格式化或静态检查。
