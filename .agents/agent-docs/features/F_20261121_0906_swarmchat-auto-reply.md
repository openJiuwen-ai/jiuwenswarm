# SwarmChat 群成员自动判断回复实施记录

## 关联依据

- 设计：`D-20261120-1701-swarmchat-auto-reply`（草稿，未经评审；需求方在 2026-11-21 要求开始实现）。core 侧为 agent-core 的 `D-20261121-0832-group-member-notification`。
- spec：`S_02_colleague-swarmchat` 新增“自动判断回复”一节。
- 日期：2026-11-21。
- 实际实施范围：群级判断配置与成员回复规则、判断与通知模块、三类成员的送达、恢复与停止、群轮次校验、前端设置与状态展示、中英文使用说明。

## 决策归属与关系

新决定。`S_02` 中“只处理结构化 mentions 指向同事的公开消息”的适用范围缩小为没有通知的消息；同事的预留、去重、接力预算与投递不变。

## 上下文与跨边界影响

未 @ 的用户消息被 core 接受后，`team_helpers` 调度后台判断；判断结果写入 `auto_replies.json`；同事经桥接进入同事调度器，专家与专家团代理经 core 通知入口被启动并读到该消息；`group_turn` 依据同一份记录承认该轮；前端从群历史响应与 `group.auto_reply.updated` 读取结果。
依赖 agent-core 工作区中未提交、未发布的通知入口；本仓固定的 core 版本没有该入口。

## 实际实现与开发决策

- `group_auto_reply.py`：`schedule` 创建后台任务；`judge` 在按消息的锁内写 `pending`、调用模型、保存结果；`deliver` 按成员类型送达并逐成员标记；`recover_group` 重送未送达的通知并处理中断的判断；`stop` 取消任务、丢弃未送达通知（core 撤回已于 2026-11-23 删除，见下文）。
- 判断模型复用 `ModelSelectionResolver` 与 `build_model_from_selection`，并套用诊断模块对请求参数的清理，避免把 `reasoning_level` 等内部字段传给厂商 SDK。
- 同事通知通过 `register_colleague_notifier` 由桥接注册，运行时模块不反向依赖 JiuwenMate。
- 恢复没有做成独立的启动任务，而是挂在三个已有时机：运行时就绪、同事 5 秒补扫、同一群的下一次判断。
- 被 core 以 `ValueError` 拒绝的通知标为已丢弃，不重试。

## 与设计的偏差

- 设计 5.3 的 `group.member.update` 没有新增。网关对 Web 请求方法有固定放行清单（`agent_gateway` 的 `app_web_handlers.py`），新方法需要另发网关版本；成员回复规则改由已放行的 `group.update` 的 `reply_rules` 字段提交。
- 设计写 `members[].reply_mode`，实际在群公开信息顶层返回 `reply_rules`，成员条目不变。既有测试对成员公开字段做精确比对，成员条目也参与建群与加人的请求比对。
- 设计 5.11 的界面是成员详情里的两张单选卡片。现有界面没有成员详情页，实际在群设置面板增加“自动判断回复”区：总开关、判断模型下拉、每个成员一个开关。
- 设计 5.10 的 `recover` 在“服务就绪后执行一次”，实际见上一节。
- 以上偏差未回到设计阶段确认。

## 真实联调（2026-11-23）

环境：本机调试服务，数据根 `~/.jiuwenswarm`，`PYTHONPATH` 前置本地 agent-core 工作区（含未提交的通知入口）；经 Vite 开发服务器（5174）访问页面；模型 DeepSeek-V4-Pro。默认模型 deepseek-v4-flash 在供应商侧返回 402 余额不足，未使用。
重启时 `jiuwenswarm-start debug` 执行的 `uv sync` 使 `.venv` 中 `openjiuwen-e2a` 只剩元数据、缺少 `e2a` 包，服务无法启动；按锁定版本重装该包后恢复。旧的常驻 worker 未被 `jiuwenswarm-stop` 停掉，手动结束后新服务才使用新代码。

在页面新建群“自动回复联调”（`web_1a20607f458_0fe332de6f05`：活动策划助手、设计专家团、小九），群会话模型选 DeepSeek-V4-Pro，判断模型为跟随群会话模型。实际结果：

| 用户消息 | 判断结果（耗时） | 成员行为 |
| --- | --- | --- |
| 你好 | 通知小九（7.0 秒） | 小九约 16 秒时回复 |
| 帮我策划一场 20 人的团队秋游活动… | 通知活动策划助手（4.3 秒） | 专家经 core 通知被启动，约 35 秒时公开回复 |
| 好的，谢谢 | 通知小九（2.8 秒） | 同事请求以 ignored 结束，未回复 |
| 给一个咖啡店 logo 选配色… | 通知设计专家团（4.7 秒） | 专家团代理约 30 秒时公开回复，未形成组织执行 |
| @活动策划助手 用一句话说说秋游要带什么 | 未判断 | 被 @ 的专家回复 |
| 你好，在吗（小九已改为仅被 @ 时） | 通知活动策划助手（8.6 秒） | 理由写的是“暂不需要该成员响应”，属于模型误用工具 |

- `history.jsonl` 中全部未 @ 的用户消息 `mentions` 为空，带 @ 的那条只含用户所选成员；`auto_replies.json` 有 5 条记录且均已送达；重启后页面恢复出这 5 条判断结果。
- 设置面板的总开关、判断模型下拉、成员开关均可用并持久化。
- 重启后的服务日志中没有自动判断相关的异常。

联调中的修改：
- 前端竞态：发送后的刷新若在判断完成前发出，会用过期的 `pending` 覆盖已推送的结果，界面要等下一次 10 秒轮询才更新。刷新结果不再把非 `pending` 的状态降回 `pending`；修复后第四条消息在 5.7 秒时显示结果。
- 被通知的成员可以选择不回复，此时没有终态信号，等待占位会一直显示。对自动判断产生且尚无执行的占位加 3 分钟时限（`AUTO_REPLY_WAIT_MS`），被 @ 的占位不变。
- 判断提示词与工具描述补充“每次调用都会唤醒成员，不要为了说明不需要而调用”。用真实模型对 5 条消息各调用 2 次复测：寒暄类稳定通知一位成员、闲聊不通知、职责内问题通知对应成员；“好的，谢谢”一次不通知、一次仍以“无需进一步回复”为理由通知。

未实测：单独配置可用的小模型作判断模型及其耗时、升级前真实存在的群（仅以删除字段模拟）、群页面上没有整群停止按钮（停止经其他入口的 `chat.interrupt` 触发）。

### 同事请求卡住的排查（2026-11-23）

现象：10:06 重启后，为激活群运行时发送“@小九 回一个“收到”即可”，同事请求停在 dispatched 约 13 分钟。
已证实：
- 参与判定调用正常返回；随后的主流式调用（DeepSeek-V4-Pro，12 个工具）报 `stream frame timeout: stage=first_token, timeout=300.0s, chunk_count=0`，进程内自动重试两次，每次同样等满 300 秒。
- 卡住期间从进程外对同一模型做非流式、流式、流式加 12 个工具的最小调用，均在 3 秒内返回。
- 经 `chat.interrupt` 停止后请求以 cancelled 结束；之后同一会话中不带 @ 由小九回复的消息、@小九 的消息、原样重发的同一句话都正常回复（8 至 20 秒）。
- 再次重启后，第一条 @小九 的消息 18 秒回复。
结论：未能复现，原因未查明。已排除 @ 路径本身、消息内容、“重启后首次执行”以及模型端点整体不可用。该请求走的是原有的提及路径，判断与通知代码不在其调用链上；卡住发生在同事执行内部的模型流式调用。未取得当次请求的消息内容（模型日志不记录消息体），因此不能排除当时会话上下文的影响。
与本次改动的可能关联只有时间上的重合：卡住时群运行时刚就绪，恢复流程正在向专家送达通知。没有证据表明两者有因果关系。

### 停止状态与停止按钮（2026-11-23）

- 整群停止时，判断中的记录改记为独立的 `stopped` 状态，页面显示“已停止，未判断由谁回复”，不再与判断失败共用文案。该状态是终态，恢复流程与重复请求都不会重新判断。
- 群聊页面在有判断进行、有成员等待回复或有执行未结束时，在发送按钮旁显示停止按钮，点击发送 `chat.interrupt`（intent=cancel, mode=team）。
- 停止成功后，停止时刻之前发出的消息下、没有执行卡片的等待占位不再显示（仅当前页面有效，刷新后由服务端状态决定）。这一条超出了需求方点名的两项，是为了让停止按钮点击后能消失。
- 验证：后端相关 142 项、前端群聊 42 项通过，构建通过。页面实测两次：判断进行中点击停止，显示“已停止”且无成员回复；专家被通知并显示等待占位后点击停止，占位与按钮消失，45 秒内无回复。空闲时不显示按钮。未测执行卡片运行中的停止与多成员同时回复时的停止。

### 第二次同事请求卡住（2026-11-23 10:47）

需求方在新群（`web_1a2064c62e2_96a6178c1e36`）发送“你好”，判断在 4 秒内通知小九并已送达，之后无回复。同事请求停在 dispatched，尚无执行事件；卡在参与判定的非流式模型调用（10:47:00 发出，至 10:56 未返回）。
10:53 至 10:56 从进程外对 DeepSeek-V4-Pro 端点做了 7 次最小对话调用（含 4 次并发），全部在 25 至 30 秒超时；同一地址的 `/v1/models` 在 0.08 秒内返回 401。结论：端点可连通，但对话补全在该时段不响应，同事请求因此挂起。判断调用本身在 10:46:56 至 10:47:00 正常完成，说明端点是在其后停止响应的。
这与上午那次卡住的表现一致（模型调用无返回），但上午那次卡住期间进程外调用曾成功，两次是否同一原因未能确认。图像能力探测调用（温度 0、无结束日志）曾被怀疑，已排除：它有 5 秒超时且关闭了观测日志。

### 不带 @ 的实质性任务（2026-11-23 11:22 起，端点恢复后）

同一测试群，DeepSeek-V4-Pro。
- 第一次发送“帮我做一份完整的 30 人团建活动方案，写成 Markdown 文档交付给我…”：判断调用 15 秒超时，记为 failed，无成员被唤起（端点仍不稳定，同时段 3 次进程外探测 3.0 至 5.7 秒返回）。
- 原样重发：5 秒内通知活动策划助手。专家先 `write_file`，再调用 `send_file_to_user` 被拒，随即在 11:25:19 发出一条不带附件、声称“已发送”的文字回复；之后查环境变量、读文件、检索源码，约 3 分钟后调用 `start_group_task` 开出任务卡片，11:28:07 以带附件的消息交付 `30人团建活动方案.md`。从发送到交付约 3 分 45 秒，群里出现两条回复，其中第一条的“已发送”不属实。
- 对照：随后发送“@活动策划助手 帮我做一份完整的 20 人年会活动方案…”，专家 `write_file` 后立即 `start_group_task`，37 秒交付附件。
结论：不带 @ 的消息可以触发任务卡片与文件交付，`mentions` 仍为空。两次的差别不能归因于是否带 @：对照发生在同一成员会话中、紧随第一次之后，专家已在第一次中摸索出流程。未在全新会话中先做带 @ 的对照。专家的工具配置中两种情况下都包含 `swarm.group_start_task`。

| B `web_1a2067c82e9_a8e56a746789` | 不带 @（判断 5.1 秒后通知） | 106 秒，无附件，称“已交付，请查收” | 139 秒 | write_file → send_file_to_user 被拒 + 文字回复 → start_group_task → 带附件交付 |

结论：两种路径的行为与耗时基本相同，都先发一条不带附件却声称已交付的回复，再开任务补交付；两次都生成了任务执行且状态为 completed。此前那次 3 分 45 秒的绕路不是通知路径造成的。每组只有一个样本。
该“先声称已交付、后补附件”的行为在带 @ 的原有路径上同样出现，属于专家交付流程的既有问题，本次未修改。

### 重启后群聊列表为空（2026-11-23）

### 被通知的同事仍可能不回复（2026-11-23）
