# Submit a JiuwenSwarm bug report from Web chat

The [tool contract](../specs/jiuwenswarm/agents/harness/common/tools/S_02_report-issue.md) covers interactive Web chat in the personal edition.

The implementation extends the existing GitCode issue client with issue creation. The agent tool uses the workspace's GitCode integration credential so the report is filed under that account. It uses the existing Web confirmation flow and binds approval to the redacted draft. A SQLite receipt claims each approval before submission and prevents duplicate POSTs when a tool call is replayed.

Auto-Harness consumes existing issues through its separate fix flow. Reporting starts when the user asks to file a bug. Proactive detection belongs to the next phase.

## Verification

The focused run passed all 12 tests against the pinned core, gateway, and protocol revisions. It exercised Web request dispatch, approval and rejection, the GitCode POST through a simulated HTTP transport, replay after success or timeout, and the existing Auto-Harness issue runner. Windows test cleanup reported an open temporary log file after the assertions passed. Live GitCode issue creation and credential acceptance remain unverified.

## Team leader support on 2026-11-10

The Team Work and Team Code profiles now declare the reporting tool on the leader. The provider also checks the member role, personal edition, Web channel, and session before construction. Team leaders use the existing Web confirmation route and the same submission and replay handling as single agents.

All 11 focused tests passed. They cover role and channel boundaries, the leader confirmation event, the single-agent approval and replay regressions, and the Design profile. Live GitCode submission remains unverified.

## GitCode template lookup and validation on 2026-11-10

Both reporting entry points now mount `get_issue_template` alongside `report_issue`. The lookup reads the current English or Chinese form directly from GitCode. The reporter validates the template revision and answers, then renders the preview and sends the template labels explicitly. GitCode's create endpoint accepts a template path but the SDK documents that it does not apply YAML form fields or labels, so the path is exposed through lookup and the backend owns rendering.

All 18 focused tests passed. They cover lookup, formatted submission with simulated HTTP, the Chinese branch and module constraint, and a template revision changing after preview. Both live GitCode template reads succeeded. The submission tests used a simulated tracker.

## GitHub template fallback on 2026-11-11

Template reads fall back to the public GitHub mirror when GitCode returns a transport error, HTTP 429, or a server error. Both live mirrors returned identical contents for each locale. All 20 focused tests passed, including stable template IDs across hosts and a missing GitCode template remaining unavailable.

## Web issue review panel

The issue draft appears above the composer with its GitCode repository, title, labels, and rendered Markdown. The source view exposes the exact redacted body. The server projects the structured preview through the existing confirmation event, and the buttons use the original interrupt ID and one-time approval. The prior text preview remains available to clients that use the generic card.

All 20 focused backend tests and 58 frontend routing and transport tests passed. A Chromium component fixture verified the Markdown preview, exact source, publish and cancel actions, submission failure, and English and Chinese layouts. The isolated component fit a 360-pixel viewport. The WebSocket test exercised the actual InteractionSlot and mocked the server response. Live publication was not exercised.

## Web group chat

The shared group execution policy installs both reporting tools for native group members. The group question store ties each draft to the originating member and interrupt. The group composer reuses the Review issue panel, and the owner's decision goes back to the member that requested review.

The group reporting tests cover template lookup, a persisted preview, approval of the addressed interrupt, replay of the answer, and cancellation. They use simulated GitCode HTTP and check that the approved POST matches the preview. The focused backend regression run passed 184 tests. Two existing cases requiring Windows symlink privileges were excluded. All 34 frontend group-chat tests and the production build passed. A Chromium run using the built app and simulated WebSocket replies verified restored and live review panels, member attribution, and both decisions.
